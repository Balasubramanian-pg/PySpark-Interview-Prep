### 3.9.5 When would you still need to use a standard Python UDF instead of a Pandas UDF

Pandas UDFs are faster for vectorizable operations because they use Apache Arrow and process data in batches. However, standard Python UDFs (scalar UDFs) still have important use cases. You should use a standard Python UDF when the logic cannot be vectorized, when the data types are not well supported by Pandas UDFs, when the dataset is very small, or when you need row-level control that Pandas UDFs cannot provide.

**1. The logic cannot be vectorized**

Pandas UDFs operate on entire columns as pandas Series. If your logic requires row-by-row iteration, complex control flow, or state that depends on previous rows, it cannot be expressed as a vectorized operation. For example, computing a running total with custom conditions, parsing a string with a state machine, or implementing a recursive algorithm per row.

```python
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

def complex_row_logic(value):
    # Row-by-row state machine that cannot be vectorized
    if value is None:
        return "missing"
    if value < 0:
        return "negative"
    elif value == 0:
        return "zero"
    else:
        return "positive"

complex_udf = udf(complex_row_logic, StringType())
df.select(complex_udf(df["value"])).show()
```

**2. Complex data types not supported by Pandas UDFs**

Pandas UDFs have limited support for complex data types. Nested StructType, MapType, and certain ArrayType combinations may not be supported or may require deep copies that negate the performance benefit. Standard Python UDFs can handle these types more flexibly because they operate on Python objects.

```python
from pyspark.sql.types import MapType, StringType, IntegerType
from pyspark.sql.functions import udf

def process_map(m):
    if m is None:
        return None
    return {k: v * 2 for k, v in m.items()}

process_map_udf = udf(process_map, MapType(StringType(), IntegerType()))
df.select(process_map_udf(df["map_col"])).show()
```

**3. Very small datasets**

For very small datasets, the overhead of Arrow conversion and pandas batch setup can exceed the cost of row-at-a-time processing. If you are processing only a few hundred or thousand rows, a standard Python UDF may be simpler and not noticeably slower.

```python
small_df = spark.createDataFrame([(1,), (2,), (3,)], ["value"])
small_df.select(complex_udf(small_df["value"])).show()
```

**4. Need access to the entire Row object**

Pandas UDFs receive individual columns as Series. If your logic needs to inspect the entire Row, including column names and metadata, a standard Python UDF can accept a StructType column and receive a Row object. This is useful for generic processing or when the function needs to access multiple fields dynamically.

```python
from pyspark.sql.functions import struct, udf
from pyspark.sql.types import StringType

def process_row(row):
    return f"{row['a']}-{row['b']}"

process_row_udf = udf(process_row, StringType())
df.select(process_row_udf(struct("a", "b"))).show()
```

**5. Simplicity and debugging**

Standard Python UDFs are simpler to write and debug. They process one row at a time, so you can add print statements or use a debugger more easily. Pandas UDFs operate on batches and may require understanding of pandas and Arrow internals.

```python
def debug_udf(value):
    print(f"Processing value: {value}")
    return value * 2

debug_udf_spark = udf(debug_udf, IntegerType())
df.select(debug_udf_spark(df["value"])).show()
```

**6. Libraries that require row-level objects**

Some Python libraries expect row-level objects, not pandas Series. For example, certain NLP libraries, custom parsers, or APIs that operate on individual records. In these cases, a standard Python UDF is the natural fit.

```python
def call_external_api(value):
    # Some API that expects a single record
    import requests
    response = requests.get(f"https://api.example.com/{value}")
    return response.text

api_udf = udf(call_external_api, StringType())
df.select(api_udf(df["id"])).show()
```

**7. Output types not supported by Pandas UDFs**

Pandas UDFs do not support all output types. For example, returning a complex nested structure or a custom Python object may not be possible. Standard Python UDFs can return any type that Spark supports through the returnType parameter.

```python
from pyspark.sql.types import ArrayType, IntegerType

def return_list(value):
    return [value, value * 2, value * 3]

list_udf = udf(return_list, ArrayType(IntegerType()))
df.select(list_udf(df["value"])).show()
```

**8. No pandas or PyArrow installed**

If your cluster does not have pandas or PyArrow installed, you cannot use Pandas UDFs. Standard Python UDFs only require Python and the standard library. This is rare in modern clusters, but it can happen in restricted environments.

**9. Need for non-deterministic or side-effect operations**

If your UDF performs side effects such as writing to an external system, logging, or updating a database, row-at-a-time processing gives you finer control. Pandas UDFs process batches, which may complicate side-effect management.

**10. When performance is not critical**

If the job is not performance-sensitive and the data volume is moderate, a standard Python UDF is often sufficient and easier to maintain. Premature optimization with Pandas UDFs can add unnecessary complexity.

**Summary of when to use standard Python UDFs**

- The logic cannot be vectorized.
- Complex data types are not supported by Pandas UDFs.
- The dataset is very small.
- You need access to the entire Row object.
- Simplicity and debugging are priorities.
- Libraries require row-level objects.
- Output types are not supported by Pandas UDFs.
- pandas or PyArrow is not available.
- Non-deterministic or side-effect operations need row-level control.
- Performance is not critical.

In all other cases, prefer Pandas UDFs for vectorizable operations, or built-in Spark SQL functions when an equivalent exists. Built-in functions are always the fastest option because they benefit from Catalyst optimization and whole-stage code generation.
