# 3.9.2 How do Pandas UDFs execute faster than standard Python UDFs?

Pandas UDFs execute faster than standard Python UDFs because they process data in batches using Apache Arrow and vectorized operations, instead of processing one row at a time with per-row serialization. The performance difference comes from three main sources: elimination of per-row serialization, batch-oriented execution, and the use of optimized vectorized libraries.

**Standard Python UDF execution**

A standard Python UDF is applied one row at a time. For each row, Spark must:

1. Serialize the row from the JVM using pickle or cloudpickle.
2. Send the serialized row to a separate Python worker process.
3. Deserialize the row in Python.
4. Execute the Python function on the single row.
5. Serialize the result.
6. Send the result back to the JVM.
7. Deserialize the result in the JVM.

This per-row serialization and deserialization is the primary bottleneck. It also prevents whole-stage code generation and other Catalyst optimizations. The overhead per row is high, and it scales linearly with the number of rows. For millions of rows, the overhead dominates the actual computation.

**Pandas UDF execution**

A Pandas UDF processes a batch of rows at a time. The execution flow is:

1. Spark splits the input data into Arrow record batches, typically up to 10,000 rows per batch by default.
2. The entire batch is transferred to the Python worker using Apache Arrow, a columnar in-memory format. No per-row pickling is needed.
3. The batch is converted to a pandas Series or DataFrame.
4. The Python function executes vectorized operations on the entire column or DataFrame at once, using pandas, NumPy, or other optimized libraries.
5. The result is a pandas Series or DataFrame, which is converted back to Arrow format.
6. The Arrow batch is sent back to the JVM and converted to Spark rows.

Because the data is transferred in batches and in columnar format, the serialization overhead is amortized across many rows. The vectorized operations also take advantage of native CPU instructions, better cache locality, and optimized C or Cython implementations inside pandas and NumPy.

**Apache Arrow and columnar data**

Apache Arrow is the key enabler. It provides a standardized columnar memory format that both the JVM and Python can understand. Data is stored by column rather than by row, which is the natural layout for analytical operations. Arrow allows zero-copy or low-copy conversion between the JVM and Python in many cases, eliminating the expensive per-row pickle serialization. Columns with null values may trigger deep copies, but even then the batch transfer is far more efficient than row-by-row transfer.

**Vectorized operations**

Instead of calling a Python function once per row, a Pandas UDF calls the function once per batch. Inside the function, operations are applied to the entire pandas Series or DataFrame. For example, adding two columns is a single vectorized addition over the whole batch, not a loop over each row. Pandas and NumPy implement these operations in optimized native code, often using SIMD instructions. This drastically reduces Python interpreter overhead and function call overhead.

**Code example comparing scalar UDF and Pandas UDF**

Scalar Python UDF:

```python
from pyspark.sql.functions import udf
from pyspark.sql.types import LongType

def multiply_scalar(a, b):
    return a * b

multiply_udf = udf(multiply_scalar, LongType())

df = spark.createDataFrame([(1, 2), (3, 4), (5, 6)], ["a", "b"])
result = df.select(multiply_udf(df["a"], df["b"]))
result.explain(True)
```

The physical plan shows `BatchEvalPython`, indicating row-at-a-time Python UDF execution.

Pandas UDF:

```python
import pandas as pd
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import LongType

@pandas_udf(LongType())
def multiply_pandas(a: pd.Series, b: pd.Series) -> pd.Series:
    return a * b

result = df.select(multiply_pandas(df["a"], df["b"]))
result.explain(True)
```

The physical plan shows `ArrowEvalPython`, indicating batch-oriented Arrow-based execution.

**Performance gains**

Benchmarks show vectorized Python UDFs can be up to 5.76x faster than scalar Python UDFs in native execution engines. In some workloads, the improvement can reach 100x when the scalar UDF overhead dominates. The actual gain depends on the complexity of the operation, the number of rows, the number of columns, and the data types. Simple arithmetic operations see the largest relative improvement because the scalar UDF overhead is much larger than the computation itself.

**Why Pandas UDFs are still slower than built-in functions**

Even though Pandas UDFs are much faster than scalar Python UDFs, they are still slower than Spark SQL built-in functions. Built-in functions are implemented in Scala, benefit from whole-stage code generation under Tungsten, and are fully integrated into the Catalyst optimizer. A Pandas UDF is a black box to Catalyst. Predicate pushdown, column pruning, and other optimizations cannot be applied through the UDF. The data must still cross the JVM-Python boundary, even if in batches. For maximum performance, always prefer built-in functions when an equivalent exists.

**Configuration and tuning**

The batch size for Arrow transfers is controlled by `spark.sql.execution.arrow.maxRecordsPerBatch`, default 10,000. For wide DataFrames or large rows, reduce this value to avoid out-of-memory errors on the Python worker. For narrow DataFrames, increase it to reduce per-batch overhead. Arrow-based conversion for `toPandas()` and `createDataFrame()` is controlled by `spark.sql.execution.arrow.pyspark.enabled`.

**Summary**

Pandas UDFs execute faster than standard Python UDFs because they use Apache Arrow to transfer data in columnar batches, eliminating per-row pickle serialization, and they use pandas and NumPy to perform vectorized operations over entire columns instead of looping over rows. This reduces serialization overhead, Python interpreter overhead, and function call overhead. The result is up to 100x faster execution for suitable workloads. However, Pandas UDFs are still not as fast as Spark SQL built-in functions, which benefit from Catalyst optimization and whole-stage code generation. Use Pandas UDFs when you need custom Python logic that can be vectorized, and use built-in functions whenever possible.
