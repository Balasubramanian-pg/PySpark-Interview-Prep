### 3.3.1 What is a Broadcast Hash Join and when should you use it?

A Broadcast Hash Join (BHJ) is a join strategy where one side of the join is small enough to be broadcast to every executor. Spark collects the small side to the driver, then broadcasts it to all executors. Each executor builds an in-memory hash map from the broadcast data and probes it with records from the large side. The large side is not shuffled. This makes BHJ the fastest join strategy for suitable cases, especially star-schema joins between a large fact table and a small dimension table.

How it works:

- The small side is collected to the driver.
- The driver broadcasts the small side to every executor using TorrentBroadcast.
- Each executor builds a hash map keyed by the join key from the broadcast data.
- The large side is read partition by partition. For each record, Spark probes the hash map and emits matching joined rows.
- No shuffle is performed on the large side. The small side is transferred over the network once, but this is not a shuffle.

When Spark uses it:

- The estimated size of one side is below `spark.sql.autoBroadcastJoinThreshold`. The default is 10 MB. Set to -1 to disable automatic broadcast.
- The join is an equi-join. Non-equi joins use Broadcast Nested Loop Join instead.
- The join type supports broadcast. Inner joins, left outer joins where the right side is broadcast, right outer joins where the left side is broadcast, left semi joins, and left anti joins are generally supported. Full outer joins are not supported for broadcast.
- A broadcast hint is provided: `broadcast(df)` in the DataFrame API or `/*+ BROADCAST(table) */` in SQL.
- In Spark 3.x, Adaptive Query Execution (AQE) can convert a sort-merge join to a broadcast hash join at runtime if one side turns out to be small enough after filtering.

Configuration:

```
spark.sql.autoBroadcastJoinThreshold=10485760    # 10 MB default
spark.sql.broadcastTimeout=300                   # seconds to wait for broadcast
spark.sql.adaptive.enabled=true                  # AQE can convert at runtime
```

When to use it:

- Joining a large fact table with a small dimension table.
- Joining a large table with a lookup table that fits in memory.
- When one side is small enough to broadcast safely, typically a few tens of MB.
- When you want to avoid shuffling a very large table.
- When the large side is not skewed in a way that would still cause long tasks, since broadcast join does not rebalance the large side.

When not to use it:

- When the broadcast side is too large. Broadcasting a large table can cause out-of-memory errors on the driver and executors.
- When both sides are large. Use Sort Merge Join instead.
- When the join is a non-equi join. Use Broadcast Nested Loop Join only if the broadcast side is very small.
- When the small side is larger than the executor memory available for the hash map.
- When the large side is heavily skewed. Broadcast join avoids shuffling the large side, but skew within the large side partitions still causes long tasks.

Code examples:

PySpark DataFrame API:

```
from pyspark.sql.functions import broadcast

result = large_df.join(broadcast(small_df), "customer_id")
```

PySpark SQL:

```
spark.sql("""
  SELECT /*+ BROADCAST(small) */
    large.id, small.name
  FROM large
  JOIN small ON large.id = small.id
""")
```

Forcing broadcast when automatic broadcast is disabled:

```
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)
result = large_df.join(broadcast(small_df), "customer_id")
```

Checking the physical plan:

```
result.explain(True)
```

Look for `BroadcastHashJoin` in the physical plan.

Advantages:

- Avoids shuffling the large table, which is the most expensive part of a join.
- Very fast for small dimension tables.
- Reduces network I/O, disk I/O, and serialization compared to shuffle joins.
- Works well with AQE, which can convert joins at runtime.

Limitations:

- The broadcast side must fit in the memory of each executor and the driver.
- Broadcasting a table that is too large can cause out-of-memory errors.
- Not supported for all join types, especially full outer joins.
- Does not solve skew on the large side.
- If the small table changes frequently, broadcasting it repeatedly may add overhead.

Best practices:

- Keep dimension tables small, or filter them before the join so they fall below the broadcast threshold.
- Use `broadcast()` hint when you know a table is small but Spark's statistics are inaccurate.
- Monitor executor memory when broadcasting larger tables.
- Enable AQE so Spark can adapt join strategies at runtime.
- Avoid broadcasting tables larger than a few hundred MB unless you have verified memory capacity.

In summary, a Broadcast Hash Join broadcasts the small side to all executors and probes it with the large side, avoiding a shuffle of the large table. Use it when one side is small enough to fit in memory, typically for fact-dimension joins. Avoid it when the broadcast side is too large or when the join is not an equi-join.
