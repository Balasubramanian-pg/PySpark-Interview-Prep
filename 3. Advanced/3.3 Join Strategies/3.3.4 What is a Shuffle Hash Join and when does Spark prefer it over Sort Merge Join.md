### 3.3.4 What is a Shuffle Hash Join and when does Spark prefer it over Sort Merge Join

A Shuffle Hash Join (SHJ) is a join strategy where both sides of the join are shuffled by the join key, and then each partition builds an in-memory hash map from one side and probes it with the other side. It is used when one side is smaller than the other but still too large to broadcast. SHJ avoids the global sort required by Sort Merge Join, which can make it faster when the smaller side fits comfortably in memory.

How Shuffle Hash Join works:

- Shuffle phase: Both tables are repartitioned by the join key using hash partitioning. Rows with the same key from both sides land in the same partition on the same executor.
- Build phase: For each partition, Spark chooses the smaller side to build an in-memory hash map keyed by the join key. The hash map is stored in memory.
- Probe phase: Spark iterates through the larger side and probes the hash map for matching keys. For each match, it outputs the joined rows.

The key difference from Sort Merge Join is that SHJ does not sort the data. It builds a hash map and probes it, which is faster when the smaller side per partition fits in memory. However, if the smaller side does not fit, it can cause out-of-memory errors or heavy spilling.

When Spark uses Shuffle Hash Join:

- When one side is smaller than the other but still too large to broadcast.
- When `spark.sql.join.preferSortMergeJoin` is set to false.
- When the smaller side is at least three times smaller than the larger side. This is a heuristic based on size estimation.
- When the join is an equi-join.
- When the smaller side per partition is expected to fit in memory.

Configuration to enable Shuffle Hash Join:

```
spark.conf.set("spark.sql.join.preferSortMergeJoin", "false")
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)
```

Example in PySpark:

```
spark.conf.set("spark.sql.join.preferSortMergeJoin", "false")
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)

medium_df = spark.range(1000000).selectExpr("id as key", "id as medium_val")
large_df = spark.range(5000000).selectExpr("id as key", "id as large_val")

joined = medium_df.join(large_df, "key")
joined.explain(True)
```

In the physical plan, you will see `ShuffledHashJoin [key], [key], Inner` preceded by `Exchange hashpartitioning(key, 200)` on both sides.

When Spark prefers Shuffle Hash Join over Sort Merge Join:

- When the smaller side is significantly smaller than the larger side, so the hash map per partition is small and fits in memory.
- When the cost of sorting the large side outweighs the cost of building a hash map for the smaller side.
- When the join keys are not already sorted or bucketed. If data is already sorted, Sort Merge Join can skip the sort and is preferred.
- When the data is not heavily skewed. If a key is very hot, the hash map for that partition may not fit in memory, causing failures. Sort Merge Join handles skew better because it streams data and only buffers duplicate keys for a single key.
- When `spark.sql.join.preferSortMergeJoin` is false. In Spark, this configuration defaults to true, so Sort Merge Join is preferred by default. Setting it to false enables Shuffle Hash Join when the size conditions are met.

Comparison with Sort Merge Join:

Shuffle Hash Join:
- Does not sort data. Builds a hash map and probes it.
- Faster when the smaller side fits in memory.
- Sensitive to skew. A hot key can cause the hash map to grow too large and fail.
- Requires the smaller side per partition to fit in memory.
- Used when one side is much smaller than the other but too large to broadcast.

Sort Merge Join:
- Shuffles and sorts both sides, then merges sorted streams.
- Scales to very large datasets because it does not need to hold an entire partition side in memory.
- Handles skew better because it only buffers duplicate keys for a single key.
- Default for large-to-large equi-joins.
- Can skip shuffle and sort if both sides are bucketed and sorted by the join key.

When Spark prefers Shuffle Hash Join:
- When the smaller side is small enough to fit in memory per partition.
- When the size difference is large enough that building a hash map is cheaper than sorting the large side.
- When the data is not heavily skewed.
- When Sort Merge Join is disabled or not preferred.

Important caveats:

- In Spark 3.x, Adaptive Query Execution (AQE) can change join strategies at runtime. AQE may convert a Sort Merge Join to a Shuffle Hash Join or Broadcast Hash Join if it detects that one side is small enough. AQE may also handle skew by splitting skewed partitions.
- Shuffle Hash Join is not the default. Spark prefers Sort Merge Join for large joins because it is more robust to memory pressure and skew.
- If you force Shuffle Hash Join and the smaller side does not fit in memory, you may see out-of-memory errors or heavy spills. Monitor executor memory and spill metrics in the Spark UI.
- Shuffle Hash Join still requires a full shuffle of both sides, which is expensive. The main saving is avoiding the sort of the large side.

When to use Shuffle Hash Join manually:

- When you know one side is much smaller and fits in memory, but it is above the broadcast threshold.
- When Sort Merge Join is spilling heavily due to sorting the large side, and the smaller side is small enough to hash.
- When you have verified that the data is not skewed and the hash map will fit in memory.

Code example forcing Shuffle Hash Join with a hint:

```
from pyspark.sql.functions import col

result = medium_df.hint("shuffle_hash").join(large_df, "key")
```

SQL hint:

```
SELECT /*+ SHUFFLE_HASH(medium) */ *
FROM medium
JOIN large ON medium.key = large.key;
```

In summary, Shuffle Hash Join shuffles both sides and builds an in-memory hash map from the smaller side, then probes it with the larger side. Spark prefers it over Sort Merge Join when the smaller side is significantly smaller, fits in memory per partition, and the data is not heavily skewed. Sort Merge Join remains the default because it is more scalable and robust to memory pressure and skew.
