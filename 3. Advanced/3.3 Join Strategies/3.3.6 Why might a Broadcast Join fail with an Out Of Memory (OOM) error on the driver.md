### 3.3.6 Why might a Broadcast Join fail with an Out Of Memory (OOM) error on the driver

A Broadcast Join fails with an OutOfMemoryError (OOM) on the driver when the table being broadcast is too large to fit in the driver's JVM heap. The driver must collect the entire broadcast dataset into memory before it can build the hash table and distribute it to executors. If the data size exceeds the driver's available heap, the job crashes with an error like `java.lang.OutOfMemoryError: Not enough memory to build and broadcast the table to all worker nodes`.

**Why the driver is involved in a broadcast join**

In a Broadcast Hash Join, the driver does not just coordinate the join. It actually materializes the broadcast side in memory. The process works as follows:

1. The driver collects all partitions of the broadcast side using `executeCollect`.
2. Each partition is fetched as a compressed block, decompressed, and each row is copied into a new byte buffer and added to an array.
3. The driver builds an `UnsafeHashedRelation` (the hash table) from these rows.
4. The hash table is then broadcast to all executors via TorrentBroadcast.

This means the entire broadcast dataset, plus intermediate buffers and the hash table, must fit in the driver's memory. Historically, this process was inefficient: a 16 MB broadcast table could consume about 100 MB less memory after optimizations were applied. The extra memory comes from holding both the original rows and the hash table structure simultaneously.

**Common causes of driver-side OOM in broadcast joins**

1. **The broadcast table is too large**

   The most common cause is that Spark chooses a broadcast join for a table that is larger than the driver can handle. Spark decides based on `spark.sql.autoBroadcastJoinThreshold`, which defaults to 10 MB. However, the estimated size can be wrong. For example, if a table has an Array column whose data size exceeds the limits of an Int, the size statistic can become negative. Because a negative value is less than the 10 MB threshold, Spark incorrectly chooses a broadcast join even for a gigabyte-sized table. This causes the driver to run out of memory while collecting the data.

2. **Multiple concurrent broadcasts**

   If a query contains several broadcast joins, the driver must hold multiple broadcast tables in memory at the same time. The Databricks documentation notes that the risk of OOM on the driver due to concurrent broadcasts made it difficult to increase the default broadcast thresholds, as it would add more memory pressure. A query with five nested BroadcastHashJoin operations can accumulate hash tables in memory and cause OOM even on drivers with several gigabytes of heap.

3. **Underestimated table size**

   Spark uses `sizeInBytes` statistics to decide whether to broadcast. If statistics are missing or stale, Spark may underestimate the actual size of the table. This is especially common after filtering operations that reduce the row count but do not update statistics. Adaptive Query Execution (AQE) can make this worse: it may convert a sort-merge join to a broadcast join at runtime if one side appears small after filtering, but the actual data size may still be too large for the driver.

4. **Driver memory is too small for the workload**

   The default driver memory is often 1 GB or 2 GB. This is sufficient for small broadcasts but can be exceeded even by a modestly sized table. The driver also holds other data structures, such as the query plan, task metadata, and accumulator state. A broadcast that is close to the memory limit can push the driver over the edge.

5. **Inefficient memory usage during broadcast construction**

   The process of building the broadcast hash table allocates memory for each row, decompresses blocks, and copies data into buffers. In older Spark versions, `BroadcastExchangeExec` used `executeCollect`, which held all rows in an `ArrayBuffer` before building the hash table. This doubled the memory requirement. Although later versions improved this by using an iterator, the driver still needs to hold the final hash table, which can be large.

**How to diagnose a driver-side broadcast OOM**

The error message usually contains `Not enough memory to build and broadcast the table to all worker nodes`. The stack trace may point to `BroadcastExchangeExec` or `LongToUnsafeRowMap#grow`, but these are often not the true location of the OOM. The actual OOM may have occurred while building the hash table, and the stack trace simply wraps it. Check the driver logs for GC activity and heap dumps.

To confirm that a broadcast join is the cause, examine the physical plan with `explain(True)` and look for `BroadcastHashJoin`. You can also check the Spark UI for a large broadcast exchange and driver memory usage.

**How to fix a driver-side broadcast OOM**

1. **Disable automatic broadcast for large tables**

   Set the broadcast threshold to a lower value or disable it entirely.

   ```
   spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
   ```

   This forces Spark to use sort-merge join instead, which does not require the driver to hold the broadcast table.

2. **Increase driver memory**

   If broadcast joins are necessary and the table is legitimately small enough to broadcast, increase the driver heap.

   ```
   spark.conf.set("spark.driver.memory", "8g")
   ```

   The error message itself suggests this as a workaround: "increase the spark driver memory by setting spark.driver.memory to a higher value".

3. **Reduce the broadcast table size**

   Filter and select only the necessary columns before the join. This reduces the data that the driver must collect.

   ```
   small_df = large_df.filter(large_df.date >= "2024-01-01").select("id", "name")
   ```

4. **Use broadcast hints selectively**

   If you know a table is small, use the `broadcast()` hint. If you are unsure, avoid hints and let Spark decide.

   ```
   from pyspark.sql.functions import broadcast
   result = large_df.join(broadcast(small_df), "id")
   ```

   However, be careful: a broadcast hint can force a broadcast even when the table is too large, causing OOM. Use hints only when you have verified the size.

5. **Disable AQE or tune its broadcast threshold**

   AQE can convert joins to broadcast at runtime. If this causes OOM, disable AQE or lower its broadcast threshold.

   ```
   spark.conf.set("spark.sql.adaptive.enabled", "false")
   ```

   Or set the AQE broadcast threshold separately:

   ```
   spark.conf.set("spark.sql.adaptive.autoBroadcastJoinThreshold", "5MB")
   ```

6. **Monitor and limit concurrent broadcasts**

   Avoid queries with many broadcast joins. If possible, break the query into steps and write intermediate results to storage.

7. **Use executor-side broadcast join (if available)**

   Some platforms (like Databricks) support executor-side broadcast join, which avoids collecting the broadcast table on the driver. Consult your platform documentation.

**Code example: forcing a sort-merge join to avoid driver OOM**

```
# Disable broadcast and force sort-merge join
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
spark.conf.set("spark.sql.join.preferSortMergeJoin", "true")

result = large_df1.join(large_df2, "id")
result.explain(True)  # Should show SortMergeJoin
```

**Summary**

A Broadcast Join fails with a driver OOM when the broadcast table is too large to fit in the driver's heap. The driver must collect the entire table, build a hash table, and hold it in memory before broadcasting. Common causes include incorrect size estimation, multiple concurrent broadcasts, underestimated table sizes, and insufficient driver memory. Fixes include disabling broadcast, increasing driver memory, reducing table size, tuning AQE, and using sort-merge join instead. Always verify the physical plan and monitor driver memory when using broadcast joins.
