### 3.3.5 How do you force Spark to use a specific join strategy using hints

Spark allows you to influence the join strategy through hints. Hints are directives you add to a DataFrame join or SQL query to tell the optimizer which strategy you prefer. They are useful when Spark's cost-based optimizer makes a poor choice, when statistics are inaccurate, or when you know something about the data that Spark does not. Hints are not guaranteed to be honored. Spark may ignore a hint if it is not applicable or if it would cause an error. In Spark 3.x, Adaptive Query Execution (AQE) can also override hints at runtime if it finds a better plan.

Types of join hints:

- `BROADCAST` or `broadcast(df)`: Forces a Broadcast Hash Join. The hinted table is broadcast to all executors.
- `MERGE` or `merge(df)`: Forces a Sort Merge Join.
- `SHUFFLE_HASH` or `shuffle_hash(df)`: Forces a Shuffle Hash Join.
- `SHUFFLE_REPLICATE_NL` or `shuffle_replicate_nl(df)`: Forces a Shuffle-and-Replicate Nested Loop Join.

Using hints in the DataFrame API:

PySpark provides the `broadcast()` function and the `hint()` method.

```
from pyspark.sql.functions import broadcast

# Force Broadcast Hash Join
result = large_df.join(broadcast(small_df), "customer_id")

# Force Sort Merge Join
result = df1.hint("merge").join(df2, "customer_id")

# Force Shuffle Hash Join
result = df1.hint("shuffle_hash").join(df2, "customer_id")

# Force Shuffle-and-Replicate Nested Loop Join
result = df1.hint("shuffle_replicate_nl").join(df2, "customer_id")
```

You can also apply the hint to a specific side by using the hint on that DataFrame before the join. For example, to broadcast the right side:

```
result = left_df.join(right_df.hint("broadcast"), "key")
```

Using hints in SQL:

SQL hints are placed inside `/*+ ... */` comments immediately after the `SELECT` keyword.

```
-- Force Broadcast Hash Join on the small table
SELECT /*+ BROADCAST(small) */ *
FROM large
JOIN small ON large.id = small.id;

-- Force Sort Merge Join
SELECT /*+ MERGE(large, small) */ *
FROM large
JOIN small ON large.id = small.id;

-- Force Shuffle Hash Join on the medium table
SELECT /*+ SHUFFLE_HASH(medium) */ *
FROM medium
JOIN large ON medium.id = large.id;

-- Force Shuffle-and-Replicate Nested Loop Join
SELECT /*+ SHUFFLE_REPLICATE_NL(large) */ *
FROM large
JOIN small ON large.a < small.b;
```

Aliases for hints:

- `BROADCAST` is also written as `BROADCASTJOIN`.
- `MERGE` is also written as `SHUFFLE_MERGE`.
- `SHUFFLE_HASH` has no common alias.
- `SHUFFLE_REPLICATE_NL` has no common alias.

How to apply a hint to both sides:

For `MERGE`, you can specify both tables: `/*+ MERGE(t1, t2) */`. For `BROADCAST`, `SHUFFLE_HASH`, and `SHUFFLE_REPLICATE_NL`, you typically specify the table to be broadcast, hashed, or replicated.

Checking whether the hint was applied:

Use `explain(True)` to see the physical plan.

```
result.explain(True)
```

Look for the join operator in the plan:

- `BroadcastHashJoin` for broadcast.
- `SortMergeJoin` for merge.
- `ShuffledHashJoin` for shuffle hash.
- `BroadcastNestedLoopJoin` or `CartesianProduct` for nested loop.

If the hint was ignored, you will see a different join operator. Check the Spark UI or driver logs for warnings about hints not being applied.

Caveats and limitations:

- Hints are not guaranteed. Spark may ignore a hint if it is not applicable, if the hinted table is too large to broadcast, or if it would cause an error.
- In Spark 3.x, AQE can override hints at runtime. For example, AQE may convert a hinted sort-merge join to a broadcast join if one side turns out to be small enough. To disable AQE for a specific query, set `spark.sql.adaptive.enabled=false`.
- Broadcasting a table that is too large can cause out-of-memory errors on the driver and executors. Use broadcast hints only when you are sure the table fits in memory.
- Shuffle Hash Join hints can cause out-of-memory errors if the smaller side per partition does not fit in memory. Monitor spills and GC.
- Hints are a manual override. Prefer letting Spark's optimizer and AQE make decisions unless you have a specific reason.
- Hints apply only to the join they are attached to. They do not affect other joins in the same query.

When to use which hint:

- Use `BROADCAST` when one side is small enough to fit in memory and you want to avoid shuffling the large side. This is common for fact-dimension joins.
- Use `MERGE` when both sides are large and you want a sort-merge join. This is the default, but you may force it if Spark incorrectly chooses broadcast or shuffle hash.
- Use `SHUFFLE_HASH` when one side is significantly smaller than the other but too large to broadcast, and you know the smaller side per partition fits in memory. This avoids sorting the large side.
- Use `SHUFFLE_REPLICATE_NL` only for non-equi joins when the replicated side is very small. This is rarely needed and can be very expensive.

Example combining AQE and hints:

```
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)

# Force sort-merge join, but AQE may still convert to broadcast if one side is small
result = df1.hint("merge").join(df2, "key")
```

If you want to completely disable AQE for a query to ensure the hint is honored:

```
spark.conf.set("spark.sql.adaptive.enabled", "false")
result = df1.hint("merge").join(df2, "key")
```

In summary, you can force a specific join strategy using hints in the DataFrame API (`broadcast()`, `hint("merge")`, `hint("shuffle_hash")`, `hint("shuffle_replicate_nl")`) or SQL (`/*+ BROADCAST(t) */`, `/*+ MERGE(t1,t2) */`, `/*+ SHUFFLE_HASH(t) */`, `/*+ SHUFFLE_REPLICATE_NL(t) */`). Hints are not guaranteed and may be overridden by AQE. Use them when you have a clear reason and verify the physical plan.
