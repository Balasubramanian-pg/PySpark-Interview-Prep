### 3.3.3 Explain how Sort Merge Join works under the hood

Sort Merge Join (SMJ) is the default join strategy for large-to-large equi-joins in Spark. It is scalable because it does not require holding an entire partition side in memory, unlike Shuffle Hash Join. SMJ works in three main phases: shuffle, sort, and merge. Understanding these phases helps you optimize joins, diagnose spills, and leverage bucketing to avoid shuffles entirely.

**Phase 1: Shuffle**

Both sides of the join are repartitioned by the join key using hash partitioning. Spark computes `hash(joinKey) % numPartitions` for each row and sends it to the corresponding reduce partition. This guarantees that all rows with the same join key from both tables end up in the same partition on the same executor. The number of reduce partitions is controlled by `spark.sql.shuffle.partitions` (default 200), unless Adaptive Query Execution (AQE) coalesces them later. The shuffle writes data to disk on the map side and reads it over the network on the reduce side. This is the most expensive part of SMJ.

**Phase 2: Sort**

After the shuffle, each partition contains rows from both sides, but they are not ordered. Spark sorts each partition by the join key. For each side, the sort is a standard external sort: it uses an in-memory buffer, spills to disk when the buffer fills, and merges spill files into a single sorted run. The sorted data is then used in the merge phase. If both tables are already bucketed and sorted by the join key with the same number of buckets, Spark can skip both the shuffle and the sort, reading the bucketed files directly.

**Phase 3: Merge**

The merge phase is the core of SMJ. For each partition, Spark has two sorted streams: one from the left table and one from the right table. It uses two pointers, one for each stream, and advances them based on the join key comparison.

- If `leftKey < rightKey`, advance the left pointer.
- If `leftKey > rightKey`, advance the right pointer.
- If `leftKey == rightKey`, a match is found. Spark must handle duplicate keys on either side.

For duplicate keys, Spark buffers all rows with the same key from one side (typically the left side) and then iterates through the matching rows on the other side to produce the joined output. This buffering is bounded by the number of duplicates for a single key, not the entire partition. If a key has a huge number of duplicates (skew), this buffer can grow large and cause memory pressure or spills.

The merge phase does not need to hold the entire partition in memory. It only needs the current rows and the buffer for duplicate keys. This is why SMJ scales well: it processes data in a streaming fashion, comparing and advancing pointers.

**Example of a Sort Merge Join in PySpark:**

```
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)  # disable broadcast
spark.conf.set("spark.sql.join.preferSortMergeJoin", "true")

left = spark.range(1000000).selectExpr("id as key", "id as left_val")
right = spark.range(1000000).selectExpr("id as key", "id as right_val")

joined = left.join(right, "key")
joined.explain(True)
```

In the physical plan, you will see `SortMergeJoin [key], [key]` preceded by `Exchange hashpartitioning(key, 200)` and `Sort [key]` on both sides.

**Physical plan example:**


**Handling of duplicate keys:**

Suppose the left side has key `K` appearing 1000 times and the right side has key `K` appearing 500 times. When the merge phase reaches `K`, it buffers all 1000 left rows in memory. Then it iterates through the 500 right rows and outputs 1000 * 500 = 500,000 joined rows for that key. The buffer holds only the left rows for that single key. If a key is extremely hot (e.g., millions of duplicates), the buffer can exceed memory and spill to disk, or cause an out-of-memory error. This is a common symptom of data skew.

**Memory management and spill:**

During the sort phase, Spark uses `spark.sql.shuffle.partitions` to determine the number of partitions. If a partition is too large, the sort may spill to disk. During the merge phase, the duplicate-key buffer can also spill. You can monitor spills in the Spark UI under the "Spill (Memory)" and "Spill (Disk)" columns. To reduce spills, increase the number of shuffle partitions, filter data early, or handle skew with salting.

**Bucketing optimization:**

If both tables are bucketed by the join key with the same number of buckets and sorted by the key, Spark can use a `SortMergeJoin` without the `Exchange` and `Sort` nodes. The physical plan will show `FileScan` nodes with `Bucketed: true` and the join will read corresponding buckets directly. This eliminates the shuffle and the sort, making the join much faster.

Example of creating bucketed tables:

```
left.write
  .bucketBy(100, "key")
  .sortBy("key")
  .saveAsTable("left_bucketed")

right.write
  .bucketBy(100, "key")
  .sortBy("key")
  .saveAsTable("right_bucketed")

joined = spark.table("left_bucketed").join(spark.table("right_bucketed"), "key")
joined.explain(True)
```

In the plan, you should not see `Exchange` or `Sort` for the join keys if the bucketing metadata is used correctly.

**Advantages of Sort Merge Join:**

- Scales to very large datasets because it does not need to hold an entire partition side in memory.
- Handles skew better than Shuffle Hash Join because it does not build a hash map for the entire partition.
- Works well when data is already sorted or bucketed by the join key.
- Can spill to disk gracefully under memory pressure.

**Disadvantages of Sort Merge Join:**

- Requires a full shuffle of both sides unless bucketing is used.
- Requires a sort of both sides, which is CPU and memory intensive.
- Can be slower than Broadcast Hash Join when one side is small.
- Sensitive to skew on the join key. A hot key can cause the duplicate-key buffer to grow large and spill or fail.

**When Spark chooses Sort Merge Join:**

- Default for large equi-joins when broadcast is not applicable.
- Controlled by `spark.sql.join.preferSortMergeJoin`, which defaults to true.
- Used when both sides are too large to broadcast and one side is not significantly smaller than the other.
- Can be forced by disabling broadcast (`spark.sql.autoBroadcastJoinThreshold=-1`) and setting `spark.sql.join.preferSortMergeJoin=true`.

**Tuning Sort Merge Join:**

- Increase `spark.sql.shuffle.partitions` to reduce partition size and spills.
- Enable AQE to coalesce shuffle partitions and handle skew automatically.
- Use bucketing to avoid the shuffle and sort entirely.
- Filter and select early to reduce the amount of data shuffled.
- Handle skew with salting if a few keys dominate.
- Monitor the Spark UI for shuffle read/write sizes, spills, and task durations.

In summary, Sort Merge Join shuffles both sides by the join key, sorts each partition, and then merges the sorted streams using two pointers. It buffers duplicate keys on one side to produce the joined output. It scales well because it streams data and does not hold entire partitions in memory. Bucketing can eliminate the shuffle and sort, making it the fastest option for large-to-large joins.
