# 3.7.3 How does AQE dynamically switch join strategies at runtime?

Adaptive Query Execution (AQE) dynamically switches join strategies at runtime by collecting actual data size statistics after shuffle stages complete, then re-optimizing the remaining query plan before executing subsequent stages. The primary conversion is from a Sort-Merge Join (SMJ) to a more efficient Broadcast Hash Join (BHJ), and in some cases to a Shuffled Hash Join (SHJ).

**Why dynamic switching is necessary**

Without AQE, the static optimizer chooses a join strategy based on compile-time statistics that may be stale, missing, or inaccurate. The optimizer may choose a Sort-Merge Join for a table that is actually small enough to broadcast, resulting in an unnecessary full shuffle. Conversely, if the optimizer incorrectly chooses a broadcast join for a table that turns out to be large, it may cause out-of-memory errors. AQE corrects these misestimations at runtime using accurate measurements.

**The switching mechanism**

AQE operates through a series of query stages separated by shuffle or broadcast exchange boundaries. The process works as follows:

1. **Initial plan with AQE node.** When AQE is enabled, the query plan contains an `AdaptiveSparkPlan` node at the root. Inside, the initial plan contains placeholder nodes that will be replaced with runtime decisions.

2. **Leaf stages execute first.** Spark executes the initial stages that have no dependencies. For a join, this typically means the shuffle stages for both sides of the join.

3. **Runtime statistics collected.** After each shuffle stage completes, AQE gathers the actual byte size of each partition from the shuffle write phase. These statistics are accurate measurements of the materialized data, not estimates. Each shuffle stage reports data statistics such as `Statistics(sizeInBytes=658.1 KiB, rowCount=2.81E+4, isRuntime=true)` once execution completes.

4. **Join strategy re-evaluated.** The `AdaptiveSparkPlan` node detects that new runtime statistics are available and triggers a re-optimization of the remaining plan. The `DynamicJoinSelection` rule examines the runtime sizes of both join sides and decides whether to change the join strategy.

5. **Strategy conversion.** If one side's runtime size is below the broadcast threshold, AQE converts the Sort-Merge Join to a Broadcast Hash Join. The original plan is replaced with the new physical plan.

6. **Execution continues with the new plan.** The remaining stages execute using the optimized join strategy.

**Converting Sort-Merge Join to Broadcast Hash Join**

The primary conversion AQE performs is from Sort-Merge Join to Broadcast Hash Join. AQE can convert an SMJ to a BHJ when the runtime size of one of the join sides does not exceed `spark.sql.adaptive.autoBroadcastJoinThreshold` (default 10 MiB, which falls back to `spark.sql.autoBroadcastJoinThreshold` if not set).

When the conversion happens, the shuffle on the small side is replaced with a broadcast exchange, and the large side is no longer shuffled. This eliminates the network and disk I/O of a full shuffle, which is the most expensive part of a join.

However, AQE's conversion is not unconditional. The `DemoteBroadcastHashJoin` rule prevents AQE from converting SMJ to BHJ when the side that would be broadcast has a high ratio of empty partitions. Specifically, if the non-empty partition ratio of the build side is lower than `spark.sql.adaptive.nonEmptyPartitionRatioForBroadcastJoin` (default 0.2), the rule adds a `NO_BROADCAST_HASH` hint to avoid the conversion. This is because a broadcast join with many empty partitions can be slower than a sort-merge join due to the overhead of broadcasting an almost-empty table.

**Converting Sort-Merge Join to Shuffled Hash Join**

AQE can also convert a Sort-Merge Join to a Shuffled Hash Join (SHJ) when the runtime partition sizes are small enough to build local hash maps safely. This conversion is controlled by `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold`, which sets the maximum size in bytes per partition that can be allowed to build a local hash map. When all partition sizes are within this threshold, AQE prefers SHJ over SMJ because SHJ avoids the sort phase entirely.

If `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold` is not set, it falls back to `spark.sql.adaptive.advisoryPartitionSizeInBytes`. This allows AQE to convert SMJ to SHJ by default when partitions are small enough.

**Local shuffle reader optimization**

When AQE converts an SMJ to a BHJ, it can also apply the local shuffle reader optimization. Controlled by `spark.sql.adaptive.localShuffleReader.enabled` (default true), this optimization reads shuffle files locally to save network traffic when the shuffle data is already available on the same executor. The local shuffle reader avoids the shuffle read phase entirely when the SMJ transforms to BHJ after applying AQE rules.

**Key configuration parameters**

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.adaptive.enabled` | true (3.2+) | Master switch for AQE |
| `spark.sql.adaptive.autoBroadcastJoinThreshold` | 10 MiB | AQE-side broadcast threshold. Falls back to `spark.sql.autoBroadcastJoinThreshold` if not set |
| `spark.sql.adaptive.nonEmptyPartitionRatioForBroadcastJoin` | 0.2 | Minimum non-empty partition ratio for a relation to be broadcast. Below this ratio, BHJ is demoted to SMJ |
| `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold` | Falls back to `advisoryPartitionSizeInBytes` | Maximum partition size for building local hash maps in SHJ |
| `spark.sql.adaptive.localShuffleReader.enabled` | true | Enables local shuffle reader to avoid network reads after BHJ conversion |
| `spark.sql.autoBroadcastJoinThreshold` | 10 MiB | Static broadcast threshold used as fallback for the AQE threshold |

**Code example**

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
         .appName("AQEJoinSwitchExample")
         .config("spark.sql.adaptive.enabled", "true")
         .config("spark.sql.adaptive.autoBroadcastJoinThreshold", "30m")
         .config("spark.sql.adaptive.nonEmptyPartitionRatioForBroadcastJoin", "0.2")
         .config("spark.sql.adaptive.localShuffleReader.enabled", "true")
         .getOrCreate())

# Large fact table
large_df = spark.range(10000000).selectExpr("id as key", "id as value")

# Small dimension table that may not be recognized as small at compile time
small_df = spark.range(500000).selectExpr("id as key", "id as dim_value")

# Initially planned as Sort-Merge Join
joined = large_df.join(small_df, "key")

# Before execution, the plan shows SortMergeJoin
joined.explain(True)

# Execute and re-inspect
joined.count()
joined.explain(True)

# After execution, the plan shows BroadcastHashJoin if AQE converted it
```

To see the dynamic conversion, run `explain(True)` before and after execution. Before execution, the plan shows the initial `SortMergeJoin`. After execution, the plan shows `AdaptiveSparkPlan isFinalPlan=true` with `BroadcastHashJoin` replacing the Sort-Merge Join. The `AdaptiveSparkPlan` node is the root node for all AQE queries, and its `isFinalPlan` flag changes from `false` to `true` after execution completes.

**Verifying the switch in the Spark UI**

In the Spark UI SQL tab, the query plan evolves as execution progresses. Executed nodes (with metrics available) are frozen, while unexecuted nodes may change due to re-optimization. Look for the physical join node in the current plan. If AQE converted the join, you will see `BroadcastHashJoin` where the initial plan had `SortMergeJoin`. The `AdaptiveSparkPlan` node will show `isFinalPlan=true` after completion.

**Important caveats**

AQE's join strategy conversion is one-way. It can convert an SMJ to a BHJ or SHJ, but it cannot convert a BHJ back to an SMJ if the broadcast side turns out to be too large. This means if the static optimizer incorrectly chooses a broadcast join for a table that is actually large, AQE cannot fix it. The broadcast may fail with an out-of-memory error on the driver. To prevent this, keep the static `spark.sql.autoBroadcastJoinThreshold` at a conservative value and let AQE handle the conversion upward from SMJ.

AQE's skew join handling also interacts with join strategy conversion. When a skewed partition is detected, AQE splits it and replicates the matching side. This works with both SMJ and SHJ, but not with BHJ. If AQE has already converted the join to BHJ, skew handling does not apply because the broadcast side is already replicated across all executors.

If the initial shuffle partition count is very large (more than 2000 partitions), AQE may not be able to detect join strategy opportunities due to `CompressedMapStatus` losing per-partition size information. In such cases, the driver log will show `OptimizeSkewedJoin: number of skewed partitions: left 0, right 0` even when skew is present.

**Summary**

AQE dynamically switches join strategies by executing shuffle stages first, collecting actual partition size statistics, and re-optimizing the remaining plan. The primary conversion is from Sort-Merge Join to Broadcast Hash Join when one side's runtime size falls below the broadcast threshold. The `DemoteBroadcastHashJoin` rule prevents conversion when the build side has a high ratio of empty partitions. AQE can also convert SMJ to Shuffled Hash Join when partition sizes are small enough to build local hash maps. The local shuffle reader optimization avoids network reads after BHJ conversion. The switch is visible in `explain(True)` output and in the Spark UI SQL tab. AQE's conversion is one-way: it can upgrade from SMJ to BHJ/SHJ but cannot demote a BHJ back to SMJ.
