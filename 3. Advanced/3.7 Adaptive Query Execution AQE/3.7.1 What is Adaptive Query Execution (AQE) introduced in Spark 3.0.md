# 3.7.1 What is Adaptive Query Execution (AQE) introduced in Spark 3.0?

### 3.7.1 What is Adaptive Query Execution (AQE) introduced in Spark 3.0

Adaptive Query Execution (AQE) is a runtime optimization framework introduced in Spark 3.0 that re-optimizes query plans based on statistics collected during query execution. It was designed to address the inefficiency and lack of flexibility in query execution plans caused by insufficient, inaccurate, or obsolete optimizer statistics.

**Why AQE Was Introduced**

Traditional Spark optimization relies on the Cost-Based Optimizer (CBO), which uses pre-collected table statistics (row counts, distinct values, etc.) to generate a query plan before execution begins. However, these statistics can often be outdated or inaccurate, leading to suboptimal plans such as choosing a costly Sort-Merge Join when a Broadcast Hash Join would be far more efficient.

AQE solves this by collecting actual runtime statistics from completed query stages and re-optimizing the remaining plan on the fly. This dynamic approach ensures the plan adapts to the real data distribution and volume, rather than relying on potentially stale estimates.

**How AQE Works**

AQE breaks a query plan into query stages separated by shuffle or broadcast exchange boundaries, which act as materialization points.

1. Leaf stages run first. Spark executes the initial stages that do not depend on others.
2. Runtime statistics collected. As each stage materializes its intermediate results, AQE gathers statistics on actual partition sizes, row counts, and data distribution.
3. Plan re-optimization. Based on these runtime statistics, AQE re-runs the optimizer (including logical and physical rules) and updates the remaining execution plan.
4. Repeat. The framework then identifies and executes new stages whose dependencies are met, repeating the execute-reoptimize-execute cycle until the entire query is complete.

**Core Features of AQE**

In Spark 3.0, AQE shipped with three primary features.

1. Dynamically Coalescing Shuffle Partitions

The default number of shuffle partitions (`spark.sql.shuffle.partitions`, typically 200) is often a poor fit for a given query, leading to either too many small tasks or too few large tasks. AQE solves this by merging adjacent small shuffle partitions into larger ones after a shuffle stage completes, targeting a configurable size (e.g., 64 MB). This reduces scheduling overhead and avoids the small-file problem.

Key configurations:
- `spark.sql.adaptive.coalescePartitions.enabled` (default: `true`)
- `spark.sql.adaptive.advisoryPartitionSizeInBytes` (default: `64m`)
- `spark.sql.adaptive.coalescePartitions.minPartitionNum`

2. Dynamically Switching Join Strategies

When the static optimizer misestimates table sizes, it may choose a Sort-Merge Join (SMJ) for a table that is actually small enough to broadcast. AQE uses runtime statistics to detect when one side of a join is small enough and dynamically converts the SMJ to a more efficient Broadcast Hash Join (BHJ). This eliminates the need for manual broadcast hints.

Key configurations:
- `spark.sql.adaptive.autoBroadcastJoinThreshold` (default: `10m`)
- `spark.sql.adaptive.localShuffleReader.enabled` (default: `true`)

3. Dynamically Optimizing Skew Joins

Data skew, where one or a few join keys are much more frequent than others, causes a few tasks to process far more data than the rest, creating a long tail that dominates runtime. AQE detects skewed partitions at runtime and splits them into smaller sub-partitions, replicating the matching side as needed to distribute the hot key across multiple tasks.

Key configurations:
- `spark.sql.adaptive.skewJoin.enabled` (default: `true`)
- `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (default: `5`)
- `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default: `256MB`)

A partition is considered skewed only if it exceeds both the median partition size multiplied by the factor and the absolute byte threshold.

**Key Configuration Parameters**

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.adaptive.enabled` | `true` (Spark 3.2+) | Master switch for AQE |
| `spark.sql.adaptive.coalescePartitions.enabled` | `true` | Enable partition coalescing |
| `spark.sql.adaptive.advisoryPartitionSizeInBytes` | `64m` | Target size for coalesced partitions |
| `spark.sql.adaptive.coalescePartitions.minPartitionNum` | (none) | Minimum number of partitions after coalescing |
| `spark.sql.adaptive.autoBroadcastJoinThreshold` | `10m` | AQE-side broadcast threshold |
| `spark.sql.adaptive.localShuffleReader.enabled` | `true` | Enable local shuffle reader to reduce reads |
| `spark.sql.adaptive.skewJoin.enabled` | `true` | Enable skew join handling |
| `spark.sql.adaptive.skewJoin.skewedPartitionFactor` | `5` | Multiplier for median partition size |
| `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` | `256MB` | Absolute size threshold for skew |

**Important Interactions and Limitations**

Interaction with Dynamic Partition Pruning (DPP): When AQE and DPP are both enabled, DPP takes precedence and AQE will not take effect. To use AQE, you must disable DPP by setting `spark.sql.optimizer.dynamicPartitionPruning.enabled` to `false`.

Skew handling limitations: AQE's skew join optimization only supports two-table joins and does not support FULL OUTER JOIN data skew. For outer joins, skew on the non-preserved side cannot trigger the optimization.

Map-side partitions: AQE does not automatically set the map-side partition number. To fully benefit from partition coalescing, it is recommended to set a relatively high initial shuffle partition count via `spark.sql.shuffle.partitions`.

**Code Example**

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
         .appName("AQEExample")
         .config("spark.sql.adaptive.enabled", "true")
         .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
         .config("spark.sql.adaptive.advisoryPartitionSizeInBytes", "64m")
         .config("spark.sql.adaptive.skewJoin.enabled", "true")
         .config("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")
         .config("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
         .config("spark.sql.adaptive.autoBroadcastJoinThreshold", "10m")
         .config("spark.sql.optimizer.dynamicPartitionPruning.enabled", "false")
         .getOrCreate())

df1 = spark.range(10000000).selectExpr("id as key", "id as value")
df2 = spark.range(100).selectExpr("id as key", "id as dim_value")

joined = df1.join(df2, "key")
joined.explain(True)
```

In the physical plan, you will see `AdaptiveSparkPlan` as the root node. After execution, the plan will show `AQEShuffleRead` for coalesced partitions and `BroadcastHashJoin` if AQE converted the join.

**Summary**

Adaptive Query Execution is a significant advancement in Spark SQL that transforms the optimizer from a static, compile-time process into a dynamic, runtime-adaptive framework. By leveraging actual execution statistics, AQE automatically handles common performance pitfalls like suboptimal partition counts, inefficient join strategies, and data skew. Enabled by default in Spark 3.2+, it is the first line of defense for query performance tuning and eliminates the need for many manual tuning techniques such as setting shuffle partitions, writing broadcast hints, and salting skewed keys.
