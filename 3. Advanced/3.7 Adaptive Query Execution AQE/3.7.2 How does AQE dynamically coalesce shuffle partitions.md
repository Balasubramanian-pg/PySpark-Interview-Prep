# 3.7.2 How does AQE dynamically coalesce shuffle partitions?

Adaptive Query Execution (AQE) dynamically coalesces shuffle partitions by collecting runtime statistics after each shuffle stage completes and merging small contiguous partitions into larger ones. This process addresses the long-standing problem of choosing a fixed number of shuffle partitions (`spark.sql.shuffle.partitions`) that works well for all stages of a query.

**The problem without AQE**

Without AQE, the number of shuffle partitions is determined by a static configuration, `spark.sql.shuffle.partitions`, which defaults to 200. This single value must serve every shuffle in every query. When the setting is too large relative to the actual output size, a shuffle stage produces many small or empty files. These small tasks have worse I/O throughput and suffer from scheduling overhead and task setup overhead. When the setting is too small, partitions become large and may spill or cause out-of-memory errors. The correct value is data-dependent and cannot be known in advance for a query with multiple stages.

**How AQE coalescing works**

AQE operates by materializing shuffle stages and collecting statistics before re-optimizing the remaining plan. The coalescing process follows these steps:

1. **Shuffle stage executes.** A shuffle stage runs using the initial number of partitions, which is controlled by `spark.sql.adaptive.coalescePartitions.initialPartitionNum` (default is the same as `spark.sql.shuffle.partitions`, typically 200).

2. **Runtime statistics collected.** After the shuffle write phase completes, AQE gathers the actual byte size of each shuffle partition from the task metrics. These are the runtime statistics, which are more accurate than any compile-time estimate.

3. **Coalescing rule applied.** The `CoalesceShufflePartitions` rule examines the partition sizes and merges contiguous shuffle partitions according to a target size specified by `spark.sql.adaptive.advisoryPartitionSizeInBytes` (default 64 MB). It packs adjacent small partitions together until the combined size approaches the target.

4. **Plan updated.** The original `ShuffleQueryStageExec` is replaced with an `AQEShuffleReadExec` node that uses a `CoalescedPartitionSpec` to describe the merged read ranges. This means the downstream stage reads fewer, larger partitions without introducing an additional shuffle.

5. **Reduced task count.** The result is fewer tasks in the downstream stage. If the original shuffle produced 200 small partitions, AQE might coalesce them into 20 or 30 larger partitions, each close to the target size. This reduces scheduling overhead and improves I/O throughput because each task reads more data sequentially.

**Key configuration parameters**

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.adaptive.enabled` | true (3.2+) | Master switch for AQE |
| `spark.sql.adaptive.coalescePartitions.enabled` | true | Enables partition coalescing. Only effective when the master switch is also true |
| `spark.sql.adaptive.advisoryPartitionSizeInBytes` | 64 MB | Target size for coalesced partitions. Takes effect when AQE coalesces small partitions or splits skewed partitions |
| `spark.sql.adaptive.coalescePartitions.initialPartitionNum` | same as `spark.sql.shuffle.partitions` | Initial number of shuffle partitions before AQE coalescing |
| `spark.sql.adaptive.coalescePartitions.minPartitionNum` | 1 | Minimum number of partitions after coalescing. If not set, the cluster's default parallelism is used |

**Setting the advisory partition size**

The `advisoryPartitionSizeInBytes` parameter is the primary tuning knob for coalescing. The default is 64 MB. When reading and writing data with HDFS, matching this value to the HDFS block size is often the best choice, such as 128 MB or 256 MB. A larger target size produces fewer, larger partitions, which is beneficial when the job writes many small files. A smaller target size preserves more parallelism, which may be necessary when downstream operations require more concurrent tasks.

**Code example**

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
         .appName("AQECoalesceExample")
         .config("spark.sql.adaptive.enabled", "true")
         .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
         .config("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m")
         .config("spark.sql.adaptive.coalescePartitions.initialPartitionNum", "500")
         .config("spark.sql.adaptive.coalescePartitions.minPartitionNum", "10")
         .getOrCreate())

df = spark.range(10000000).selectExpr("id as key", "id % 100 as group_id")
result = df.groupBy("group_id").count()
result.explain(True)
```

In the physical plan, look for `AdaptiveSparkPlan` as the root node. After execution, the plan will show `AQEShuffleRead coalesced` for the coalesced partition read, indicating that AQE merged the shuffle partitions.

**Interaction with other AQE features**

Coalescing is one of three core AQE features, alongside dynamic join strategy conversion and skew join handling. The order of operations matters. In Spark 3.2 and later, `OptimizeSkewedJoin` runs before `CoalesceShufflePartitions`. Skew detection uses the raw partition sizes before coalescing, ensuring that a skewed partition is not hidden by merging it with a small neighbor. However, a known issue exists where coalescing can concentrate data into a single partition after skew detection has already run, creating a new skew problem that AQE does not re-check.

**Limitations and caveats**

- **AQE and Dynamic Partition Pruning (DPP) conflict.** When AQE and DPP are both enabled, DPP takes precedence and AQE does not take effect. To use AQE coalescing, set `spark.sql.optimizer.dynamicPartitionPruning.enabled` to `false`.
- **ExpandExec limits coalescing.** When a stage contains `ExpandExec` (used for rollup, cube, or grouping sets), the `CoalesceShufflePartitions` rule is not adjusted during the AQE phase, which reduces the parallelism benefit.
- **Not all queries benefit.** AQE coalescing only applies to queries that contain at least one exchange, such as a join, aggregate, or window operation. Pure map-only jobs with no shuffle are not affected.
- **Target size is advisory.** Spark will attempt to coalesce partitions to the target size but does not guarantee it. For output stages, setting `minPartitionNum` to 1 encourages Spark to coalesce as much as possible, but the result may still vary.
- **Coalesce() operator is not affected.** If you use the DataFrame `coalesce()` method, AQE does not touch it because `coalesce()` does not perform a full shuffle and merges existing partitions without redistributing data.

**Best practices**

- Enable AQE and coalescing for all workloads. For most queries, this is the highest-value tuning action and requires no code changes.
- Set `advisoryPartitionSizeInBytes` to match your storage block size, such as 128 MB for HDFS.
- Increase `initialPartitionNum` to a high value when you want AQE to have more granular partitions to coalesce from, especially for large shuffles.
- Set `minPartitionNum` to a low value (such as 1) when writing output to encourage fewer files, or to a higher value when downstream parallelism is required.
- Monitor the Spark UI SQL tab. Look for `AQEShuffleRead coalesced` nodes to confirm that coalescing is active.
- Disable DPP if you need AQE coalescing to take effect.
