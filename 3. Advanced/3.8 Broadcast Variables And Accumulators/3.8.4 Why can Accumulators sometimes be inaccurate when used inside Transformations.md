# 3.8.4 Why can Accumulators sometimes be inaccurate when used inside Transformations?

Accumulators are write-only shared variables that executors can add to, and the driver reads the final value after an action completes. They are designed to be used inside actions such as `foreach` or `foreachPartition`. When used inside transformations such as `map`, `filter`, or `flatMap`, the accumulator value can become inaccurate because transformations are lazy and may be recomputed multiple times. This leads to double counting, triple counting, or completely incorrect results.

**The core reason: lazy evaluation and recomputation**

Transformations in Spark are lazy. They build a lineage graph but do not execute until an action is called. When an action runs, Spark may recompute a transformation if:

- The task fails and is retried.
- A stage is re-executed due to a fetch failure.
- Speculative execution launches a duplicate task.
- Multiple actions are called on the same RDD or DataFrame, causing the entire lineage to be recomputed each time.
- The RDD is not cached and is used in multiple places.

Each time a transformation is recomputed, any accumulator updates inside that transformation are applied again. This is why the accumulator value can be larger than expected.

**Example of incorrect usage**

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("AccumulatorIncorrect").getOrCreate()
sc = spark.sparkContext

acc = sc.accumulator(0)

rdd = sc.parallelize([1, 2, 3, 4])

# Accumulator update inside a transformation (map)
mapped = rdd.map(lambda x: acc.add(x))

# First action triggers computation
mapped.count()
print("After first action:", acc.value)  # 10

# Second action triggers recomputation of the same lineage
mapped.count()
print("After second action:", acc.value)  # 20 (double counted)
```

In this example, the accumulator is updated inside `map`. The first `count()` action computes the transformation and adds each element to the accumulator, resulting in 10. The second `count()` action recomputes the same transformation from scratch because the RDD is not cached, so the accumulator is updated again, resulting in 20. The correct value should be 10.

**Task failure and retry**

If a task fails and Spark retries it, the accumulator updates from the failed attempt are not rolled back. The retried task will apply the updates again. This can cause double counting even if the transformation is only executed once logically.

**Speculative execution**

If speculative execution is enabled, Spark may launch multiple copies of the same task to avoid stragglers. Both copies may update the accumulator, even though only one result is kept. This also causes double counting.

**Multiple actions on the same DataFrame**

If you call multiple actions on the same DataFrame without caching, the entire lineage is recomputed each time. If an accumulator is updated inside a transformation in that lineage, it will be updated once per action. This is a common mistake when using accumulators for debugging or counting.

**Correct usage: accumulators inside actions**

To avoid inaccuracy, use accumulators only inside actions such as `foreach` or `foreachPartition`. Actions are executed exactly once per task, and Spark guarantees that accumulator updates inside actions are applied only once per task, even if the task is retried. This is because the action is the final step, and Spark does not recompute it.

```python
acc = sc.accumulator(0)

rdd = sc.parallelize([1, 2, 3, 4])

# Correct: accumulator update inside an action (foreach)
rdd.foreach(lambda x: acc.add(x))

print("After foreach:", acc.value)  # 10
```

If you need to perform a transformation and also count something, you can use a `mapPartitions` action that returns the data and updates the accumulator, or you can use a DataFrame aggregation to compute the count. For exact counts, use DataFrame `groupBy` or `count` instead of accumulators.

**Workaround for transformations: use a new accumulator API or cache**

In Spark 2.x and later, there is a new accumulator API that provides stronger guarantees. However, the standard `sc.accumulator` still has the same caveats. The safest approach is to avoid accumulators in transformations entirely.

If you must use an accumulator in a transformation, you can cache the RDD or DataFrame after the transformation so that subsequent actions do not recompute it. But this does not protect against task retries or speculative execution. Caching only prevents recomputation across multiple actions.

```python
mapped = rdd.map(lambda x: acc.add(x))
mapped.cache()
mapped.count()  # first action, updates accumulator
mapped.count()  # second action, uses cached data, no recomputation
```

However, if a task fails and is retried, the accumulator will still be updated again. So caching is not a complete solution.

**Best practices**

- Use accumulators only inside actions such as `foreach` or `foreachPartition`.
- Do not use accumulators inside transformations like `map`, `filter`, `flatMap`, or `select`.
- For exact counts or sums, use DataFrame aggregations (`groupBy`, `agg`, `count`) or RDD actions (`reduce`, `fold`) instead of accumulators.
- If you must use an accumulator in a transformation, be aware that the value may be inaccurate if the job is recomputed. Use it only for approximate debugging, not for correctness-critical logic.
- Monitor accumulator values in the Spark UI. If the value seems too high, check whether the transformation is being recomputed.
- For custom accumulators, the same rules apply. Use them only in actions.

**Why actions are safe**

Actions are the final step in a Spark job. They trigger the execution of the lineage and return a result to the driver. Once an action completes, the accumulator updates are collected and the final value is computed. If a task fails, Spark retries the task, but the accumulator updates from the failed attempt are not counted. Spark guarantees that accumulator updates inside actions are applied only once per task. This is why actions are the recommended place for accumulators.

**Summary**

Accumulators can be inaccurate when used inside transformations because transformations are lazy and can be recomputed multiple times due to task retries, stage re-execution, speculative execution, or multiple actions on the same lineage. Each recomputation applies the accumulator updates again, leading to double counting. To avoid this, use accumulators only inside actions such as `foreach` or `foreachPartition`. For exact counts and sums, use DataFrame aggregations or RDD actions. If you must use an accumulator in a transformation, cache the data and be aware that retries and speculation can still cause inaccuracy.
