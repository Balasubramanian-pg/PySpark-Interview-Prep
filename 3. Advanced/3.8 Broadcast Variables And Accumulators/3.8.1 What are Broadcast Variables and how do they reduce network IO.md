### 3.8.1 What are Broadcast Variables and how do they reduce network IO

A broadcast variable is a read-only shared variable that Spark distributes to all executors once and caches on each machine. Instead of shipping the same data with every task, the driver sends the broadcast value to each executor one time. All tasks running on that executor share the same cached copy. Broadcast variables are created with `sc.broadcast(value)` and accessed inside transformations or actions through `.value`.

They are used for large read-only data that every task needs, such as lookup tables, dictionaries, configuration maps, or machine learning models. They are not used for data that changes or for data that is too large to fit in executor memory.

**How broadcast variables reduce network IO**

Without a broadcast variable, if you reference a large object inside a transformation, Spark captures that object in the closure of the task. The closure is serialized and sent with every task. If you have 10,000 tasks, the same data is serialized and transferred 10,000 times. This creates excessive network IO, serialization overhead, and garbage collection pressure.

With a broadcast variable, the data is sent once per executor, not once per task. The driver stores the value in its block manager and assigns it a broadcast ID. When an executor needs the value, it fetches it once and caches it in its local block manager. All tasks on that executor read the cached copy. For large broadcast values, Spark uses a BitTorrent-like protocol called TorrentBroadcast to distribute the data efficiently across executors, reducing the load on the driver.

This reduces network IO in several ways:
- The value is transferred once per executor instead of once per task.
- Tasks no longer include the large object in their serialized closure, so task size is smaller.
- The data is cached and reused across multiple tasks and multiple stages on the same executor.
- Serialization and deserialization happen once per executor rather than once per task.
- For joins, broadcast variables enable map-side joins, which avoid shuffling the large table entirely. This eliminates the network cost of a full shuffle.

**Code example without broadcast**

```python
lookup = {"a": 1, "b": 2, "c": 3}
rdd = sc.parallelize(["a", "b", "c", "d"] * 100000)

# The lookup dictionary is captured in the closure and sent with every task
result = rdd.map(lambda x: lookup.get(x, 0)).collect()
```

**Code example with broadcast**

```python
lookup = {"a": 1, "b": 2, "c": 3}
broadcast_lookup = sc.broadcast(lookup)
rdd = sc.parallelize(["a", "b", "c", "d"] * 100000)

# The lookup dictionary is sent once per executor and cached
result = rdd.map(lambda x: broadcast_lookup.value.get(x, 0)).collect()

# Release the broadcast data when no longer needed
broadcast_lookup.unpersist()
```

**How it works under the hood**

1. The driver serializes the value and stores it in its block manager.
2. The driver creates a `Broadcast` object with a unique broadcast ID.
3. When a task on an executor needs the value, the executor checks its local block manager.
4. If the value is not present, the executor fetches it from the driver or from another executor that already has it.
5. The value is cached on the executor in deserialized form for fast access.
6. Subsequent tasks on the same executor reuse the cached copy without any network transfer.
7. TorrentBroadcast divides large values into blocks and distributes them in a peer-to-peer manner to reduce driver load.

**When to use broadcast variables**

- When you have a large read-only lookup table or dictionary needed by all tasks.
- When you want to perform a map-side join manually to avoid a shuffle.
- When the data is small enough to fit comfortably in executor memory.
- When you are using RDDs and need to share data across tasks without shipping it repeatedly.

**When not to use broadcast variables**

- When the data is too large to fit in executor memory. This can cause out-of-memory errors.
- When the data changes frequently. Broadcast variables are immutable.
- When the data is small enough that shipping it with each task is not a problem. The overhead of broadcasting may not be worth it.
- When you are using DataFrames and Spark can automatically choose a broadcast join using `broadcast()` or `spark.sql.autoBroadcastJoinThreshold`.

**Best practices**

- Always call `unpersist()` on broadcast variables when they are no longer needed to free executor memory.
- Monitor broadcast memory usage in the Spark UI under the Executors tab.
- Use broadcast variables for lookup tables that are accessed many times across many tasks.
- For DataFrame joins, prefer the `broadcast()` hint or let Spark choose a broadcast join automatically.
- Do not modify the broadcast value. It is read-only.
- If the broadcast value is very large, consider using a broadcast join or a different join strategy instead.

**Summary**

Broadcast variables are read-only shared variables that Spark distributes to all executors once and caches on each machine. They reduce network IO by eliminating the need to ship the same data with every task. The value is transferred once per executor, cached, and reused by all tasks on that executor. This reduces serialization overhead, task size, network transfer, and garbage collection pressure. Broadcast variables are especially useful for lookup tables and map-side joins. Always unpersist them when no longer needed, and avoid using them for data that is too large to fit in executor memory.
