### 3.4.3 When should you choose MEMORY_AND_DISK over MEMORY_ONLY

`MEMORY_ONLY` and `MEMORY_AND_DISK` are two storage levels used with `persist()`. The choice depends on whether the dataset fits in memory, how expensive it is to recompute lost partitions, and how much disk I/O you are willing to trade for recomputation.

**MEMORY_ONLY**

- Stores partitions as deserialized Java objects in the JVM heap.
- If a partition does not fit in memory, it is evicted and recomputed on demand when needed again.
- Fastest for CPU because data is already deserialized and in memory.
- Can cause repeated recomputation if the dataset is larger than available memory.
- Best when the dataset fits comfortably in memory and recomputation is cheap.

**MEMORY_AND_DISK**

- Stores partitions as deserialized Java objects in memory.
- If a partition does not fit in memory, it spills to disk instead of being evicted and recomputed.
- When the partition is needed again, it is read from disk rather than recomputed.
- Slower than pure memory access due to disk I/O, but avoids recomputation cost.
- Best when the dataset is too large for memory or recomputation is expensive.

**When to choose MEMORY_AND_DISK over MEMORY_ONLY**

Choose `MEMORY_AND_DISK` in these situations:

1. **The dataset does not fit in memory.** If the total size of the cached data exceeds the available storage memory across executors, `MEMORY_ONLY` will evict partitions and recompute them repeatedly. `MEMORY_AND_DISK` spills those partitions to disk, avoiding recomputation.

2. **Recomputation is expensive.** If the lineage is long, involves multiple shuffles, complex UDFs, external API calls, or non-deterministic operations, recomputing a partition can be very costly. Reading from disk is usually cheaper than recomputing a complex lineage.

3. **The job is iterative or reused multiple times.** In iterative algorithms like machine learning training or graph processing, the same dataset is accessed many times. Recomputation on each access can dominate runtime. Spilling to disk once is more efficient.

4. **You want predictable performance.** `MEMORY_ONLY` can cause unpredictable spikes when evicted partitions are recomputed. `MEMORY_AND_DISK` provides more stable performance because lost partitions are read from disk, not recomputed.

5. **Memory is limited or shared.** In a multi-tenant cluster or when other workloads compete for memory, `MEMORY_ONLY` may evict your data frequently. `MEMORY_AND_DISK` provides a safety net by using disk.

6. **The cost of disk I/O is lower than the cost of recomputation.** If the transformations are CPU-heavy, spilling to disk and reading back is often faster than recomputing the entire lineage.

7. **You are using DataFrames and want the default robust behavior.** For DataFrames, `cache()` already uses `MEMORY_AND_DISK`. If you explicitly call `persist(StorageLevel.MEMORY_ONLY)`, you may lose the disk fallback. Unless you have a specific reason to force memory only, `MEMORY_AND_DISK` is the safer default for large DataFrames.

**When MEMORY_ONLY might still be better**

- The dataset fits entirely in memory with room to spare.
- The lineage is short and cheap to recompute, such as a simple `map` or `filter` on a small dataset.
- You want the lowest possible latency and are willing to accept recomputation if memory pressure occurs.
- You are running in an environment where disk I/O is extremely slow or unreliable.

**Code examples in PySpark**

Caching an RDD with MEMORY_ONLY:

```python
from pyspark import StorageLevel

rdd = sc.parallelize(range(1000000))
rdd.persist(StorageLevel.MEMORY_ONLY)
rdd.count()
rdd.unpersist()
```

Caching an RDD with MEMORY_AND_DISK:

```python
rdd.persist(StorageLevel.MEMORY_AND_DISK)
rdd.count()
rdd.unpersist()
```

Caching a DataFrame with MEMORY_ONLY:

```python
df = spark.range(1000000)
df.persist(StorageLevel.MEMORY_ONLY)
df.count()
df.unpersist()
```

Caching a DataFrame with MEMORY_AND_DISK:

```python
df.persist(StorageLevel.MEMORY_AND_DISK)
df.count()
df.unpersist()
```

**How to detect whether MEMORY_ONLY is causing problems**

Check the Spark UI under the Storage tab. Look for:

- Fraction of cached data in memory.
- Number of partitions evicted.
- Recomputation time in the Stages tab.
- Spill (memory) and Spill (disk) metrics.

If you see many evicted partitions and high recomputation time, switch to `MEMORY_AND_DISK`.

**Trade-offs summary**

| Aspect | MEMORY_ONLY | MEMORY_AND_DISK |
|---|---|---|
| Memory usage | High | High |
| Disk usage | None | Used when memory is full |
| CPU efficiency | Highest when data fits | High, but disk read adds latency |
| Recomputation | Yes, for evicted partitions | No, spills to disk |
| Best for | Small datasets that fit in memory | Large datasets or expensive recomputation |
| Fault tolerance | Recompute lost partitions | Recompute lost partitions; disk data may survive executor restart if persistent |

**Important notes**

- In PySpark, stored objects are always serialized with Pickle. The difference between MEMORY_ONLY and MEMORY_AND_DISK still applies in terms of memory versus disk fallback, but the serialization aspect is handled automatically.
- `MEMORY_AND_DISK` does not guarantee that all data stays in memory. It uses memory first and spills the rest to disk. It is not a pure disk level; use `DISK_ONLY` for that.
- Always call `unpersist()` when the cached data is no longer needed to release memory and disk resources.
- For DataFrames, `cache()` is equivalent to `persist(StorageLevel.MEMORY_AND_DISK)`. So if you want MEMORY_ONLY, you must call `persist(StorageLevel.MEMORY_ONLY)` explicitly.

In summary, choose `MEMORY_AND_DISK` over `MEMORY_ONLY` when the dataset is too large to fit in memory, when recomputation is expensive, when the job is iterative, or when you need predictable performance and a disk fallback. Choose `MEMORY_ONLY` only when the dataset fits comfortably in memory and recomputation is cheap.
