# 3.4.4 What happens if you try to cache a DataFrame but there isn't enough memory?

### 3.4.4 What happens if you try to cache a DataFrame but there isn't enough memory

When you cache a DataFrame and there is not enough memory to hold all partitions, Spark does not fail immediately. Instead, it falls back to the behavior defined by the storage level. The default storage level for DataFrames is `MEMORY_AND_DISK`, which means Spark tries to keep as many partitions in memory as possible and spills the remaining partitions to disk. If you explicitly use `MEMORY_ONLY`, Spark will evict partitions from memory and recompute them when they are needed again. In both cases, the job may still succeed, but performance can degrade due to disk I/O or recomputation.

**Default behavior for DataFrames: MEMORY_AND_DISK**

When you call `df.cache()` on a DataFrame, it is equivalent to `df.persist(StorageLevel.MEMORY_AND_DISK)`. The caching process works as follows:

- Each partition is first stored in memory as deserialized Java objects.
- When the total cached data exceeds the available storage memory (controlled by `spark.memory.storageFraction` and total executor memory), Spark begins to evict partitions from memory.
- For `MEMORY_AND_DISK`, evicted partitions are written to disk instead of being discarded. The disk location is the executor's local temporary directory.
- When a partition is needed for a subsequent action, Spark checks memory first. If it is not in memory, it reads the partition from disk rather than recomputing it.
- This continues until the cached data is no longer needed and `unpersist()` is called.

The result is that caching still provides a benefit: you avoid recomputing the entire lineage. However, reading from disk is slower than reading from memory, so the performance improvement may be less than if everything fit in memory.

**Behavior with MEMORY_ONLY**

If you explicitly use `df.persist(StorageLevel.MEMORY_ONLY)`, Spark will not spill to disk. When memory is insufficient:

- Partitions that do not fit are evicted from memory and discarded.
- When an evicted partition is needed again, Spark recomputes it from the original lineage.
- If the lineage is long or involves shuffles, this recomputation can be very expensive.
- Repeated eviction and recomputation can cause the job to slow down significantly, and in extreme cases it may appear to hang or run out of memory during recomputation.

**Behavior with serialized storage levels**

If you use a serialized level such as `MEMORY_ONLY_SER` or `MEMORY_AND_DISK_SER`, data is stored as byte arrays. Serialization reduces memory usage, so more data can fit in memory before eviction or spilling occurs. However, reading the data requires deserialization, which increases CPU usage. The fallback behavior for serialized levels follows the same pattern: `MEMORY_ONLY_SER` recomputes evicted partitions, while `MEMORY_AND_DISK_SER` spills them to disk.

**What about the driver?**

The driver is not involved in caching DataFrame partitions. Caching happens on the executors. The driver only coordinates the process. Therefore, insufficient executor memory is the concern, not driver memory. However, if the DataFrame is very large and the driver collects results (e.g., `collect()`), that is a separate issue.

**How to detect insufficient memory during caching**

Check the Spark UI under the Storage tab:

- Look at the "Size in Memory" and "Size on Disk" columns for the cached DataFrame.
- If "Size on Disk" is greater than zero, spilling occurred.
- Look at the "Fraction Cached" percentage. If it is less than 100%, not all partitions are cached.
- In the Executors tab, check the "Storage Memory" usage and spilling metrics.
- In the Stages tab, look for "Spill (Memory)" and "Spill (Disk)" in the task metrics.

You can also check the driver logs for warnings such as:

```
WARN storage.MemoryStore: Not enough space to cache partition in memory! 
```

or

```
WARN memory.MemoryStore: Memory store is full, spilling to disk
```

**Code example: caching a DataFrame and checking storage**

```python
from pyspark import StorageLevel

df = spark.range(10000000)  # large DataFrame

# Default cache: MEMORY_AND_DISK
df.cache()
df.count()  # triggers caching

# Check storage info
spark.catalog.isCached("df")  # if registered as a table
# Or inspect the Spark UI Storage tab

# Explicit MEMORY_ONLY
df.persist(StorageLevel.MEMORY_ONLY)
df.count()
df.unpersist()
```

**What you can do if memory is insufficient**

1. **Use MEMORY_AND_DISK** (default for DataFrames). This avoids recomputation by spilling to disk.

2. **Use a serialized storage level** such as `MEMORY_AND_DISK_SER` to reduce memory footprint. In PySpark, serialization is always used, so the benefit may be limited, but in Scala/Java it can help significantly.

3. **Increase executor memory** if the cluster has available resources:
   ```
   spark.conf.set("spark.executor.memory", "8g")
   ```

4. **Reduce the data size before caching**. Filter, select only necessary columns, or aggregate to reduce the volume.
   ```python
   df_filtered = df.filter(df.date >= "2024-01-01").select("id", "amount")
   df_filtered.cache()
   ```

5. **Increase the storage memory fraction** if the workload is cache-heavy. The default `spark.memory.storageFraction` is 0.5 (50% of the unified memory). You can increase it, but this reduces memory available for execution.
   ```
   spark.conf.set("spark.memory.storageFraction", "0.6")
   ```

6. **Avoid caching large DataFrames that do not fit**. If the DataFrame is too large to benefit from caching, consider writing intermediate results to storage (e.g., Parquet) and reading them back instead.

7. **Unpersist when done**. Always call `unpersist()` to release memory and disk resources for other operations.

8. **Use off-heap memory** if configured. `OFF_HEAP` storage level can reduce GC pressure and use memory outside the JVM heap, but it requires `spark.memory.offHeap.enabled=true` and a specified size.

**Summary of outcomes**

| Storage Level | If not enough memory |
|---|---|
| MEMORY_ONLY | Evict partitions; recompute on demand |
| MEMORY_AND_DISK | Spill partitions to disk; read from disk on demand |
| MEMORY_ONLY_SER | Evict partitions; recompute on demand (serialized) |
| MEMORY_AND_DISK_SER | Spill partitions to disk; read from disk on demand (serialized) |
| DISK_ONLY | Write all partitions to disk; no memory usage |
| OFF_HEAP | Store in off-heap memory; evict or recompute depending on configuration |

In summary, if you try to cache a DataFrame and there is not enough memory, Spark does not fail. It either spills to disk (if using MEMORY_AND_DISK, the default for DataFrames) or evicts and recomputes (if using MEMORY_ONLY). Spilling to disk is slower than memory but avoids recomputation. Recomputation can be very expensive for long lineages. Monitor the Storage tab in the Spark UI to see whether spilling or eviction is occurring, and adjust storage levels, memory configuration, or data size accordingly.
