# 3.4.2 What are the different Storage Levels in Spark?

Spark provides several storage levels that offer different trade-offs between memory usage and CPU efficiency. These levels are configured through the `StorageLevel` class and are used with `persist()`. The `cache()` method is a shorthand for the default storage level, which is `MEMORY_ONLY` for RDDs and `MEMORY_AND_DISK` for DataFrames.

### Available Storage Levels

The following table summarizes the core storage levels available in Spark:

| Storage Level | Meaning |
|---|---|
| **MEMORY_ONLY** | Store RDD as deserialized Java objects in the JVM. If the RDD does not fit in memory, some partitions will not be cached and will be recomputed on the fly each time they are needed. This is the default level for RDDs. |
| **MEMORY_AND_DISK** | Store RDD as deserialized Java objects in the JVM. If the RDD does not fit in memory, store the partitions that don't fit on disk, and read them from there when they're needed. This is the default level for DataFrames. |
| **MEMORY_ONLY_SER** | Store RDD as serialized Java objects (one byte array per partition). This is generally more space-efficient than deserialized objects, especially when using a fast serializer, but more CPU-intensive to read. Available in Java and Scala only. |
| **MEMORY_AND_DISK_SER** | Similar to MEMORY_ONLY_SER, but spill partitions that don't fit in memory to disk instead of recomputing them on the fly each time they're needed. Available in Java and Scala only. |
| **DISK_ONLY** | Store the RDD partitions only on disk. |
| **MEMORY_ONLY_2, MEMORY_AND_DISK_2, etc.** | Same as the levels above, but replicate each partition on two cluster nodes. |
| **OFF_HEAP** | Similar to MEMORY_ONLY_SER, but store the data in off-heap memory. This requires off-heap memory to be enabled. Experimental. |

### Detailed Explanation of Each Level

**MEMORY_ONLY**
This is the most CPU-efficient option because data is stored as deserialized Java objects. Operations on the RDD run as fast as possible. However, if the RDD does not fit in memory, partitions that are not cached will be recomputed every time they are needed, which can be expensive if the lineage is long.

**MEMORY_AND_DISK**
This level is more robust than MEMORY_ONLY. Deserialized objects are stored in memory, but if a partition does not fit, it is written to disk instead of being recomputed. This avoids the cost of recomputation at the expense of disk I/O when the partition is needed again.

**MEMORY_ONLY_SER and MEMORY_AND_DISK_SER**
Serialized storage is more space-efficient because it stores one byte array per partition. This allows more data to fit in memory, but reading the data requires deserialization, which increases CPU usage. MEMORY_ONLY_SER recomputes partitions that don't fit, while MEMORY_AND_DISK_SER spills them to disk.

**DISK_ONLY**
Data is stored only on disk. This is the slowest option for access but is useful when memory is very limited and recomputation is expensive. It provides durability across executor restarts as long as the disk is persistent.

**Replicated Levels (_2)**
Adding a `_2` suffix (e.g., `MEMORY_ONLY_2`, `MEMORY_AND_DISK_2`) replicates each partition on two cluster nodes. This provides faster fault recovery because if one node fails, the data is still available on another node. The trade-off is doubled storage usage.

**OFF_HEAP**
This is similar to MEMORY_ONLY_SER but stores data in off-heap memory instead of the JVM heap. This reduces garbage collection overhead and allows executors to be smaller and share a pool of memory. It requires off-heap memory to be enabled and is experimental.

### Important Note for Python Users

In Python, stored objects are always serialized with the Pickle library. This means that choosing a serialized storage level (like `MEMORY_ONLY_SER`) does not matter because PySpark always serializes data. The available storage levels in Python include `MEMORY_ONLY`, `MEMORY_ONLY_2`, `MEMORY_AND_DISK`, `MEMORY_AND_DISK_2`, `DISK_ONLY`, and `DISK_ONLY_2`.

### Which Storage Level to Choose

Spark's storage levels are designed to provide different trade-offs between memory usage and CPU efficiency. The following guidelines help in selecting the right level:

1. **If your RDDs fit comfortably with the default storage level (`MEMORY_ONLY`), leave them that way.** This is the most CPU-efficient option, allowing operations on the RDDs to run as fast as possible.
2. **If not, try using `MEMORY_ONLY_SER`** and selecting a fast serialization library to make the objects much more space-efficient, but still reasonably fast to access. This is available in Java and Scala.
3. **Don't spill to disk unless the functions that computed your datasets are expensive, or they filter a large amount of the data.** Otherwise, recomputing a partition may be as fast as reading it from disk.
4. **Use the replicated storage levels if you want fast fault recovery** (e.g., if using Spark to serve requests from a web application). All the storage levels provide full fault tolerance by recomputing lost data, but the replicated ones let you continue running tasks on the RDD without waiting to recompute a lost partition.

### Code Examples in PySpark

**Persisting a DataFrame with a specific storage level:**

```python
from pyspark.storagelevel import StorageLevel

df = spark.range(1000000)

# Persist in memory and disk (default for DataFrames)
df.persist(StorageLevel.MEMORY_AND_DISK)

# Persist in memory only
df.persist(StorageLevel.MEMORY_ONLY)

# Persist on disk only
df.persist(StorageLevel.DISK_ONLY)

# Persist with replication (on two nodes)
df.persist(StorageLevel.MEMORY_AND_DISK_2)

# Always unpersist when done
df.unpersist()
```

**Caching an RDD with the default level (MEMORY_ONLY):**

```python
rdd = sc.parallelize(range(1000000))
rdd.cache()  # equivalent to rdd.persist(StorageLevel.MEMORY_ONLY)
rdd.count()  # triggers caching
rdd.unpersist()
```

**Persisting an RDD with a custom level:**

```python
rdd.persist(StorageLevel.MEMORY_AND_DISK_SER)
rdd.count()
rdd.unpersist()
```

### Summary of Trade-offs

| Storage Level | Memory Usage | CPU Usage | Fault Tolerance | Recomputation | Disk I/O |
|---|---|---|---|---|---|
| MEMORY_ONLY | High | Low | Recompute | Yes (for lost partitions) | No |
| MEMORY_AND_DISK | High | Low | Recompute + Disk | No (spills to disk) | Yes (when spilling) |
| MEMORY_ONLY_SER | Low | High | Recompute | Yes (for lost partitions) | No |
| MEMORY_AND_DISK_SER | Low | High | Recompute + Disk | No (spills to disk) | Yes (when spilling) |
| DISK_ONLY | None | Low | Disk | No | Always |
| Replicated (_2) | Double | Same as base | Fast recovery | No | Same as base |
| OFF_HEAP | Off-heap | High | Recompute | Yes | No |

In summary, Spark's storage levels let you tune the balance between memory usage, CPU efficiency, and fault tolerance. The default levels (`MEMORY_ONLY` for RDDs, `MEMORY_AND_DISK` for DataFrames) are appropriate for most workloads. Use serialized levels when memory is constrained, replicated levels when fast recovery is critical, and disk-based levels when memory is extremely limited. Always remember to `unpersist()` when the cached data is no longer needed to release cluster resources.
