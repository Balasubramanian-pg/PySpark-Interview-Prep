# 3.6.3 What is Rule-based optimization vs Cost-based optimization (CBO)?

Spark SQL uses two main types of query optimization: rule-based optimization (RBO) and cost-based optimization (CBO). Rule-based optimization applies a fixed set of heuristic rules that are always considered beneficial, regardless of data statistics. Cost-based optimization uses table and column statistics to estimate the cost of alternative plans and chooses the cheapest one. Both are part of the Catalyst Optimizer, but they operate at different stages and solve different problems.

**Rule-based optimization (RBO)**

RBO applies a set of predefined rules to the logical plan. These rules are based on heuristics and algebraic equivalences. They are always applied when the pattern matches, and they do not require statistics. RBO is fast and predictable, but it can make suboptimal decisions when the data distribution is not uniform or when statistics are available.

Common RBO rules in Spark SQL:
- Predicate pushdown: moves filters closer to the data source to reduce the amount of data read.
- Column pruning: removes columns that are not needed by the query.
- Constant folding: evaluates constant expressions at compile time.
- Boolean expression simplification: simplifies conditions like `a AND true` to `a`.
- Limit pushdown: pushes `LIMIT` closer to the source.
- Aggregate pushdown: pushes partial aggregations closer to the source.
- Null propagation: simplifies expressions involving nulls.
- Remove redundant aliases and projections.
- Join reordering: some simple reordering rules, but full join reordering is part of CBO.

RBO is enabled by default and cannot be disabled entirely. It is applied during the logical optimization phase. You can see its effects in the optimized logical plan from `explain(True)`. For example, a filter on a Parquet file will appear in the `FileScan` node as `PushedFilters`.

Example of predicate pushdown (RBO):

```python
df = spark.read.parquet("/data/events")
filtered = df.filter("date >= '2024-01-01' AND country = 'US'")
filtered.explain(True)
```

In the optimized logical plan and physical plan, the `FileScan` node shows `PushedFilters: [IsNotNull(date), GreaterThanOrEqual(date, 2024-01-01), IsNotNull(country), EqualTo(country, US)]`. This means the filter is pushed down to the Parquet reader, so only matching row groups are read.

**Cost-based optimization (CBO)**

CBO uses statistics about tables and columns to estimate the cost of alternative physical plans. It then chooses the plan with the lowest estimated cost. CBO is especially important for join ordering and join strategy selection. It requires statistics to be collected and maintained.

Statistics used by CBO:
- Table-level: row count, size in bytes.
- Column-level: number of distinct values (NDV), null count, min/max, average length.
- These are stored in the metastore and can be collected with `ANALYZE TABLE`.

How CBO works:
1. Collect statistics: Run `ANALYZE TABLE` to compute statistics. In PySpark, use `spark.sql("ANALYZE TABLE my_table COMPUTE STATISTICS FOR COLUMNS col1, col2")`.
2. Estimate cardinality: For each operator, CBO estimates the number of rows and the size of the output. It uses statistics and assumptions about data distribution.
3. Estimate cost: CBO estimates I/O cost, CPU cost, network cost, and memory cost for each candidate plan.
4. Choose the cheapest plan: CBO compares plans and selects the one with the lowest estimated cost.

CBO is controlled by the following configurations:
- `spark.sql.cbo.enabled`: Enables CBO for estimating statistics of operators. Default is true in Spark 3.x.
- `spark.sql.cbo.joinReorder.enabled`: Enables join reordering based on CBO. Default is true in Spark 3.x.
- `spark.sql.cbo.joinReorder.dp.threshold`: Maximum number of joins for dynamic programming join reordering. Default is 12.
- `spark.sql.cbo.starSchemaDetection`: Enables star schema detection for join reordering. Default is false.

Join reordering is one of the main benefits of CBO. For a query with multiple joins, CBO can reorder the joins to minimize the size of intermediate results. For example, if you join a large fact table with two dimension tables, CBO can choose to join the smaller dimension first, then join the result with the other dimension. This reduces the amount of data shuffled.

Example of enabling CBO and collecting statistics:

```python
spark.conf.set("spark.sql.cbo.enabled", "true")
spark.conf.set("spark.sql.cbo.joinReorder.enabled", "true")

spark.sql("ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS customer_id, order_date")
spark.sql("ANALYZE TABLE customers COMPUTE STATISTICS FOR COLUMNS customer_id")
```

After collecting statistics, CBO can choose better join strategies and orders. You can see the effect in the physical plan. For example, a multi-way join may be reordered, and a broadcast hash join may be chosen for a small dimension table.

**Key differences between RBO and CBO**

Data dependence: RBO does not use data statistics. CBO relies on statistics about tables and columns.

Decision making: RBO applies fixed rules that are always considered beneficial. CBO estimates the cost of alternative plans and chooses the cheapest.

Join reordering: RBO performs only simple reordering. CBO performs full join reordering using dynamic programming.

Join strategy: RBO may choose a join strategy based on simple heuristics like size thresholds. CBO uses estimated cardinalities and costs to choose between broadcast hash join, shuffle hash join, and sort-merge join.

Performance: RBO is fast and adds little overhead. CBO adds overhead for collecting and using statistics, but can produce much better plans for complex queries.

Accuracy: RBO can be suboptimal when data distribution is skewed or when statistics would reveal a better plan. CBO can be more accurate but depends on the quality and freshness of statistics.

Configuration: RBO is always enabled. CBO must be enabled and requires statistics to be collected.

**When to use which**

RBO is always active and handles common optimizations like predicate pushdown and column pruning. It is sufficient for simple queries and when statistics are not available.

CBO is beneficial for complex queries with multiple joins, when statistics are available and up to date. It is especially useful for:
- Multi-way joins where join order matters.
- Queries where one table is much smaller than others, and you want Spark to choose a broadcast join.
- Queries where data distribution is skewed, and you want Spark to choose a more robust join strategy.

To use CBO effectively:
- Collect statistics regularly with `ANALYZE TABLE`.
- Enable `spark.sql.cbo.enabled` and `spark.sql.cbo.joinReorder.enabled`.
- Keep statistics up to date after significant data changes.
- Monitor the physical plan to verify that CBO is making good choices.

**Limitations of CBO**

- CBO depends on statistics. If statistics are missing, stale, or inaccurate, CBO may make poor decisions.
- Collecting statistics can be expensive for large tables. Use sampling or incremental statistics where possible.
- CBO does not handle all types of queries. For example, it may not reorder joins with non-equi conditions or complex expressions.
- CBO can be overridden by Adaptive Query Execution (AQE) at runtime, which re-optimizes the plan based on actual data sizes.

**Example of CBO join reordering**

Suppose you have three tables: `fact` (large), `dim1` (small), `dim2` (medium). A query joins all three. RBO might join `fact` with `dim1` first, then with `dim2`, producing a large intermediate result. CBO might join `dim1` with `dim2` first (since both are small), then join the result with `fact`. This reduces the size of the intermediate result and the shuffle.

```sql
SELECT *
FROM fact f
JOIN dim1 d1 ON f.key1 = d1.key
JOIN dim2 d2 ON f.key2 = d2.key;
```

With CBO and statistics, Spark can choose the optimal join order. You can see the reordered plan in the physical plan.

**Summary**

Rule-based optimization applies fixed heuristic rules that do not require statistics. It handles common optimizations like predicate pushdown, column pruning, and constant folding. Cost-based optimization uses statistics to estimate the cost of alternative plans and chooses the cheapest. It is especially important for join reordering and join strategy selection. RBO is always enabled and fast. CBO must be enabled, requires statistics, and can produce better plans for complex queries. Both work together in the Catalyst Optimizer to produce an efficient physical plan. Use `explain(True)` to see the effects of both.
