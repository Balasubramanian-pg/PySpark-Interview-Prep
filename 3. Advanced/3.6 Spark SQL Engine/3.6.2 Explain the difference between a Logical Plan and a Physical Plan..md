# 3.6.2 Explain the difference between a Logical Plan and a Physical Plan.

A logical plan describes what to compute. A physical plan describes how to compute it. Spark SQL uses both during query execution. The logical plan is declarative and does not specify execution details. The physical plan is operational and specifies the actual algorithms, partitioning, and operators that run on the cluster.

**Logical Plan**

- Represents the query as a tree of logical operators such as `Project`, `Filter`, `Join`, `Aggregate`, `Sort`, `Limit`, and `Union`.
- Does not specify join strategies, partitioning, sorting, or data movement.
- Is independent of the underlying execution engine.
- Exists in three forms: parsed logical plan, analyzed logical plan, and optimized logical plan.
- Parsed logical plan: the raw tree from parsing SQL or building DataFrame operations. Column names and types are unresolved.
- Analyzed logical plan: the Analyzer resolves table names, column names, data types, and functions using the catalog. It validates the query.
- Optimized logical plan: rule-based and cost-based optimizations are applied. Predicate pushdown, column pruning, constant folding, and join reordering happen here.
- You can inspect it with `explain(True)`. The first three plans shown are the parsed, analyzed, and optimized logical plans.

**Physical Plan**

- Represents the actual execution strategy.
- Specifies physical operators such as `FileScan`, `Filter`, `Project`, `HashAggregate`, `SortMergeJoin`, `BroadcastHashJoin`, `ShuffledHashJoin`, `Exchange`, `Sort`, and `WholeStageCodegen`.
- Includes partitioning and ordering information. For example, `Exchange hashpartitioning(key, 200)` indicates a hash shuffle on `key` into 200 partitions.
- Is chosen by the physical planner from one or more candidate plans. Cost-based optimization may compare plans using statistics.
- Is what actually runs as Spark jobs and stages.
- May be divided into code-generated stages marked with `*(n)`. Whole-stage code generation fuses operators into a single Java function.
- You can inspect it with `explain(True)`. The last plan shown is the physical plan.

**Key Differences**

Purpose: Logical plan says what to compute. Physical plan says how to compute it.

Operators: Logical plan uses logical operators like `Join`, `Filter`, `Aggregate`. Physical plan uses physical operators like `BroadcastHashJoin`, `SortMergeJoin`, `HashAggregate`, `Exchange`.

Execution details: Logical plan does not include partitioning, sorting, or join strategy. Physical plan includes these details.

Optimization: Logical plan is optimized by rule-based and cost-based transformations. Physical plan is the result of physical planning and cost-based selection.

Dependency: Logical plan is independent of the execution engine. Physical plan is specific to Spark's execution engine and Tungsten.

Code generation: Physical plan may be compiled into bytecode using whole-stage code generation. Logical plan is not code-generated.

**Example**

```python
df1 = spark.range(100).selectExpr("id as key", "id as a")
df2 = spark.range(1000).selectExpr("id as key", "id as b")
joined = df1.join(df2, "key")
joined.explain(True)
```

The output shows four plans. The parsed logical plan shows an unresolved `Join`. The analyzed logical plan resolves `key`, `a`, and `b`. The optimized logical plan may push filters or prune columns. The physical plan shows the chosen join strategy. If `df2` is small, it may show `BroadcastHashJoin`. If both are large, it may show `SortMergeJoin` with `Exchange hashpartitioning(key, 200)` and `Sort` nodes.

**Why this matters**

Understanding the difference helps you read `explain(True)` output and diagnose performance issues. If you see a `SortMergeJoin` when you expected a `BroadcastHashJoin`, you can check statistics, broadcast thresholds, or hints. If you see an unnecessary `Exchange`, you can look for ways to avoid a shuffle. If you see `*(1)` code-generated stages, whole-stage code generation is active.

**Summary**

A logical plan describes what to compute using logical operators and is optimized in multiple phases. A physical plan describes how to compute it using physical operators, partitioning, and ordering. Logical plans are declarative and engine-independent. Physical plans are operational and engine-specific. Spark SQL transforms a logical plan into a physical plan through analysis, logical optimization, physical planning, and code generation. You can view all phases with `explain(True)`.
