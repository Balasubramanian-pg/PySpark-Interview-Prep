# 3.6.1 What is the Catalyst Optimizer and what are its main phases?

The Catalyst Optimizer is the query optimization framework in Spark SQL. It transforms a user's query into an optimized physical plan through a series of rule-based and cost-based transformations. It is extensible, meaning you can add custom optimization rules. Catalyst powers DataFrame, Dataset, and SQL execution in Spark.

Catalyst operates in four main phases: analysis, logical optimization, physical planning, and code generation. Cost-based optimization is part of physical planning and join reordering.

**Phase 1: Analysis**

The query is parsed into an unresolved logical plan. The Analyzer resolves column names, data types, table references, and functions using the catalog. It produces a resolved logical plan. If a name cannot be resolved, it throws an `AnalysisException`.

Responsibilities:
- Resolve table names and column names.
- Resolve data types and casts.
- Resolve functions and operators.
- Validate semantic correctness.
- Expand views and handle special cases like null propagation.

**Phase 2: Logical Optimization**

A set of rule-based optimizations is applied to the resolved logical plan. The result is an optimized logical plan. Common rules include predicate pushdown, column pruning, constant folding, boolean expression simplification, and join reordering (when CBO is enabled).

Common optimization rules:
- Predicate pushdown: moves filters closer to the data source.
- Column pruning: removes unused columns.
- Constant folding: evaluates constant expressions at compile time.
- Boolean expression simplification: simplifies conditions like `a AND true`.
- Limit pushdown: pushes `LIMIT` closer to the source.
- Aggregate pushdown: pushes partial aggregations closer to the source.
- Join reordering: reorders joins to minimize intermediate result sizes (CBO).

**Phase 3: Physical Planning**

The optimized logical plan is converted into one or more physical plans. The planner uses strategies to choose physical operators. For example, a join might become a BroadcastHashJoin or a SortMergeJoin. Cost-based optimization may compare plans and choose the cheapest one based on statistics.

Key activities:
- Choose join strategies: broadcast hash join, shuffle hash join, sort-merge join.
- Insert Exchange nodes for shuffles.
- Insert Sort nodes where needed.
- Apply cost-based optimization if statistics are available.
- Select the final physical plan.

**Phase 4: Code Generation**

The selected physical plan is compiled into Java bytecode using whole-stage code generation. This eliminates virtual function calls and intermediate data structures, improving CPU efficiency. The generated code is compiled at runtime using Janino.

Whole-stage code generation:
- Fuses multiple operators into a single Java function.
- Avoids materializing intermediate rows.
- Improves CPU cache locality.
- Reduces overhead per row.

Operators with `*(n)` prefix in the physical plan are part of a code-generated stage.

**Viewing the phases**

You can see the output of each phase using `explain(True)`.

```python
df = spark.range(1000000).selectExpr("id as key", "id as value")
filtered = df.filter("key > 100")
filtered.explain(True)
```

The output shows the parsed, analyzed, optimized logical plans, and the physical plan.

**Example of a physical plan**

```python
df1 = spark.range(100).selectExpr("id as key", "id as a")
df2 = spark.range(1000).selectExpr("id as key", "id as b")
joined = df1.join(df2, "key")
joined.explain(True)
```

The physical plan shows the join strategy and any shuffles. Look for `BroadcastHashJoin` or `SortMergeJoin`, `Exchange`, and `*(n)` code-generated stages.

**Extensibility**

Catalyst is extensible. You can add custom optimization rules by extending `Rule[LogicalPlan]` and registering them with `spark.experimental.extraOptimizations`. This is advanced and rarely needed, but it shows the flexibility of the framework.

**Cost-based optimization**

Cost-based optimization (CBO) uses statistics about tables and columns to choose the cheapest physical plan. It is part of physical planning and is especially important for join ordering and join strategy selection. Statistics are collected with `ANALYZE TABLE` and stored in the metastore. CBO is controlled by `spark.sql.cbo.enabled` and `spark.sql.cbo.joinReorder.enabled`.

In summary, the Catalyst Optimizer is the query optimization framework in Spark SQL. Its main phases are analysis, logical optimization, physical planning, and code generation. Cost-based optimization is part of physical planning. Catalyst applies rule-based and cost-based transformations to produce an efficient physical plan. You can inspect each phase with `explain(True)`.
