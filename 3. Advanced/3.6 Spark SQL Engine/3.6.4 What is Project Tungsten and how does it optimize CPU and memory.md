### 3.6.4 What is Project Tungsten and how does it optimize CPU and memory

Project Tungsten is a set of improvements to Spark's execution engine that focus on CPU and memory efficiency. It was introduced in Spark 1.5 and is a core part of Spark SQL. Tungsten shifts Spark from relying on Java objects and the JVM object model to using compact binary data, cache-aware algorithms, and runtime code generation. The goal is to make Spark execution closer to the metal, reducing garbage collection overhead, memory footprint, and CPU instruction overhead.

Tungsten has three main components:

1. Memory management and binary processing
2. Cache-aware computation
3. Whole-stage code generation

Together, these components improve both CPU and memory performance. Tungsten is enabled by default. You can see its effects in physical plans with operators like `WholeStageCodegen` and the `*(n)` prefix.

**1. Memory management and binary processing**

Traditional Spark execution uses Java objects to represent rows. Each row is an object graph with many small objects, references, and headers. This consumes a lot of memory and creates heavy garbage collection pressure. Tungsten replaces Java objects with a compact binary format called `UnsafeRow`.

`UnsafeRow` stores data in a contiguous byte array using an offset-based layout. Each row has a null bitmap and fixed-length slots for fields. Variable-length fields store offsets and lengths. This representation:
- Reduces memory footprint because there is no per-object header or pointer overhead.
- Reduces GC pressure because fewer objects are allocated.
- Allows Spark to operate directly on serialized data, avoiding repeated serialization and deserialization.
- Enables efficient spilling and shuffling because binary data can be written and read back without conversion.

Tungsten also provides specialized memory structures such as `UnsafeExternalSorter`, `UnsafeShuffleWriter`, and `UnsafeRow`-based hash maps. These structures operate on off-heap memory or on-heap binary memory and are designed for cache efficiency.

Configuration:
```
spark.sql.tungsten.enabled=true          # default true
spark.memory.offHeap.enabled=true        # enable off-heap memory
spark.memory.offHeap.size=1g             # size of off-heap memory
```

**2. Cache-aware computation**

Modern CPUs are much faster than main memory. To achieve high throughput, algorithms must be cache-friendly. Tungsten uses algorithms and data structures that:
- Store data in contiguous memory rather than linked structures.
- Avoid pointer chasing, which causes cache misses.
- Process data in tight loops that fit in CPU caches.
- Use sort and hash algorithms designed for cache locality.

For example, Tungsten's sort implementation uses cache-efficient merge and quick sort variants. Its hash maps use open addressing and contiguous arrays instead of linked lists. These choices reduce cache misses and improve instruction-level parallelism.

**3. Whole-stage code generation**

Whole-stage code generation is the most visible Tungsten feature. It fuses multiple physical operators into a single Java function. Instead of executing each operator separately with virtual function calls and iterator chains, Spark generates specialized Java source code for the entire pipeline, compiles it at runtime using Janino, and executes the compiled function.

How it works:
- The physical plan is divided into stages. A stage is a sequence of operators that can be fused without a shuffle or exchange.
- For each stage, Spark generates Java code that processes rows in a tight loop.
- The generated code eliminates virtual function calls between operators.
- It avoids materializing intermediate rows.
- It improves CPU cache locality and reduces per-row overhead.

You can see whole-stage code generation in the physical plan. Operators with `*(n)` prefix are part of a code-generated stage. For example:

```python
df = spark.range(1000000).filter("id > 100").selectExpr("id * 2 as doubled")
df.explain(True)
```

The plan shows `*(1) Filter` and `*(1) Project` inside the same code-generated stage. The `*(1)` means the whole stage is code-generated.

Whole-stage code generation can be disabled with:
```
spark.sql.codegen.wholeStage=false
```
This is not recommended unless debugging.

**How Tungsten optimizes CPU**

- Eliminates virtual function calls between operators.
- Avoids creating intermediate rows and iterators.
- Generates specialized bytecode for the query.
- Uses cache-friendly algorithms and data structures.
- Reduces branching and pointer chasing.
- Processes data in tight loops that keep the CPU pipeline busy.
- Reduces serialization and deserialization overhead.

**How Tungsten optimizes memory**

- Uses compact binary representation (`UnsafeRow`) instead of Java objects.
- Reduces per-row memory overhead.
- Lowers garbage collection pressure and pause times.
- Enables off-heap memory usage to reduce JVM heap pressure.
- Supports efficient spilling and shuffling of binary data.
- Uses memory structures designed for cache locality and low overhead.

**Code examples**

Enabling Tungsten and off-heap memory:

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
         .appName("TungstenExample")
         .config("spark.sql.tungsten.enabled", "true")
         .config("spark.memory.offHeap.enabled", "true")
         .config("spark.memory.offHeap.size", "1g")
         .getOrCreate())
```

Viewing whole-stage code generation in the physical plan:

```python
df = spark.range(1000000).filter("id > 100").selectExpr("id * 2 as doubled")
df.explain(True)
```

Look for `WholeStageCodegen` and `*(1)` in the plan.

Disabling whole-stage code generation for debugging:

```python
spark.conf.set("spark.sql.codegen.wholeStage", "false")
df.explain(True)
```

After disabling, you will see separate operators without the `*(n)` prefix. This is slower but easier to read.

**Limitations and considerations**

- Not all operators are code-generated. Some operators, such as those involving Python UDFs, may break the code-generation pipeline and fall back to row-by-row processing.
- Python UDFs are a common cause of losing whole-stage code generation. Use built-in functions or Pandas UDFs where possible.
- Tungsten's binary format is internal. You do not interact with `UnsafeRow` directly unless writing custom physical operators.
- Off-heap memory requires explicit configuration and is not enabled by default.
- Whole-stage code generation has a compilation cost. For very short queries, the compilation overhead may not be worth it, but Spark caches generated code for repeated patterns.
- Tungsten is most beneficial for CPU-bound and memory-bound workloads, such as large scans, aggregations, joins, and sorts.

**Summary**

Project Tungsten is a set of execution engine improvements in Spark that optimize CPU and memory. It uses compact binary processing (`UnsafeRow`), cache-aware algorithms, and whole-stage code generation. These optimizations reduce memory footprint, lower garbage collection overhead, eliminate virtual function calls, and improve CPU cache locality. Tungsten is enabled by default and is a core reason why Spark SQL is fast. You can see its effects in physical plans through `WholeStageCodegen` and the `*(n)` prefix. To get the most benefit, avoid Python UDFs that break code generation, enable off-heap memory when appropriate, and use built-in functions and DataFrame operations.
