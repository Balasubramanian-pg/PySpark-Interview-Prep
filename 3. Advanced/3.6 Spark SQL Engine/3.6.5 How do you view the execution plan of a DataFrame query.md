### 3.6.5 How do you view the execution plan of a DataFrame query

You can view the execution plan of a DataFrame query using the `explain()` method. It prints the plan to the console without executing the query. Spark provides several explain modes that show different levels of detail, from a simple physical plan to the full parsed, analyzed, optimized logical plans, and generated code.

**Basic usage**

```python
df = spark.range(1000000).selectExpr("id as key", "id as value")
filtered = df.filter("key > 100")
filtered.explain()
```

By default, `explain()` prints only the physical plan. This is the plan that will actually run on the cluster. It shows physical operators such as `FileScan`, `Filter`, `Project`, `Exchange`, `HashAggregate`, `SortMergeJoin`, and `BroadcastHashJoin`. Operators with a `*(n)` prefix are part of a whole-stage code-generated stage.

**Extended mode**

`explain(True)` or `explain("extended")` prints four plans:

1. Parsed Logical Plan
2. Analyzed Logical Plan
3. Optimized Logical Plan
4. Physical Plan

```python
filtered.explain(True)
```

This is the most common mode for debugging. It shows how the query is transformed from raw syntax to an optimized physical plan. You can see predicate pushdown, column pruning, constant folding, join strategy selection, and shuffles.

**Simple mode**

`explain("simple")` prints only the physical plan, same as the default.

```python
filtered.explain("simple")
```

**Formatted mode**

`explain("formatted")` prints the physical plan in a more readable format with additional details such as join conditions, output columns, and partitioning. This is useful when the default physical plan is hard to read.

```python
filtered.explain("formatted")
```

**Cost mode**

`explain("cost")` prints the optimized logical plan with statistics and cost estimates. It requires statistics to be collected with `ANALYZE TABLE`. It shows estimated row counts, sizes, and costs for each operator.

```python
filtered.explain("cost")
```

**Codegen mode**

`explain("codegen")` prints the generated Java code for whole-stage code generation. This is useful for understanding how Tungsten compiles the query into bytecode. It is verbose and mainly for advanced debugging.

```python
filtered.explain("codegen")
```

**SQL EXPLAIN**

If you are using SQL, you can use the `EXPLAIN` statement.

```python
df.createOrReplaceTempView("my_table")

spark.sql("EXPLAIN SELECT * FROM my_table WHERE key > 100").show(truncate=False)
spark.sql("EXPLAIN EXTENDED SELECT * FROM my_table WHERE key > 100").show(truncate=False)
spark.sql("EXPLAIN COST SELECT * FROM my_table WHERE key > 100").show(truncate=False)
spark.sql("EXPLAIN CODEGEN SELECT * FROM my_table WHERE key > 100").show(truncate=False)
spark.sql("EXPLAIN FORMATTED SELECT * FROM my_table WHERE key > 100").show(truncate=False)
```

`EXPLAIN` is equivalent to `explain("simple")`. `EXPLAIN EXTENDED` is equivalent to `explain(True)`. `EXPLAIN COST` and `EXPLAIN CODEGEN` correspond to the cost and codegen modes.

**Viewing the plan in the Spark UI**

When a query runs, the Spark UI SQL tab shows the physical plan and per-operator metrics. Click on the query to see the DAG visualization and the plan. This is useful after the job has run because you can see actual row counts, shuffle sizes, and task durations.

**Accessing the plan programmatically**

In PySpark, you can access the physical plan as a string using the internal JVM object, but this is not recommended for production code.

```python
print(df._jdf.queryExecution().executedPlan().toString())
print(df._jdf.queryExecution().optimizedPlan().toString())
print(df._jdf.queryExecution().logical().toString())
```

In Scala, you can use `df.queryExecution` directly.

**Example: comparing plans**

```python
df1 = spark.range(100).selectExpr("id as key", "id as a")
df2 = spark.range(1000).selectExpr("id as key", "id as b")
joined = df1.join(df2, "key")

joined.explain(True)
```

The output shows the parsed, analyzed, optimized logical plans, and the physical plan. In the physical plan, look for the join strategy:

- `BroadcastHashJoin` if one side is small enough to broadcast.
- `SortMergeJoin` with `Exchange hashpartitioning(key, 200)` and `Sort` nodes if both sides are large.
- `ShuffledHashJoin` if shuffle hash join is chosen.

**Interpreting the physical plan**

Key elements to look for:

- `Exchange`: a shuffle. It shows the partitioning scheme and number of partitions, such as `Exchange hashpartitioning(key, 200)`.
- `Sort`: a sort operation, often used before a sort-merge join.
- `BroadcastHashJoin`: a broadcast join. The broadcast side is shown as `BroadcastExchange`.
- `SortMergeJoin`: a sort-merge join.
- `HashAggregate`: an aggregation. There may be two `HashAggregate` nodes separated by an `Exchange` for partial and final aggregation.
- `FileScan`: a scan of a file source. It shows `PushedFilters`, `PartitionFilters`, and `DataFilters`.
- `*(n)`: whole-stage code generation. All operators with the same `*(n)` prefix are fused into one code-generated stage.
- `AQEShuffleRead`: Adaptive Query Execution coalescing or skew handling.

**When to use which mode**

- Default `explain()`: quick look at the physical plan.
- `explain(True)`: full picture for debugging logical and physical plans.
- `explain("formatted")`: readable physical plan with more details.
- `explain("cost")`: cost-based optimization details, requires statistics.
- `explain("codegen")`: generated Java code, for advanced debugging.
- Spark UI SQL tab: after execution, to see actual metrics and task details.

**Summary**

To view the execution plan of a DataFrame query, use `df.explain()` for the physical plan, `df.explain(True)` for all logical and physical plans, and `df.explain("formatted")`, `df.explain("cost")`, or `df.explain("codegen")` for specialized views. In SQL, use `EXPLAIN`, `EXPLAIN EXTENDED`, `EXPLAIN COST`, `EXPLAIN CODEGEN`, and `EXPLAIN FORMATTED`. The Spark UI SQL tab shows the plan with runtime metrics after the query executes. These tools help you diagnose performance issues, verify optimizations, and understand how Spark executes your query.
