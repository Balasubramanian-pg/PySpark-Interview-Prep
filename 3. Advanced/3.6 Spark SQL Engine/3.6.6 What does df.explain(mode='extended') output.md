### 3.6.6 What does `df.explain(mode='extended')` output

`df.explain(mode='extended')`, or equivalently `df.explain(True)`, prints four plans to the console. It does not execute the query. It shows how Spark transforms the DataFrame from raw syntax into an optimized physical plan. The four plans are:

1. Parsed Logical Plan
2. Analyzed Logical Plan
3. Optimized Logical Plan
4. Physical Plan

Each plan represents a different stage of query processing in the Catalyst Optimizer.

**1. Parsed Logical Plan**

This is the raw tree produced by parsing the DataFrame operations or SQL text. It is unresolved. Column names, table names, and data types are not yet checked against the catalog. It shows logical operators such as `Project`, `Filter`, `Join`, `Aggregate`, and `Range`. If you wrote `df.filter("key > 100")`, the parsed plan shows a `Filter` node with the expression `(key > 100)` but does not know what `key` refers to or whether it is valid.

**2. Analyzed Logical Plan**

The Analyzer resolves the parsed plan using the catalog. It resolves table names, column names, data types, and functions. It validates that the query is semantically correct. If a column does not exist, it throws an `AnalysisException`. The analyzed plan shows resolved attributes with unique expression IDs, such as `key#10L` and `value#11L`. It also inserts implicit casts where needed. This plan is logically equivalent to the parsed plan but fully resolved.

**3. Optimized Logical Plan**

The Optimizer applies rule-based and cost-based transformations to the analyzed plan. This is where predicate pushdown, column pruning, constant folding, boolean expression simplification, limit pushdown, aggregate pushdown, and join reordering happen. The result is an optimized logical plan that is semantically equivalent to the analyzed plan but more efficient. For example, a filter on a Parquet file may be pushed into the `FileScan` node, and unused columns may be removed.

**4. Physical Plan**

The physical planner converts the optimized logical plan into one or more physical plans and chooses the best one. The physical plan specifies the actual execution strategy. It shows physical operators such as `FileScan`, `Filter`, `Project`, `HashAggregate`, `SortMergeJoin`, `BroadcastHashJoin`, `ShuffledHashJoin`, `Exchange`, `Sort`, and `WholeStageCodegen`. It includes partitioning and ordering information, such as `Exchange hashpartitioning(key, 200)`. Operators with a `*(n)` prefix are part of a whole-stage code-generated stage. The physical plan is what actually runs as Spark jobs and stages.

**Example**

```python
df = spark.range(1000000).selectExpr("id as key", "id as value")
filtered = df.filter("key > 100")
filtered.explain(mode="extended")
```

The output looks similar to this (abbreviated):

```
== Parsed Logical Plan ==
'Filter ('key > 100)
+- Project [id#0L AS key#2L, id#0L AS value#3L]
   +- Range (0, 1000000, step=1, splits=Some(8))

== Analyzed Logical Plan ==
key: bigint, value: bigint
Filter (key#2L > cast(100 as bigint))
+- Project [id#0L AS key#2L, id#0L AS value#3L]
   +- Range (0, 1000000, step=1, splits=Some(8))

== Optimized Logical Plan ==
Project [id#0L AS key#2L, id#0L AS value#3L]
+- Filter (id#0L > 100)
   +- Range (0, 1000000, step=1, splits=Some(8))

== Physical Plan ==
*(1) Project [id#0L AS key#2L, id#0L AS value#3L]
+- *(1) Filter (id#0L > 100)
   +- *(1) Range (0, 1000000, step=1, splits=8)
```

In this example, the optimized logical plan pushes the filter down and eliminates the separate `Project` for the filter. The physical plan shows whole-stage code generation with `*(1)`.

**How to use each plan**

Parsed logical plan: useful to see how Spark interpreted your syntax. It helps debug parsing errors or unexpected operator ordering.

Analyzed logical plan: useful to verify that column names and data types are resolved correctly. It helps debug `AnalysisException` errors such as "cannot resolve column".

Optimized logical plan: useful to see which optimizations were applied. Look for pushed filters, pruned columns, and simplified expressions. If an optimization did not happen, this plan shows why.

Physical plan: useful to see the actual execution strategy. Look for join strategies, shuffles, sorts, and code-generated stages. This is the plan to inspect for performance tuning.

**Other explain modes**

- `explain()` or `explain(mode='simple')`: prints only the physical plan.
- `explain(mode='extended')` or `explain(True)`: prints all four plans.
- `explain(mode='formatted')`: prints the physical plan in a more readable format with additional details.
- `explain(mode='cost')`: prints the optimized logical plan with statistics and cost estimates. Requires `ANALYZE TABLE` statistics.
- `explain(mode='codegen')`: prints the generated Java code for whole-stage code generation.

**SQL equivalent**

In SQL, `EXPLAIN EXTENDED SELECT ...` produces the same four plans.

```python
df.createOrReplaceTempView("my_table")
spark.sql("EXPLAIN EXTENDED SELECT * FROM my_table WHERE key > 100").show(truncate=False)
```

**Summary**

`df.explain(mode='extended')` outputs the parsed logical plan, analyzed logical plan, optimized logical plan, and physical plan. It does not execute the query. It is the most useful mode for debugging and understanding how Spark transforms a DataFrame query. Use it to verify that column resolution is correct, that optimizations like predicate pushdown and column pruning are applied, and that the physical plan uses the expected join strategies and partitioning. The physical plan is the final plan that runs on the cluster.
