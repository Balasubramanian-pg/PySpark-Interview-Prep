### 3.2.2 What is the difference between Narrow and Wide transformations?

In Spark, transformations are classified as narrow or wide based on how data moves between partitions. This classification determines whether a shuffle is required, how stages are formed, and how fault tolerance works.

Narrow transformation:

- Each input partition contributes to at most one output partition.
- No shuffle is required. Data stays within the same partition.
- Multiple narrow transformations can be pipelined together into a single stage.
- Fault tolerance is cheap. If a partition is lost, only the corresponding parent partition needs to be recomputed.
- Examples on RDDs: `map`, `filter`, `flatMap`, `mapPartitions`, `union`, `sample`, `coalesce` (without shuffle).
- Examples on DataFrames: `select`, `filter`, `withColumn`, `drop`, `union`, `limit`.

Wide transformation:

- Each input partition can contribute to multiple output partitions.
- Requires a shuffle. Data is redistributed across the network.
- Creates a stage boundary. The upstream stage writes shuffle data, and the downstream stage reads it.
- Fault tolerance is more expensive. If a partition is lost, multiple parent partitions may need to be recomputed.
- Examples on RDDs: `groupByKey`, `reduceByKey`, `join` (unless broadcast), `distinct`, `repartition`, `sortByKey`, `orderBy`.
- Examples on DataFrames: `groupBy`, `join` (unless broadcast), `distinct`, `repartition`, `orderBy`, `dropDuplicates`.

Key differences summarized:

Data movement: Narrow transformations move no data across partitions. Wide transformations shuffle data across the network.

Stage boundaries: Narrow transformations stay within a single stage. Wide transformations create a new stage.

Shuffle: Narrow transformations do not shuffle. Wide transformations always shuffle.

Cost: Narrow transformations are cheap and fast. Wide transformations are expensive due to network I/O, disk I/O, serialization, and sorting.

Fault recovery: Narrow transformations recover by recomputing a single parent partition. Wide transformations may require recomputing multiple parent partitions.

Code examples for narrow transformations:

```
rdd = sc.parallelize(range(100), 10)

# map and filter are narrow
rdd2 = rdd.map(lambda x: x * 2)
rdd3 = rdd2.filter(lambda x: x > 10)

# DataFrame narrow transformations
df2 = df.select("id", "amount")
df3 = df2.filter(df2.amount > 100)
df4 = df3.withColumn("tax", df3.amount * 0.1)
```

These operations can all be pipelined into one stage without a shuffle.

Code examples for wide transformations:

```
# groupByKey and reduceByKey are wide
grouped = rdd.groupByKey()
reduced = rdd.reduceByKey(lambda a, b: a + b)

# join is wide unless one side is broadcast
joined = df1.join(df2, "id")

# distinct and repartition are wide
distinct_df = df.distinct()
repart_df = df.repartition(100, "customer_id")

# orderBy is wide because it requires a global sort
sorted_df = df.orderBy("amount")
```

Each of these triggers a shuffle and a stage boundary.

Special cases:

- `coalesce()` without shuffle is narrow because it only merges existing partitions without moving data across the network. However, it can still create uneven partitions. `coalesce(n, shuffle=True)` becomes wide because it shuffles.
- `join` can be narrow if it is a broadcast join. In a broadcast join, the small table is broadcast to all executors, and the large table is not shuffled. This avoids a wide dependency for the large table.

Why this matters for performance:

Narrow transformations are preferred because they avoid the cost of shuffling. Wide transformations are unavoidable for operations like grouping and joining large datasets, but you can reduce their cost by broadcasting small tables, using bucketing, filtering early, and enabling Adaptive Query Execution (AQE).

In the Spark DAG, narrow dependencies allow pipelining and efficient recovery. Wide dependencies force a shuffle and are the main reason jobs become slow or fail due to memory pressure.
