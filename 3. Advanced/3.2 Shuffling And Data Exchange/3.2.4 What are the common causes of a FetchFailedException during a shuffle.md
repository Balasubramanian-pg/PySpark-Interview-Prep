### 3.2.4 What are the common causes of a FetchFailedException during a shuffle?

A `FetchFailedException` is thrown when a reduce task cannot fetch its shuffle data from a map task's executor. It tells you where the stage noticed damage, not necessarily where the damage began. The exception contains the BlockManagerId, shuffleId, mapId, and reduceId of the failed fetch. The root cause is almost always that the shuffle blocks are no longer available, typically because the executor holding them is lost, unresponsive, or under memory pressure.

**1. Executor or host lost**

This is the most common cause. When an executor is terminated, its shuffle data stored on local disk disappears. The producing executor may already be gone, its local file may be missing or corrupt, or the shuffle service may be unavailable. Common scenarios include:

- Cluster downsizing during an auto-scaling event before the shuffle data is read.
- Spot instance termination.
- An executor becoming unresponsive or running out of memory.
- Cluster manager (YARN, Kubernetes) killing the executor due to exceeding container memory limits.

**2. Executor memory pressure and GC pauses**

If an executor is heavily loaded and garbage collection is triggered, it cannot serve shuffle data to other executors, causing fetch failures. An `OutOfMemoryError` or prolonged GC pauses can make the executor unresponsive. The reduce side may also fail with `failed to allocate direct memory` when fetching many large shuffle blocks simultaneously.

**3. Network issues**

Network timeouts, connection resets, or a healthy server being unreachable long enough to exhaust the client's retries can cause fetch failures. The `spark.shuffle.io.maxRetries` parameter (default 3) controls how many times Spark retries a failed fetch. The maximum delay from retries is calculated as `maxRetries * retryWait`, defaulting to 15 seconds.

**4. Data skew**

When data is extremely skewed, a few reduce tasks pull much larger shuffle blocks than others. This can cause those tasks to fail with out-of-memory errors or direct memory allocation failures during the fetch. Salting the join key is often the only reliable solution for severe skew.

**5. External shuffle service issues**

If the external shuffle service crashes or restarts, it may lose its in-memory executor registration state, causing fetch failures for shuffle data that should still be available on disk. When using the external shuffle service, a `FetchFailedException` often means the service running on that host has become unavailable.

**6. Configuration issues**

- `spark.shuffle.io.maxRetries` set too low for large shuffles.
- `spark.reducer.maxReqsInFlight` too high, causing too many concurrent fetch requests and direct memory exhaustion.
- `spark.sql.shuffle.partitions` too low, creating oversized partitions that exceed memory during fetch.
- Netty direct buffer memory limits being exceeded when fetching many blocks simultaneously.

**How to diagnose**

Start with the driver log and record the shuffle ID, map ID, reduce ID, and block-manager address from the first fetch failure. Then look slightly earlier for an executor-removal message and its reason. If the executor disappeared first, investigate the executor exit, container event, or node health. If the executor remained registered, inspect its log for connection resets, timeouts, or file-not-found messages. In the Spark UI, sort the task table by Shuffle Read Fetch Wait Time and Shuffle Remote Reads to identify whether the bottleneck is I/O or memory pressure.

**Common fixes**

- Increase `spark.shuffle.io.maxRetries` for large shuffles.
- Enable the external shuffle service so executor GC does not affect shuffle serving.
- Increase shuffle partitions or enable AQE to coalesce partitions and handle skew.
- Reduce `spark.reducer.maxReqsInFlight` and disable Netty direct buffers if direct memory allocation fails.
- Broadcast small tables to avoid shuffling the large side in joins.
- Filter and select data early to reduce shuffle volume and memory pressure.
