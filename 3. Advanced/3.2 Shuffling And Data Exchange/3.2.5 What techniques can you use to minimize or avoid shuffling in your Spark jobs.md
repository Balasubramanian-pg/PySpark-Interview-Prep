### 3.2.5 What techniques can you use to minimize or avoid shuffling in your Spark jobs?

Shuffling is the most expensive operation in Spark. While some shuffles are unavoidable, such as grouping by a high-cardinality key or joining two large tables, you can significantly reduce their number, size, and cost. The following techniques help minimize or avoid shuffles.

**1. Use broadcast joins for small tables**

When one side of a join is small enough to fit in memory, broadcast it to all executors. This avoids shuffling the large side.

```
from pyspark.sql.functions import broadcast

result = large_df.join(broadcast(small_df), "customer_id")
```

Control the threshold with `spark.sql.autoBroadcastJoinThreshold` (default 10 MB). Set it to -1 to disable automatic broadcast.

```
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "20971520")  # 20 MB
```

**2. Filter and select early**

Apply filters and column pruning before joins and aggregations. Less data means smaller shuffles.

```
filtered = df.filter(df.date >= "2024-01-01").select("customer_id", "amount")
result = filtered.join(other, "customer_id")
```

**3. Use bucketing**

Bucket tables by the join key with the same number of buckets. This enables shuffle-free joins when both sides are bucketed and the metadata is available.

```
df.write
  .bucketBy(100, "customer_id")
  .sortBy("customer_id")
  .saveAsTable("orders_bucketed")
```

**4. Partition by low-cardinality filter columns**

Partitioning by columns used in `WHERE` clauses enables partition pruning, reducing the data read before a shuffle.

```
df.write.partitionBy("date", "country").parquet("/path/orders")
```

Avoid partitioning by high-cardinality columns like `customer_id`, which creates many small files.

**5. Prefer `reduceByKey` over `groupByKey` on RDDs**

`reduceByKey` performs map-side combining before the shuffle, reducing the amount of data transferred. `groupByKey` sends all values without combining.

```
# Good: map-side combine reduces shuffle data
rdd.reduceByKey(lambda a, b: a + b)

# Bad: no map-side combine, all values are shuffled
rdd.groupByKey().mapValues(sum)
```

**6. Use `aggregateByKey` or `combineByKey` for custom aggregations**

These also perform map-side combining.

```
rdd.aggregateByKey((0, 0),
    lambda acc, v: (acc[0] + v, acc[1] + 1),
    lambda acc1, acc2: (acc1[0] + acc2[0], acc1[1] + acc2[1])
)
```

**7. Avoid unnecessary `repartition` and `distinct`**

`repartition` always shuffles. Use it only when you need to increase partitions or need even distribution. `distinct` shuffles. If you only need to drop duplicates on a subset of columns, use `dropDuplicates` with those columns.

```
# Avoid if possible
df.repartition(100)
df.distinct()

# Better: use dropDuplicates on subset
df.dropDuplicates(["customer_id", "order_id"])
```

**8. Use `coalesce` instead of `repartition` when reducing partitions**

`coalesce` avoids a shuffle when decreasing the number of partitions.

```
# No shuffle
df_fewer = df.coalesce(10)

# Shuffle
df_even = df.repartition(10)
```

**9. Enable Adaptive Query Execution (AQE)**

AQE re-optimizes the plan at runtime. It coalesces shuffle partitions, switches join strategies, and handles skew, reducing the effective cost of shuffles.

```
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "134217728")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
```

**10. Tune shuffle partitions**

Set `spark.sql.shuffle.partitions` based on data size. Too many partitions create small tasks and many small shuffle blocks. Too few create large partitions and spills.

```
spark.conf.set("spark.sql.shuffle.partitions", "200")
```

**11. Use the DataFrame API and let the optimizer work**

The Catalyst optimizer automatically inserts partial aggregations and pushes filters down. Prefer DataFrame operations over RDDs when possible.

```
df.groupBy("customer_id").agg(sum("amount").alias("total"))
```

**12. Use window functions with partitioning**

Window functions that use `partitionBy` can avoid a full shuffle if the data is already partitioned correctly. However, they still require a shuffle if the partitioning changes.

```
from pyspark.sql.window import Window
from pyspark.sql.functions import row_number

window = Window.partitionBy("customer_id").orderBy("order_date")
df.withColumn("rn", row_number().over(window))
```

**13. Use `mapPartitions` for expensive setup**

If you need to initialize a resource per partition, `mapPartitions` avoids repeated setup per row. This does not reduce shuffle but improves overall performance.

```
def process_partition(iterator):
    # setup once per partition
    for row in iterator:
        yield row

rdd.mapPartitions(process_partition)
```

**14. Use columnar formats and compression**

Parquet and ORC reduce I/O before and after shuffles. Enable shuffle compression.

```
spark.conf.set("spark.shuffle.compress", "true")
spark.conf.set("spark.shuffle.spill.compress", "true")
```

**15. Avoid `distinct` when possible**

`distinct` shuffles. If you only need unique values on a subset of columns, use `dropDuplicates` with those columns, or combine with other operations.

```
# Instead of distinct on all columns
df.select("customer_id").distinct()

# Use groupBy
df.groupBy("customer_id").count()
```

**16. Pre-partition or pre-bucket data**

If you control the data layout, write tables partitioned or bucketed by commonly used keys. This avoids shuffles in downstream joins and aggregations.

```
df.write
  .partitionBy("date")
  .bucketBy(100, "customer_id")
  .sortBy("customer_id")
  .saveAsTable("orders")
```

**17. Use caching to avoid recomputation**

If a shuffled DataFrame is used multiple times, cache it to avoid recomputing the shuffle.

```
df.cache()
df.count()  # materialize
```

**18. Handle skew with salting**

Skew causes a few reducers to do most of the work. Salting spreads hot keys across multiple partitions. This adds a shuffle but prevents failures and long tails.

```
from pyspark.sql.functions import rand, floor, concat, lit

salt_range = 10
large_salted = large_df.withColumn(
    "salted_key", concat(large_df.customer_id, lit("_"), floor(rand() * salt_range))
)
```

**19. Use join hints**

You can force a broadcast join or a sort-merge join with hints.

```
from pyspark.sql.functions import broadcast
large_df.join(broadcast(small_df), "customer_id")

# Or use SQL hint
spark.sql("SELECT /*+ BROADCAST(small) */ * FROM large JOIN small ON large.id = small.id")
```

**20. Avoid Cartesian products**

Cross joins without a condition can explode in size and cause massive shuffles. Avoid them unless necessary.

```
# Avoid
df1.crossJoin(df2)

# Better: use a proper join condition
df1.join(df2, df1.id == df2.id)
```

In summary, minimize shuffles by broadcasting small tables, filtering early, using bucketing and partitioning, preferring map-side combining, avoiding unnecessary repartitioning, enabling AQE, tuning shuffle partitions, and using the DataFrame optimizer. Some shuffles are unavoidable, but you can often reduce their size and cost.
