# 3.5.3 What is Salting and how does it solve skewness during joins?

Salting is a technique to distribute a hot key across multiple partitions by adding a random suffix (called salt) to the key. This breaks the hot key into many smaller keys, each going to a different partition. When joining, the other side must be replicated for each salt value so that matching rows can still be found. Salting converts one large skewed partition into many smaller partitions that can be processed in parallel.

Why salting is needed:

During a shuffle join, all rows with the same join key go to the same partition. If one key has millions of rows and others have a few, one reducer processes almost all the data while the rest sit idle. This creates a long tail of slow tasks, memory pressure, spills, and sometimes out-of-memory errors. Increasing the number of shuffle partitions does not help because the hash function still sends all rows with the same key to the same partition. Salting changes the key itself so that the hot key is split across multiple partitions.

How salting works for a join:

1. Choose a salt range, for example 0 to 9 (10 salts).
2. On the large table, add a new column `salt` with a random integer in the salt range. Then create a `salted_key` by concatenating the original join key with the salt.
3. On the small table, replicate each row for every salt value. Create the same `salted_key` by concatenating the original join key with each salt value.
4. Join the two tables on `salted_key`.
5. After the join, drop the salt column and any duplicates that may have been introduced.

Because the large table's hot key is now split into 10 different salted keys, the data is distributed across 10 partitions instead of one. The small table is replicated 10 times, but since it is small, this is cheap. The join on `salted_key` produces the same result as joining on the original key, because every row from the large table still matches its corresponding row from the small table through the salted key.

Example in PySpark:

```python
from pyspark.sql.functions import rand, floor, concat, lit, explode, array, col

salt_range = 10

# Large table: add salt
large_salted = large_df.withColumn(
    "salt", floor(rand() * salt_range)
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

# Small table: replicate for each salt
small_replicated = small_df.withColumn(
    "salt", explode(array([lit(i) for i in range(salt_range)]))
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

# Join on salted key
joined = large_salted.join(small_replicated, "salted_key")

# Clean up: drop salt and salted_key
result = joined.drop("salt", "salted_key")
```

Step-by-step explanation of the code:

- `floor(rand() * salt_range)` generates a random integer from 0 to salt_range - 1 for each row in the large table.
- `concat(col("join_key"), lit("_"), col("salt"))` creates the salted key, for example `"US_3"` instead of `"US"`.
- `explode(array([lit(i) for i in range(salt_range)]))` creates one row for each salt value for every row in the small table. If the small table has 100 rows and salt_range is 10, the replicated small table has 1000 rows.
- The join on `salted_key` matches `"US_3"` from the large table with `"US_3"` from the small table.
- After the join, drop the salt and salted_key columns to get back the original schema.

How salting solves skewness:

Without salting, all rows with key `"US"` go to one partition. If `"US"` has 10 million rows, that partition is huge. With salting and salt_range = 10, the rows are split into 10 keys: `"US_0"`, `"US_1"`, ..., `"US_9"`. Each of these goes to a different partition, so the 10 million rows are spread across 10 partitions of 1 million rows each. The work is now parallelized. The small table is replicated 10 times, but since it is small, the cost is negligible.

Choosing the salt range:

The salt range should be chosen based on the severity of the skew and the available cluster resources. A common starting point is 10 to 100. If the hot key has 100 million rows and you use salt_range = 10, each salted partition still has 10 million rows, which may still be too large. In that case, increase the salt range to 100 or 1000. The trade-off is that a larger salt range replicates the small table more times, increasing the size of the replicated side. Choose the smallest salt range that makes the skewed partitions small enough to process efficiently.

A rule of thumb: salt_range should be approximately the ratio of the hot key's row count to the average partition size. For example, if the hot key has 100 million rows and you want each partition to have at most 1 million rows, use salt_range = 100.

Salting for aggregations:

For groupBy operations, salting works differently. You salt the key, perform a partial aggregation, then remove the salt and perform a final aggregation. This is called two-phase aggregation.

```python
from pyspark.sql.functions import rand, floor, sum

# Add salt
salted = df.withColumn("salt", floor(rand() * 10))

# Partial aggregation with salted key
partial = salted.groupBy("key", "salt").agg(sum("value").alias("partial_sum"))

# Final aggregation without salt
final = partial.groupBy("key").agg(sum("partial_sum").alias("total"))
```

In the first phase, the hot key is split into 10 salted keys, so the partial aggregation is distributed across 10 partitions. In the second phase, the partial sums are combined into the final result. The second phase is much smaller because it only processes the partial sums, not the original rows.

Salting for joins with outer joins:

For inner joins, salting works as described. For left outer joins, you need to be careful because rows in the large table that do not match any row in the small table should still appear in the output with nulls. If you replicate the small table, a row from the large table with salted key `"US_3"` will not match any small table row if `"US"` does not exist in the small table. But because you replicated the small table for all salt values, if `"US"` exists, it will have a row for salt 3. If `"US"` does not exist, no salt value will match, and the left outer join will correctly produce nulls. So salting works for left outer joins as long as the small table is replicated for all salt values.

For full outer joins, salting is more complex because you need to handle rows from both sides that do not match. In practice, full outer joins with salting are rarely used. Consider alternative approaches such as splitting the join into left outer and right anti joins, or using AQE skew join.

Limitations of salting:

- It adds overhead: the small table is replicated salt_range times, and the large table gets an extra column and a shuffle.
- It only helps if the skew is caused by a few hot keys. If the data is uniformly distributed but partitions are too large, increasing the number of shuffle partitions is a better solution.
- It requires knowing which keys are hot. If you salt all keys, you add overhead without benefit. Salt only the hot keys.
- It complicates the query. You need to add salt, replicate, join, and clean up. This makes the code harder to read and maintain.
- It may not work well with all join types, especially full outer joins.

Alternatives to salting:

- Broadcast the small side: If one side is small, broadcast it to avoid shuffling the large side. This eliminates the shuffle skew for the large side.
- Enable AQE skew join: AQE automatically splits skewed partitions and replicates the matching side. This is easier than manual salting and works for inner and outer joins.
- Isolate skewed keys: Process the hot keys separately with a broadcast join or a dedicated job, and union the results with the rest.
- Use bucketing: Bucketing by the join key with a sufficient number of buckets can distribute data more evenly.

In summary, salting solves skewness during joins by adding a random suffix to the hot key, splitting it across multiple partitions. The other side of the join is replicated for each salt value so that matching rows can still be found. Salting converts one large skewed partition into many smaller partitions that can be processed in parallel. It is effective for inner and left outer joins, but adds overhead and complexity. Use it when the skew is severe and other techniques like broadcast joins or AQE are not sufficient.
