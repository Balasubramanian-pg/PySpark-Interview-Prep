# 3.5.5 How does isolating the skewed key and processing it separately help?

Isolating the skewed key means splitting the data into two parts: the rows whose join or group key is a hot key, and the rows with all other keys. You process the hot-key part with a technique that handles skew well, process the normal part with a standard shuffle join or aggregation, and then union the results. This avoids sending all rows for the hot key through a single reducer during the main shuffle, which eliminates the long tail and reduces memory pressure.

Why isolating the skewed key helps:

- Avoids a single reducer bottleneck: In a normal shuffle join or groupBy, all rows with the same key go to the same partition. If one key is extremely frequent, one reducer processes almost all the data while others sit idle. By isolating that key, you handle it separately, so the main shuffle only distributes the remaining, evenly spread keys.

- Allows a tailored strategy for the hot key: The hot-key subset is usually much smaller than the full dataset. You can broadcast the small side for that subset, or apply salting only to the hot key, or use a different join type. The normal part does not need those special treatments, so it runs efficiently with standard shuffle partitioning.

- Reduces memory pressure and spills: The hot-key partition in a normal join can be enormous, causing spills or out-of-memory errors. When you isolate it, you can process it in smaller chunks, or with a broadcast join that does not require shuffling the large side. The normal part has balanced partitions and fits comfortably in memory.

- Improves overall runtime: The main shuffle processes fewer rows and fewer bytes because the hot key is removed. The hot-key job runs in parallel and can be optimized separately. The union of the two results is cheap because both parts are already computed.

- Enables AQE or manual salting on a smaller dataset: If you want to salt the hot key, salting the entire dataset adds overhead for all keys. Isolating the hot key lets you apply salting or AQE skew join only where it is needed.

- Works for both joins and aggregations: For joins, you can broadcast the small side for the hot-key subset. For aggregations, you can perform a two-phase aggregation on the hot key while the normal keys use a standard groupBy.

Example for a skewed join:

Suppose `large_df` is skewed on `join_key = "US"`, and `small_df` is a dimension table. You split `large_df` into `hot_df` (where `join_key = "US"`) and `normal_df` (all other keys). Then:

- Process `hot_df` with a broadcast join against `small_df` (since the hot subset is now smaller and the small table can be broadcast).
- Process `normal_df` with a standard sort-merge join against `small_df`.
- Union the two results.

```python
from pyspark.sql.functions import col, broadcast

hot_key = "US"

hot_df = large_df.filter(col("join_key") == hot_key)
normal_df = large_df.filter(col("join_key") != hot_key)

# Process hot keys with broadcast join
hot_result = hot_df.join(broadcast(small_df), on="join_key", how="inner")

# Process normal keys with regular join
normal_result = normal_df.join(small_df, on="join_key", how="inner")

# Union the results
final_result = hot_result.union(normal_result)
```

If there are multiple hot keys, you can either isolate them one by one or filter them into a single `hot_df` using `isin`.

```python
hot_keys = ["US", "NULL", "unknown"]
hot_df = large_df.filter(col("join_key").isin(hot_keys))
normal_df = large_df.filter(~col("join_key").isin(hot_keys))
```

For a left outer join, the same approach works. The hot-key subset is joined with the small table using a left outer join, and the normal subset is joined with a standard left outer join. Union preserves the semantics.

Example for a skewed aggregation:

Suppose you have a `groupBy("key")` and `key = "US"` is hot. You can isolate the hot key, aggregate it separately with a two-phase aggregation (salting), and aggregate the normal keys with a standard groupBy. Then union.

```python
from pyspark.sql.functions import rand, floor, sum, col

hot_key = "US"

hot_df = df.filter(col("key") == hot_key)
normal_df = df.filter(col("key") != hot_key)

# Hot key: two-phase aggregation with salting
salt_range = 10
hot_salted = hot_df.withColumn("salt", floor(rand() * salt_range).cast("int"))
hot_partial = hot_salted.groupBy("key", "salt").agg(sum("value").alias("partial_sum"))
hot_final = hot_partial.groupBy("key").agg(sum("partial_sum").alias("total"))

# Normal keys: standard aggregation
normal_final = normal_df.groupBy("key").agg(sum("value").alias("total"))

# Union
final_result = hot_final.union(normal_final)
```

If the hot key is not the only skewed key, you can isolate multiple hot keys into one `hot_df` and process them together. For example, if both `"US"` and `"NULL"` are hot, put them in the same `hot_df` and apply salting or broadcast join to that subset.

When to use isolation:

- When one or a few keys dominate the data distribution, and the rest of the keys are evenly distributed.
- When the hot-key subset is small enough to process with a broadcast join or a two-phase aggregation.
- When salting the entire dataset would add too much overhead, but salting only the hot key is acceptable.
- When AQE skew join is not available or does not fully resolve the skew.

Limitations:

- You need to know which keys are hot. You can find them by running a key frequency count.
- The hot-key subset must be small enough to process efficiently. If the hot key contains most of the data, isolating it does not help much because the hot subset is still large. In that case, salting or AQE skew join is more appropriate.
- You add extra jobs and unions. For a small number of hot keys, this overhead is negligible compared to the savings from avoiding the long tail.
- The union of the two results may still require a shuffle if the output needs to be sorted or repartitioned. But the heavy join or aggregation work is already done.

Comparison with salting:

Salting modifies the key for the entire dataset and replicates the small side. Isolation splits the dataset and applies different strategies to each part. Isolation is often simpler and avoids replicating the small table for all keys. It is particularly effective when the hot key is a single value and you can broadcast the small side for that subset. Salting is more general and works when there are many hot keys or when the hot key cannot be easily isolated.

In summary, isolating the skewed key and processing it separately helps by removing the hot key from the main shuffle, allowing a tailored strategy for the hot subset, reducing memory pressure, and improving overall runtime. It is a practical technique for both joins and aggregations when the skew is caused by a few dominant keys. Use it when the hot-key subset is manageable and you can process it with a broadcast join, salting, or two-phase aggregation.
