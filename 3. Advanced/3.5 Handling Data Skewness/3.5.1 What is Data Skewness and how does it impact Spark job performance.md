### 3.5.1 What is Data Skewness and how does it impact Spark job performance

Data skewness is the uneven distribution of data across partitions in a distributed dataset. In an ideal Spark job, each partition contains roughly the same amount of data, so all tasks finish in about the same time. With skew, one or a few partitions contain far more data than others. Because Spark processes one partition per task, the tasks handling the large partitions take much longer, while tasks handling small partitions finish quickly and their executors sit idle. The overall job runtime is determined by the slowest task, so skew creates a long tail that dominates execution time.

Skew can occur in any operation that repartitions data by key, such as joins, groupBy, distinct, reduceByKey, and repartition. It is most common when the join or grouping key has a few very frequent values. For example, if 90 percent of rows have `country = "US"`, then a `groupBy("country")` sends almost all data to one partition. That partition becomes a bottleneck.

Common causes of skew:

- Hot keys in joins, such as a popular customer ID or a default value.
- Null values in the join or group key. All nulls hash to the same partition.
- Placeholder values like -1, 0, "unknown", or "N/A" used for missing data.
- Grouping by a low-cardinality column such as status, country, or category.
- Repartitioning on a skewed column.
- Natural power-law distributions in web logs, sales, or event data.

How skew impacts Spark job performance:

1. Long tail and increased runtime:
   A few tasks process much more data than others. The stage cannot finish until these stragglers complete. In the Spark UI, you see task durations that are highly uneven. The median task may finish in seconds, while the maximum task takes minutes or hours.

2. Memory pressure and out-of-memory errors:
   A skewed partition may be too large to fit in executor memory. This causes spills to disk, long garbage collection pauses, or `OutOfMemoryError`. In joins, the skewed side may need to build a hash map or buffer duplicate keys, which can exceed memory.

3. Shuffle overhead:
   Skewed keys produce large shuffle blocks. These blocks take longer to write, transfer, and read. They also increase network congestion and disk I/O. Fetch failures can occur if a reducer cannot retrieve a large block in time.

4. Wasted cluster resources:
   While a few executors are busy processing skewed partitions, most executors are idle. CPU, memory, and network resources are underutilized, so the cluster is not working at full capacity.

5. Spills and disk I/O:
   Skewed tasks often spill intermediate data to disk because they cannot hold it in memory. This adds significant disk I/O and slows down the task further.

6. Job failures and retries:
   Severe skew can cause executor OOM, fetch failures, or stage retries. In the worst case, the job fails repeatedly and may never complete without intervention.

7. Skewed aggregations:
   In groupBy operations, a hot key means one reducer performs most of the aggregation. If the aggregation requires holding state for many keys, that reducer may run out of memory.

8. Skewed joins:
   In sort-merge joins, the reducer buffers all rows for a duplicate key from one side. If a key appears millions of times, the buffer grows large and may spill or fail. In shuffle hash joins, the hash map for the hot key may not fit in memory.

How to detect skew:

- Spark UI Stages tab: Look at the task duration distribution. If a few tasks are much slower than the median, you have skew.
- Shuffle read size: Sort tasks by shuffle read size. A few tasks reading much more data indicate skew.
- Spill metrics: Check Spill (Memory) and Spill (Disk) columns. Skewed tasks often spill heavily.
- Executor memory: Look for executors with high GC time or OOM errors.
- Key distribution: Run a query to count the frequency of each key.

Example of detecting skew by key distribution:

```python
from pyspark.sql.functions import col, count

key_counts = df.groupBy("join_key").agg(count("*").alias("cnt"))
key_counts.orderBy(col("cnt").desc()).show(10)

total = df.count()
top_keys = key_counts.orderBy(col("cnt").desc()).limit(5).collect()
for row in top_keys:
    print(f"Key {row['join_key']}: {row['cnt']} rows ({row['cnt']/total*100:.2f}%)")
```

Example of detecting skew by partition size:

```python
from pyspark.sql.functions import spark_partition_id, count

df.withColumn("partition_id", spark_partition_id()) \
  .groupBy("partition_id") \
  .agg(count("*").alias("row_count")) \
  .orderBy("row_count", ascending=False) \
  .show()
```

If a few partitions have much larger row counts, the data is skewed.

How to handle skew (brief overview):

- Salting the key: Add a random suffix to the hot key to spread it across multiple partitions. Replicate the other side for each salt value. After the join, remove the salt.
- Broadcast the small side: If one side of a join is small, broadcast it to avoid shuffling the large side.
- Enable Adaptive Query Execution (AQE) skew join: AQE can automatically split skewed partitions and replicate the matching side.
- Isolate skewed keys: Process hot keys separately with a broadcast join or a dedicated job, and union the results.
- Two-phase aggregation: For groupBy, perform a partial aggregation with a salted key, then a final aggregation without the salt.
- Increase shuffle partitions: This can help if the key is not extremely hot, but it does not solve true skew.
- Filter nulls and default values: Remove or handle them separately to avoid hot partitions.

Example of salting for a join:

```python
from pyspark.sql.functions import rand, floor, concat, lit, explode, array, col

salt_range = 10

large_salted = large_df.withColumn(
    "salt", floor(rand() * salt_range)
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

small_replicated = small_df.withColumn(
    "salt", explode(array([lit(i) for i in range(salt_range)]))
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

joined = large_salted.join(small_replicated, "salted_key")
result = joined.drop("salt", "salted_key")
```

Example of two-phase aggregation:

```python
from pyspark.sql.functions import rand, floor, sum

salted = df.withColumn("salt", floor(rand() * 10))
partial = salted.groupBy("key", "salt").agg(sum("value").alias("partial_sum"))
final = partial.groupBy("key").agg(sum("partial_sum").alias("total"))
```

In summary, data skewness is the uneven distribution of data across partitions. It causes a long tail of slow tasks, memory pressure, spills, shuffle overhead, wasted resources, and sometimes job failures. Detecting skew through the Spark UI and key distribution analysis is the first step. Handling it with salting, broadcast joins, AQE, and two-phase aggregation can significantly improve performance and stability.
