### 3.5.4 Write a PySpark pseudo-code to salt a skewed join

**Answer:**

Salting a skewed join means adding a random suffix (salt) to the join key on the large table, replicating the small table for each salt value, joining on the salted key, and then cleaning up the salt. This distributes the hot key across multiple partitions, so no single reducer processes all the rows for that key. The following pseudo-code demonstrates the technique for an inner join, followed by notes for left outer joins and aggregation.

Assume you have two DataFrames:

- `large_df`: the large, skewed table.
- `small_df`: the small table to join with.
- Join key column: `join_key`.
- Salt range: an integer, for example 10.

**Step 1: Choose a salt range**

The salt range determines how many pieces the hot key is split into. A larger range spreads the hot key more but replicates the small table more times. Start with 10 to 100. If the hot key still produces partitions that are too large, increase the range.

```python
salt_range = 10
```

**Step 2: Add salt to the large table**

Generate a random integer from 0 to salt_range - 1 for each row. Concatenate the original join key with the salt to form `salted_key`.

```python
from pyspark.sql.functions import rand, floor, concat, lit, col

large_salted = large_df.withColumn(
    "salt", floor(rand() * salt_range).cast("int")
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)
```

**Step 3: Replicate the small table for each salt value**

For each row in the small table, create one row per salt value. This ensures that every salted key from the large table can find its match.

```python
from pyspark.sql.functions import explode, array

small_replicated = small_df.withColumn(
    "salt", explode(array([lit(i) for i in range(salt_range)]))
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)
```

**Step 4: Join on the salted key**

Perform the join using `salted_key` instead of the original `join_key`. This is the actual shuffled join that now benefits from the salt distribution.

```python
joined = large_salted.join(small_replicated, on="salted_key", how="inner")
```

**Step 5: Clean up the salt columns**

Drop the `salt` and `salted_key` columns to restore the original schema. If the small table had columns with the same names as the large table, you may need to rename or drop duplicates.

```python
result = joined.drop("salt", "salted_key")
```

If the small table also had a `salt` column, drop it explicitly:

```python
result = joined.drop("salt", "salted_key", small_df["salt"])
```

**Complete inner join example**

```python
from pyspark.sql.functions import rand, floor, concat, lit, col, explode, array

salt_range = 10

# Large table: add salt
large_salted = large_df.withColumn(
    "salt", floor(rand() * salt_range).cast("int")
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

# Small table: replicate for each salt
small_replicated = small_df.withColumn(
    "salt", explode(array([lit(i) for i in range(salt_range)]))
).withColumn(
    "salted_key", concat(col("join_key"), lit("_"), col("salt"))
)

# Join on salted key
joined = large_salted.join(small_replicated, on="salted_key", how="inner")

# Clean up
result = joined.drop("salt", "salted_key")
```

**Left outer join variation**

For a left outer join where `large_df` is the left side, the same salting approach works. The small table is replicated for all salt values. If a `join_key` exists in `large_df` but not in `small_df`, then for every salt value, the large row will have a `salted_key` that does not match any small row. The left outer join will produce nulls for the small table columns, which is the correct behavior.

```python
joined = large_salted.join(small_replicated, on="salted_key", how="left_outer")
result = joined.drop("salt", "salted_key")
```

For a right outer join, swap the roles: salt the large table, replicate the small table, and use `how="right_outer"`. For a full outer join, salting is more complex because you need to handle unmatched rows from both sides. In practice, consider using AQE skew join or splitting the join into left outer and right anti joins.

**Salting for aggregations**

Salting also works for `groupBy` on a skewed key. Use a two-phase aggregation: first aggregate with the salted key, then aggregate again to remove the salt.

```python
from pyspark.sql.functions import rand, floor, sum

salt_range = 10

# Phase 1: add salt and partially aggregate
salted = df.withColumn("salt", floor(rand() * salt_range).cast("int"))
partial = salted.groupBy("join_key", "salt").agg(sum("value").alias("partial_sum"))

# Phase 2: final aggregation
final = partial.groupBy("join_key").agg(sum("partial_sum").alias("total"))
```

**Choosing the salt range**

The salt range should be large enough to split the hot key into partitions that fit comfortably in memory, but not so large that the small table replication becomes expensive. A common heuristic:

```
salt_range = ceil(hot_key_row_count / target_rows_per_partition)
```

For example, if the hot key has 100 million rows and you want at most 1 million rows per partition, use `salt_range = 100`. Start with 10 and increase if you still see long tasks.

**Important considerations**

- Salt only the hot keys, not all keys. Salting all keys adds overhead without benefit. You can filter the large table into hot and normal parts, salt only the hot part, and union the results.
- The small table must be replicated for every salt value. If the small table is not small, replication can become expensive. In that case, consider broadcasting the small table instead of salting.
- After the join, drop the salt columns to avoid polluting the output schema.
- Salting adds an extra shuffle and an extra column. It is a trade-off: you pay some overhead to eliminate the long tail caused by skew.
- Adaptive Query Execution (AQE) can handle skew automatically in Spark 3.x. Enable `spark.sql.adaptive.skewJoin.enabled=true` before resorting to manual salting.

**When to use salting**

Use salting when:

- A join or aggregation is skewed due to a few hot keys.
- The small side of the join can be replicated without excessive cost.
- Broadcast join is not possible because the small side is too large to broadcast.
- AQE skew join is not available or does not fully resolve the skew.

Avoid salting when:

- The data is uniformly distributed but partitions are simply too large. Increase shuffle partitions instead.
- The small side is too large to replicate many times. Use broadcast or sort-merge join with AQE.
- The join is a full outer join. Salting is complex for full outer joins.

In summary, salting a skewed join in PySpark involves adding a random salt to the large table's join key, replicating the small table for each salt value, joining on the salted key, and cleaning up. This distributes the hot key across multiple partitions and eliminates the long tail. Use it selectively for severe skew when other techniques are insufficient.
