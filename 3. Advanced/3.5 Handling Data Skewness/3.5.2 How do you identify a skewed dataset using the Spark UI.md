### 3.5.2 How do you identify a skewed dataset using the Spark UI

The Spark UI is the primary tool for detecting data skew. Skew is not always obvious from code or data alone, but it leaves clear signatures in task durations, shuffle sizes, spill metrics, and executor memory usage. By examining the Stages tab, the SQL tab, and the Executors tab, you can confirm whether skew is present and identify the specific stage, key, or partition causing the problem.

**Step 1: Open the Stages tab and locate the slow stage**

Go to the Spark UI and click the Stages tab. Look for stages with long durations or stages that are part of a shuffle-heavy operation such as a join, groupBy, or distinct. Sort the stage list by duration to find the slowest stage. Click on the stage to see its task details.

**Step 2: Examine the task duration distribution**

In the stage detail page, scroll to the Tasks table. Look at the Duration column. In a healthy stage, task durations are similar. With skew, you will see a long tail: most tasks finish in a few seconds, but a few tasks take minutes or hours. The Summary Metrics section at the top of the Tasks table shows the min, 25th percentile, median, 75th percentile, and max duration. A large gap between the median and the max is a strong indicator of skew.

Example: Median duration 2 seconds, max duration 10 minutes. This means a few tasks are processing much more data than the rest.

**Step 3: Compare shuffle read sizes across tasks**

Sort the Tasks table by Shuffle Read Size or Shuffle Read Records. In a skewed stage, a few tasks will read much more shuffle data than others. For example, most tasks read 10 MB, but one task reads 2 GB. This indicates that a hot key sent almost all data to one partition. You can also sort by Shuffle Write Size in the map stage to see if the skew originates during the write phase.

**Step 4: Check spill metrics**

In the Tasks table, look at Spill (Memory) and Spill (Disk) columns. Skewed tasks often spill heavily because the partition is too large to fit in memory. If a few tasks have large spill values while others have zero, skew is likely. Spills also cause disk I/O and slow down the task further.

**Step 5: Inspect executor memory and GC time**

Go to the Executors tab. Look at the Storage Memory, GC Time, and Peak Execution Memory columns. Executors processing skewed partitions will show higher memory usage, longer GC times, and possibly out-of-memory errors. If one executor is doing much more work than others, it will have higher CPU and memory usage.

**Step 6: Use the SQL tab for DataFrame and SQL queries**

If you are using DataFrames or SQL, the SQL tab shows the physical plan and per-operator metrics. Click on the query and look for the Exchange node or the join operator. The metrics for that operator will show shuffle read sizes and task durations. Adaptive Query Execution (AQE) also reports skew detection in the SQL tab. If AQE skew join is enabled, you may see that it split skewed partitions automatically. The SQL tab can show which stage or operator is the bottleneck.

**Step 7: Check the Stage timeline and event timeline**

In the stage detail page, the Event Timeline shows when tasks start and finish. Skewed tasks appear as long bars that extend far beyond the rest. This visual representation makes the long tail obvious.

**Step 8: Verify with key distribution analysis**

The Spark UI tells you where skew is happening, but it does not tell you which key is hot. To confirm the key, run a query on the DataFrame to count key frequencies. For example:

```python
from pyspark.sql.functions import col, count

key_counts = df.groupBy("join_key").agg(count("*").alias("cnt"))
key_counts.orderBy(col("cnt").desc()).show(10)

total = df.count()
top_keys = key_counts.orderBy(col("cnt").desc()).limit(5).collect()
for row in top_keys:
    print(f"Key {row['join_key']}: {row['cnt']} rows ({row['cnt']/total*100:.2f}%)")
```

If one or a few keys dominate, those are the hot keys causing the skew.

**Step 9: Check partition sizes directly**

You can also inspect the number of rows per partition using `spark_partition_id()`.

```python
from pyspark.sql.functions import spark_partition_id, count

df.withColumn("partition_id", spark_partition_id()) \
  .groupBy("partition_id") \
  .agg(count("*").alias("row_count")) \
  .orderBy("row_count", ascending=False) \
  .show()
```

If a few partitions have much larger row counts, the data is skewed.

**Summary of Spark UI indicators for skew**

- Task durations: large gap between median and max.
- Shuffle read sizes: a few tasks read much more data.
- Spill metrics: a few tasks spill heavily.
- Executor memory: one or a few executors use much more memory or have long GC times.
- Event timeline: long bars for a few tasks.
- SQL tab: skewed operator metrics and AQE skew detection messages.

**What to do after identifying skew**

Once you confirm skew, you can address it with salting, broadcast joins, AQE skew join, two-phase aggregation, or by isolating hot keys. The Spark UI is also useful after applying a fix to verify that task durations and shuffle sizes are now balanced.
