# 1.1.6 How does Spark handle node failures during execution?

Spark treats worker-node and executor failures as normal events. The Driver detects the loss, the DAGScheduler uses the lineage DAG to recompute only missing data, and the TaskScheduler reschedules failed tasks on surviving executors. The Cluster Manager replaces lost executors when resources are available. Spark normally recovers at task or stage level, not by restarting the whole application.
- **Detect the failure**: The Driver notices an executor is lost through heartbeat timeout or the Cluster Manager. All tasks running on that executor are marked failed.
- **Retry tasks**: Failed tasks are retried up to the configured `spark.task.maxFailures` limit. If the limit is exhausted, the stage may fail.
- **Reschedule on other executors**: Unfinished tasks from the lost executor are re-enqueued and run on other available executors.
- **Recompute lost partitions using lineage**: RDDs track how they were built. If a partition is lost, Spark recomputes only that partition from its lineage instead of rerunning the entire job.
- **Invalidate lost shuffle outputs**: If the failed executor held shuffle map outputs, those outputs are considered lost. The DAGScheduler reschedules the affected map tasks or reruns the map stage to regenerate them.
- **Handle shuffle fetch failures**: If a reduce task cannot fetch shuffle data because the map output is gone, Spark reports a `FetchFailed` and goes back to the stage that generated the missing data.
- **Replace executors through the Cluster Manager**: The Cluster Manager allocates new executors when resources are available. The Driver continues scheduling work on them.
- **Use persisted or checkpointed data when available**: Cached or persisted data can reduce recomputation, but cached partitions can still be lost unless replicated. Checkpointing writes data to reliable storage so recovery does not depend only on lineage.
> [!IMPORTANT]
> Spark recovers from worker-node and executor failures by retrying tasks, recomputing lost partitions from lineage, and rerunning affected stages. It does not normally restart the entire job for a worker-node failure.
> [!WARNING]
> Driver-node failure is different. The Driver holds the scheduling state and coordinates the application. In many cluster deployments, the Driver is not automatically relaunched after a crash, so the application fails unless the cluster manager is configured to restart it or the application uses checkpointing for state recovery.
> [!NOTE]
> A worker-node failure often causes both task failures and shuffle-output loss. The visible symptom may be a `FetchFailed` followed by a map-stage rerun, not just a single task retry.
### Clear Definitions
- **Worker-node failure**: Loss of a machine that runs one or more executors. All executors on that machine are lost.
- **Executor failure**: Loss of an executor process, caused by node failure, crash, out-of-memory error, or decommissioning.
- **Lineage**: The record of transformations used to build an RDD. Spark uses it to recompute lost partitions.
- **Shuffle map output**: Intermediate data written by map tasks and read by reduce tasks.
- **Fetch failure**: A reduce task cannot read shuffle data because the map output or its executor is gone.
- **Task retry**: Rerunning a failed task on another executor or attempt.
- **Stage rerun**: Resubmitting a stage when its output data is lost.
- **Driver failure**: Loss of the Driver process. Scheduling state and in-memory application state are lost.
- **Checkpoint**: Saving data or state to reliable storage so it can be restored after failure.
### Worked Example: Node Failure During Word Count
1. A word-count job has 4 input partitions and runs on 3 executors: E1, E2, and E3.
2. The map stage finishes on all executors. E2 holds shuffle outputs for one input partition.
3. The worker node running E2 crashes. The Driver detects the lost executor.
4. Any tasks still running on E2 are marked failed and rescheduled on E1 and E3.
5. The Driver invalidates the shuffle outputs that lived on E2. The DAGScheduler schedules the affected map tasks again, and Spark recomputes those partitions from lineage.
6. A reduce task tries to fetch the missing shuffle block and reports `FetchFailed`. The DAGScheduler responds by rerunning the map stage portion that produced the missing data.
7. Once the missing shuffle data is regenerated, the reduce stage continues and the word-count job completes.
8. If the Driver node itself fails instead, the application usually fails. Recovery depends on cluster-manager restart policies or checkpointed state.
In short: Spark handles worker-node failure through executor replacement, task retries, lineage-based recomputation, and selective stage reruns. Driver failure is the more serious case and often requires external restart or checkpointing.
