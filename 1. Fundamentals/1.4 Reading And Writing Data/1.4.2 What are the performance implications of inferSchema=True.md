# 1.4.2 What are the performance implications of inferSchema=True?

### 1.4.2 Performance implications of `inferSchema=True`
`inferSchema=True` makes Spark read the file twice: once to sample and infer column types, and once to actually load the data. This extra pass adds I/O, CPU, and job startup cost. For small files the overhead is negligible, but for large files or pipelines that read many files, it can be significant.
- **Extra full or partial scan**: Spark must read data to guess types before the real read begins. This doubles the I/O for that file in the worst case.
- **Additional Spark job**: Schema inference triggers a separate job with its own stages and tasks, which adds scheduling and startup overhead.
- **Sampling behavior**: Spark does not always read the entire file. For CSV, it reads a sample determined by `spark.sql.csv.inferSchema.sampleSize` and `spark.sql.csv.inferSchema.sampleSize.maxRows`. Larger samples improve accuracy but cost more.
- **More accurate with larger samples, but slower**: A bigger sample reduces the chance of wrong types but increases the inference scan time.
- **Risk of wrong types**: A small sample may miss values that would change the inferred type, causing downstream errors or silent data loss.
- **Repeated cost across reads**: If you read the same file multiple times with inference, you pay the inference cost each time unless the schema is cached or reused.
- **Worse for many small files**: Each file may trigger its own inference pass, and the per-file overhead adds up across a large directory.
- **Compounded on wide CSVs**: More columns mean more values to sample and infer, increasing CPU time.
> [!IMPORTANT]
> `inferSchema=True` is convenient for exploration but costly at scale. It adds a data scan and a separate job before the main read. For production pipelines, define an explicit `StructType` schema to avoid the extra pass and the risk of wrong types.
> [!NOTE]
> You can tune inference sampling with `spark.sql.csv.inferSchema.sampleSize` and `spark.sql.csv.inferSchema.sampleSize.maxRows`. Larger samples improve accuracy but increase cost.
> [!WARNING]
> Inference can produce wrong types silently. An ID column with mostly numbers but a few leading-zero values may be inferred as integer and lose the zeros. A column with mixed values may fall back to string and break numeric operations later.
### Clear Definitions
- **Schema inference**: Spark scanning data to guess column data types.
- **Explicit schema**: A user-defined `StructType` that declares column names and types exactly.
- **Sample size**: The number of rows Spark reads to infer types.
- **Job**: A computation triggered by an action or by internal work such as schema inference.
- **I/O**: Reading from or writing to storage.
- **`StructType`**: Spark’s schema class for defining column names and types.
### Worked Example: Cost of Inference vs Explicit Schema
CSV file with 10 million rows and 20 columns.
**With inference**
```python
df = spark.read.csv("big.csv", header=True, inferSchema=True)
df.count()
```
Step by step:
1. Spark starts a schema inference job and reads a sample of rows.
2. Spark infers types for all 20 columns.
3. Spark starts the main read job using the inferred schema.
4. Total cost: one inference pass plus one full read.
**With explicit schema**
```python
from pyspark.sql.types import StructType, StructField, IntegerType, StringType, DoubleType
schema = StructType([
    StructField("order_id", IntegerType(), True),
    StructField("country", StringType(), True),
    StructField("amount", DoubleType(), True),
])
df = spark.read.csv("big.csv", header=True, schema=schema)
df.count()
```
Step by step:
1. Spark skips inference entirely.
2. Spark starts the main read job using the declared schema.
3. Total cost: one full read only.
In short: `inferSchema=True` trades an extra scan and job for convenience. On large or repeated reads, an explicit schema is faster, more predictable, and avoids silent type errors.
