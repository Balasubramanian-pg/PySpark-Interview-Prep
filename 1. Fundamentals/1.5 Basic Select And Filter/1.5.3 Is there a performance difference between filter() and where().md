# 1.5.3 Is there a performance difference between filter() and where()?

There is no performance difference. `filter()` and `where()` are aliases for the same DataFrame operation. They produce the same logical plan, and Catalyst optimizes both identically.
- **Same implementation**: In PySpark, `DataFrame.where` is an alias of `DataFrame.filter`. Calling either method invokes the same underlying logic.
- **Same logical plan**: Both create the same Filter node in the query plan. `df.filter(cond).explain(True)` and `df.where(cond).explain(True)` show identical parsed, analyzed, optimized, and physical plans.
- **Same optimization**: Catalyst applies the same predicate pushdown, constant folding, and filter-combining rules to both.
- **Same execution**: Both are lazy transformations. Neither triggers a job until an action such as `show()` or `count()` is called.
- **Only difference is readability**: `where()` reads naturally with SQL-style conditions. `filter()` reads naturally with column expressions. Choose based on style, not speed.
> [!IMPORTANT]
> `filter()` and `where()` are aliases. There is no measurable performance difference between them because they generate the same plan and run the same code.
> [!NOTE]
> The same alias relationship exists in Scala. `Dataset.filter` and `Dataset.where` are equivalent. In PySpark, both accept a Column expression or a SQL string.
> [!WARNING]
> Performance differences come from the condition itself, not the method name. A non-sargable condition, a Python UDF, or a filter applied after a shuffle can be slower regardless of whether you use `filter()` or `where()`.
### Clear Definitions
- **`filter()`**: A lazy DataFrame transformation that keeps rows matching a condition.
- **`where()`**: An alias of `filter()` with identical behavior.
- **Alias**: Two method names that call the same underlying implementation.
- **Logical plan**: The abstract tree of operations that Spark optimizes before execution.
- **Catalyst**: Spark SQL’s optimizer that rewrites logical plans.
- **Predicate pushdown**: Moving filters closer to the data source to reduce rows read.
### Worked Example
```python
from pyspark.sql import functions as F
a = df.filter(F.col("amount") > 100)
b = df.where(F.col("amount") > 100)
a.explain(True)
b.explain(True)
```
Step by step:
1. `a` and `b` are created from the same DataFrame with the same condition.
2. `a.explain(True)` prints the plan for `filter()`.
3. `b.explain(True)` prints the plan for `where()`.
4. Both plans contain the same Filter node and the same optimized physical plan.
5. Catalyst pushes `amount > 100` down to the scan in both cases.
6. Executors run identical tasks for both DataFrames.
In short: `filter()` and `where()` are the same operation under two names. Use whichever reads better; performance depends on the condition and the data layout, not on the method name.
