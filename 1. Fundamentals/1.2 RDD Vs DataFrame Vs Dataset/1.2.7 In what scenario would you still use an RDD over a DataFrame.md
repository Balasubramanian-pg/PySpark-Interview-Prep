# 1.2.7 In what scenario would you still use an RDD over a DataFrame?

Use an RDD when your data or logic does not fit the structured table model, or when you need low-level control over partitions, serialization, or physical execution. DataFrames are usually better for structured data, but RDDs remain useful for specific low-level cases.
- **Unstructured or non-tabular data**: Custom binary formats, raw text with irregular structure, or records that do not map cleanly to rows and columns.
- **Custom partitioning**: When you need a custom `Partitioner` to control exactly which keys go to which partition.
- **Partition-level control**: When you need `mapPartitions` to open a database connection, load a model, or initialize a parser once per partition.
- **Operations not expressible in DataFrame API**: Low-level record manipulation, custom iteration, or logic that is awkward as SQL expressions.
- **Custom serialization or Python objects**: When your pipeline depends on arbitrary Python objects and you accept the serialization cost.
- **Legacy code and RDD-based APIs**: Existing jobs or libraries written against the RDD API.
- **Precise physical execution control**: When you need direct control over lineage, caching, and task-level behavior rather than Catalyst’s optimized plan.
> [!IMPORTANT]
> DataFrames are preferred for structured and semi-structured data because Catalyst and Tungsten optimize the plan. Choose RDDs when structure is missing or low-level partition control is essential.
> [!WARNING]
> Using an RDD usually loses Catalyst and Tungsten benefits. Converting a DataFrame to `df.rdd` and back can also discard useful schema and optimization information.
> [!NOTE]
> Many partition-level tasks can now be done with DataFrame APIs such as `mapInPandas`, `applyInPandas`, or UDFs. Use RDDs only when those APIs are insufficient.
### Clear Definitions
- **RDD**: An immutable, partitioned, distributed collection with lineage, without a schema or query optimizer.
- **DataFrame**: A distributed table with named columns and a schema, optimized by Catalyst and executed with Tungsten.
- **Custom partitioner**: A user-defined rule that decides how key-value records are distributed across partitions.
- **mapPartitions**: An RDD operation that processes an entire partition at once, useful for per-partition setup.
- **Catalyst**: Spark SQL’s query optimizer.
- **Tungsten**: Spark’s execution engine for memory management and generated code.
### Worked Example: Custom Binary Log Parsing
Suppose each file contains a proprietary binary format. You need to open a parser once per partition, read records sequentially, and emit custom objects. A DataFrame cannot naturally express this binary record logic.
```python
def parse_partition(records):
    parser = BinaryParser()
    for record in records:
        yield parser.decode(record)
rdd = sc.binaryFiles("logs/").flatMap(lambda kv: kv[1].split(b"\x00"))
parsed = rdd.mapPartitions(parse_partition)
result = parsed.map(lambda obj: (obj.user_id, obj.action)).collect()
```
Step by step:
1. `sc.binaryFiles` reads raw binary files as RDD records.
2. `flatMap` splits the raw bytes into individual records.
3. `mapPartitions` creates one `BinaryParser` per partition instead of one per record.
4. The parser decodes each record into a custom object.
5. A later `map` extracts fields and `collect()` triggers execution.
6. If the decoded output becomes tabular, you can convert it to a DataFrame for downstream SQL and Catalyst optimization.
In short: use RDDs for unstructured data, custom partitioning, partition-level setup, custom serialization, and legacy low-level logic. Use DataFrames for structured data where Catalyst and Tungsten can optimize the work.
