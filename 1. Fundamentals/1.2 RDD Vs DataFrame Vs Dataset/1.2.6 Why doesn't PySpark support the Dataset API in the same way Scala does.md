# 1.2.6 Why doesn't PySpark support the Dataset API in the same way Scala does?

PySpark does not support the typed Dataset API because the Dataset API is built on language features that exist only in statically typed JVM languages like Scala and Java. Python is dynamically typed and lacks the compile-time type information and compiler mechanisms that Datasets fundamentally require.

- **Dynamic vs. static typing**: Datasets are a **strongly-typed** API. They check that your data conforms to a schema at **compile time**. Python is a **dynamically typed** language, so this kind of compile-time verification is not possible.
- **The Encoder requirement**: Datasets depend on **Encoders**. An Encoder is a component that converts JVM objects (like Scala case classes or Java Beans) to and from Spark's internal binary format. Encoders are type classes that rely on Scala's runtime reflection and `TypeTag` mechanism, which has no equivalent in Python.
- **Relationship to DataFrames**: In Scala and Java, a DataFrame is simply a type alias for `Dataset[Row]`. Because Python cannot support the typed `Dataset[T]` generic, PySpark only exposes the untyped `DataFrame` API, which operates on generic `Row` objects with schema checks performed at runtime, not compile time.

> [!IMPORTANT]
> The Dataset API is available in **Scala and Java only**. Python and R do not have a Dataset API because they are dynamically typed and lack the compile-time type-safety and Encoder infrastructure that Datasets are built upon.

> [!NOTE]
> In PySpark, you work with **DataFrames**, which are untyped Datasets (`Dataset[Row]`). You still benefit from the same Catalyst optimizer and Tungsten execution engine that Datasets use, so you do not lose performance by using DataFrames.

> [!WARNING]
> Attempting to find or use a "typed Dataset" in PySpark will not work because the API does not exist. Third-party libraries like `typedspark` can add some type-hint-like functionality for development, but they do not provide true compile-time type safety at the language level.

### Clear Definitions

- **Dataset**: A strongly-typed, immutable distributed collection available in Scala and Java, with compile-time type safety and Encoders.
- **Dynamic typing**: A language feature where variable types are checked at runtime, not at compile time. Python is dynamically typed.
- **Static typing**: A language feature where variable types are checked at compile time. Scala and Java are statically typed.
- **Encoder**: A component that converts JVM objects to and from Spark's internal binary representation. Required by all Datasets.
- **Type class**: A Scala language feature that enables ad-hoc polymorphism, used to implement Encoders.
- **TypeTag**: A Scala compiler feature that persists compile-time type information to runtime, used by Encoders.

### Worked Example: What You Gain and Lose in PySpark

**Scala (Dataset API available)**
```scala
case class Person(name: String, age: Long)
val ds = spark.read.json("people.json").as[Person]
val adults = ds.filter(p => p.age > 18) // Compiler checks that p.age is numeric
```
- The compiler verifies that `p.age` exists and is a numeric type **before the code runs**.
- If you made a typo like `p.agge`, the code would **fail to compile**.

**PySpark (DataFrame API only)**
```python
df = spark.read.json("people.json")
adults = df.filter(df.age > 18)  # Column existence and type checked at runtime
```
- If `age` does not exist or is not numeric, the error appears **only when the job runs**.
- PySpark cannot offer compile-time type safety because Python does not check types at compile time.

In short: PySpark does not support the Dataset API because Datasets require static typing and Encoders, which are features of Scala and Java that Python does not have. PySpark provides the untyped DataFrame API instead, which still benefits from Spark's optimizer and execution engine.
