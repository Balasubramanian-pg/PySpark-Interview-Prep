# 1.3.6 How does Lineage help with fault tolerance?
### 1.3.6 How Lineage helps with fault tolerance
Lineage is the record of transformations that produced each RDD. When a partition is lost because an executor or node fails, Spark walks the lineage backward to the nearest available parent data and recomputes only the missing partition. Spark does not need to replicate every partition or restart the whole job. This is how RDDs achieve fault tolerance cheaply.
- **No full data replication needed**: Spark does not store multiple copies of every partition by default. It stores the recipe for rebuilding them.
- **Recompute only what was lost**: If one partition is lost, Spark recomputes just that partition, not the entire RDD or job.
- **Walk back to the nearest parent**: Spark follows the lineage from the lost RDD to the closest parent whose data is still available, then re-applies the recorded transformations.
- **Narrow dependencies recompute cheaply**: For `map()` and `filter()`, only the corresponding parent partition is needed.
- **Wide dependencies may need more work**: For `reduceByKey()` and `groupByKey()`, lost shuffle output may require rerunning several map tasks to regenerate the missing data.
- **Works with the DAGScheduler**: The DAGScheduler uses lineage to identify which stages and tasks must rerun after a failure.
- **Checkpointing truncates lineage**: Writing an RDD to reliable storage creates a new starting point. Recovery after a checkpoint does not need to replay the full history.
- **Driver must hold the lineage**: Lineage lives on the Driver. If the Driver is lost without checkpointed state, the lineage is lost too.
> [!IMPORTANT]
> Lineage-based recovery means Spark recomputes lost partitions from recorded transformations instead of restoring replicated copies. This keeps fault tolerance cheap but makes recovery cost depend on how much work must be replayed.
> [!NOTE]
> Lineage is most efficient for narrow transformations. Wide transformations such as shuffles can make recomputation more expensive because multiple upstream tasks may need to rerun.
> [!WARNING]
> Very long lineage chains increase recovery time. Checkpointing an RDD or DataFrame to reliable storage truncates the lineage and gives Spark a cheaper starting point after a failure.
### Clear Definitions
- **Lineage**: The record of transformations used to build an RDD from its parents.
- **Fault tolerance**: The ability of a system to continue working correctly after a component fails.
- **Partition**: A logical chunk of an RDD that a task processes.
- **Narrow dependency**: A dependency where each parent partition feeds at most one child partition.
- **Wide dependency**: A dependency where multiple child partitions depend on the same parent partition, requiring a shuffle.
- **Checkpoint**: Writing an RDD to reliable storage to truncate lineage and speed up recovery.
- **DAGScheduler**: The Driver component that uses lineage to decide which stages to rerun.
- **Shuffle**: Redistribution of data across partitions, usually between stages.
### Worked Example: Recovering a Lost Partition
Code:
```python
lines = sc.textFile("huge_log.txt")
words = lines.flatMap(lambda line: line.split(" "))
pairs = words.map(lambda word: (word, 1))
counts = pairs.reduceByKey(lambda a, b: a + b)
results = counts.collect()
```
Step by step:
1. The lineage graph records: `lines -> words -> pairs -> counts`.
2. During the map stage, the executor holding partition 2 of `pairs` crashes.
3. The Driver detects the lost executor and marks the tasks on it as failed.
4. The DAGScheduler checks the lineage. Partition 2 of `pairs` depends on partition 2 of `words`, which depends on partition 2 of `lines`.
5. Spark reads partition 2 of `huge_log.txt` again, applies `flatMap` and `map` to it, and rebuilds partition 2 of `pairs`.
6. The rebuilt partition is used for the shuffle, and the reduce stage continues.
7. Only partition 2 was recomputed. The other partitions were not touched.
8. If a checkpoint had been written after `pairs`, Spark would restart from the checkpoint instead of re-reading the file and replaying `flatMap` and `map`.
In short: lineage helps fault tolerance by recording how each partition was built. When a partition is lost, Spark recomputes only that partition from the nearest available parent, avoiding full replication and full job restarts. Checkpointing shortens the lineage when recovery cost becomes too high.
