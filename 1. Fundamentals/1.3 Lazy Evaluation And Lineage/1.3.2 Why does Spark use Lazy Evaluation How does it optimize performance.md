# 1.3.2 Why does Spark use Lazy Evaluation? How does it optimize performance?

Spark uses lazy evaluation because it lets the Driver see the complete chain of transformations before running anything. With the full plan in hand, Spark can combine steps, push work closer to the data, skip columns and rows that are never needed, and avoid work that no action ever requests. It also keeps fault recovery cheap because the lineage is recorded before execution begins.
- **Sees the whole pipeline first**: Spark waits for an action so it can plan the entire chain of transformations together instead of executing them one by one.
- **Enables Catalyst optimization**: DataFrame plans can be rewritten with predicate pushdown, column pruning, constant folding, and join reordering before a single row is read.
- **Enables whole-stage code generation**: Tungsten can fuse an entire stage of operators into one generated function because the full stage is known in advance.
- **Avoids unnecessary computation**: If no action is called, nothing runs. If only a few columns are needed, the rest are never read.
- **Reduces data movement**: Filters are pushed toward the source, so fewer rows are shuffled across the network.
- **Combines narrow transformations**: Multiple narrow operations such as `map` and `filter` can run in the same stage without intermediate materialization.
- **Plans partitions and tasks once**: The Driver knows how many partitions and tasks are needed before scheduling, which avoids repeated scheduling overhead.
- **Cheap fault recovery**: Lineage is recorded during planning, so lost partitions can be recomputed without rerunning the entire application.
- **Improves resource use**: Executors receive only the work that is actually needed, which reduces CPU, memory, and I/O waste.
> [!IMPORTANT]
> Lazy evaluation is what makes Spark’s optimizers possible. If Spark ran each transformation immediately, Catalyst could not rewrite the full plan and Tungsten could not fuse whole stages.
> [!NOTE]
> Lazy evaluation optimizes the plan, not the data. The performance gains come from reading less data, moving less data, and running fewer operators per row.
> [!WARNING]
> Lazy evaluation can hide repeated work. If you call several actions on the same uncached DataFrame or RDD, Spark may recompute the whole chain each time. Use `cache()` or `persist()` when reusing data across actions.
### Clear Definitions
- **Lazy evaluation**: Delaying computation until a result is actually needed.
- **Transformation**: A lazy operation that returns a new dataset, such as `map()` or `filter()`.
- **Action**: An operation that triggers computation, such as `count()` or `write()`.
- **Catalyst**: Spark SQL’s optimizer that rewrites logical plans into efficient physical plans.
- **Tungsten**: Spark’s execution engine for memory management and code generation.
- **Predicate pushdown**: Moving filters closer to the data source so fewer rows are read.
- **Column pruning**: Reading only the columns a query needs.
- **Whole-stage code generation**: Fusing all operators in a stage into one generated function.
- **Narrow transformation**: A transformation where each input partition feeds at most one output partition, such as `map()`.
- **Lineage**: The record of transformations used to build a dataset, used for recomputation.
### Worked Example: How Lazy Evaluation Optimizes a Query
Code:
```python
df = spark.read.parquet("sales.parquet")
result = (
    df.filter(df.amount > 100)
      .select("country", "amount")
      .groupBy("country")
      .sum("amount")
)
result.show()
```
Step by step:
1. **Eager alternative (what Spark avoids)**: If each step ran immediately, Spark would read every column of every row, filter, then select, then shuffle, then aggregate. That reads and moves far more data than needed.
2. **Lazy plan building**: `filter`, `select`, and `groupBy` only add nodes to the plan. No data is read.
3. **Column pruning**: Catalyst sees that only `country` and `amount` are needed, so Parquet reads just those two columns instead of the full file.
4. **Predicate pushdown**: Catalyst moves `amount > 100` into the Parquet scan, so only matching rows are read from disk.
5. **Stage planning**: The `groupBy` needs a shuffle, so Spark creates a map stage (scan, filter, project, partial aggregate) and a reduce stage (final aggregate).
6. **Whole-stage code generation**: Tungsten fuses the scan, filter, projection, and partial aggregation into one generated function, avoiding per-row function calls.
7. **Execution**: Executors read only the needed columns and rows, shuffle only the partial aggregates, and compute the final sums.
8. **Result**: `show()` returns the aggregated table with far less I/O, network traffic, and CPU work than the eager equivalent.
In short: lazy evaluation lets Spark see the whole pipeline before running it, so Catalyst can rewrite the plan and Tungsten can fuse execution. The result is less data read, less data shuffled, and fewer operations per row.
