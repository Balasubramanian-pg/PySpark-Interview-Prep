# 1.3.5 What is an RDD Lineage Graph?

An RDD Lineage Graph is the record of how an RDD was built from its parent RDDs through transformations. Each node is an RDD, and each edge is a transformation that produced the child from the parent. Spark keeps this graph on the Driver so it can recompute lost partitions and plan jobs without relying on data replication. It is the mechanism behind RDD resilience.
- **Record of transformations**: Every transformation such as `map()`, `filter()`, and `reduceByKey()` adds an edge to the lineage graph.
- **Nodes are RDDs**: Each RDD is a node. The graph starts from the source RDD and ends at the target RDD.
- **Edges are dependencies**: An edge points from a parent RDD to a child RDD and labels the transformation that connects them.
- **Narrow dependencies**: Each parent partition feeds at most one child partition, as in `map()` and `filter()`. These stay within one stage.
- **Wide dependencies**: Multiple child partitions depend on the same parent partition, as in `reduceByKey()` and `groupByKey()`. These require a shuffle and split the graph into stages.
- **Fault recovery mechanism**: If a partition is lost, Spark walks the lineage backward to find the nearest available parent and recomputes only the missing partition.
- **Used for planning**: The DAGScheduler walks the lineage to create stages and tasks when an action is called.
- **Grows lazily**: The graph grows as you write transformations. It is not executed until an action triggers a job.
> [!IMPORTANT]
> The lineage graph is how Spark achieves fault tolerance without replicating every partition. Lost data is recomputed from the recorded transformations instead of being restored from a copy.
> [!NOTE]
> Lineage is stored on the Driver. If the Driver fails and is not restarted with checkpointed state, the lineage is lost and the application cannot recover in the same way.
> [!WARNING]
> Very long lineage chains can make recomputation expensive. Checkpointing an RDD truncates the lineage by writing data to reliable storage, so recovery starts from the checkpoint instead of the original source.
### Clear Definitions
- **RDD**: An immutable, partitioned, distributed collection of records with lineage.
- **Lineage graph**: A directed acyclic graph of RDDs connected by the transformations that produced them.
- **Narrow dependency**: A dependency where each parent partition maps to at most one child partition.
- **Wide dependency**: A dependency where multiple child partitions depend on the same parent partition, requiring a shuffle.
- **Checkpoint**: Writing an RDD to reliable storage to truncate its lineage and speed up recovery.
- **DAGScheduler**: The Driver component that uses lineage to split a job into stages.
- **Partition**: A logical chunk of an RDD that a task processes.
### Worked Example: Lineage Graph for Word Count
Code:
```python
lines = sc.textFile("huge_log.txt")
words = lines.flatMap(lambda line: line.split(" "))
pairs = words.map(lambda word: (word, 1))
counts = pairs.reduceByKey(lambda a, b: a + b)
results = counts.collect()
```
Step by step:
1. `lines` is the source RDD node. Its lineage is just the file read.
2. `flatMap` adds an edge from `lines` to `words`. This is a narrow dependency.
3. `map` adds an edge from `words` to `pairs`. This is also a narrow dependency.
4. `reduceByKey` adds an edge from `pairs` to `counts`. This is a wide dependency because data must be shuffled by key.
5. The lineage graph now has four nodes and three edges. Nothing has been computed yet.
6. `collect()` triggers a job. The DAGScheduler walks the lineage and cuts it at the shuffle boundary, creating a map stage and a reduce stage.
7. Suppose a partition of `pairs` is lost during execution. Spark walks the lineage from `pairs` back to `words` and then to `lines`, and recomputes only that partition.
8. If a checkpoint were written after `pairs`, recovery would start from the checkpoint instead of recomputing from the file.
In short: the lineage graph is Spark’s memory of how each RDD was built. It enables stage planning, fault recovery by recomputation, and lineage truncation through checkpointing.
