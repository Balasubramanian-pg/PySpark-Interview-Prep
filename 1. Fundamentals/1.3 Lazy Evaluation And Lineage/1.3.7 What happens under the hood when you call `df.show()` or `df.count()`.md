# 1.3.7 What happens under the hood when you call `df.show()` or `df.count()`?

Both `df.show()` and `df.count()` are actions. They trigger the full Spark execution pipeline: Catalyst optimization, physical planning, stage and task creation by the DAGScheduler, task scheduling by the TaskScheduler, execution on executors, and results returned to the Driver. The main difference is what each action requests: `count()` asks for one number per partition, while `show()` asks for a limited number of rows to display.
- **Action recognition**: The Driver sees the action and asks the `SparkSession` to execute the DataFrame’s logical plan.
- **Catalyst analysis**: Catalyst resolves column names and types against the schema, producing an analyzed logical plan.
- **Catalyst optimization**: Catalyst applies rules such as predicate pushdown, column pruning, constant folding, and join reordering to produce an optimized logical plan.
- **Physical planning**: Catalyst generates one or more physical plans and selects the cheapest, for example choosing a scan type or join strategy.
- **Job creation**: The DAGScheduler converts the physical plan into a job, splitting it into stages at shuffle boundaries.
- **Task creation**: Each stage is split into tasks, usually one per partition. The TaskScheduler assigns tasks to executors.
- **Execution on executors**: Executors read data, apply the operators, and produce results. For `count()`, each task returns a partial count. For `show()`, each task returns rows until the limit is satisfied.
- **Result collection**: The Driver aggregates partial results. `count()` sums the partial counts and returns one number. `show()` takes the first `n` rows, formats them, and prints a table.
- **Cleanup**: Completed stages release shuffle data and temporary resources according to Spark’s cleanup policies.
> [!IMPORTANT]
> `df.show()` and `df.count()` both trigger a full job. Neither runs eagerly on the DataFrame itself; the DataFrame only holds a plan until one of these actions is called.
> [!NOTE]
> `count()` is usually cheaper than `show()` for large datasets because it only needs partial counts from each partition and does not need to materialize rows for display. `show()` often uses `take(n)` internally, which stops reading partitions once enough rows are collected.
> [!WARNING]
> Calling `show()` or `count()` multiple times on an uncached DataFrame recomputes the entire chain each time. Use `cache()` or `persist()` if you need to reuse the same data across multiple actions.
### Clear Definitions
- **Action**: An operation that triggers computation, such as `show()` or `count()`.
- **Catalyst**: Spark SQL’s optimizer that rewrites logical plans into efficient physical plans.
- **DAGScheduler**: The Driver component that converts a physical plan into stages and submits them as tasks.
- **TaskScheduler**: The Driver component that assigns tasks to executors.
- **Stage**: A shuffle-separated part of a job.
- **Task**: The smallest unit of work, usually one partition in one stage.
- **Partial result**: A per-task output that the Driver aggregates, such as a count per partition.
- **Shuffle**: Redistribution of data across partitions, usually between stages.
### Worked Example: df.count() under the hood
Code:
```python
df = spark.read.parquet("sales.parquet")
df.filter(df.amount > 100).count()
```
Step by step:
1. **Action triggered**: `count()` is called on the filtered DataFrame.
2. **Catalyst analysis**: Catalyst resolves `amount` against the Parquet schema.
3. **Catalyst optimization**: Catalyst pushes `amount > 100` into the Parquet scan and prunes all other columns, so only `amount` is read.
4. **Physical plan**: Catalyst produces a physical plan: scan Parquet with the filter, then aggregate a count.
5. **Job and stage creation**: The DAGScheduler creates one job. There is no shuffle, so it is a single stage.
6. **Task creation**: If the Parquet file has 8 partitions, the Driver creates 8 tasks, one per partition.
7. **Execution**: Each executor scans its partition, applies the filter, and returns a partial count.
8. **Aggregation**: The Driver sums the 8 partial counts and returns the final number.
9. **Cleanup**: The stage finishes and temporary resources are released.
### Worked Example: df.show() under the hood
Code:
```python
df = spark.read.parquet("sales.parquet")
df.filter(df.amount > 100).show()
```
Step by step:
1. **Action triggered**: `show()` is called. By default, it displays 20 rows.
2. **Catalyst analysis and optimization**: Same as `count()`, Catalyst resolves and optimizes the plan, pushing the filter down and pruning columns.
3. **Physical plan with limit**: `show()` adds a limit to the plan, so Spark does not need to scan all partitions if enough rows are found early.
4. **Job and stage creation**: The DAGScheduler creates a job. Without a shuffle, it is a single stage.
5. **Task execution**: Tasks run on partitions. Each task returns rows until the limit is satisfied. If the first partition already has 20 matching rows, later partitions may be skipped.
6. **Result collection**: The Driver takes the returned rows, formats them into a table with column headers, and prints the output.
7. **Cleanup**: The stage finishes and temporary resources are released.
In short: both `show()` and `count()` trigger Catalyst optimization, physical planning, stage and task creation, executor execution, and Driver-side result aggregation. `count()` aggregates partial counts into one number, while `show()` collects a limited number of rows and prints them as a table.
