## 2.6.4 What is the difference between `rollup()` and `cube()`?

`rollup` produces hierarchical subtotals in the order you list the columns. `cube` produces every possible combination of the listed columns. Both are multi dimensional aggregation helpers. Both return subtotal rows with `null` in the aggregated columns.

```mermaid
graph TD
    A[Grouping columns a, b, c] --> B{rollup or cube}
    B -->|rollup| C[Prefix subsets only]
    C --> D[(a,b,c) (a,b) (a) ()]
    B -->|cube| E[All subsets]
    E --> F[(a,b,c) (a,b) (a,c) (b,c) (a) (b) (c) ()]
    D --> G[n + 1 grouping sets]
    F --> H[2^n grouping sets]
    G --> I[Fewer rows, cheaper]
    H --> J[More rows, more shuffle and skew risk]
```

### Grouping sets produced

For `rollup(a, b, c)`:

| Grouping set | Meaning |
|---|---|
| `(a, b, c)` | Full detail |
| `(a, b)` | Subtotal over `c` |
| `(a)` | Subtotal over `b, c` |
| `()` | Grand total |

For `cube(a, b, c)`:

| Grouping set | Meaning |
|---|---|
| `(a, b, c)` | Full detail |
| `(a, b)` | Subtotal over `c` |
| `(a, c)` | Subtotal over `b` |
| `(b, c)` | Subtotal over `a` |
| `(a)` | Subtotal over `b, c` |
| `(b)` | Subtotal over `a, c` |
| `(c)` | Subtotal over `a, b` |
| `()` | Grand total |

### Core comparison

| Topic | `rollup(a, b, c)` | `cube(a, b, c)` |
|---|---|---|
| Grouping sets | Prefix subsets only | All subsets |
| Count for n columns | `n + 1` | `2^n` |
| Order of columns | Matters. Defines hierarchy | Does not matter for the set of groupings |
| Output rows | Fewer | Much larger |
| Cost | Lower | Higher |
| Typical use | Hierarchies such as year, month, day | Cross dimensional analysis across independent dimensions |
| Shuffle volume | Moderate | High, grows exponentially with column count |
| Skew risk | Lower | Higher because more grouping sets share the shuffle |
| Null subtotal rows | Yes | Yes |
| Grand total | Yes | Yes |
| Intermediate combinations | Only prefixes | All combinations |

### Count growth

| Columns n | `rollup` sets | `cube` sets |
|---|---|---|
| 2 | 3 | 4 |
| 3 | 4 | 8 |
| 4 | 5 | 16 |
| 5 | 6 | 32 |
| 6 | 7 | 64 |
| 10 | 11 | 1024 |

`cube` grows exponentially. Ten columns means 1024 grouping sets and potentially 1024 times the aggregation work. Use it only when the number of columns is small.

### Syntax

PySpark:

```python
from pyspark.sql.functions import sum

# rollup: hierarchical subtotals in order
df.rollup("year", "month", "day").agg(sum("sales").alias("sales"))

# cube: all combinations
df.cube("region", "product", "channel").agg(sum("sales").alias("sales"))
```

Scala:

```scala
import org.apache.spark.sql.functions._

df.rollup("year", "month", "day").agg(sum("sales").alias("sales"))
df.cube("region", "product", "channel").agg(sum("sales").alias("sales"))
```

SQL:

```sql
SELECT year, month, day, sum(sales) AS sales
FROM t
GROUP BY ROLLUP(year, month, day);

SELECT region, product, channel, sum(sales) AS sales
FROM t
GROUP BY CUBE(region, product, channel);
```

### Null handling and subtotal detection

Both produce `null` in grouped columns for subtotal rows. A real `null` in the data is indistinguishable from a subtotal `null` unless you use `grouping` or `grouping_id`.

| Function | Meaning |
|---|---|
| `grouping(col)` | Returns `1` when `col` is aggregated away in that row, `0` when it is part of the grouping |
| `grouping_id(cols...)` | Bitmask across multiple columns, useful to label each grouping set |

PySpark:

```python
from pyspark.sql.functions import sum, grouping, grouping_id

df.rollup("year", "month").agg(
    sum("sales").alias("sales"),
    grouping("year").alias("g_year"),
    grouping("month").alias("g_month"),
    grouping_id("year", "month").alias("gid")
)
```

SQL:

```sql
SELECT
  year, month, sum(sales) AS sales,
  grouping(year) AS g_year,
  grouping(month) AS g_month,
  grouping_id(year, month) AS gid
FROM t
GROUP BY ROLLUP(year, month);
```

Use `grouping` or `grouping_id` to label subtotal rows, for example as `TOTAL` or `SUBTOTAL`. Do not rely on `null` alone.

### Use cases

| Scenario | Better choice |
|---|---|
| Year, quarter, month, day hierarchy | `rollup` |
| Country, state, city hierarchy | `rollup` |
| Sales by region and product and channel, all combinations | `cube` |
| Independent dimensions with small cardinality | `cube` |
| Large number of grouping columns | `rollup` or explicit `grouping sets` |
| Only specific subtotals are needed | `grouping sets` with an explicit list |
| Grand total plus full detail only | `rollup` if columns form a hierarchy, otherwise `grouping sets` |

`grouping sets` is the most explicit option. Use it when you need a subset of combinations that neither `rollup` nor `cube` matches exactly.

```sql
GROUP BY GROUPING SETS ((region, product), (region), ())
```

### Performance notes

- Both expand one aggregation into multiple grouping sets. The planner may rewrite them as a single shuffle with a grouping id.
- `cube` multiplies the shuffle and aggregation work by the number of grouping sets. Cost grows exponentially with column count.
- `rollup` grows linearly with column count. It is the safer default for hierarchies.
- Both can increase skew. Subtotal rows have fewer grouping keys, so they concentrate on fewer partitions.
- Filter input before rollup or cube. Only rows needed for the subtotals should reach the aggregation.
- Avoid cubing high cardinality columns. The number of grouping sets and the row count both explode.
- Use `grouping sets` when only a few combinations are needed. It avoids computing unneeded sets.
- Check the physical plan. Spark may choose a different strategy depending on the number of grouping sets and the shuffle partition count.

### Common pitfalls

| Pitfall | Effect | Fix |
|---|---|---|
| Using `cube` with many columns | Exponential grouping sets, very slow job | Use `rollup` or explicit `grouping sets` |
| Treating `null` as a real value | Subtotal rows misread as data | Use `grouping` or `grouping_id` |
| Assuming `cube` order matters | Confusion about output | Order does not change the set of groupings |
| Assuming `rollup` gives all combinations | Missing intermediate totals | Use `cube` or `grouping sets` |
| Not filtering before cube | Extra rows in every grouping set | Filter first |
| High cardinality columns in cube | Huge shuffle and skew | Reduce cardinality or avoid cube |
| Forgetting grand total | Missing `()` set | Both include it, but verify with `grouping_id` |
| Using a UDF for subtotal labels | Breaks codegen | Use `grouping` with `when` |

### End to end example

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import sum, grouping_id

spark = SparkSession.builder.getOrCreate()

df = spark.createDataFrame(
    [("2024", "Q1", 100), ("2024", "Q2", 150), ("2025", "Q1", 120)],
    ["year", "quarter", "sales"]
)

rollup_out = df.rollup("year", "quarter").agg(
    sum("sales").alias("sales"),
    grouping_id("year", "quarter").alias("gid")
)

cube_out = df.cube("year", "quarter").agg(
    sum("sales").alias("sales"),
    grouping_id("year", "quarter").alias("gid")
)
```

`rollup_out` has 3 grouping sets: `(year, quarter)`, `(year)`, `()`. `cube_out` has 4: `(year, quarter)`, `(year)`, `(quarter)`, `()`. The `gid` column labels each row so subtotal rows are identifiable.

### Rule of thumb

| Need | Use |
|---|---|
| Hierarchical subtotals in a defined order | `rollup` |
| Every combination of a few dimensions | `cube` |
| Specific combinations only | `grouping sets` |
| Many columns with a hierarchy | `rollup` |
| Many columns with no hierarchy | `grouping sets`, not `cube` |
