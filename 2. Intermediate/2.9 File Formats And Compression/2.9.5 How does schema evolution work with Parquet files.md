# 2.9.5 How does schema evolution work with Parquet files?

Schema evolution with Parquet in Spark is governed by a single, powerful, but off-by-default option: **schema merging**. It allows Spark to read a collection of Parquet files with different, but compatible, schemas as if they shared a single, unified schema.

```mermaid
graph TD
    A[Collection of Parquet files with different schemas] --> B{Read with mergeSchema = true?}
    B -->|No (Default)| C[Spark picks a single schema from the summary file or a random file]
    C --> D[Query may fail or silently produce incorrect results if schemas differ]
    B -->|Yes| E[Spark reads schema footers of all files]
    E --> F[Merge schemas into a single, unified schema]
    F --> G[Unified schema includes all columns from all files]
    G --> H[Missing columns in older files are filled with null]
    H --> I[Query executes successfully on the unified schema]
```

### The Core Mechanism: Schema Merging

Schema merging is the process of reconciling different but compatible schemas from a set of Parquet files. It is not enabled by default because it is a relatively expensive operation; Spark must read the footer of every file to construct the final schema.

| Aspect | Description |
| :--- | :--- |
| **What it does** | Detects different but compatible schemas across Parquet files and merges them into a single superset schema. |
| **How to enable** | Set the read option `.option("mergeSchema", "true")` or the global SQL config `spark.sql.parquet.mergeSchema` to `true`. |
| **Default behavior** | `spark.sql.parquet.mergeSchema` is `false`. Spark picks the schema from the summary file or a random data file, assuming all others are the same. |
| **Cost** | **Expensive.** Requires reading metadata from all files, a task that is otherwise avoided in most queries. |

### What Schema Evolution Supports

Schema merging in Spark handles several evolution operations, primarily by leveraging Parquet's ability to store schema per file.

| Operation | Support | Mechanism / Detail |
| :--- | :--- | :--- |
| **Add a new column** | **Yes** | The most common and robust case. New columns are added to the merged schema. Rows from older files that lack the column will have `null` for it. |
| **Remove a column** | **Yes** (Conditional) | If a column is absent in some files, it will be `null` for those files in the merged schema. This works when reading by **name** (Spark's default). Reading by **index** (e.g., in some Hive setups) can break on column removal. |
| **Change column position** | **Yes** | Spark reads Parquet by column **name**, not by position. Reordering columns across files is handled transparently. The merged schema presents a consistent column order. |
| **Type Promotion** | **Partially** | Compatible type changes (e.g., `int` to `long`, `float` to `double`) can be merged. Spark will promote to the wider type in the unified schema. |

### Key Limitations and Pitfalls

Parquet schema evolution is not a free-for-all. Its limitations are critical to understand to avoid data corruption or job failures.

| Limitation | Explanation |
| :--- | :--- |
| **Column Renaming** | **Not supported natively.** Parquet stores column names in each file. If you rename a column, Spark sees it as a different column. The merged schema will contain **both** the old and new names, with one being `null` in files where it doesn't exist. Renaming is only possible with a metadata layer like Delta Lake or Iceberg that maintains a mapping. |
| **Incompatible Type Changes** | **Fails.** Changing a column from a compatible type (e.g., `int` to `string`) will cause the merge to fail. Spark cannot find a common, lossless type for these. |
| **Nested Structure Evolution** | **Complex and Buggy.** Adding columns to nested structs (especially within maps or arrays) can lead to field ID mismatch errors in some Spark/Iceberg versions. Support is less mature than for top-level columns. |
| **Performance Overhead** | Enabling `mergeSchema` adds a metadata read for every file. On tables with millions of files, this can significantly slow down query planning. |
| **Structured Streaming** | The `mergeSchema` option has **no practical effect** in Structured Streaming. The schema is typically fixed for the life of the stream. |

### Practical Guidance and Best Practices

To use Parquet schema evolution effectively, follow these rules:

*   **Prefer Reading by Name**: This is Spark's default and is essential for handling column additions and removals. Ensure `spark.sql.parquet.fieldId.read.ignoreMissing` is not set in a way that breaks name-based resolution.
*   **Enable `mergeSchema` Only When Needed**: Keep it off for stable datasets to avoid performance overhead. Enable it for specific reads where you know schema changes have occurred.
*   **Use a Table Format for Complex Evolution**: For robust support of renaming, type changes, and nested evolution, use a transactional table format like **Delta Lake** or **Apache Iceberg**. These layers maintain a separate, evolvable schema and map it to the underlying Parquet files, decoupling schema evolution from the file format's limitations.
*   **Test Nested Evolution Carefully**: If you must evolve nested structures with plain Parquet files, test thoroughly. The field ID handling can be inconsistent across different writers and Spark versions.
*   **Consider Field IDs**: Newer Spark versions can use Parquet field IDs for more robust evolution. However, this depends on the writer embedding them correctly. Inconsistent field ID usage can lead to subtle read failures.

In summary, Parquet's native schema evolution is a powerful tool for the common case of **adding columns** to a dataset. It relies on the `mergeSchema` option, which must be explicitly enabled. For more complex changes like renaming or incompatible type promotion, a metadata layer like Delta Lake or Iceberg is the recommended solution.
