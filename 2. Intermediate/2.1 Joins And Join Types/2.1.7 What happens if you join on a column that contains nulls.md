# 2.1.7 What happens if you join on a column that contains nulls

Joining on `null` values silently drops matches because `null == null` evaluates to `UNKNOWN`, not `TRUE`. You must explicitly handle null keys using null-safe equality or preprocessing, otherwise you'll lose valid data without Spark throwing an error.

### 0. Setup

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.getOrCreate()

# Left DataFrame: Users with unassigned IDs
users_df = spark.createDataFrame([
    (1, "Alice"),
    (None, "Bob"),
    (3, "Charlie")
], ["user_id", "name"])

# Right DataFrame: Orders with unassigned user links
orders_df = spark.createDataFrame([
    (1, "Order_A"),
    (None, "Order_B"),
    (4, "Order_C")
], ["user_id", "order_id"])
```

### 1. Core Concept & Decision Tree (CRITICAL)

Use this tree to decide how to route null keys before they silently evaporate in your join.

```mermaid
graph TD
    A[Joining on a column with nulls] --> B{Do rows with null keys need to match each other?}
    B -- No --> C[Use standard join: on='col']
    B -- Yes --> D{Can you safely replace nulls with a sentinel value like 'UNKNOWN'?}
    D -- Yes --> E[Preprocess with coalesce/fill before joining]
    D -- No --> F[Use Null-Safe Equality: on=df1.col.eqNullSafe(df2.col)]
```

### 2. Syntax & Implementation

```python
# Standard Join: Drops the null row because null == null is UNKNOWN
standard_join = users_df.join(orders_df, on="user_id", how="inner")

# Null-Safe Join: Uses <=> under the hood to explicitly match nulls
null_safe_join = users_df.join(
    orders_df, 
    on=users_df["user_id"].eqNullSafe(orders_df["user_id"]), 
    how="inner"
)

null_safe_join.show()
```


### 4. Interview Pro-Tips / Gotchas

*   **The Silent Drop Trap:** This is the most common data loss bug in production. Spark follows SQL's 3-valued logic (True, False, Unknown). A join filter only passes on `True`. When both keys are `null`, the condition is `Unknown`, and the row gets filtered out. If your interviewer asks why your record counts dropped after a join, check your null keys first.
*   **First Principles (Hash Phase):** During a shuffle join, Spark hashes the join key to route rows to the correct executor. Standard hashing treats `null` as a distinct value, but the equality check still fails. `eqNullSafe()` bypasses this by using a custom comparator that explicitly maps `null <=> null` to `true` before routing. It's safer than `coalesce(null, "UNKNOWN")` because it doesn't mutate your raw data or risk collision with actual sentinel values in your dataset.
*   **Null Skew Warning:** If 80%+ of your join keys are `null`, `eqNullSafe` will funnel all those rows into a single partition during the shuffle. That partition becomes a hotspot and can OOM your task. If you're dealing with heavy null concentration, pre-filter the nulls, join the valid keys, then union the null partitions back. Never let a single `null` bucket dominate your cluster.
