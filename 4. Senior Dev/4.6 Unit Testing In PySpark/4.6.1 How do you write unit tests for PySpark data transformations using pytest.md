### 4.6.1 How do you write unit tests for PySpark data transformations using pytest

Unit testing PySpark data transformations with **pytest** verifies that your DataFrame logic produces correct results before it runs on a cluster. The challenge is that Spark is designed for distributed execution, while unit tests need to be fast, deterministic, and isolated. The standard approach is to run a local SparkSession in-process, build small input DataFrames from Python lists, apply your transformation functions, and assert on the output using DataFrame-aware comparison helpers. This answer covers the pytest fixtures, patterns, assertion libraries, and performance practices that make PySpark unit tests reliable and fast.

#### Setting Up pytest and a Session-Scoped SparkSession

The single most important performance decision is to create the SparkSession **once per test session**, not once per test. Creating a SparkSession is expensive; repeating it for every test turns a fast suite into a multi-minute run. Use a `conftest.py` file with a session-scoped fixture so all tests share one SparkSession.

```python
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    return (
        SparkSession.builder
        .master("local[2]")                              # two threads for parallelism
        .appName("PySparkUnitTests")
        .config("spark.sql.shuffle.partitions", "2")      # keep shuffles tiny
        .config("spark.default.parallelism", "2")
        .config("spark.ui.enabled", "false")              # skip UI overhead
        .config("spark.sql.adaptive.enabled", "false")    # deterministic plans
        .getOrCreate()
    )
```

Place this fixture in `conftest.py` so pytest discovers it automatically. The `scope="session"` argument ensures the SparkSession is created once and reused across all test modules. Setting `spark.sql.shuffle.partitions` to a small number is critical: the default of 200 creates 200 tasks for every shuffle, which is wasteful for two-row test DataFrames. The `pytest-spark` plugin provides `spark_context` and `spark_session` fixtures out of the box if you prefer not to write your own.

#### Testing DataFrame Transformations

The core pattern is to separate your transformation logic into pure functions that accept a DataFrame and return a DataFrame. This makes them directly testable.

```python
# transforms.py
from pyspark.sql import DataFrame
from pyspark.sql.functions import col, count_if

def filter_and_aggregate(df: DataFrame) -> DataFrame:
    return (
        df.filter(col("amount") > 15.0)
          .groupBy("category")
          .agg(count_if(col("amount") > 15.0).alias("total"))
    )
```

```python
# test_transforms.py
from chispa.dataframe_comparer import assert_df_equality
from transforms import filter_and_aggregate

def test_filter_and_aggregate(spark):
    input_data = [(1, "a", 10.0), (2, "b", 20.0), (3, "a", 30.0)]
    input_df = spark.createDataFrame(input_data, ["id", "category", "amount"])

    result = filter_and_aggregate(input_df)

    expected_data = [("a", 2), ("b", 1)]
    expected_df = spark.createDataFrame(expected_data, ["category", "total"])

    assert_df_equality(result, expected_df, ignore_row_order=True)
```

Using a helper like `chispa.assert_df_equality` produces readable error messages when DataFrames differ. It supports `ignore_row_order` and `ignore_nullable` flags, which avoid false failures from ordering or nullable metadata. You can also use `pyspark.testing.assertDataFrameEqual` for a built-in alternative in Spark 3.4+.

#### Testing Edge Cases: Nulls, Empty DataFrames, and Schema

Edge cases are where most transformation bugs hide. Test null handling explicitly, verify schema contracts, and confirm behavior on empty input.

```python
def test_null_handling(spark):
    df = spark.createDataFrame(
        [(1, "alice@example.com"), (2, None), (3, "charlie@example.com")],
        ["user_id", "email"]
    )
    result = df.withColumn("has_email", col("email").isNotNull())
    assert result.filter("has_email = false").count() == 1

def test_empty_dataframe(spark):
    schema = "id INT, category STRING, amount DOUBLE"
    empty_df = spark.createDataFrame([], schema)
    result = filter_and_aggregate(empty_df)
    assert result.count() == 0

def test_schema_contract(spark):
    df = spark.createDataFrame([(1, "a")], ["id", "val"])
    result = df.withColumn("id", col("id").cast("long"))
    assert dict(result.dtypes)["id"] == "bigint"
```

#### Testing UDFs and Pandas UDFs

Test UDF logic as a plain Python function first, then verify it through Spark to catch serialization issues. For Pandas UDFs, test with small Pandas DataFrames and validate the output schema.

```python
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import StringType
import pandas as pd

def categorize(amount):
    if amount is None:
        return "unknown"
    return "low" if amount < 50 else "high"

def test_categorize_directly():
    assert categorize(10) == "low"
    assert categorize(100) == "high"
    assert categorize(None) == "unknown"

def test_udf_in_spark(spark):
    categorize_udf = pandas_udf(categorize, StringType())
    df = spark.createDataFrame([(10,), (100,), (None,)], ["amount"])
    result = df.select(categorize_udf(col("amount")).alias("cat")).collect()
    assert [row.cat for row in result] == ["low", "high", "unknown"]
```

#### Testing SQL Queries

If your logic is expressed in SQL, register a temporary view and run the query against it. The SQL equivalent is the same query you would run in production.

```python
def test_sql_aggregation(spark):
    data = [(1, "a", 10.0), (2, "b", 20.0), (3, "a", 30.0)]
    df = spark.createDataFrame(data, ["id", "category", "amount"])
    df.createOrReplaceTempView("sales")

    result = spark.sql("""
        SELECT category, SUM(amount) AS total
        FROM sales
        WHERE amount > 15.0
        GROUP BY category
        ORDER BY category
    """)

    expected = [("a", 30.0), ("b", 20.0)]
    assert [tuple(row) for row in result.collect()] == expected
```

```sql
-- SQL equivalent tested by the query above
SELECT category, SUM(amount) AS total
FROM sales
WHERE amount > 15.0
GROUP BY category
ORDER BY category;
```

#### Testing Streaming Transformations

Structured Streaming tests can be split into two layers: test the transformation logic with static DataFrames, then test the streaming query with a memory sink or `foreachBatch`. The static test catches most logic bugs with sub-second feedback.

```python
def test_streaming_batch_logic(spark):
    # Test the batch function directly with a static DataFrame
    input_df = spark.createDataFrame([(1, "a"), (2, "b")], ["id", "val"])
    result = input_df.withColumn("upper_val", upper(col("val")))
    assert result.count() == 2

def test_streaming_query_with_memory_sink(spark):
    query = (
        spark.readStream.format("rate").load()
        .writeStream
        .outputMode("append")
        .format("memory")
        .queryName("test_stream")
        .option("checkpointLocation", "/tmp/checkpoints/test_stream")
        .start()
    )
    query.processAllAvailable()
    query.stop()
    assert spark.sql("SELECT * FROM test_stream").count() > 0
```

#### Mocking External Dependencies

Mock external I/O to keep unit tests fast and isolated. Patch database reads, file reads, or API calls so the test does not depend on infrastructure.

```python
from unittest.mock import patch

def test_pipeline_with_mocked_source(spark):
    with patch("my_module.read_from_database") as mock_read:
        mock_read.return_value = spark.createDataFrame([(1, "a")], ["id", "val"])
        result = my_pipeline(spark)
        assert result.count() == 1
```

#### Assertion Libraries and Comparison Strategies

Comparing DataFrames directly with `==` does not work. Use one of the following approaches.

| Method | Best For | Notes |
|---|---|---|
| `chispa.assert_df_equality` | Most DataFrame comparisons | Descriptive errors, `ignore_row_order`, `ignore_nullable` |
| `pyspark.testing.assertDataFrameEqual` | Spark 3.4+ native comparison | Built-in, supports schema and data checks |
| `subtract()` both ways | Order-independent set comparison | Two passes over data; good for small results |
| `collect()` and Python list equality | Small, ordered results | Simple but fails on row order |
| `pandas.testing.assert_frame_equal` | After `toPandas()` on small data | Requires identical dtypes and indexes |

#### Configuration Parameters for Test Performance

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.shuffle.partitions` | `200` | Set to 2 for tests to avoid 200-task shuffles. |
| `spark.default.parallelism` | varies | Set to 2 for local tests. |
| `spark.ui.enabled` | `true` | Set to `false` to skip UI overhead. |
| `spark.sql.adaptive.enabled` | `true` | Set to `false` for deterministic physical plans. |
| `spark.sql.adaptive.coalescePartitions.enabled` | `true` | Disable for reproducible partition counts. |
| `spark.sql.catalogImplementation` | `in-memory` | Use in-memory catalog for tests to avoid Hive metastore. |
| `spark.sql.warehouse.dir` | `/user/hive/warehouse` | Point to a temp directory in tests. |
| `spark.driver.host` | auto | Set to `127.0.0.1` to avoid hostname resolution delays. |
| `spark.sql.execution.arrow.pyspark.enabled` | `false` | Enable Arrow for faster Pandas conversion in tests. |

#### Performance Implications and Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Session-scoped SparkSession | Fast, one JVM for the suite | Shared state can leak between tests |
| Function-scoped SparkSession | Full isolation | Very slow; avoid |
| Small shuffle partitions | Fast shuffles | May hide partitioning bugs |
| `ignore_row_order=True` | Fewer false failures | Can mask ordering bugs |
| Mocking I/O | Fast, no infrastructure | Does not test integration |
| Integration tests | Catch real cluster issues | Slow, require infrastructure |

#### Best Practices

- Use a session-scoped SparkSession fixture in `conftest.py`.
- Set `spark.sql.shuffle.partitions` to 2 and `spark.ui.enabled` to `false` for speed.
- Separate transformation functions from I/O so they can be tested with static DataFrames.
- Use `chispa` or `assertDataFrameEqual` for readable DataFrame comparisons.
- Test nulls, empty DataFrames, duplicate keys, and schema contracts.
- Test UDF logic as plain Python first, then through Spark.
- Mock external I/O to keep tests fast and isolated.
- Keep test data small; `collect()` on large DataFrames can cause driver OOM.
- Run unit tests on every commit; run integration tests on a real cluster less frequently.

#### Common Pitfalls and Limitations

- Creating a SparkSession inside every test function. This is the most common cause of slow PySpark test suites.
- Leaving `spark.sql.shuffle.partitions` at 200, which creates 200 tasks for tiny test DataFrames.
- Comparing DataFrames with `==`. Use `chispa`, `subtract()`, or `collect()`.
- Testing only the happy path and missing null, empty, and duplicate-key edge cases.
- Mocking too much, which makes tests pass while production fails.
- Using real time in streaming tests, which makes them flaky. Use `processAllAvailable()` and memory sinks.
- Sharing session-level configuration changes across tests without resetting them.
- Relying on local mode to catch partitioning, skew, or resource-contention bugs.
- Forgetting to stop the SparkSession at the end of the session, which can leak resources.

#### Summary

Writing unit tests for PySpark transformations with pytest centers on a session-scoped SparkSession fixture, pure transformation functions, small deterministic DataFrames, and DataFrame-aware assertion helpers such as `chispa.assert_df_equality` or `pyspark.testing.assertDataFrameEqual`. Set `spark.sql.shuffle.partitions` to 2 and disable the UI for speed. Test edge cases explicitly, mock external I/O, and separate unit tests from integration tests. The most common mistake is creating a new SparkSession per test, which makes suites prohibitively slow. In interviews, emphasize the fixture pattern, the importance of testing transformation logic in isolation, and the boundary between unit tests and cluster-level integration tests.
