### 4.6.3 How do you mock or isolate the SparkSession for unit tests to run faster

Creating a **SparkSession** is expensive. Each new session starts a JVM, initializes a SparkContext, allocates memory, and sets up internal services. When a test suite creates a new SparkSession for every test, the startup cost dominates the runtime and turns a fast feedback loop into a multi-minute wait. The solution is not to mock the SparkSession entirely, because that bypasses the execution engine and hides real bugs. Instead, the correct approach is to **isolate** a single local SparkSession, reuse it across the suite, configure it with minimal resources, and clean up state between tests. Mocking is reserved for external I/O boundaries, not for Spark itself. This answer explains the patterns, configuration, and trade-offs that make PySpark unit tests fast and reliable.

#### Why SparkSession Creation Is Expensive

A SparkSession is heavyweight by design. It launches a JVM, initializes the SparkContext, starts the driver, sets up the block manager, and prepares the SQL catalog. On a typical development machine, creating a SparkSession takes 2–5 seconds. If a test suite has 100 tests and each creates its own session, the suite spends 200–500 seconds just on startup. Reusing one session for the entire suite reduces that cost to a single startup.

The cost is not just time. Each session consumes memory, opens network ports, and registers with the local file system. Repeated creation and teardown can leave lingering processes, port conflicts, and unstable test runs.

#### Session-Scoped Fixture: The Primary Isolation Pattern

The standard solution is a **session-scoped pytest fixture**. It creates the SparkSession once when the test session starts and reuses it for every test. The fixture lives in `conftest.py` so pytest discovers it automatically.

```python
# conftest.py
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    return (
        SparkSession.builder
        .master("local[2]")
        .appName("PySparkUnitTests")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.default.parallelism", "2")
        .config("spark.ui.enabled", "false")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.catalogImplementation", "in-memory")
        .config("spark.driver.host", "127.0.0.1")
        .getOrCreate()
    )
```

The `scope="session"` argument is the critical detail. It tells pytest to call the fixture once per session, not once per test. Every test function that declares `spark` as an argument receives the same SparkSession instance.

`getOrCreate()` provides an additional safety net. If a SparkSession already exists, it returns that session instead of creating a new one. This prevents accidental session duplication when tests are run in an environment where a session might already be active.

The `pytest-spark` plugin provides `spark_context` and `spark_session` fixtures out of the box if you prefer not to write your own. It handles session lifecycle and configuration, but the session-scoped pattern is simple enough to implement directly.

#### Configuring the SparkSession for Test Speed

The default Spark configuration is designed for production clusters, not for unit tests. Several parameters should be overridden to reduce overhead and increase determinism.

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.shuffle.partitions` | `200` | Set to `2` for tests. The default creates 200 tasks for every shuffle, which is wasteful for small test DataFrames. |
| `spark.default.parallelism` | varies | Set to `2` for local tests. Controls the number of partitions for RDD operations. |
| `spark.ui.enabled` | `true` | Set to `false`. The Spark UI is not needed in tests and adds startup and memory overhead. |
| `spark.sql.adaptive.enabled` | `true` | Set to `false` for deterministic physical plans. AQE can change partition counts and join strategies between runs. |
| `spark.sql.adaptive.coalescePartitions.enabled` | `true` | Disable along with AQE for reproducible partition counts. |
| `spark.sql.catalogImplementation` | `in-memory` (default in some builds) | Use `in-memory` to avoid Hive metastore initialization. Explicitly set it to `in-memory` if your build defaults to `hive`. |
| `spark.driver.host` | auto-detected | Set to `127.0.0.1` to avoid hostname resolution delays and binding issues in local mode. |
| `spark.sql.warehouse.dir` | `/user/hive/warehouse` | Point to a temporary directory in tests if you use a Hive catalog. |
| `spark.sql.execution.arrow.pyspark.enabled` | `false` | Enable Arrow for faster conversion between Spark and Pandas DataFrames in tests. |
| `spark.master` | none | Set to `local[2]` or `local[1]`. Two threads allow some parallelism without excessive overhead. |

Setting `spark.sql.shuffle.partitions` to 2 is the single most impactful change. A `groupBy` on a three-row DataFrame with the default 200 partitions creates 200 tasks, each processing almost no data. Reducing it to 2 cuts shuffle overhead by two orders of magnitude.

#### Isolating State Between Tests

Even with a shared SparkSession, tests can interfere with each other through shared state. Temp views, cached DataFrames, and configuration changes persist across tests and cause flaky failures. Isolation requires explicit cleanup.

The following patterns prevent state leakage:

- **Drop temporary views** after each test. Use a function-scoped fixture that runs cleanup after the test.
- **Clear the cache** with `spark.catalog.clearCache()` to release cached DataFrames.
- **Reset configuration changes** with `spark.conf.unset()` or by re-setting the original value.
- **Use unique names** for temp views and tables in each test to avoid collisions.
- **Avoid global mutable state** in your transformation functions. Pure functions that accept and return DataFrames are naturally isolated.

A cleanup fixture looks like this:

```python
@pytest.fixture(scope="function", autouse=True)
def clean_spark_state(spark):
    yield
    spark.catalog.clearCache()
    for table in spark.catalog.listTables():
        if table.isTemporary:
            spark.catalog.dropTempView(table.name)
    spark.conf.unset("spark.sql.shuffle.partitions")
```

The `autouse=True` argument makes the fixture run for every test without being explicitly requested. The `yield` separates setup from teardown. After the test, the cache is cleared, temporary views are dropped, and modified configurations are reset.

#### When and How to Mock SparkSession (and When Not To)

Mocking the SparkSession itself is almost always the wrong approach. A mocked SparkSession returns fake DataFrames that do not execute real Spark code. Tests that pass against a mock can fail in production because they never exercised the actual query planner, serializer, or execution engine. Mocking SparkSession trades correctness for speed in a way that defeats the purpose of unit testing Spark transformations.

Mocking is appropriate for **external I/O boundaries**, not for Spark internals. If your pipeline reads from a database, calls an API, or writes to a file system, mock those calls so the test does not depend on infrastructure.

```python
from unittest.mock import patch

def test_pipeline_with_mocked_source(spark):
    with patch("my_module.read_from_database") as mock_read:
        mock_read.return_value = spark.createDataFrame([(1, "a")], ["id", "val"])
        result = my_pipeline(spark)
        assert result.count() == 1
```

In this example, the SparkSession is real, the DataFrame operations are real, and only the external database call is mocked. This is the correct boundary for mocking.

For pure Python logic inside UDFs, test the function directly without Spark at all. This is the fastest possible test and catches logic errors before they reach the distributed engine.

```python
def categorize(amount):
    if amount is None:
        return "unknown"
    return "low" if amount < 50 else "high"

def test_categorize_directly():
    assert categorize(10) == "low"
    assert categorize(100) == "high"
    assert categorize(None) == "unknown"
```

#### Complete Self-Contained Example

The following example shows a complete test module with a session-scoped SparkSession, a transformation function, and tests that use `chispa` for DataFrame comparison.

```python
# transforms.py
from pyspark.sql import DataFrame
from pyspark.sql.functions import col, upper

def clean_names(df: DataFrame) -> DataFrame:
    return df.withColumn("name", upper(col("name"))).filter(col("name").isNotNull())
```

```python
# test_transforms.py
import pytest
from pyspark.sql import SparkSession
from chispa import assert_df_equality
from transforms import clean_names

@pytest.fixture(scope="session")
def spark():
    return (
        SparkSession.builder
        .master("local[2]")
        .appName("PySparkUnitTests")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.default.parallelism", "2")
        .config("spark.ui.enabled", "false")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.catalogImplementation", "in-memory")
        .config("spark.driver.host", "127.0.0.1")
        .getOrCreate()
    )

@pytest.fixture(scope="function", autouse=True)
def clean_spark_state(spark):
    yield
    spark.catalog.clearCache()
    for table in spark.catalog.listTables():
        if table.isTemporary:
            spark.catalog.dropTempView(table.name)

def test_clean_names(spark):
    input_data = [(1, "alice"), (2, "bob"), (3, None)]
    input_df = spark.createDataFrame(input_data, ["id", "name"])

    result = clean_names(input_df)

    expected_data = [(1, "ALICE"), (2, "BOB")]
    expected_df = spark.createDataFrame(expected_data, ["id", "name"])

    assert_df_equality(result, expected_df, ignore_row_order=True, ignore_nullable=True)
```

This example runs in under a second after the initial SparkSession startup. The session is created once, the state is cleaned between tests, and the comparison uses `chispa` for readable diffs.

#### SQL Equivalents

If your transformation is expressed in SQL, you can test it without creating a new SparkSession. Register a temporary view and run the query.

```python
def test_sql_transformation(spark):
    data = [(1, "a", 10.0), (2, "b", 20.0)]
    df = spark.createDataFrame(data, ["id", "category", "amount"])
    df.createOrReplaceTempView("sales")

    result = spark.sql("""
        SELECT category, SUM(amount) AS total
        FROM sales
        GROUP BY category
        ORDER BY category
    """)

    expected = [("a", 10.0), ("b", 20.0)]
    assert [tuple(row) for row in result.collect()] == expected
```

```sql
SELECT category, SUM(amount) AS total
FROM sales
GROUP BY category
ORDER BY category;
```

The SQL query uses the same shared SparkSession. No new session is created.

#### Performance Implications and Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Session-scoped SparkSession | Fast, one JVM for the suite | Shared state can leak between tests |
| Function-scoped SparkSession | Full isolation | Very slow; avoid |
| Real local SparkSession | Tests actual Spark behavior | Startup cost; still faster than per-test |
| Mocked SparkSession | No startup cost | Does not test Spark execution; hides bugs |
| Mocking external I/O | Fast, isolated | Does not test integration |
| Cleanup fixture | Prevents state leakage | Adds slight overhead per test |
| Small shuffle partitions | Fast shuffles | May hide partitioning bugs |
| Disabling AQE | Deterministic plans | Different from production behavior |

#### Best Practices

- Use a session-scoped SparkSession fixture in `conftest.py`.
- Set `spark.sql.shuffle.partitions` to 2 and `spark.ui.enabled` to `false`.
- Use `spark.sql.catalogImplementation=in-memory` to avoid Hive metastore startup.
- Use a function-scoped cleanup fixture to clear cache and drop temp views.
- Do not mock SparkSession. Mock external I/O boundaries instead.
- Test pure Python UDF logic without Spark for the fastest feedback.
- Keep test data small and deterministic.
- Use `chispa` or `pyspark.testing.assertDataFrameEqual` for DataFrame comparisons.
- Run unit tests on every commit; run integration tests on a real cluster less frequently.

#### Common Pitfalls and Limitations

- Creating a SparkSession inside every test function. This is the most common cause of slow PySpark test suites.
- Leaving `spark.sql.shuffle.partitions` at 200, which creates 200 tasks for tiny test DataFrames.
- Forgetting to clean up temp views and cached DataFrames, causing state leakage between tests.
- Mocking SparkSession entirely, which bypasses the execution engine and hides real bugs.
- Using `collect()` on large DataFrames in tests, which can cause driver OOM.
- Sharing session-level configuration changes across tests without resetting them.
- Relying on local mode to catch partitioning, skew, or resource-contention bugs.
- Not stopping the SparkSession at the end of the session, which can leak resources.
- Using real time in streaming tests, which makes them flaky. Use `processAllAvailable()` and memory sinks.

#### Summary

The fastest PySpark unit tests reuse a single session-scoped SparkSession, configured with minimal resources and deterministic settings. Mocking SparkSession itself is an anti-pattern because it bypasses the execution engine and hides real bugs; mocking should be reserved for external I/O boundaries. Isolation is achieved through session-scoped fixtures, function-scoped cleanup, and small shuffle partitions. The key configuration changes are `spark.sql.shuffle.partitions=2`, `spark.ui.enabled=false`, `spark.sql.adaptive.enabled=false`, and `spark.sql.catalogImplementation=in-memory`. In interviews, emphasize the session-scoped fixture pattern, the importance of cleanup between tests, and the boundary between unit tests and cluster-level integration tests.
