### 4.6.4 What are the best practices for comparing two DataFrames in a test

Comparing two DataFrames is the core assertion in any PySpark unit test. The goal is to verify that a transformation produces the expected logical result, regardless of physical row order, partition layout, or schema metadata differences that do not affect correctness. Naive approaches such as `collect()` and Python list equality are brittle, slow, and fail on large data. Dedicated assertion libraries and careful handling of row order, schema, nullability, and floating-point precision are the foundation of reliable DataFrame tests. This answer covers the methods, trade-offs, and best practices for comparing DataFrames in PySpark tests.

#### Core Challenges in DataFrame Comparison

DataFrames are distributed, unordered collections with schema metadata. Direct comparison is not built into the Python `==` operator. Several factors cause false failures if not handled explicitly.

- **Row order**: Spark does not guarantee row order unless you explicitly sort. Two DataFrames with identical rows in different orders are logically equal for most transformations.
- **Schema and metadata**: A hand-constructed expected DataFrame may infer nullable flags differently from a transformation output. Schema metadata such as column comments or nullability can differ without affecting data correctness.
- **Nullability**: Spark tracks whether a column can contain nulls. A transformation may produce a non-nullable column while a manually created DataFrame marks it as nullable.
- **Floating-point precision**: Distributed arithmetic can produce tiny differences due to non-associative operations. Exact equality fails on values like `0.1 + 0.2` versus `0.3`.
- **Large data**: Pulling all rows to the driver with `collect()` causes out-of-memory errors and defeats the purpose of distributed testing.
- **Duplicate rows**: Set-based comparisons like `subtract()` handle duplicates correctly, but `collect()` and list equality do not unless you account for multiplicity.

#### Comparison Methods and When to Use Them

| Method | Pros | Cons | Best For |
|---|---|---|---|
| `chispa.assert_df_equality` | Descriptive color-coded diffs, `ignore_row_order`, `ignore_nullable`, `ignore_column_order`, `ignore_metadata` | Third-party dependency | Most DataFrame comparisons |
| `pyspark.testing.assertDataFrameEqual` | Built into Spark 3.4+, no extra dependency | Less flexible than chispa, no approximate equality | Projects on Spark 3.4+ with minimal dependencies |
| `subtract()` both ways | Order-independent, distributed, handles duplicates | Two passes over data, no detailed diff on failure | Simple set-equality checks, large DataFrames |
| `collect()` and Python list equality | Simple, fast for tiny data | Not distributed, order-sensitive, fails on large data | Very small DataFrames with known order |
| `toPandas()` and `pandas.testing.assert_frame_equal` | Familiar Pandas API, precise dtype checks | Collects all data to driver, dtype mismatches cause failures | Small DataFrames where Pandas semantics are desired |
| `exceptAll()` | Distributed set difference with duplicates | Only returns differing rows, no field-level diff | Finding rows present in one but not the other |

#### Using chispa for Readable Comparisons

`chispa` is the most widely used assertion library for PySpark tests. It provides `assert_df_equality` and related helpers that produce human-readable diffs.

```python
from chispa import assert_df_equality
from pyspark.sql.functions import col, upper

def test_clean_names(spark):
    input_df = spark.createDataFrame([(1, "alice"), (2, "bob")], ["id", "name"])
    result = input_df.withColumn("name", upper(col("name")))

    expected_df = spark.createDataFrame([(1, "ALICE"), (2, "BOB")], ["id", "name"])

    assert_df_equality(result, expected_df, ignore_row_order=True, ignore_nullable=True)
```

The `ignore_row_order=True` parameter treats the DataFrames as unordered sets, which is the correct semantics for most transformations. `ignore_nullable=True` strips nullable flags from both schemas before comparison, avoiding false failures when a hand-constructed expected DataFrame has different nullability metadata.

For UDF testing, `assert_column_equality` compares two columns within the same DataFrame and produces focused output.

```python
from chispa import assert_column_equality
import pyspark.sql.functions as F

def remove_non_word_characters(col):
    return F.regexp_replace(col, r"[^\w\s]+", "")

def test_remove_non_word_characters(spark):
    data = [("jo&&se", "jose"), ("**li**", "li"), (None, None)]
    df = (spark.createDataFrame(data, ["name", "expected_name"])
          .withColumn("clean_name", remove_non_word_characters(F.col("name"))))
    assert_column_equality(df, "clean_name", "expected_name")
```

When the assertion fails, chispa highlights the specific rows that differ, making debugging faster.

#### Using pyspark.testing (Spark 3.4+)

Spark 3.4 introduced built-in assertion utilities. They are a good choice when you want zero additional dependencies.

```python
from pyspark.testing import assertDataFrameEqual

def test_aggregation(spark):
    input_df = spark.createDataFrame([("a", 10), ("b", 20), ("a", 30)], ["cat", "amt"])
    result = input_df.groupBy("cat").sum("amt")

    expected_df = spark.createDataFrame([("a", 40), ("b", 20)], ["cat", "sum(amt)"])

    assertDataFrameEqual(result, expected_df, checkRowOrder=False)
```

The `checkRowOrder=False` parameter is the equivalent of chispa's `ignore_row_order`. The built-in utility also supports `ignoreNullable`, `ignoreColumnOrder`, and `ignoreSchemaMetadata` in later Spark versions. It does not provide an approximate equality helper.

#### Manual Comparison with subtract()

For simple cases or when you want to avoid dependencies, `subtract()` in both directions verifies set equality. This is distributed and handles duplicates correctly.

```python
def test_join(spark):
    left = spark.createDataFrame([(1, "a"), (2, "b")], ["id", "left_val"])
    right = spark.createDataFrame([(1, "x"), (3, "y")], ["id", "right_val"])

    result = left.join(right, on="id", how="inner")
    expected = spark.createDataFrame([(1, "a", "x")], ["id", "left_val", "right_val"])

    assert result.subtract(expected).count() == 0
    assert expected.subtract(result).count() == 0
```

This approach does not produce a detailed diff. If the assertion fails, you know only that the DataFrames differ, not which rows or columns are wrong. Use `exceptAll()` to find the differing rows when you need more detail.

#### Handling Row Order and Schema Differences

Row order is the most common source of false failures. Always use an order-independent comparison unless the transformation explicitly guarantees order, such as `orderBy()`. For schema differences, decide whether the difference is meaningful. Nullability and metadata often differ between hand-constructed expected DataFrames and transformation outputs. Use `ignore_nullable=True` and `ignore_metadata=True` when these differences are not part of the test's intent.

If you need to verify the schema as a contract, compare schemas separately.

```python
from chispa.schema_comparer import assert_schema_equality

def test_output_schema(spark):
    df = spark.createDataFrame([(1, "a")], ["id", "name"])
    result = df.withColumn("id", col("id").cast("long"))

    expected_schema = spark.createDataFrame([(1, "a")], ["id", "name"]).schema
    expected_schema = expected_schema.add("id", "bigint", False)

    assert_schema_equality(result.schema, expected_schema, ignore_nullable=False)
```

#### Approximate Equality for Floating Point

Floating-point columns require tolerance-based comparison. `chispa.assert_approx_df_equality` accepts a `precision` parameter.

```python
from chispa import assert_approx_df_equality

def test_approx_equality(spark):
    actual_df = spark.createDataFrame([(1, 0.1 + 0.2)], ["id", "value"])
    expected_df = spark.createDataFrame([(1, 0.3)], ["id", "value"])

    assert_approx_df_equality(actual_df, expected_df, precision=1e-9)
```

Without this, exact equality fails on values that are mathematically equal but differ in the last bits due to floating-point arithmetic.

#### Performance Implications and Configuration

The comparison method affects test speed and memory usage. `collect()` on large DataFrames is dangerous. `subtract()` and `exceptAll()` are distributed and scale. chispa and `assertDataFrameEqual` use distributed operations internally and pull only aggregated diffs to the driver.

Configuration parameters that improve test performance:

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.shuffle.partitions` | `200` | Set to `2` for tests to avoid 200-task shuffles. |
| `spark.default.parallelism` | varies | Set to `2` for local tests. |
| `spark.ui.enabled` | `true` | Set to `false` to skip UI overhead. |
| `spark.sql.adaptive.enabled` | `true` | Set to `false` for deterministic physical plans. |
| `spark.sql.adaptive.coalescePartitions.enabled` | `true` | Disable for reproducible partition counts. |
| `spark.sql.catalogImplementation` | `in-memory` | Use in-memory catalog to avoid Hive metastore startup. |
| `spark.driver.host` | auto | Set to `127.0.0.1` to avoid hostname resolution delays. |

Trade-offs between comparison methods:

| Choice | Benefit | Cost |
|---|---|---|
| chispa | Readable diffs, flexible parameters | Third-party dependency |
| pyspark.testing | Built-in, no dependency | Less flexible, Spark 3.4+ only |
| subtract() | Distributed, no dependency | No detailed diff |
| collect() | Simple, exact | Driver OOM on large data, order-sensitive |
| toPandas() | Pandas ecosystem | Collects all data, dtype mismatches |
| ignore_row_order | Fewer false failures | May mask ordering bugs |
| exact comparison | Catches ordering bugs | False failures from non-deterministic order |

#### Best Practices

- Use `chispa.assert_df_equality` or `pyspark.testing.assertDataFrameEqual` for most comparisons. They provide readable diffs and flexible parameters.
- Set `ignore_row_order=True` (or `checkRowOrder=False`) unless the transformation explicitly guarantees order.
- Set `ignore_nullable=True` when comparing hand-constructed expected DataFrames against transformation output.
- Use `assert_column_equality` for UDF testing; it produces more focused output than whole-DataFrame comparison.
- Use `assert_approx_df_equality` for floating-point columns to avoid precision-related false failures.
- Keep test DataFrames small. Unit tests should not process large data.
- Use a session-scoped SparkSession and set `spark.sql.shuffle.partitions=2` for speed.
- Test schema as a separate contract when the schema is important, not as a side effect of data comparison.
- Use `subtract()` or `exceptAll()` for simple set-equality checks when you want to avoid dependencies.
- Never use `collect()` on large DataFrames in tests. It can cause driver OOM and slow down the suite.

#### Common Pitfalls and Limitations

- Comparing DataFrames with `==` does not work. Python's equality operator is not defined for DataFrames.
- Using `collect()` on large DataFrames causes driver out-of-memory errors and defeats distributed testing.
- Ignoring row order causes false failures. Always use an order-independent comparison unless order is guaranteed.
- Schema nullability and metadata differences cause failures even when data is correct. Use `ignore_nullable` and `ignore_metadata`.
- Floating-point comparisons without tolerance fail on mathematically equal values.
- `subtract()` does not report which rows differ. Use `exceptAll()` or a dedicated assertion library for detailed diffs.
- chispa and `assertDataFrameEqual` have version-specific behavior. Check compatibility with your PySpark version.
- Comparing DataFrames that contain `NaN` values requires special handling. Use `allow_nan_equality` in chispa if needed.
- Duplicate rows are handled correctly by `subtract()` and `exceptAll()` but not by naive `collect()` and list equality unless you account for multiplicity.
- Mocking SparkSession bypasses the execution engine and hides real bugs. Do not mock SparkSession for DataFrame comparison tests.

#### Summary

Comparing two DataFrames in a PySpark test requires handling row order, schema differences, nullability, and floating-point precision. The best practice is to use a dedicated assertion library such as `chispa` or the built-in `pyspark.testing.assertDataFrameEqual`, configured with `ignore_row_order=True` and `ignore_nullable=True` as appropriate. For simple cases, `subtract()` in both directions provides distributed set equality without dependencies. Avoid `collect()` on large DataFrames, and never compare DataFrames with `==`. Test schemas separately when they are contracts, and use approximate equality for floating-point columns. In interviews, emphasize the trade-offs between readability, dependency footprint, and distributed scalability, and demonstrate awareness of the common false-failure modes.
