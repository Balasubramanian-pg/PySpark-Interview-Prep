### 4.6.5 How do you test UDFs locally without spinning up a full Spark cluster

User-defined functions (UDFs) encapsulate custom logic that cannot be expressed with built-in Spark functions. Testing them does not require a cluster. The key insight is that a UDF is just a Python function wrapped for distributed execution. You can test the Python function directly with plain unit tests, and then verify the Spark integration in a local SparkSession running in `local` mode. This two-layer approach catches logic errors quickly and isolates serialization or type issues without the overhead of a cluster.

#### The Two-Layer Testing Approach

Testing UDFs effectively means separating the pure logic from the Spark execution wrapper.

- **Layer 1: Pure Python unit tests.** Test the function as you would any Python function. No SparkSession, no DataFrame, no cluster. These tests run in milliseconds and catch the majority of logic errors.
- **Layer 2: Local SparkSession integration tests.** Create a local SparkSession with `master("local[2]")`, register the UDF, apply it to a small DataFrame, and assert the output. This catches serialization issues, null handling, and type mismatches that only appear in Spark.

This separation is important because Spark UDFs introduce overhead and complexity. Testing the Python function first ensures that when an integration test fails, the problem is in the Spark integration, not the logic.

#### Testing the Python Function Directly

Most UDF logic is pure Python. Test it with pytest or unittest without any Spark dependency.

```python
# udfs.py
def categorize_amount(amount):
    if amount is None:
        return "unknown"
    if amount < 50:
        return "low"
    return "high"
```

```python
# test_udfs.py
from udfs import categorize_amount

def test_categorize_amount_low():
    assert categorize_amount(10) == "low"

def test_categorize_amount_high():
    assert categorize_amount(100) == "high"

def test_categorize_amount_none():
    assert categorize_amount(None) == "unknown"

def test_categorize_amount_boundary():
    assert categorize_amount(50) == "high"
    assert categorize_amount(49.99) == "low"
```

These tests run instantly. They verify the function contract, including edge cases such as `None` and boundary values. If the function has external dependencies, mock them at this layer.

#### Testing the UDF in a Local SparkSession

After the Python function is verified, test it through Spark. Use a session-scoped local SparkSession configured for speed. The goal is to confirm that Spark can serialize the function, call it per row, and return the expected type.

```python
import pytest
from pyspark.sql import SparkSession
from pyspark.sql.functions import udf, col
from pyspark.sql.types import StringType
from chispa import assert_df_equality
from udfs import categorize_amount

@pytest.fixture(scope="session")
def spark():
    return (
        SparkSession.builder
        .master("local[2]")
        .appName("UDFLocalTests")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.ui.enabled", "false")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.catalogImplementation", "in-memory")
        .getOrCreate()
    )

def test_categorize_udf(spark):
    categorize_udf = udf(categorize_amount, StringType())

    input_df = spark.createDataFrame(
        [(1, 10.0), (2, 100.0), (3, None)],
        ["id", "amount"]
    )

    result = input_df.withColumn("category", categorize_udf(col("amount")))

    expected_df = spark.createDataFrame(
        [(1, 10.0, "low"), (2, 100.0, "high"), (3, None, "unknown")],
        ["id", "amount", "category"]
    )

    assert_df_equality(result, expected_df, ignore_row_order=True)
```

The local SparkSession runs in the same JVM as the test. It does not require a cluster. The configuration parameters keep the session lightweight: `spark.sql.shuffle.partitions=2` avoids 200-task shuffles, `spark.ui.enabled=false` skips UI startup, and `spark.sql.adaptive.enabled=false` ensures deterministic plans.

#### Testing Pandas UDFs (Vectorized UDFs)

Pandas UDFs operate on Pandas Series or DataFrames and use Apache Arrow for transfer. They are faster than row-at-a-time Python UDFs but have additional requirements. Test them in two layers as well.

First, test the underlying Pandas function directly with small Pandas DataFrames.

```python
# pandas_udfs.py
import pandas as pd

def categorize_series(amounts: pd.Series) -> pd.Series:
    return amounts.apply(lambda x: "unknown" if pd.isna(x) else ("low" if x < 50 else "high"))
```

```python
# test_pandas_udfs.py
import pandas as pd
from pandas_udfs import categorize_series

def test_categorize_series_directly():
    input_series = pd.Series([10.0, 100.0, None])
    result = categorize_series(input_series)
    expected = pd.Series(["low", "high", "unknown"])
    pd.testing.assert_series_equal(result, expected)
```

Then, test the Pandas UDF through Spark. Enable Arrow for faster conversion.

```python
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import StringType

def test_categorize_pandas_udf(spark):
    categorize_pandas_udf = pandas_udf(categorize_series, StringType())

    input_df = spark.createDataFrame(
        [(1, 10.0), (2, 100.0), (3, None)],
        ["id", "amount"]
    )

    result = input_df.withColumn("category", categorize_pandas_udf(col("amount")))

    expected_df = spark.createDataFrame(
        [(1, 10.0, "low"), (2, 100.0, "high"), (3, None, "unknown")],
        ["id", "amount", "category"]
    )

    assert_df_equality(result, expected_df, ignore_row_order=True)
```

For Pandas UDFs, ensure `spark.sql.execution.arrow.pyspark.enabled=true` is set in the SparkSession configuration to avoid fallback to slower non-Arrow paths.

#### Testing UDFs in SQL

If you register the UDF for SQL use, test it through a SQL query. Register the UDF and run a query against a temporary view.

```python
def test_udf_in_sql(spark):
    spark.udf.register("categorize_amount", categorize_amount, StringType())

    input_df = spark.createDataFrame(
        [(1, 10.0), (2, 100.0), (3, None)],
        ["id", "amount"]
    )
    input_df.createOrReplaceTempView("amounts")

    result = spark.sql("""
        SELECT id, amount, categorize_amount(amount) AS category
        FROM amounts
    """)

    expected = [(1, 10.0, "low"), (2, 100.0, "high"), (3, None, "unknown")]
    assert [tuple(row) for row in result.collect()] == expected
```

SQL equivalent for the UDF call:

```sql
SELECT id, amount, categorize_amount(amount) AS category
FROM amounts;
```

#### Configuration for Fast Local UDF Tests

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.shuffle.partitions` | `200` | Set to `2` for tests to avoid 200-task shuffles. |
| `spark.default.parallelism` | varies | Set to `2` for local tests. |
| `spark.ui.enabled` | `true` | Set to `false` to skip UI overhead. |
| `spark.sql.adaptive.enabled` | `true` | Set to `false` for deterministic plans. |
| `spark.sql.catalogImplementation` | `in-memory` | Use in-memory catalog to avoid Hive metastore startup. |
| `spark.driver.host` | auto | Set to `127.0.0.1` to avoid hostname resolution delays. |
| `spark.sql.execution.arrow.pyspark.enabled` | `false` | Enable Arrow for Pandas UDF tests. |
| `spark.sql.execution.arrow.pyspark.fallback.enabled` | `true` | Set to `false` to fail fast if Arrow is not available. |

#### Performance Implications and Trade-offs

| Layer | Speed | Catches | Does Not Catch |
|---|---|---|---|
| Pure Python test | Milliseconds | Logic errors, edge cases, null handling | Serialization, Spark type conversion |
| Local SparkSession test | Seconds (after session startup) | Serialization, type mismatches, Spark integration | Cluster-specific issues, skew, resource contention |
| Cluster integration test | Minutes | Everything above plus distributed behavior | N/A |

Python UDFs are slower than Pandas UDFs because each row is serialized between the JVM and Python. Pandas UDFs batch data using Arrow, reducing overhead. Testing the pure Python function is always the fastest and should be the first line of defense.

#### Best Practices

- Test the Python function directly before testing the Spark UDF. This separates logic errors from integration errors.
- Use a session-scoped local SparkSession with minimal resources. Do not create a new session per test.
- Test edge cases: `None`, empty strings, boundary values, and type mismatches.
- For Pandas UDFs, test the Pandas function directly with Pandas DataFrames, then through Spark with Arrow enabled.
- Use `chispa` or `pyspark.testing.assertDataFrameEqual` for DataFrame comparisons.
- Keep UDF logic pure and side-effect free. Avoid external dependencies inside the UDF.
- Set `spark.sql.execution.arrow.pyspark.fallback.enabled=false` in tests to catch Arrow compatibility issues early.
- Test the UDF in SQL if it is registered for SQL use.
- Do not mock SparkSession. Mock external I/O boundaries instead.

#### Common Pitfalls and Limitations

- Non-serializable objects captured in the UDF closure cause failures at runtime. Test the UDF in Spark to catch these.
- Python UDFs return `None` for null inputs by default, but the declared return type may not be nullable. This causes errors. Test null handling explicitly.
- Pandas UDFs require Arrow. If Arrow is not installed or compatible, the UDF falls back to slower paths or fails. Test with Arrow enabled.
- Type mismatches between the Python return value and the declared Spark type cause runtime errors. Test with representative data.
- Python UDFs are significantly slower than built-in functions. If performance matters, consider Pandas UDFs or built-in alternatives.
- Testing only through Spark without testing the Python function directly makes debugging harder and slows down the test suite.
- Local mode does not replicate cluster behavior for partitioning, skew, or resource contention. Use cluster integration tests for those concerns.
- UDFs that rely on global state or external files may behave differently in distributed execution. Avoid such dependencies.
- The `udf` function in PySpark is deprecated in favor of the `@udf` decorator in some contexts. Both work; test accordingly.

#### Summary

Testing UDFs locally without a cluster follows a two-layer approach. First, test the pure Python function with plain unit tests. This is fast and catches logic errors, null handling, and edge cases. Second, test the UDF in a local SparkSession running in `local` mode to verify serialization, type conversion, and Spark integration. For Pandas UDFs, test the underlying Pandas function directly, then through Spark with Arrow enabled. Configuration parameters such as `spark.sql.shuffle.partitions=2`, `spark.ui.enabled=false`, and `spark.sql.execution.arrow.pyspark.enabled=true` keep tests fast. Best practices include testing edge cases, avoiding non-serializable closures, and never mocking SparkSession. In interviews, emphasize the separation of logic testing from integration testing and the importance of local mode for catching serialization issues without cluster overhead.
