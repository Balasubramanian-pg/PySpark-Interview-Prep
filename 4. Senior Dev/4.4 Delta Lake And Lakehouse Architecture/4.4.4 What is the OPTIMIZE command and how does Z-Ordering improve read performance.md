### 4.4.4 What is the OPTIMIZE command and how does Z-Ordering improve read performance

**OPTIMIZE** and **Z-Ordering** are Delta Lake's primary tools for maintaining read performance as tables grow. Frequent writes, streaming ingestion, and updates create many small Parquet files, a condition known as the **small file problem**. Small files increase metadata overhead, reduce parallelism, and weaken data skipping because file-level statistics become fragmented. The `OPTIMIZE` command performs **bin-packing** to compact small files into larger, right-sized files. When combined with `ZORDER BY`, it also physically co-locates related data within files, tightening the min/max ranges stored in file statistics so that queries can skip more files. This answer explains both mechanisms, their performance implications, configuration parameters, trade-offs, and when to use each.

#### The Small File Problem

Delta Lake's ACID transaction log and append-only architecture naturally produce file fragmentation. Every write operation, whether from a batch job or a streaming pipeline, generates new Parquet files. Over time, this leads to metadata overhead (reading thousands of small files requires significant I/O just to process file metadata), inefficient parallelization (query engines struggle to distribute small files efficiently), and reduced data skipping effectiveness (statistics at the file level become less useful when data is scattered across many files). A table with 10,000 files of 10 MB each performs significantly worse than the same data consolidated into 100 files of 1 GB each. Common causes include user repartitioning, frequent incremental updates, and partitioning on high-cardinality columns.

#### The OPTIMIZE Command: File Compaction

`OPTIMIZE` performs **bin-packing**, grouping small files into optimally sized bins and rewriting them as larger files. The operation is **idempotent**: running it twice on the same dataset has no additional effect on the second run.

Basic syntax in PySpark and SQL:

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/sales")

# Compact all small files in the table
delta_table.optimize().executeCompaction()

# Compact only a specific partition
delta_table.optimize().where("date = '2025-12-01'").executeCompaction()
```

```sql
-- Optimize entire table
OPTIMIZE sales;

-- Optimize specific partition
OPTIMIZE sales WHERE date = '2025-12-01';
```

The target file size is controlled by the `spark.databricks.delta.optimize.maxFileSize` configuration, which defaults to 1 GB (1073741824 bytes). For streaming workloads with frequent small writes, reducing this to 128 MB or 100 MB is often appropriate.

#### Z-Ordering: Multi-Dimensional Clustering

While `OPTIMIZE` addresses the quantity of files, `ZORDER BY` addresses their internal organization. Z-Ordering is a data layout technique that co-locates related data in the same files by applying a **Z-Order (Morton) space-filling curve** across one or more columns. The technique tightens the min/max ranges stored in file-level statistics, which improves **file skipping** when queries filter on those columns.

The Z-Order curve maps multi-dimensional data into a single dimension while preserving locality. Records with similar values across the Z-Order columns are placed in the same files. When a query filters on a Z-Ordered column, Delta Lake consults the file-level min/max statistics and skips any file whose range does not overlap the filter predicate.

Z-Ordering is applied as part of the `OPTIMIZE` command, and the columns are specified each time you run it—they are not stored in table metadata.

```python
# Apply Z-Ordering on two columns
delta_table.optimize().executeZOrderBy("order_date", "region")
```

```sql
OPTIMIZE sales ZORDER BY (order_date, region);
```

Scope Z-Ordering with a `WHERE` predicate to limit which files are rewritten. This is useful for incremental maintenance, such as Z-Ordering only the most recent data after an ingestion run.

```python
# Z-Order only files that contain data from the last 7 days
delta_table.optimize().where("order_date >= current_date() - INTERVAL 7 DAYS").executeZOrderBy("order_date", "region")
```

```sql
OPTIMIZE sales WHERE order_date >= current_date() - INTERVAL 7 DAYS ZORDER BY (order_date, region);
```

Using a `WHERE` predicate reduces the amount of data rewritten, lowering compute cost and execution time.

#### How Z-Ordering Improves Read Performance

The mechanism is straightforward: Delta Lake stores min/max statistics for each column in each data file's `add` action in the transaction log. When a query includes a filter such as `WHERE region = 'US'`, Delta Lake reads the statistics and determines whether a file could contain matching rows. If the file's min/max range for `region` does not include `'US'`, the file is skipped entirely.

Without Z-Ordering, a table that is sorted by insertion time or ingestion order has wide min/max ranges for filter columns. Every file might contain values spanning the entire range of `region`, so no files are skipped. With Z-Ordering, records are reorganized so that files have narrow min/max ranges for the Z-Ordered columns. For example, instead of every file containing regions from "DE" to "US", Z-Ordering can produce files that contain only "US" records, files that contain only "DE" and "ES" records, and so on. A query for `region = 'US'` then reads only the files whose range includes "US", skipping the rest.

| Aspect | Without Z-Ordering | With Z-Ordering |
|---|---|---|
| File min/max range for filter column | Wide, overlapping across files | Narrow, non-overlapping ranges |
| Data skipping effectiveness | Low; most files scanned | High; many files skipped |
| Query I/O | Reads all files | Reads only matching files |
| Layout | Ingestion order or arbitrary | Multi-dimensional locality |

#### Performance Implications and Configuration

`OPTIMIZE` rewrites data files and writes a new commit to the transaction log. It is a full data rewrite operation for the files it touches. The time required scales with the total data volume being optimized, not just the amount of new data.

Z-Ordering is **not idempotent**; it operates incrementally. The time Z-Ordering takes is not guaranteed to decrease over multiple runs. However, if no new data was added to a partition that was just Z-Ordered, running Z-Ordering again on that partition has no effect.

Real-world performance improvements from `OPTIMIZE` operations include query latency reductions of 40–60% on tables with severe fragmentation, up to 80% reduction in metadata processing time, and fewer API calls to object storage. A production e-commerce table with 15,000 small files was optimized to 150 files, reducing aggregate queries from 45 seconds to 18 seconds.

| Parameter | Default | Description |
|---|---|---|
| `spark.databricks.delta.optimize.maxFileSize` | `1073741824` (1 GB) | Target output file size for OPTIMIZE. |
| `spark.databricks.delta.optimizeWrite.binSize` | `1024` (MB) | Target bin size for optimize write. |
| `spark.databricks.delta.autoCompact.enabled` | `true` (Databricks) | Enables automatic small-file compaction after writes. |
| `spark.databricks.delta.autoCompact.maxFileSize` | `128` (MB) | Target file size for auto compaction. |
| `spark.databricks.delta.optimizeWrite.enabled` | `true` (Databricks) | Enables pre-write bin-packing. |
| `delta.targetFileSize` | none | Table property to set target file size for OPTIMIZE. |
| `delta.autoOptimize.autoCompact` | none | Table property to enable auto compaction per table. |
| `delta.autoOptimize.optimizeWrite` | none | Table property to enable optimize write per table. |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| OPTIMIZE (bin-packing) | Reduces small files, improves parallelism, idempotent | Full rewrite of affected files; compute and I/O cost |
| ZORDER BY | Improves data skipping for multi-column filters | Full data rewrite; not idempotent; not incremental |
| Z-Order on 1–3 columns | Strong locality, effective file skipping | More columns degrade effectiveness exponentially |
| Z-Order on 5+ columns | Seems comprehensive | No single dimension has strong locality; file skipping becomes ineffective |
| Scoped Z-Order with WHERE | Reduces rewritten data and compute cost | Only filters on partition/clustering keys |
| Liquid clustering | Incremental, flexible, handles skew | Newer; not compatible with Z-Ordering or partitioning |
| Auto compaction | Automatic maintenance after writes | Can add write latency |
| Optimize write | Pre-write bin-packing, fewer small files | Shuffles data before write; adds overhead |

#### Z-Ordering vs Liquid Clustering

Databricks recommends **liquid clustering** for all new tables instead of Z-Ordering. Liquid clustering uses the Hilbert curve for 2+ columns—an improvement over Z-Order, which applies only the Z-Order curve for multi-dimensional clustering. Liquid clustering is incremental, persists clustering columns in table metadata, and handles skewed data more effectively. Z-Ordering remains appropriate for existing workflows on older runtimes or when you need multi-column file skipping without partitioning.

| Aspect | Z-Ordering | Liquid Clustering |
|---|---|---|
| Column changes | Must rerun OPTIMIZE ZORDER BY with new columns | ALTER TABLE ... CLUSTER BY persists the definition |
| Incremental support | No incremental mode; use WHERE to limit scope | Incremental mode processes only new/changed files |
| Metadata | No persistent column definition | Clustering columns stored in table metadata |
| Multi-column layout | Z-Order curve | Hilbert curve for 2+ columns |
| Skew handling | Fails on skewed data | Adapts to distribution |

#### Complete Python Example

The following self-contained example creates a Delta table with small files, runs OPTIMIZE and Z-Ordering, and demonstrates the effect on query performance.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, rand, lit
from delta.tables import DeltaTable
import time

spark = (
    SparkSession.builder
    .appName("OptimizeZOrderDemo")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

table_path = "/tmp/delta/optimize_zorder_demo"

# Create a table with many small files by writing multiple times
for i in range(20):
    data = [(j, f"region_{j % 5}", f"2025-01-{j % 28 + 1:02d}") for j in range(i * 100, (i + 1) * 100)]
    df = spark.createDataFrame(data, ["id", "region", "order_date"])
    df.write.format("delta").mode("append").save(table_path)

# Inspect file count before optimization
delta_table = DeltaTable.forPath(spark, table_path)
files_before = spark.read.format("delta").load(table_path).rdd.getNumPartitions()
print(f"Partitions before OPTIMIZE: {files_before}")

# Run OPTIMIZE with Z-Ordering
delta_table.optimize().executeZOrderBy("region", "order_date")

# Inspect file count after optimization
files_after = spark.read.format("delta").load(table_path).rdd.getNumPartitions()
print(f"Partitions after OPTIMIZE: {files_after}")

# Query with a filter on the Z-Ordered column
start = time.time()
result = spark.read.format("delta").load(table_path).where(col("region") == "region_0").count()
print(f"Filtered query returned {result} rows in {time.time() - start:.2f} seconds")

spark.stop()
```

#### SQL Equivalents

```sql
-- Compact small files
OPTIMIZE sales;

-- Compact with Z-Ordering
OPTIMIZE sales ZORDER BY (region, order_date);

-- Scope Z-Ordering to recent data
OPTIMIZE sales WHERE order_date >= current_date() - INTERVAL 7 DAYS ZORDER BY (region, order_date);

-- Inspect table history to see OPTIMIZE operations
DESCRIBE HISTORY sales;

-- Inspect table details to see file count
DESCRIBE DETAIL sales;
```

#### Best Practices

- Run `OPTIMIZE` regularly on tables that receive frequent small writes, such as streaming ingestion or MERGE operations.
- Use `ZORDER BY` on the 1–3 columns most frequently used as query filters. Identify these columns by analyzing query patterns, not by guessing.
- Use a `WHERE` predicate to scope `OPTIMIZE ZORDER BY` to recently modified partitions for large tables. This avoids rewriting the entire table on every run.
- Set `spark.databricks.delta.optimize.maxFileSize` appropriately for your workload. 1 GB is the default, but 128 MB is often better for streaming.
- For new tables, prefer liquid clustering over Z-Ordering. It is incremental, flexible, and handles skew better.
- Enable auto compaction and optimize write for tables that receive frequent small writes.
- Monitor table size, file count, and query performance using `DESCRIBE DETAIL` and `DESCRIBE HISTORY`.
- Run `OPTIMIZE` during off-peak hours for large tables, because it rewrites data and consumes compute and I/O.

#### Common Pitfalls and Limitations

- Z-Ordering is not idempotent. Running it repeatedly does not guarantee decreasing execution time.
- Z-Ordering on 5 or more columns degrades effectiveness exponentially. Five-column Z-Order often performs worse than two-column Z-Order for frequent query patterns.
- Z-Ordering fails on skewed data. If one value dominates a column, every file may contain that value, and no files can be skipped.
- Running `OPTIMIZE ZORDER BY` daily on a large table performs a full data rewrite every day, even if only a small amount of new data was added.
- `OPTIMIZE` does not delete the original small files immediately. Delta Lake retains them to support snapshot isolation; they are removed by `VACUUM` after the retention period.
- `OPTIMIZE` on a partitioned table applies within each partition independently. It does not reorganize data across partitions.
- Z-Ordering and partitioning can be combined, but liquid clustering is not compatible with either.
- The `WHERE` clause in `OPTIMIZE` only supports filters on partition or clustering key attributes.
- Auto compaction and optimize write add overhead to write operations. They are beneficial for tables with frequent small writes but can slow down bulk writes.

#### Summary

The `OPTIMIZE` command solves the small file problem by compacting many small Parquet files into fewer, right-sized files using bin-packing. It is idempotent and improves query performance by reducing metadata overhead and increasing parallelism. Z-Ordering, applied through `OPTIMIZE ZORDER BY`, goes further by physically co-locating related data using a space-filling curve, which tightens file-level min/max statistics and enables effective data skipping for multi-column filters. Z-Ordering works best on 1–3 columns and fails on skewed data. For new tables, liquid clustering is the recommended alternative because it is incremental, flexible, and handles skew more gracefully. In interviews, emphasize the distinction between compaction and clustering, the idempotent versus incremental nature of the two operations, and the importance of scoping Z-Ordering to avoid unnecessary full rewrites.
