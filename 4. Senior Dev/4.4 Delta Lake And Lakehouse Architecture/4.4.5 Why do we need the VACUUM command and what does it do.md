### 4.4.5 Why do we need the VACUUM command and what does it do

**VACUUM** is the Delta Lake command that physically deletes data files that are no longer referenced by the current transaction log and are older than a specified retention threshold. Delta Lake retains old data files to support time travel, snapshot isolation, and concurrent readers. Without VACUUM, storage grows indefinitely as every write, update, delete, and merge leaves behind files that are no longer part of the current table state. VACUUM is therefore essential for cost management, compliance with data deletion requirements, and reducing metadata overhead. However, it directly affects time travel and streaming consumers, so its retention policy must be chosen carefully.

#### What VACUUM Does

VACUUM performs a specific and limited operation. It does not compact files, rewrite data, or change the table schema. It only deletes files.

- It reads the transaction log to determine the current snapshot of the table.
- It lists all data files in the table directory.
- It identifies files that are not referenced by the current snapshot and are older than the retention threshold.
- It deletes those files from storage.
- It does not delete transaction log entries. Log retention is controlled separately by `delta.logRetentionDuration`.
- It is not triggered automatically. It must be run manually or scheduled.
- It supports a dry run mode that lists files that would be deleted without actually deleting them.

VACUUM is different from OPTIMIZE. OPTIMIZE compacts small files into larger ones and rewrites data. VACUUM only removes files that are already unreferenced. They are complementary: OPTIMIZE improves read performance, while VACUUM reclaims storage.

#### Why VACUUM is Needed

Delta Lake's ACID guarantees and time travel depend on retaining historical data files. Every commit adds new files and may mark old files as removed. The removed files remain physically present until VACUUM deletes them.

- **Storage cost**: Without VACUUM, deleted or overwritten data accumulates forever, increasing cloud storage costs.
- **Compliance and data deletion**: Regulations such as GDPR require physical deletion of personal data upon request. VACUUM ensures that deleted rows are physically removed after the retention period.
- **Metadata overhead**: A large number of stale files increases directory listing time and can slow down table operations.
- **Snapshot isolation**: Readers that started before a write may still need old files. VACUUM must wait until those readers are done, which is why a retention threshold exists.

#### How VACUUM Works

VACUUM uses the transaction log to distinguish referenced files from unreferenced ones. A file is unreferenced if it is not part of the latest table snapshot. However, it may still be needed by an older version for time travel or by a concurrent reader. The retention threshold ensures that VACUUM does not delete files that might still be in use.

The default retention is 7 days (168 hours). Delta Lake enforces a safety check that prevents you from setting a retention below this threshold unless you explicitly disable the check. This prevents accidental deletion of files needed for time travel or by long-running queries.

| Parameter | Default | Description |
|---|---|---|
| `delta.deletedFileRetentionDuration` | `7 days` | Default retention for VACUUM. Files older than this can be deleted. |
| `delta.logRetentionDuration` | `30 days` | Retention for transaction log entries. VACUUM does not affect this. |
| `spark.databricks.delta.retentionDurationCheck.enabled` | `true` | Prevents VACUUM with retention below the safety threshold. |
| `spark.databricks.delta.vacuum.parallelDelete.enabled` | `false` | Enables parallel file deletion during VACUUM. |
| `spark.databricks.delta.vacuum.parallelDelete.parallelism` | `20` | Number of parallel delete threads when parallel delete is enabled. |

#### Syntax and Examples

VACUUM can be run in SQL or through the DeltaTable API in PySpark.

SQL syntax:

```sql
-- Vacuum with default retention (7 days)
VACUUM sales;

-- Vacuum with a specific retention
VACUUM sales RETAIN 168 HOURS;

-- Dry run: list files that would be deleted without deleting them
VACUUM sales RETAIN 168 HOURS DRY RUN;
```

PySpark syntax:

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/sales")

# Vacuum with default retention
delta_table.vacuum()

# Vacuum with specific retention in hours
delta_table.vacuum(168)

# Dry run: returns a DataFrame of files that would be deleted
files_to_delete = delta_table.vacuum(168)
files_to_delete.show(truncate=False)
```

#### Complete Self-Contained Example

The following example creates a Delta table, deletes rows, demonstrates that time travel works before VACUUM, then runs VACUUM and shows that time travel to the vacuumed version fails.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col
from delta.tables import DeltaTable

spark = (
    SparkSession.builder
    .appName("VacuumDemo")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

table_path = "/tmp/delta/vacuum_demo"

# Create version 0
data = [(1, "Alice", 100.0), (2, "Bob", 200.0), (3, "Charlie", 300.0)]
df = spark.createDataFrame(data, ["id", "name", "amount"])
df.write.format("delta").mode("overwrite").save(table_path)

# Create version 1 by deleting a row
delta_table = DeltaTable.forPath(spark, table_path)
delta_table.delete(condition=col("id") == 2)

print("Current version after delete:")
spark.read.format("delta").load(table_path).orderBy("id").show()

print("Time travel to version 0 before VACUUM:")
spark.read.format("delta").option("versionAsOf", 0).load(table_path).orderBy("id").show()

# Run VACUUM with 0 hours retention to force deletion of unreferenced files.
# This requires disabling the safety check, which is shown for demonstration only.
spark.conf.set("spark.databricks.delta.retentionDurationCheck.enabled", "false")
delta_table.vacuum(0)

print("Time travel to version 0 after VACUUM (expected to fail if files were deleted):")
try:
    spark.read.format("delta").option("versionAsOf", 0).load(table_path).orderBy("id").show()
except Exception as e:
    print("Time travel failed as expected:", type(e).__name__)

spark.stop()
```

In production, never set retention to 0. Use a retention that matches your time travel and streaming consumer requirements.

#### Performance Implications

VACUUM is an I/O-intensive operation. It lists all files in the table directory and deletes the unreferenced ones. For tables with millions of files, this can take a long time. Parallel delete can speed up the deletion phase, but listing is still sequential in most implementations.

- VACUUM does not rewrite data, so it does not consume CPU for compression or encoding.
- VACUUM reduces storage cost and can improve directory listing performance by reducing the number of files.
- VACUUM can run concurrently with writes. Delta Lake's optimistic concurrency control ensures that files added by concurrent writers are not deleted because they are referenced in the latest snapshot.
- VACUUM can break streaming queries that are reading from the Delta table if those queries are lagging behind and still need files that are older than the retention threshold. Always set retention longer than the maximum expected streaming lag.
- VACUUM cannot be undone. Deleted files are gone unless the underlying storage has versioning or backups enabled.

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Short retention (e.g., 0 hours) | Immediate storage reclamation, faster compliance deletion | Breaks time travel and can break lagging streaming consumers |
| Long retention (e.g., 30 days) | Preserves time travel and streaming reliability | Higher storage cost, more files retained |
| Default retention (7 days) | Balanced for most workloads | Still requires coordination with streaming consumers |
| Parallel delete enabled | Faster deletion for large tables | More I/O load on storage |
| Dry run | Safe preview of what will be deleted | Does not reclaim storage |

#### Best Practices

- Set `delta.deletedFileRetentionDuration` based on your time travel and streaming consumer requirements.
- Always run VACUUM with a `DRY RUN` first on large tables to see which files will be deleted.
- Do not disable the retention duration safety check unless you fully understand the consequences.
- Schedule VACUUM during off-peak hours to avoid impacting concurrent queries.
- Ensure that the retention period is longer than the maximum lag of any streaming query reading from the table.
- Back up data before running VACUUM if you need long-term historical retention that exceeds the retention threshold.
- Monitor storage usage and file counts with `DESCRIBE DETAIL` to decide when to run VACUUM.
- Use OPTIMIZE separately to compact small files. VACUUM does not compact.

#### Common Pitfalls and Limitations

- Running VACUUM with a short retention breaks time travel to older versions.
- VACUUM can break streaming queries that are behind. The stream fails with `FileNotFoundException` when it tries to read a vacuumed file.
- VACUUM does not delete transaction log entries. Log cleanup is controlled by `delta.logRetentionDuration`.
- VACUUM does not compact small files. Use OPTIMIZE for that.
- VACUUM is not automatic. It must be scheduled or run manually.
- VACUUM cannot be rolled back. Deleted files are permanently removed unless storage versioning is enabled.
- VACUUM on a table with concurrent writers is safe, but it can conflict with long-running readers that still need old files if retention is too short.
- VACUUM does not delete files from cloud storage immediately if bucket versioning or lifecycle policies retain them.
- Setting retention to 0 disables the safety check and is dangerous. It should only be used in test environments.

#### Summary

VACUUM is the Delta Lake command that physically deletes data files no longer referenced by the current transaction log and older than the retention threshold. It is needed to control storage costs, comply with data deletion requirements, and reduce metadata overhead. VACUUM only deletes data files; it does not touch the transaction log, compact files, or rewrite data. Its default retention is 7 days, and a safety check prevents shorter retention unless explicitly disabled. The main trade-off is between storage savings and the ability to time travel or support lagging streaming consumers. In interviews, emphasize that VACUUM is a storage reclamation tool, not a performance optimization tool, and that its retention policy must be coordinated with time travel and streaming requirements.
