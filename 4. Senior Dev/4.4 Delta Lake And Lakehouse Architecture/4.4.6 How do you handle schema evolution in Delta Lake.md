### 4.4.6 How do you handle schema evolution in Delta Lake

**Schema evolution** is the controlled modification of a Delta table's schema over time as source data changes. In a Lakehouse, upstream systems frequently add, rename, or widen columns, and pipelines must accommodate these changes without rewriting all existing data or breaking downstream consumers. Delta Lake provides a layered approach: **schema enforcement** protects the table by default, while **schema evolution** is an opt-in behavior that allows additive changes, type widening, and column mapping. This answer explains each mechanism, when to use it, and the trade-offs involved.

#### Schema Enforcement: The Default Protection

By default, Delta Lake enforces **schema on write**. When you attempt to write a DataFrame whose schema does not match the target table, the write fails with an `AnalysisException` instead of silently altering the table. This protects the table from accidental schema drift caused by malformed source data, upstream bugs, or incompatible type changes.

- Enforcement applies to batch writes, streaming writes, and `MERGE` operations.
- A write fails if the DataFrame contains columns not present in the table, or if column types are incompatible.
- Enforcement does not prevent legitimate schema changes; it only requires them to be explicit.

The following example shows a write that fails under schema enforcement:

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("SchemaEnforcementDemo").getOrCreate()

# Create a table with two columns
base_df = spark.createDataFrame([("bob", 47), ("li", 23)], ["first_name", "age"])
base_df.write.format("delta").mode("overwrite").save("/tmp/delta/people")

# This write fails: the DataFrame has an extra "country" column
new_df = spark.createDataFrame(
    [("frank", 68, "usa"), ("jordana", 26, "brasil")],
    ["first_name", "age", "country"]
)
try:
    new_df.write.format("delta").mode("append").save("/tmp/delta/people")
except Exception as e:
    print("Schema enforcement rejected the write:", type(e).__name__)
```

The SQL equivalent:

```sql
CREATE TABLE people (first_name STRING, age INT) USING DELTA;

-- This INSERT fails because the table has no country column
INSERT INTO people VALUES ('frank', 68, 'usa');
```

#### Enabling Schema Evolution with mergeSchema

The most common way to handle additive schema changes is the `mergeSchema` option on a DataFrame write. When set to `true`, Delta Lake adds columns that exist in the source DataFrame but not in the target table. Existing columns are preserved, and existing rows receive `NULL` for the new columns.

```python
# Append with schema evolution enabled
new_df.write \
    .format("delta") \
    .option("mergeSchema", "true") \
    .mode("append") \
    .save("/tmp/delta/people")

# The table now has three columns: first_name, age, country
spark.read.format("delta").load("/tmp/delta/people").show()
```

`mergeSchema` supports only **additive changes**. It does not remove existing columns, rename columns, or change existing column types. For non-additive changes, use `overwriteSchema` or DDL.

#### Automatic Schema Merge with autoMerge

Setting `mergeSchema` on every write is tedious. You can enable automatic schema merge for the session with `spark.databricks.delta.schema.autoMerge.enabled`. The default is `false`; when set to `true`, writes and `MERGE` operations can add new columns from the source without the per-write option.

```python
spark.conf.set("spark.databricks.delta.schema.autoMerge.enabled", "true")

# Now appends with new columns succeed without the mergeSchema option
new_df.write.format("delta").mode("append").save("/tmp/delta/people")
```

In SQL, the session setting is applied with `SET`:

```sql
SET spark.databricks.delta.schema.autoMerge.enabled = TRUE;
```

Automatic schema merge is permissive. It will even append a DataFrame with no schema overlap, adding all columns from the source and populating existing rows with `NULL`. This flexibility requires guardrails: validate source schemas before writing, or use a schema registry as the single source of truth.

#### Explicit Schema Changes with ALTER TABLE

For precise control, use DDL to add, rename, reorder, or replace columns. These operations update the table metadata in the transaction log without rewriting existing data files.

```sql
-- Add a column at the end
ALTER TABLE people ADD COLUMNS (country STRING);

-- Add a column after a specific column
ALTER TABLE people ADD COLUMNS (age_years INT AFTER first_name);

-- Add a nested field
ALTER TABLE people ADD COLUMNS (address.city STRING);

-- Rename a column (requires column mapping)
ALTER TABLE people RENAME COLUMN first_name TO given_name;

-- Change a column comment or reorder
ALTER TABLE people ALTER COLUMN age COMMENT 'Age in years';
ALTER TABLE people ALTER COLUMN age FIRST;
```

Notes on DDL behavior:

- When you add a column to an existing Delta table, you cannot define a `DEFAULT` value. Existing rows are treated as `NULL` for the new column.
- Nested column additions are supported only for `STRUCT` types, not arrays or maps.
- Renaming and dropping columns require **column mapping** to be enabled on the table before the operation. Column mapping tracks columns by name in table metadata rather than by physical order, allowing renames and drops without rewriting data files.
- Schema updates conflict with all concurrent Delta write operations. Streaming queries reading from the table will terminate and must be restarted.

To enable column mapping:

```sql
ALTER TABLE people SET TBLPROPERTIES ('delta.columnMapping.mode' = 'name');
```

#### Replacing the Schema with overwriteSchema

When the schema change is non-additive, such as renaming columns, removing columns, or changing data types, use `overwriteSchema` with `mode("overwrite")`. This replaces the table schema with the schema of the incoming DataFrame and rewrites the table definition. It is more disruptive than `mergeSchema` because downstream consumers expecting the old schema can break.

```python
new_df.write \
    .format("delta") \
    .option("overwriteSchema", "true") \
    .mode("overwrite") \
    .save("/tmp/delta/people")
```

Use this option deliberately. Unlike `mergeSchema`, it discards the previous schema contract.

#### Schema Evolution in MERGE Operations

`MERGE` supports schema evolution through the `WITH SCHEMA EVOLUTION` clause in SQL, or by setting `spark.databricks.delta.schema.autoMerge.enabled = true` for the session. When enabled, the merge operation can add new source columns to the target as part of the upsert.

```sql
MERGE INTO target t
USING source s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WITH SCHEMA EVOLUTION;
```

In PySpark with Delta 2.3+:

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/target")
(delta_table.alias("t")
 .merge(source_df.alias("s"), "s.id = t.id")
 .withSchemaEvolution()
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute())
```

#### Type Widening

Type widening allows you to change a column's data type to a broader type without rewriting existing data files. This is useful when a column initially defined as `INT` needs to store larger values or when a `FLOAT` needs to become `DOUBLE`. Type widening is enabled by setting a table property and requires protocol support from readers and writers.

```sql
ALTER TABLE people SET TBLPROPERTIES ('delta.enableTypeWidening' = 'true');
ALTER TABLE people ALTER COLUMN age TYPE BIGINT;
```

Supported widening paths are restricted, such as `INT` to `BIGINT`, `FLOAT` to `DOUBLE`, and `DATE` to `TIMESTAMP`. Not all type changes are allowed.

#### Comparison of Schema Evolution Mechanisms

| Mechanism | Behavior | Rewrites Data | Downstream Impact | When to Use |
|---|---|---|---|---|
| `mergeSchema` option | Adds new columns from source | No | Additive only; existing readers unaffected | Per-write control for ETL pipelines |
| `autoMerge` session setting | Adds new columns automatically | No | Additive only; permissive | Frequent evolving sources |
| `ALTER TABLE ADD COLUMNS` | Adds columns via DDL | No | Additive; existing rows get `NULL` | Explicit, controlled schema changes |
| `ALTER TABLE RENAME COLUMN` | Renames column via metadata | No (requires column mapping) | Consumers using old name break | Schema cleanup |
| `overwriteSchema` | Replaces table schema | Yes (metadata) | Breaking change | Non-additive changes, realignment |
| `WITH SCHEMA EVOLUTION` in MERGE | Evolves target during upsert | No | Additive only | Streaming upserts with new columns |
| Type widening | Broader type without rewrite | No | Readers must support new type | Column type maturity |

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.databricks.delta.schema.autoMerge.enabled` | `false` | Enables automatic schema merge for writes and MERGE operations. |
| `delta.columnMapping.mode` | `none` | Enables column mapping (`name` or `id`) for rename and drop operations. |
| `delta.enableTypeWidening` | `false` | Enables type widening for supported type changes. |
| `spark.databricks.delta.schema.autoMerge.enabled` (session) | `false` | Session-level override for automatic schema merge. |
| `delta.minReaderVersion` | `1` | Minimum reader protocol version; column mapping and type widening require higher versions. |
| `delta.minWriterVersion` | `2` | Minimum writer protocol version. |

#### Best Practices

- Keep schema enforcement enabled by default. It is your primary defense against silent data corruption.
- Use `mergeSchema` or `autoMerge` for additive changes in ETL pipelines where source schemas evolve naturally.
- Prefer explicit `ALTER TABLE` DDL for schema changes that require review and approval in production.
- Enable column mapping before you need to rename or drop columns, because it must be set before the operation.
- Use a schema registry or a documented schema definition as the single source of truth for critical tables.
- Test schema changes in a staging environment before applying them to production tables.
- Restart streaming queries after schema updates, because schema changes conflict with concurrent streaming reads.
- Monitor schema history with `DESCRIBE HISTORY` to audit who changed what and when.

#### Common Pitfalls and Limitations

- `mergeSchema` and `autoMerge` are additive only. They cannot remove columns or change existing types.
- Automatic schema merge is permissive. Without guardrails, a malformed source can add unwanted columns with `NULL` values.
- `overwriteSchema` is destructive to the schema contract. Downstream consumers that expect the old schema will break.
- Column renaming and dropping require column mapping, which must be enabled before the operation and changes the table protocol.
- Schema updates conflict with all concurrent Delta write operations. Streaming queries reading from the table will terminate.
- When you add a column to an existing Delta table, you cannot define a `DEFAULT` value. Existing rows are `NULL`.
- Type widening is restricted to specific type pairs and requires protocol version upgrades.
- Nested column additions are supported only for `STRUCT` types, not arrays or maps.
- Schema evolution does not rewrite existing data files. Historical data retains the old physical schema and is reconciled at read time.

#### Summary

Schema evolution in Delta Lake is a controlled, opt-in capability layered on top of schema enforcement. The default behavior rejects writes that do not match the table schema, protecting data integrity. Additive changes are handled with `mergeSchema` or automatic schema merge, which add new columns without rewriting data. Non-additive changes require `overwriteSchema` or DDL operations such as `ALTER TABLE ADD COLUMNS`, `RENAME COLUMN`, and `TYPE` changes. Column mapping enables rename and drop without data rewrites. `MERGE` supports schema evolution for upserts. In production, keep enforcement enabled, use schema registries as the source of truth, and test schema changes before applying them to critical tables. In interviews, emphasize that schema evolution is permissive and must be managed deliberately, and that it trades flexibility for the need to protect downstream consumers.
