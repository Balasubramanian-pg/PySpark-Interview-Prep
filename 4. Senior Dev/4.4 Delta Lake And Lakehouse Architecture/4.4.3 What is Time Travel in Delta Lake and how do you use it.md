### 4.4.3 What is Time Travel in Delta Lake and how do you use it

**Time travel** in Delta Lake allows you to query a table as it existed at a specific version number or timestamp. It is built directly on the Delta transaction log, which records every change to the table as an immutable commit. Time travel is used for auditing, debugging, reproducing machine learning experiments, recovering from accidental writes, and comparing data across versions. In interviews, it is important to explain how time travel works, how to use it in PySpark and SQL, and how retention policies such as `VACUUM` affect its availability.

#### How Time Travel Works

Every write, update, delete, merge, or schema change to a Delta table creates a new version in the transaction log. Each version is identified by an integer, starting at 0. The transaction log stores the set of data files that make up the table at each version, along with schema and statistics.

When you query a historical version, Delta Lake reads the transaction log up to that version, resolves the list of data files, and performs a normal Parquet scan on those files. It does not copy or rewrite data. This makes time travel efficient as long as the referenced data files still exist and the log entries are retained.

- **Version-based time travel** uses an integer version number. It is precise and fast because Delta Lake can directly locate the checkpoint and log entries for that version.
- **Timestamp-based time travel** uses a timestamp string. Delta Lake finds the latest version whose commit timestamp is less than or equal to the given timestamp. Commit timestamps are recorded in the `commitInfo` action and are based on the driver clock, so they can be slightly imprecise across time zones or clock skew.

Time travel is read-only. To make an older version the current version, you use `RESTORE`, which creates a new commit that reverts the table to the specified version.

#### Using Time Travel in PySpark

The DataFrame reader accepts `versionAsOf` and `timestampAsOf` options.

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("TimeTravelDemo").getOrCreate()

# Read a specific version
df_v0 = spark.read.format("delta").option("versionAsOf", 0).load("/data/sales")
df_v0.show()

# Read a specific timestamp
df_ts = (
    spark.read.format("delta")
    .option("timestampAsOf", "2025-01-01 00:00:00")
    .load("/data/sales")
)
df_ts.show()

# Read the current version
df_current = spark.read.format("delta").load("/data/sales")
df_current.show()
```

The `DeltaTable` API provides a programmatic way to inspect history and restore.

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/sales")

# Show the table history
delta_table.history().show(truncate=False)

# Restore to version 0
delta_table.restoreToVersion(0)

# Restore to a timestamp
delta_table.restoreToTimestamp("2025-01-01 00:00:00")
```

#### SQL Equivalents

Delta Lake extends Spark SQL with time travel syntax.

```sql
-- Query a specific version
SELECT * FROM sales VERSION AS OF 0;

-- Query a specific timestamp
SELECT * FROM sales TIMESTAMP AS OF '2025-01-01 00:00:00';

-- Inspect table history
DESCRIBE HISTORY sales;

-- Restore to a previous version
RESTORE TABLE sales TO VERSION AS OF 0;

-- Restore to a timestamp
RESTORE TABLE sales TO TIMESTAMP AS OF '2025-01-01 00:00:00';
```

#### Version vs Timestamp Comparison

| Method | Syntax | Precision | Use Case | Notes |
|---|---|---|---|---|
| Version | `versionAsOf` / `VERSION AS OF` | Exact integer | Reproducible reads, debugging known commits | Fast and deterministic |
| Timestamp | `timestampAsOf` / `TIMESTAMP AS OF` | Commit timestamp | Auditing, approximate recovery | Depends on driver clock and time zone |
| RESTORE | `restoreToVersion` / `RESTORE TABLE` | Exact version or timestamp | Rollback to a previous state | Creates a new commit; does not delete history |

#### Retention and VACUUM

Time travel depends on two retention settings:

- `delta.logRetentionDuration` controls how long transaction log entries are kept. The default is 30 days. If log entries are removed, time travel to those versions is no longer possible.
- `delta.deletedFileRetentionDuration` controls how long removed data files are kept before `VACUUM` can delete them. The default is 7 days. If `VACUUM` removes files that are still referenced by a historical version, that version becomes unqueryable.

`VACUUM` is not triggered automatically. Running it with a retention shorter than the default requires disabling a safety check. Always coordinate VACUUM with your time travel requirements.

| Parameter | Default | Description |
|---|---|---|
| `delta.logRetentionDuration` | `30 days` | Retention for transaction log entries. |
| `delta.deletedFileRetentionDuration` | `7 days` | Default retention for VACUUM. |
| `delta.checkpointInterval` | `10` | Number of commits before writing a checkpoint. |
| `spark.databricks.delta.retentionDurationCheck.enabled` | `true` | Prevents VACUUM with retention below the safety threshold. |
| `spark.databricks.delta.vacuum.parallelDelete.enabled` | `false` | Enables parallel file deletion during VACUUM. |

#### Complete Self-Contained Example

The following example creates a Delta table, performs several writes, and demonstrates version and timestamp time travel.

```python
import time
from pyspark.sql import SparkSession
from pyspark.sql.functions import col
from delta.tables import DeltaTable

spark = (
    SparkSession.builder
    .appName("DeltaTimeTravelDemo")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

table_path = "/tmp/delta/time_travel_demo"

# Create version 0
data = [(1, "Alice", 100.0), (2, "Bob", 200.0)]
df = spark.createDataFrame(data, ["id", "name", "amount"])
df.write.format("delta").mode("overwrite").save(table_path)

# Create version 1 by appending
new_data = [(3, "Charlie", 300.0)]
new_df = spark.createDataFrame(new_data, ["id", "name", "amount"])
new_df.write.format("delta").mode("append").save(table_path)

# Create version 2 by updating
delta_table = DeltaTable.forPath(spark, table_path)
delta_table.update(
    condition=col("id") == 1,
    set={"amount": col("amount") + 50.0}
)

print("Current version:")
spark.read.format("delta").load(table_path).orderBy("id").show()

print("Version 0:")
spark.read.format("delta").option("versionAsOf", 0).load(table_path).orderBy("id").show()

print("Version 1:")
spark.read.format("delta").option("versionAsOf", 1).load(table_path).orderBy("id").show()

print("Table history:")
spark.sql(f"DESCRIBE HISTORY delta.`{table_path}`").show(truncate=False)

# Restore to version 0 and verify
delta_table.restoreToVersion(0)
print("After restore to version 0:")
spark.read.format("delta").load(table_path).orderBy("id").show()

spark.stop()
```

#### Performance Implications

Time travel reads are generally as fast as normal reads because Delta Lake uses the transaction log to resolve the file list and then performs a standard Parquet scan. However, older versions may have more small files or less optimized data layout, especially if `OPTIMIZE` has been run since. Checkpoints speed up log replay for recent versions, but very old versions may require replaying more JSON commits if checkpoints are infrequent.

- Reading a historical version does not affect the current table.
- Time travel to a version whose files have been vacuumed fails with a `FileNotFoundException`.
- `RESTORE` writes a new commit and may trigger a full rewrite of metadata, but it does not copy data files.

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Long log retention | Longer time travel window | More storage for log files |
| Short log retention | Less storage | Limited time travel |
| Long deleted file retention | Files available for time travel | More storage and slower VACUUM |
| Short deleted file retention | Faster storage cleanup | Time travel breaks after VACUUM |
| Version-based time travel | Precise and fast | Requires knowing the version number |
| Timestamp-based time travel | Intuitive for auditing | Depends on commit timestamps and clock skew |
| RESTORE | Makes an old version current | Adds a new commit; not a true rollback of history |

#### Best Practices

- Use `versionAsOf` for reproducible reads and debugging. Version numbers are deterministic.
- Use `timestampAsOf` for auditing when the exact version is unknown, but be aware of clock skew.
- Set `delta.logRetentionDuration` and VACUUM retention according to compliance and recovery requirements.
- Do not run VACUUM with a retention shorter than your time travel needs. The default safety check exists for this reason.
- Use `DESCRIBE HISTORY` to inspect versions, operations, and timestamps before restoring.
- Treat time travel as a diagnostic and recovery aid, not as a backup strategy. Back up the table and log together.
- Monitor log size and checkpoint frequency. A very large log slows down snapshot reconstruction.
- Test time travel after schema changes to confirm that historical reads still work.

#### Common Pitfalls and Limitations

- Running VACUUM with a short retention removes files needed for time travel, making older versions unqueryable.
- Timestamp-based time travel can be ambiguous if multiple commits share the same timestamp or if the driver clock is skewed.
- Time travel does not protect against data loss if the underlying storage is corrupted or deleted.
- `RESTORE` creates a new commit. It does not erase the history of the versions it reverts.
- Time travel to a version created before a schema change may return data with the old schema, which can surprise downstream consumers.
- Delta Lake's time travel is per-table. It does not provide cross-table consistent snapshots.
- If the transaction log is manually modified or corrupted, time travel may fail.
- Time travel does not work on tables that have been converted from Parquet without a transaction log.
- Very old versions may be slow to read if they require replaying many JSON commits without a checkpoint.

#### Summary

Time travel in Delta Lake allows you to query a table at a specific version or timestamp by reading the transaction log and the data files referenced by that version. It is used for auditing, debugging, reproducibility, and recovery. You can use `versionAsOf` or `timestampAsOf` in PySpark, or `VERSION AS OF` and `TIMESTAMP AS OF` in SQL. `RESTORE` makes an older version current by creating a new commit. Time travel availability depends on log retention and VACUUM retention. In interviews, emphasize that time travel is read-only, built on the transaction log, and not a substitute for backups. It is a powerful diagnostic and recovery tool, but it must be managed with retention policies and storage costs in mind.
