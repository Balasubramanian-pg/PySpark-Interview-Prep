### 4.3.4 How do you handle late-arriving data using Watermarking

**Late-arriving data** is data whose event time is older than the current progress of a streaming query. In real-world streams, events can be delayed by network issues, mobile offline periods, or upstream buffering. Without a mechanism to bound how long Spark waits for such data, stateful operations would retain state indefinitely, leading to unbounded memory and disk usage. **Watermarking** is Structured Streaming's solution: it defines a threshold on event time that tells Spark how long to wait for late data, after which older state is cleaned up and late records are dropped. This topic is critical for interviews because it tests understanding of event-time processing, state management, output modes, and the trade-off between completeness and resource usage.

#### Event Time vs Processing Time

- **Event time** is the timestamp embedded in the data, representing when the event actually occurred. It is the correct time axis for most business logic.
- **Processing time** is the wall-clock time when the record is processed by Spark. It is not reliable for business logic because it depends on arrival delays.
- Watermarking operates on event time. It uses the maximum event time observed so far to decide which data is too late.

Spark tracks the maximum event time seen across all partitions. The watermark is defined as `maxEventTime - delay`. Any record with event time older than the watermark is considered late and is dropped from stateful operations. State for windows that end before the watermark is also cleaned up.

#### How Watermarking Works

You define a watermark with `withWatermark(eventTimeColumn, delay)`. The delay is a string like `"10 minutes"` or `"5 seconds"`. Spark updates the watermark after each micro-batch based on the maximum event time in that batch. The watermark is global across the query.

- For streaming aggregations, a watermark is required to use append mode. It allows Spark to finalize windows and emit results once the watermark passes the window end.
- For stream-stream joins, watermarks on both sides are required. They bound the join state by defining how long to wait for matching events.
- For `dropDuplicates`, a watermark is recommended to clean up old keys from the state store.
- Without a watermark, stateful operations keep state forever, which can cause out-of-memory errors or checkpoint bloat.

The watermark is a moving threshold. It only moves forward. If a batch contains an event with a very large event time, the watermark jumps forward, potentially causing many older records to be dropped. This is why event-time skew and outliers must be handled carefully.

#### Basic Watermark Example

The following self-contained example uses a rate source, adds a watermark, and performs a windowed aggregation. It prints the results from a memory sink.

```python
import time
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window

spark = SparkSession.builder.appName("WatermarkDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

# Simulate a stream with event-time timestamps
stream_df = (
    spark.readStream.format("rate")
    .option("rowsPerSecond", 5)
    .option("numPartitions", 1)
    .load()
)

# Define a watermark of 10 seconds on the timestamp column
watermarked = stream_df.withWatermark("timestamp", "10 seconds")

# Windowed aggregation: 5-second windows
windowed_counts = (
    watermarked
    .groupBy(window(col("timestamp"), "5 seconds"))
    .count()
)

query = (
    windowed_counts.writeStream
    .outputMode("append")  # append mode requires a watermark for aggregations
    .format("memory")
    .queryName("watermark_results")
    .option("checkpointLocation", "/tmp/checkpoints/watermark_demo")
    .trigger(processingTime="2 seconds")
    .start()
)

time.sleep(10)
query.stop()

spark.sql("SELECT * FROM watermark_results ORDER BY window.start").show(truncate=False)
spark.stop()
```

The SQL equivalent for the windowed aggregation is:

```sql
SELECT window(timestamp, '5 seconds') AS w, count(*) AS cnt
FROM events
GROUP BY window(timestamp, '5 seconds');
```

To apply the watermark in SQL, you must first create a temporary view from the watermarked DataFrame:

```python
stream_df.withWatermark("timestamp", "10 seconds").createOrReplaceTempView("events")
```

#### Watermark in Stream-Stream Joins

Stream-stream joins require watermarks on both sides and time-range conditions. The watermark bounds how long Spark retains join state. Without it, the join state grows without bound because Spark cannot know when a match will never arrive.

```python
impressions = (
    spark.readStream.format("kafka")
    .option("kafka.bootstrap.servers", "localhost:9092")
    .option("subscribe", "impressions")
    .load()
    .selectExpr("CAST(value AS STRING) AS json")
    .selectExpr("get_json_object(json, '$.adId') AS adId",
                "cast(get_json_object(json, '$.impressionTime') AS timestamp) AS impressionTime")
    .withWatermark("impressionTime", "10 minutes")
)

clicks = (
    spark.readStream.format("kafka")
    .option("kafka.bootstrap.servers", "localhost:9092")
    .option("subscribe", "clicks")
    .load()
    .selectExpr("CAST(value AS STRING) AS json")
    .selectExpr("get_json_object(json, '$.adId') AS adId",
                "cast(get_json_object(json, '$.clickTime') AS timestamp) AS clickTime")
    .withWatermark("clickTime", "10 minutes")
)

joined = (
    impressions.join(
        clicks,
        impressions.adId == clicks.adId,
        "inner"
    )
    .where("clickTime BETWEEN impressionTime AND impressionTime + INTERVAL 1 HOUR")
)
```

SQL equivalent for the join condition:

```sql
SELECT i.adId, i.impressionTime, c.clickTime
FROM impressions i
JOIN clicks c
  ON i.adId = c.adId
 AND c.clickTime BETWEEN i.impressionTime AND i.impressionTime + INTERVAL 1 HOUR;
```

#### Watermark in Deduplication

`dropDuplicates` on a streaming DataFrame keeps a state of seen keys. With a watermark, Spark can remove keys older than the watermark, bounding state size.

```python
deduped = (
    stream_df
    .withWatermark("timestamp", "1 minute")
    .dropDuplicates(["user_id", "event_id"])
)
```

Without the watermark, the state store grows indefinitely as new keys arrive.

#### Multiple Watermarks

When a query has multiple watermarks, Spark uses a policy to determine the global watermark. The default policy is `min`, which takes the minimum of all watermarks. This ensures that no data is dropped prematurely. You can change this with `spark.sql.streaming.multipleWatermarkPolicy`, but `min` is the safe choice for correctness.

| Policy | Behavior | When to Use |
|---|---|---|
| `min` (default) | Global watermark is the minimum of all watermarks | Correctness-critical, avoids dropping data |
| `max` | Global watermark is the maximum of all watermarks | Aggressive state cleanup, may drop data |

#### Output Modes and Watermarks

Watermarks interact tightly with output modes.

| Output Mode | Watermark Behavior | Supported Operations |
|---|---|---|
| Append | Required for aggregations. Windows emitted only after watermark passes window end. | Aggregations, stream-stream joins |
| Update | Optional but recommended. State cleaned up for old keys. | Aggregations, `dropDuplicates` |
| Complete | Not allowed. Complete mode requires full state, which contradicts watermark cleanup. | Aggregations only |

#### Performance Implications and Configuration

Watermark delay directly affects state size and latency. A larger delay tolerates more late data but keeps state longer and delays final results. A smaller delay reduces state and latency but drops late data sooner.

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.streaming.multipleWatermarkPolicy` | `min` | Global watermark policy when multiple watermarks exist |
| `spark.sql.streaming.stateStore.providerClass` | `HDFSBackedStateStoreProvider` | State store implementation; RocksDB is an alternative |
| `spark.sql.streaming.stateStore.maintenanceInterval` | `60s` | Interval for state store maintenance |
| `spark.sql.streaming.stateStore.minDeltasForSnapshot` | `10` | Deltas before writing a state snapshot |
| `spark.sql.streaming.noDataMicroBatches.enabled` | `true` | Skips empty micro-batches |
| `spark.sql.streaming.stopTimeout` | `0` | Timeout for stopping a streaming query |
| `spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled` | `false` | Enables changelog checkpointing for RocksDB state store |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles in each micro-batch |
| `spark.sql.streaming.aggregation.stateFormatVersion` | `2` | State format version for streaming aggregations |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Large watermark delay | Tolerates late data, more complete results | Larger state, delayed finalization, higher memory/disk usage |
| Small watermark delay | Smaller state, faster finalization | Drops late data sooner, potential data loss |
| Watermark in append mode | Clean incremental output | Requires waiting for watermark to pass window end |
| Watermark in update mode | Faster updates, bounded state | Still drops late data beyond delay |
| No watermark | Simpler logic | Unbounded state, risk of OOM and checkpoint bloat |
| RocksDB state store | Handles larger state efficiently | More configuration, native dependency |

#### Best Practices

- Always use event-time processing and watermarks for stateful streaming queries.
- Choose the watermark delay based on business tolerance for late data, not on cluster resources alone.
- Use `min` multiple watermark policy unless you have a specific reason to drop data more aggressively.
- Monitor state size and batch duration in the Structured Streaming tab of the Spark UI.
- Use RocksDB state store when state grows beyond what the HDFS-backed store can handle.
- Test with realistic late-data patterns to verify that your watermark delay does not drop important events.
- Keep checkpoint locations on durable storage and never change the watermark delay without starting a new checkpoint.
- For stream-stream joins, ensure both sides have watermarks and that the time-range condition is correct.

#### Common Pitfalls and Limitations

- Using a watermark with complete output mode is not supported and causes an analysis error.
- Append mode with an aggregation without a watermark is not supported.
- A single outlier event with a very large timestamp can push the watermark forward and drop many valid records.
- Late data older than the watermark is silently dropped. There is no built-in late-data side output.
- Watermarks only move forward. If data arrives out of order across partitions, the global watermark is based on the maximum seen, which may drop data from slower partitions.
- `dropDuplicates` without a watermark grows state indefinitely.
- Stream-stream joins without watermarks grow state indefinitely and may fail with OOM.
- Changing the watermark delay requires a new checkpoint; resuming from an old checkpoint with a different delay can cause incorrect results.
- Watermarking does not guarantee that all late data is captured. It only bounds how long Spark waits.

#### Summary

Watermarking is the mechanism that makes stateful Structured Streaming queries scalable and correct in the presence of late-arriving data. It defines a threshold on event time, cleans up state for old windows, and drops records that arrive after the threshold. Watermarks are required for append mode aggregations and stream-stream joins, and are recommended for update mode and deduplication. The watermark delay is a trade-off between completeness and resource usage: larger delays tolerate more late data but increase state size and latency, while smaller delays reduce state but drop late data sooner. In interviews, emphasize the event-time basis, the interaction with output modes, and the operational implications of choosing a delay.
