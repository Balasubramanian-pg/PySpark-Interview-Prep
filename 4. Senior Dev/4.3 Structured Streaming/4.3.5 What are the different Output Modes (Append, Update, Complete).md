### 4.3.5 What are the different Output Modes (Append, Update, Complete)

In Structured Streaming, an **output mode** determines which rows of the result table are written to the sink after each micro-batch. Spark maintains an internal result table that is updated as new data arrives. The output mode decides whether the sink receives only newly appended rows, rows that changed, or the entire result table. This choice affects correctness, state size, sink compatibility, latency, and exactly-once behavior. Interview questions often focus on when each mode is valid, how watermarks interact with them, and why complete mode can become a scalability problem.

#### How Output Modes Work

Structured Streaming treats a stream as an unbounded table. Each trigger processes new input and updates the result table. The output mode controls the delta written to the sink.

- **Append mode** writes only rows that are newly added to the result table since the last trigger.
- **Update mode** writes rows that were added or updated since the last trigger.
- **Complete mode** writes the entire result table on every trigger.

Not every operation supports every mode. Aggregations, deduplication, joins, and watermarks constrain which modes are valid. The sink also constrains the mode. For example, the file sink only supports append mode.

#### Append Mode

Append mode is the default. It emits only new rows that will never be updated again. It is the safest mode for immutable event streams and file-based sinks.

- Supported for stateless transformations such as `select`, `filter`, and `map`.
- Supported for streaming aggregations only when a watermark is present. Spark waits until a window is finalized by the watermark before emitting it.
- Supported for stream-stream joins when both sides have watermarks and time-range conditions.
- Late data older than the watermark is dropped and never emitted.
- Produces the smallest sink write volume because each row is written once.

A typical append-mode query uses `withWatermark` before a windowed aggregation.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window

spark = SparkSession.builder.appName("AppendModeDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

stream = spark.readStream.format("rate").option("rowsPerSecond", 10).load()

windowed = (
    stream
    .withWatermark("timestamp", "10 seconds")
    .groupBy(window(col("timestamp"), "5 seconds"))
    .count()
)

query = (
    windowed.writeStream
    .outputMode("append")
    .format("memory")
    .queryName("append_results")
    .option("checkpointLocation", "/tmp/checkpoints/append_mode")
    .trigger(processingTime="5 seconds")
    .start()
)
```

The SQL analogue for the aggregation is the same query shape, but the output mode is configured in the DataFrame writer, not in the SQL text.

```sql
SELECT window(timestamp, '5 seconds') AS w, count(*) AS cnt
FROM events
GROUP BY window(timestamp, '5 seconds');
```

#### Update Mode

Update mode emits rows that were added or changed since the last trigger. It is useful for dashboards, counters, and sinks that can perform upserts.

- Supported for streaming aggregations, including those without a watermark. Without a watermark, state grows without bound.
- Supported for `dropDuplicates` and other stateful operations that can emit updates.
- Not supported by the file sink. Use a sink that can handle updates, such as Kafka, memory, console, or a custom `foreachBatch` writer.
- With a watermark, state for old keys is cleaned up, but late data older than the watermark is dropped.
- The sink receives only changed keys, so write volume depends on how many keys are updated per trigger.

Update mode is often used when you want the latest count per key without rewriting the full result table.

```python
update_counts = stream.groupBy(col("value") % 5).count()

update_query = (
    update_counts.writeStream
    .outputMode("update")
    .format("memory")
    .queryName("update_results")
    .option("checkpointLocation", "/tmp/checkpoints/update_mode")
    .trigger(processingTime="2 seconds")
    .start()
)
```

#### Complete Mode

Complete mode writes the entire result table on every trigger. It is supported only for streaming aggregations. It is not supported with watermarks because a watermark drops old state, which would contradict the requirement to emit the full result table.

- Supported for aggregations such as `groupBy(...).count()` and `groupBy(...).agg(...)`.
- Not supported for stateless transformations, deduplication, or joins.
- Not supported with `withWatermark`.
- State must retain the full result table for the lifetime of the query. This grows without bound as the number of distinct keys grows.
- Write volume is proportional to the size of the result table on every trigger.

Complete mode is appropriate for small-cardinality aggregations where the full snapshot is needed, such as a dashboard showing the latest totals for a fixed set of categories.

```python
complete_counts = stream.groupBy(col("value") % 5).count()

complete_query = (
    complete_counts.writeStream
    .outputMode("complete")
    .format("memory")
    .queryName("complete_results")
    .option("checkpointLocation", "/tmp/checkpoints/complete_mode")
    .trigger(processingTime="2 seconds")
    .start()
)
```

#### Comparison of Output Modes

| Output Mode | Rows Written | Supported Operations | Watermark | File Sink | State Growth |
|---|---|---|---|---|---|
| Append | Only new, final rows | Stateless, watermarked aggregations, watermarked stream-stream joins | Required for aggregations | Yes | Bounded with watermark |
| Update | New and updated rows | Aggregations, `dropDuplicates`, some stateful operations | Recommended for cleanup | No | Bounded with watermark |
| Complete | Entire result table | Aggregations only | Not allowed | No | Unbounded |

#### Sink Compatibility

| Sink | Append | Update | Complete |
|---|---|---|---|
| File | Yes | No | No |
| Kafka | Yes | Yes | Yes |
| Console | Yes | Yes | Yes |
| Memory | Yes | Yes | Yes |
| `foreachBatch` | Yes | Yes | Yes |
| `foreach` | Yes | Yes | Yes |

Even when a sink supports a mode, the query must also support it. For example, Kafka supports update mode, but a stateless `select` query does not produce updates in update mode because there is nothing to update.

#### Performance Implications and Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Append mode | Minimal write volume, exactly-once with file sink | Delayed output for aggregations until watermark finalizes windows |
| Update mode | Emits latest counts quickly | State retained per key; sink must handle updates |
| Complete mode | Always provides full snapshot | O(result size) write per trigger and unbounded state |
| Watermark with append/update | Bounds state and drops late data | Late data beyond the watermark is lost |
| No watermark with update | Simpler query logic | State grows without bound |
| Complete mode without watermark | Full result table always available | State grows without bound and can cause OOM |

Relevant configuration parameters:

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.streaming.checkpointLocation` | none | Default checkpoint directory for streaming queries |
| `spark.sql.streaming.stateStore.providerClass` | `HDFSBackedStateStoreProvider` | State store implementation; RocksDB is an alternative |
| `spark.sql.streaming.stateStore.maintenanceInterval` | `60s` | Interval for state store maintenance |
| `spark.sql.streaming.stateStore.minDeltasForSnapshot` | `10` | Deltas before writing a state snapshot |
| `spark.sql.streaming.noDataMicroBatches.enabled` | `true` | Skips empty micro-batches |
| `spark.sql.streaming.stopTimeout` | `0` | Timeout for stopping a streaming query |
| `spark.sql.streaming.multipleWatermarkPolicy` | `min` | Global watermark policy when multiple watermarks exist |
| `spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled` | `false` | Enables changelog checkpointing for RocksDB state store |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles in each micro-batch |
| `spark.sql.streaming.aggregation.stateFormatVersion` | `2` | State format version for streaming aggregations |

#### Complete Self-Contained Example

The following example runs two queries against a rate source. One uses update mode and the other uses complete mode. It prints the results from the memory sink after a short run.

```python
import time
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.appName("OutputModesDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

# Update mode: emit new and updated rows for a streaming aggregation.
stream_update = spark.readStream.format("rate").option("rowsPerSecond", 5).load()
update_counts = stream_update.groupBy(col("value") % 5).count()

update_query = (
    update_counts.writeStream
    .outputMode("update")
    .format("memory")
    .queryName("update_results")
    .option("checkpointLocation", "/tmp/checkpoints/update_mode")
    .trigger(processingTime="2 seconds")
    .start()
)

# Complete mode: emit the entire result table for a streaming aggregation.
stream_complete = spark.readStream.format("rate").option("rowsPerSecond", 5).load()
complete_counts = stream_complete.groupBy(col("value") % 5).count()

complete_query = (
    complete_counts.writeStream
    .outputMode("complete")
    .format("memory")
    .queryName("complete_results")
    .option("checkpointLocation", "/tmp/checkpoints/complete_mode")
    .trigger(processingTime="2 seconds")
    .start()
)

time.sleep(10)
update_query.stop()
complete_query.stop()

print("Update mode results:")
spark.sql("SELECT * FROM update_results ORDER BY 1").show(truncate=False)
print("Complete mode results:")
spark.sql("SELECT * FROM complete_results ORDER BY 1").show(truncate=False)

spark.stop()
```

#### Best Practices

- Use append mode for immutable event streams and file sinks where each row should be written once.
- Use update mode when downstream consumers need the latest value per key and can handle upserts.
- Use complete mode only for small-cardinality aggregations where the full snapshot is required.
- Always set `checkpointLocation` on durable storage. Changing the output mode usually requires a new checkpoint directory.
- Add watermarks to stateful append and update queries to bound state and control late data.
- Monitor state size, batch duration, and input rate in the Structured Streaming tab of the Spark UI.
- Use RocksDB state store when state grows beyond what the default HDFS-backed state store can handle efficiently.
- Test failure recovery to confirm that the chosen output mode and sink provide the required delivery guarantee.

#### Common Pitfalls and Limitations

- Append mode with a streaming aggregation without a watermark is not supported and fails analysis.
- Complete mode is not supported with a watermark.
- Complete mode is only supported for aggregations, not for joins, `dropDuplicates`, or stateless queries.
- Update mode is not supported by the file sink.
- Complete mode writes the entire result table every trigger, which can cause excessive sink writes and driver or executor OOM.
- Update mode still retains state per key. Without a watermark, that state grows without bound.
- Late data older than the watermark is dropped in append and update modes.
- Changing the output mode after a query has started is not allowed. Stop the query and start a new one with a compatible checkpoint.
- The memory sink is for debugging only. It retains all results in driver memory and is not suitable for production.

#### Summary

Output modes define what Structured Streaming writes to the sink after each micro-batch. Append mode emits only new, final rows and is the default for immutable streams and file sinks. Update mode emits new and changed rows and is useful for aggregations and upserts. Complete mode emits the entire result table and is limited to aggregations without watermarks. The choice of mode affects state size, sink compatibility, latency, and exactly-once behavior. In production, append and update modes with watermarks are generally preferred because they bound state and write volume, while complete mode should be reserved for small result sets.
