# 4.3.1 What is the difference between Spark Streaming and Structured Streaming?

### 4.3.1 What is the difference between Spark Streaming and Structured Streaming

**Spark Streaming** is the original streaming engine built on **DStreams** and the RDD API. It processes data as a sequence of small batches, but it does not use the Spark SQL optimizer, does not have first-class event-time semantics, and requires manual handling of offsets, state, and exactly-once guarantees. **Structured Streaming** is the modern streaming engine built on the DataFrame and Dataset APIs and the Spark SQL engine. It models a stream as an unbounded table and supports event-time processing, watermarks, output modes, stateful operations, and exactly-once semantics with replayable sources and idempotent sinks. In Spark 3.x, Structured Streaming is the recommended API, while Spark Streaming remains a legacy API in maintenance mode.

#### Core Conceptual Difference

- **Spark Streaming** represents a stream as a sequence of RDDs, called a **DStream** or discretized stream. Each batch interval produces one RDD, and transformations are applied to each RDD independently.
- **Structured Streaming** represents a stream as an **unbounded table** that grows over time. Queries are expressed as DataFrame or SQL operations, and Spark incrementally updates the result as new data arrives.
- Spark Streaming uses the RDD lineage graph for fault tolerance and recomputation. Structured Streaming uses checkpointing, write-ahead logs, and a state store.
- Spark Streaming requires manual offset management and idempotent sinks for end-to-end exactly-once. Structured Streaming provides a declarative exactly-once model when the source is replayable, the checkpoint is durable, and the sink is idempotent or transactional.
- Spark Streaming has no built-in watermark or late-data handling. Structured Streaming has first-class watermarks and event-time windowing.

#### Comparison Table

| Aspect | Spark Streaming (DStreams) | Structured Streaming |
|---|---|---|
| API abstraction | RDD and DStream | DataFrame, Dataset, SQL |
| Execution engine | RDD lineage, batch scheduler | Spark SQL, Catalyst, Tungsten |
| Optimization | Manual tuning | Catalyst optimizer, whole-stage codegen, AQE |
| Event-time support | No native event-time | Native event-time and watermarks |
| Late data handling | Manual | Built-in watermarks |
| Output modes | Not applicable | Append, update, complete |
| Stateful operations | `updateStateByKey`, `mapWithState` | Aggregations, `dropDuplicates`, stream-stream joins, `mapGroupsWithState` |
| Exactly-once | Manual offset management and idempotent sinks | Declarative with replayable source, checkpoint, idempotent sink |
| Fault tolerance | Lineage, checkpointing, receiver WAL | Checkpointing, state store, write-ahead logs |
| SQL support | No native SQL; per-batch workarounds | Full Spark SQL and DataFrame API |
| Continuous processing | No | Experimental continuous mode |
| Maturity in Spark 3.x | Legacy, maintenance mode | Actively developed and recommended |
| Typical latency | Seconds | Hundreds of milliseconds to seconds; milliseconds in continuous mode |

#### Execution and Optimization

Spark Streaming processes each batch interval as a separate RDD job. The DAG is not optimized by Catalyst, and there is no whole-stage code generation or adaptive query execution. Performance tuning relies on manual partitioning, batch interval selection, backpressure, and receiver configuration.

Structured Streaming uses the same Catalyst optimizer and Tungsten execution engine as batch Spark SQL. The physical plan can be inspected in the SQL tab of the Spark UI, and adaptive query execution can reorder joins, coalesce partitions, and handle skew at runtime. This generally produces better performance with less manual tuning.

#### Event Time, Watermarks, and Late Data

Spark Streaming has no native event-time concept. Windows are based on processing time or simple batch intervals. Late data is either included in the current batch or requires custom logic.

Structured Streaming uses event time as the primary time axis. A watermark defined with `withWatermark(eventTimeColumn, delay)` tells Spark how long to wait for late data. State for old windows is cleaned up, and records older than the watermark are dropped. Watermarks are required for append mode aggregations and stream-stream joins, and are recommended for update mode and `dropDuplicates`.

#### Fault Tolerance and Exactly-Once

Spark Streaming can recover from failures using checkpointing and lineage. Receiver-based sources can use a write-ahead log. Exactly-once end-to-end requires manual offset management and an idempotent or transactional sink. Direct Kafka integration allows offsets to be committed, but the application must ensure that output writes and offset commits are coordinated.

Structured Streaming achieves exactly-once when three conditions hold:

- The source is replayable, such as Kafka or a file source.
- The checkpoint location is durable and unique per query.
- The sink is idempotent or transactional, such as a file sink, Delta Lake, or an idempotent `foreachBatch` upsert.

Checkpointing stores source offsets, commit logs, state store data, and query metadata. On failure, Spark reads the last committed batch, re-reads from the correct offsets, and recomputes the batch.

#### Stateful Operations

Spark Streaming provides `updateStateByKey` and `mapWithState` for stateful processing. These APIs are lower-level and require manual state management and checkpointing.

Structured Streaming provides higher-level stateful operations:

- Streaming aggregations such as `groupBy(...).count()` and `groupBy(...).agg(...)`.
- `dropDuplicates` for deduplication.
- Stream-stream joins with watermarks.
- Arbitrary stateful processing with `mapGroupsWithState`, `flatMapGroupsWithState`, and `applyInPandasWithState`.

State is stored in a state store. The default is `HDFSBackedStateStoreProvider`. RocksDB can be enabled for larger state.

#### SQL Support

Spark Streaming has no native SQL support. You can register a temporary view inside `foreachRDD` and run SQL on each batch, but this is batch SQL, not streaming SQL.

Structured Streaming supports full Spark SQL. You can create a temporary view from a streaming DataFrame and run SQL queries against it.

```python
stream_df.withWatermark("timestamp", "10 seconds").createOrReplaceTempView("events")
```

```sql
SELECT window(timestamp, '5 seconds') AS w, count(*) AS cnt
FROM events
GROUP BY window(timestamp, '5 seconds');
```

#### DStreams Example

The following self-contained example uses Spark Streaming with a queued RDD. It demonstrates the DStream API and batch-interval model.

```python
from pyspark import SparkContext
from pyspark.streaming import StreamingContext

sc = SparkContext("local[2]", "DStreamDemo")
ssc = StreamingContext(sc, 1)  # 1-second batch interval
ssc.checkpoint("/tmp/checkpoints/dstream_demo")

# Self-contained input: an RDD queued as a single batch
rdd = sc.parallelize([("a", 1), ("b", 1), ("a", 1)])
stream = ssc.queueStream([rdd])

counts = stream.reduceByKey(lambda a, b: a + b)
counts.pprint()

ssc.start()
ssc.awaitTerminationOrTimeout(5000)
ssc.stop(stopSparkContext=True)
```

#### Structured Streaming Example

The following self-contained example uses Structured Streaming with a rate source, a watermark, and a windowed aggregation. It uses append mode, which requires a watermark for aggregations.

```python
import time
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window

spark = SparkSession.builder.appName("StructuredStreamingDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

stream_df = spark.readStream.format("rate").option("rowsPerSecond", 5).load()

windowed = (
    stream_df
    .withWatermark("timestamp", "10 seconds")
    .groupBy(window(col("timestamp"), "5 seconds"))
    .count()
)

query = (
    windowed.writeStream
    .outputMode("append")
    .format("memory")
    .queryName("structured_results")
    .option("checkpointLocation", "/tmp/checkpoints/structured_demo")
    .trigger(processingTime="2 seconds")
    .start()
)

time.sleep(10)
query.stop()

spark.sql("SELECT * FROM structured_results ORDER BY window.start").show(truncate=False)
spark.stop()
```

#### Relevant Configuration Parameters

| `spark.streaming.receiver.writeAheadLog.enabled` | `false` | Enables write-ahead log for receivers |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Spark Streaming | Mature DStream API, simple for legacy workloads | No SQL optimizer, no event-time, manual exactly-once |
| Structured Streaming | Full SQL, event-time, watermarks, exactly-once | Requires checkpointing discipline and state management |
| DStreams `mapWithState` | Fine-grained state control | Deprecated direction, manual checkpointing |
| Structured Streaming state store | Declarative state with cleanup | State size must be managed with watermarks |
| Micro-batch | High throughput and full feature set | Higher latency than continuous |
| Continuous mode | Millisecond latency | Experimental, stateless only, at-least-once |

#### Best Practices and When to Use

- Use Structured Streaming for all new streaming workloads in Spark 3.x.
- Use Spark Streaming only when maintaining existing DStreams code or when a legacy integration requires it.
- Always set a durable and unique `checkpointLocation` for Structured Streaming queries.
- Use event-time processing and watermarks for stateful operations to bound state.
- Prefer append or update output modes with watermarks over complete mode for large result sets.
- Monitor state size, batch duration, and input rate in the Structured Streaming tab of the Spark UI.
- For Spark Streaming, enable backpressure and use the direct Kafka integration instead of receiver-based Kafka when possible.
- Test failure recovery to confirm the delivery guarantee for both engines.

#### Common Pitfalls and Limitations

- Spark Streaming has no native event-time or watermark support. Late data requires custom logic.
- Spark Streaming exactly-once requires manual offset management and idempotent sinks.
- DStreams are in maintenance mode. New features and optimizations target Structured Streaming.
- Structured Streaming complete mode is not supported with watermarks and can cause unbounded state.
- Structured Streaming append mode with an aggregation requires a watermark.
- Missing `checkpointLocation` causes Structured Streaming queries to fail.
- Changing the checkpoint location loses offsets and state.
- Continuous processing in Structured Streaming is experimental and supports only stateless operations.
- SQL in Spark Streaming is per-batch only and does not provide streaming SQL semantics.

#### Summary

Spark Streaming and Structured Streaming differ in API, execution engine, fault tolerance, event-time support, and feature set. Spark Streaming uses DStreams and RDDs, lacks native SQL and event-time semantics, and requires manual exactly-once handling. Structured Streaming uses the DataFrame and SQL APIs, runs on the Catalyst and Tungsten engines, supports event-time watermarks, output modes, stateful operations, and declarative exactly-once with replayable sources and idempotent sinks. In Spark 3.x, Structured Streaming is the recommended choice for new pipelines, while Spark Streaming is a legacy API for existing applications.
