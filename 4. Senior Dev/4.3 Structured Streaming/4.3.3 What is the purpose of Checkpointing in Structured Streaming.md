### 4.3.3 What is the purpose of Checkpointing in Structured Streaming

Checkpointing is the durable write-ahead log and state store that enables Structured Streaming queries to recover from failures and maintain exactly-once processing guarantees. In a streaming context, the driver can fail, executors can be lost, and sources can deliver data out of order. Without checkpointing, Spark would have no record of which offsets were processed, what state was accumulated, or which micro-batches were committed. This answer explains what checkpointing stores, how it works, how it interacts with stateful operations and exactly-once semantics, and the configuration and operational practices that keep streaming pipelines reliable.

#### What Checkpointing Stores

Checkpointing persists several types of metadata and data to durable storage:

- **Source offsets**: The offset range for each micro-batch, per partition, for sources such as Kafka or file sources.
- **Commit log**: A record of which micro-batches have been successfully processed and committed to the sink.
- **State store data**: For stateful operations like aggregations, `dropDuplicates`, stream-stream joins, and `mapGroupsWithState`, the accumulated state is persisted. This includes snapshots and deltas.
- **Metadata**: Query ID, schema, logical plan, and configuration needed to reconstruct the query on restart.
- **Source metadata**: Information about sources that require it, such as file sources tracking which files have been processed.

These files are organized in subdirectories within the checkpoint location: `offsets`, `commits`, `state`, `metadata`, and `sources`.

#### How Checkpointing Works

The checkpointing process follows a write-ahead log pattern:

- Before processing a micro-batch, Spark writes the planned offsets to the checkpoint's `offsets` directory.
- It processes the batch, updates state, and writes output to the sink.
- After successful completion, it writes a commit file to the `commits` directory.
- State updates are written to the state store, which is backed by the checkpoint location. The state store uses a write-ahead log and periodic snapshots.
- On failure and restart, Spark reads the latest committed batch from the checkpoint. It re-reads data from the source starting at the offsets of the last uncommitted batch. It recomputes the batch. If the sink is idempotent or transactional, exactly-once is achieved.

#### Configuring Checkpoint Location

The checkpoint location is set via the `checkpointLocation` option on `writeStream`. It must be a durable, reliable storage system such as HDFS, S3, ADLS, GCS, or DBFS. It must be unique per streaming query. Two queries cannot share the same checkpoint location. If not set, Spark will fail the query unless a default is configured via `spark.sql.streaming.checkpointLocation`. However, using a global default is discouraged because it can lead to accidental sharing.

The following example shows a complete streaming query with checkpointing:

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window

spark = SparkSession.builder.appName("CheckpointingDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

stream_df = spark.readStream.format("rate").option("rowsPerSecond", 5).load()

windowed = (
    stream_df
    .withWatermark("timestamp", "10 seconds")
    .groupBy(window(col("timestamp"), "5 seconds"))
    .count()
)

query = (
    windowed.writeStream
    .outputMode("append")
    .format("parquet")
    .option("path", "/data/output/windowed_counts")
    .option("checkpointLocation", "/data/checkpoints/windowed_counts")  # durable, unique
    .trigger(processingTime="10 seconds")
    .start()
)
```

#### Exactly-Once Semantics

Checkpointing is necessary but not sufficient for exactly-once processing. Three conditions must hold:

- **Replayable source**: Kafka, file sources, or any source that can re-read from a given offset.
- **Idempotent or transactional sink**: File sink, Delta Lake, or a `foreachBatch` implementation that performs upserts idempotently.
- **Durable checkpoint**: The checkpoint location must survive driver and cluster failures.

If any condition is missing, the pipeline provides at-least-once semantics, meaning duplicates are possible after a failure.

| Sink | Default Guarantee | Exactly-Once Support |
|------|-------------------|----------------------|
| File (parquet, orc, json) | Exactly-once | Yes |
| Kafka | At-least-once | With idempotent producer and correct offset management |
| `foreachBatch` | At-least-once | User must make batch writes idempotent |
| `foreach` | At-least-once | User must implement idempotence |
| Delta Lake | Exactly-once | Yes (transactional) |
| Console / Memory | At-least-once | Not for production |

#### Stateful Operations and Checkpointing

Stateful operations persist their state in the checkpoint location. This includes streaming aggregations, `dropDuplicates`, stream-stream joins, and arbitrary stateful operations such as `mapGroupsWithState`. The state store is backed by the checkpoint location. By default, Spark uses `HDFSBackedStateStoreProvider`. For larger state, you can enable RocksDB:

```python
query = (
    windowed.writeStream
    .outputMode("update")
    .format("memory")
    .queryName("rocksdb_state")
    .option("checkpointLocation", "/data/checkpoints/rocksdb_state")
    .option("spark.sql.streaming.stateStore.providerClass",
            "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
    .trigger(processingTime="5 seconds")
    .start()
)
```

#### Performance Implications and Configuration

Checkpointing adds I/O overhead. Writing offsets, commits, and state snapshots takes time. The frequency and size of state writes depend on the trigger interval, state size, and state store provider. Larger state means longer checkpoint times and potentially higher latency.

| Parameter | Default | Description |
|-----------|---------|-------------|
| `spark.sql.streaming.checkpointLocation` | none | Default checkpoint directory for streaming queries. Setting this globally is not recommended. |
| `spark.sql.streaming.stateStore.providerClass` | `HDFSBackedStateStoreProvider` | State store implementation. Use RocksDB for large state. |
| `spark.sql.streaming.stateStore.maintenanceInterval` | `60s` | Interval for state store maintenance (e.g., snapshot cleanup). |
| `spark.sql.streaming.stateStore.minDeltasForSnapshot` | `10` | Number of delta files before writing a state snapshot. |
| `spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled` | `false` | Enables changelog checkpointing for RocksDB, reducing snapshot overhead. |
| `spark.sql.streaming.noDataMicroBatches.enabled` | `true` | Skips empty micro-batches, avoiding unnecessary checkpoint writes. |
| `spark.sql.streaming.stopTimeout` | `0` | Timeout for stopping a streaming query gracefully. |
| `spark.sql.streaming.multipleWatermarkPolicy` | `min` | Global watermark policy when multiple watermarks exist. |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles in each micro-batch. Affects state partitioning. |
| `spark.sql.streaming.aggregation.stateFormatVersion` | `2` | State format version for streaming aggregations. |

Trade-offs in checkpointing design:

| Choice | Benefit | Cost |
|--------|---------|------|
| Frequent checkpoints (small trigger interval) | Lower latency, faster recovery from last committed batch | More I/O, higher overhead, more files |
| Infrequent checkpoints (large trigger interval) | Less I/O overhead, higher throughput | Higher latency, more data to reprocess on failure |
| HDFS-backed state store | Simple, durable, no native dependency | Slower for large state, more memory pressure |
| RocksDB state store | Handles larger state efficiently, faster updates | Native library, more configuration, disk usage |
| Changelog checkpointing for RocksDB | Reduces full snapshot writes, faster checkpoints | Requires RocksDB and additional configuration |

#### Best Practices

- Always set an explicit, unique `checkpointLocation` on durable storage for every streaming query.
- Never share a checkpoint location between two queries, even if they read the same source.
- Do not delete or modify checkpoint files manually. Use Spark's APIs to stop and restart queries.
- Use RocksDB state store when state grows beyond what the HDFS-backed store can handle efficiently.
- Monitor checkpoint size, state store metrics, and batch duration in the Spark UI's Structured Streaming tab.
- Test failure recovery by killing the query and restarting it to verify exactly-once behavior.
- When changing query logic, especially stateful operations, start a new checkpoint location if the state schema is incompatible.
- Use `availableNow` trigger for backfills to process available data and stop, which still uses checkpointing for incremental progress.
- Keep the checkpoint location on storage with high availability and low latency for the driver and executors.

#### Common Pitfalls and Limitations

- Missing `checkpointLocation` causes the query to fail at start with an analysis error.
- Using a local filesystem path for checkpointing in a distributed cluster fails because executors and driver may not share the same local disk.
- Changing the checkpoint location loses all state and offsets, effectively starting a new query.
- Changing the query logic without changing the checkpoint can lead to incorrect results if the state schema is incompatible.
- Checkpoint directories can grow large if state is not cleaned up by watermarks or if the query runs for a long time without maintenance.
- Concurrent access to the same checkpoint location from multiple queries causes corruption and failures.
- Checkpointing does not back up the output data. It only stores query progress and state. Output data must be stored separately.
- State store schema evolution is limited. Upgrading Spark versions or changing stateful operations may require a new checkpoint.
- If the source is not replayable (e.g., socket), exactly-once is impossible even with checkpointing.
- If the sink is not idempotent, duplicates can occur after recovery.

#### Summary

Checkpointing is the foundation of fault tolerance and exactly-once processing in Structured Streaming. It stores source offsets, commit logs, state store data, and query metadata in a durable location. On failure, Spark reads the last committed batch and reprocesses from the correct offsets. Exactly-once requires a replayable source, an idempotent or transactional sink, and a durable checkpoint. Stateful operations rely on the state store, which is backed by the checkpoint location. Configuration choices such as state store provider, checkpoint frequency, and RocksDB changelog checkpointing affect performance and scalability. In production, always use a unique, durable checkpoint location per query, monitor state growth, and test recovery to ensure reliability.
