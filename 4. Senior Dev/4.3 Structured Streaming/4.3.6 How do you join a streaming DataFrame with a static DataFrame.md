### 4.3.6 How do you join a streaming DataFrame with a static DataFrame

A **stream-static join** combines an incrementally processed streaming DataFrame with a batch DataFrame that is read once at the start of the query. It is the standard pattern for enriching streaming events with reference or dimension data such as user profiles, product catalogs, or currency rates. Because the join is stateless on the streaming side, it does not require a watermark, but it also means updates to the static side are not observed until the query is restarted. Understanding this trade-off is central to designing reliable streaming enrichment pipelines.

#### What Is a Stream-Static Join

- The static DataFrame is read only once when the query starts. Its contents are effectively fixed for the lifetime of the query.
- The streaming DataFrame is processed incrementally in each micro-batch.
- The join is stateless. Spark does not maintain join state across micro-batches.
- No watermark is required because there is no state to bound.
- The static side can be broadcast if it is small, which avoids shuffling the streaming side.
- Supported join types in Spark 3.x for continuous streaming include inner, left outer, and right outer. Full outer joins are not supported for continuous stream-static joins because the static side is read once and unmatched static rows cannot be emitted correctly without knowing all future streaming data.
- Output mode is append. Update mode is not applicable because there is no aggregation state to update.

#### Basic Syntax

The following example shows an inner stream-static join using a rate source and a small static dimension table.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.appName("StreamStaticJoinDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

# Static dimension table
static_df = spark.createDataFrame(
    [(1, "Alice"), (2, "Bob"), (3, "Charlie")],
    ["user_id", "user_name"]
)

# Streaming source
stream_df = (
    spark.readStream.format("rate")
    .option("rowsPerSecond", 5)
    .load()
    .withColumn("user_id", (col("value") % 3 + 1).cast("int"))
)

# Inner stream-static join
joined = stream_df.join(static_df, on="user_id", how="inner")

query = (
    joined.writeStream
    .outputMode("append")
    .format("memory")
    .queryName("stream_static_join")
    .option("checkpointLocation", "/tmp/checkpoints/stream_static_join")
    .trigger(processingTime="2 seconds")
    .start()
)
```

The SQL equivalent uses temporary views created from the streaming and static DataFrames.

```python
stream_df.createOrReplaceTempView("stream_view")
static_df.createOrReplaceTempView("static_view")
```

```sql
SELECT s.user_id, s.value, t.user_name
FROM stream_view s
JOIN static_view t
  ON s.user_id = t.user_id;
```

#### Broadcasting the Static Side

If the static DataFrame is small, broadcast it to avoid shuffling the streaming side in every micro-batch. Spark can broadcast automatically when the estimated size is below `spark.sql.autoBroadcastJoinThreshold`, which defaults to 10MB. You can also force it with the `broadcast` hint.

```python
from pyspark.sql.functions import broadcast

joined = stream_df.join(broadcast(static_df), on="user_id", how="left")
```

Broadcast joins are efficient for small dimension tables because the static data is sent to each executor once and reused across micro-batches. For large static tables, a sort-merge join is used, which shuffles the streaming side every micro-batch and can be expensive.

#### Refreshing Static Data

Because the static DataFrame is read once, changes to the underlying data are not picked up until the query is stopped and restarted. This is a critical limitation for slowly changing dimensions. Common patterns include the following.

- Stop and restart the query when the static data changes. This is simple but causes downtime and reprocessing from the last checkpoint.
- Use `foreachBatch` and join the streaming micro-batch with a freshly read static DataFrame inside each batch. This allows periodic refresh without restarting the query, but moves the join into batch mode and requires manual checkpointing and idempotent writes.
- Use a stream-stream join with a change stream if the dimension source can be read as a stream. This is more complex but supports continuous updates.

The following example uses `foreachBatch` to refresh the static side on every batch.

```python
def join_with_latest_static(batch_df, batch_id):
    # Read the latest static data for this batch
    static_latest = (
        spark.read.format("parquet")
        .load("/data/dim/users")
        .select("user_id", "user_name")
    )
    result = batch_df.join(static_latest, on="user_id", how="left")
    # Write idempotently, for example to a Delta table with merge
    result.write.format("delta").mode("append").save("/data/stream/enriched")

query = (
    stream_df.writeStream
    .foreachBatch(join_with_latest_static)
    .option("checkpointLocation", "/tmp/checkpoints/foreach_batch_join")
    .trigger(processingTime="10 seconds")
    .start()
)
```

#### Performance Implications and Trade-offs

| Approach | Benefit | Cost |
|---|---|---|
| Broadcast stream-static join | Avoids shuffle, fast per micro-batch | Static data must fit in executor memory; broadcast timeout risk |
| Sort-merge stream-static join | Handles large static tables | Shuffles streaming side every micro-batch |
| Static read once | Simple, low overhead | Changes require query restart |
| `foreachBatch` with fresh static read | Allows periodic refresh | Batch join, manual idempotence, no built-in state |
| Stream-stream join for dimensions | Continuous updates | Requires watermarks, state, more complexity |

Relevant configuration parameters:

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.autoBroadcastJoinThreshold` | `10485760` (10 MB) | Maximum size for automatic broadcast join |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles in each micro-batch |
| `spark.sql.streaming.checkpointLocation` | none | Default checkpoint directory for streaming queries |
| `spark.sql.streaming.stateStore.providerClass` | `HDFSBackedStateStoreProvider` | State store implementation for stateful operations |
| `spark.sql.streaming.noDataMicroBatches.enabled` | `true` | Skips empty micro-batches |
| `spark.sql.streaming.stopTimeout` | `0` | Timeout for stopping a streaming query |
| `spark.sql.broadcastTimeout` | `300` | Timeout in seconds for broadcasting |
| `spark.sql.adaptive.enabled` | `true` | Enables adaptive query execution in Spark 3.x |
| `spark.sql.adaptive.skewJoin.enabled` | `true` | Enables skew join handling with AQE |

#### Best Practices

- Use a broadcast hint for small static dimension tables to avoid shuffling the streaming side.
- Keep the static side small enough to fit in memory. If it is large, consider a different enrichment pattern.
- Use `foreachBatch` when the static data must be refreshed periodically.
- Always set `checkpointLocation` on durable storage. Changing the join logic or static source may require a new checkpoint.
- Monitor batch duration, shuffle read/write, and broadcast time in the Structured Streaming tab of the Spark UI.
- For large static tables, consider partitioning or bucketing the static data on the join key to reduce shuffle.
- Set `spark.sql.shuffle.partitions` appropriate for the micro-batch size, not the batch default of 200.
- Test failure recovery to confirm that the join and sink provide the required delivery guarantee.

#### Common Pitfalls and Limitations

- Static data changes are not picked up until the query is restarted.
- Full outer stream-static joins are not supported for continuous streaming because unmatched static rows cannot be emitted correctly.
- Broadcasting a large static DataFrame can cause driver or executor OOM and broadcast timeouts.
- Sort-merge stream-static joins shuffle the streaming side every micro-batch, which can dominate latency.
- Update output mode is not supported for stream-static joins because the join is stateless.
- Using `foreachBatch` moves the join to batch mode; you lose the built-in streaming join optimizations and must handle idempotence.
- Schema mismatches between the streaming and static sides cause analysis errors at query start.
- The static side is read once, so if the underlying files are deleted or changed, the query may fail on restart.

#### Summary

A stream-static join enriches a streaming DataFrame with a batch DataFrame that is read once at query start. It is stateless, requires no watermark, and supports inner, left outer, and right outer joins. Broadcast the static side when it is small to avoid shuffling the streaming side. Because the static side is fixed for the query lifetime, use `foreachBatch` or a stream-stream join when the dimension data must be refreshed. The main trade-offs are broadcast versus sort-merge join, read-once versus periodic refresh, and simplicity versus freshness. In interviews, emphasize the stateless nature of the join, the output mode restriction to append, and the operational implications of read-once static data.
