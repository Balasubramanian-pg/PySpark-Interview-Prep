### 4.3.2 Explain the concept of Micro-batch vs Continuous Processing

Structured Streaming provides two execution modes: **micro-batch** and **continuous processing**. Micro-batch is the default and production-ready mode that processes data in small, deterministic batches with full SQL support and exactly-once guarantees when paired with a replayable source and idempotent sink. Continuous processing is an experimental mode that runs long-lived tasks to achieve millisecond-level latency, but it supports only stateless operations and provides at-least-once fault tolerance. The choice between them affects latency, throughput, feature support, fault tolerance, and operational complexity.

#### Micro-batch Execution Model

Micro-batch mode is the default execution engine for Structured Streaming. The driver plans the query, and each trigger processes a bounded set of new input records as a small batch job.

- The driver triggers a micro-batch at a configured interval or as fast as possible.
- Each micro-batch reads new data, updates state if needed, and writes output to the sink.
- Checkpointing records offsets, commits, and state after each successful batch.
- The engine uses the same Catalyst optimizer and Tungsten execution engine as batch Spark SQL.
- It supports the full range of DataFrame and SQL operations, including aggregations, joins, `dropDuplicates`, watermarks, and arbitrary stateful processing.
- Exactly-once processing is achievable with a replayable source, a durable checkpoint, and an idempotent or transactional sink.
- Typical end-to-end latency ranges from hundreds of milliseconds to several seconds, depending on the trigger interval and processing time.
- Throughput is generally high because each micro-batch is a parallel batch job.

#### Continuous Processing Execution Model

Continuous processing is an experimental mode introduced in Spark 2.3 and still experimental in Spark 3.x. It runs long-lived tasks that continuously read, process, and write data.

- The driver coordinates **epochs**, which are logical units of work assigned to tasks.
- Tasks run continuously and process records as they arrive, rather than waiting for a batch boundary.
- End-to-end latency can be as low as approximately 1 millisecond.
- Fault tolerance is **at-least-once**, not exactly-once. Duplicates are possible after recovery.
- Only stateless, map-like operations are supported: `select`, `filter`, `map`, `flatMap`, and similar transformations.
- Aggregations, joins, `dropDuplicates`, watermarks, and stateful operations are not supported.
- Supported sources in Spark 3.x include Kafka and rate. Supported sinks include Kafka, console, and memory. The file sink is not supported in continuous mode.
- Checkpointing is still used for offsets and recovery, but the state store is not used because there are no stateful operations.

#### Comparison of Micro-batch and Continuous Processing

| Aspect | Micro-batch | Continuous Processing |
|---|---|---|
| Maturity | Production-ready | Experimental |
| Latency | Hundreds of milliseconds to seconds | Approximately 1 millisecond |
| Throughput | High | Lower per-task, depends on workload |
| Fault tolerance | Exactly-once with idempotent sink | At-least-once |
| Supported operations | Full SQL, aggregations, joins, stateful | Stateless map-like only |
| Watermarks | Yes | No |
| Stateful operations | Yes | No |
| Sources | Kafka, file, rate, socket, and others | Kafka, rate |
| Sinks | File, Kafka, `foreachBatch`, and others | Kafka, console, memory |
| Trigger type | Default, `processingTime`, `once`, `availableNow` | `continuous` |
| SQL support | Full | Limited to stateless queries |
| Checkpointing | Offsets, commits, state | Offsets and commits |

#### Micro-batch Code Example

The following self-contained example uses micro-batch mode with a watermark and a windowed aggregation. Append mode requires a watermark for aggregations because Spark must know when a window is final before emitting it.

```python
import time
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window

spark = SparkSession.builder.appName("MicroBatchDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

stream_df = (
    spark.readStream.format("rate")
    .option("rowsPerSecond", 10)
    .option("numPartitions", 1)
    .load()
)

windowed_counts = (
    stream_df
    .withWatermark("timestamp", "10 seconds")
    .groupBy(window(col("timestamp"), "5 seconds"))
    .count()
)

query = (
    windowed_counts.writeStream
    .outputMode("append")
    .format("memory")
    .queryName("micro_batch_results")
    .option("checkpointLocation", "/tmp/checkpoints/micro_batch_demo")
    .trigger(processingTime="2 seconds")
    .start()
)

time.sleep(10)
query.stop()

spark.sql("SELECT * FROM micro_batch_results ORDER BY window.start").show(truncate=False)
spark.stop()
```

The SQL equivalent for the windowed aggregation is:

```sql
SELECT window(timestamp, '5 seconds') AS w, count(*) AS cnt
FROM events
GROUP BY window(timestamp, '5 seconds');
```

#### Continuous Processing Code Example

The following example uses continuous processing with a stateless transformation. It uses the rate source and the console sink, both supported in continuous mode.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.appName("ContinuousProcessingDemo").master("local[*]").getOrCreate()
spark.sparkContext.setLogLevel("WARN")

stream_df = (
    spark.readStream.format("rate")
    .option("rowsPerSecond", 10)
    .option("numPartitions", 1)
    .load()
)

# Stateless transformation only: continuous mode does not support aggregations or joins.
transformed = stream_df.select(
    col("timestamp"),
    col("value"),
    (col("value") * 2).alias("double_value")
)

query = (
    transformed.writeStream
    .outputMode("append")
    .format("console")
    .option("checkpointLocation", "/tmp/checkpoints/continuous_demo")
    .trigger(continuous="1 second")
    .start()
)

query.awaitTermination(10)
query.stop()
spark.stop()
```

#### Performance Implications and Configuration

Micro-batch performance depends on trigger interval, shuffle partitions, state store size, and sink latency. Continuous processing performance depends on epoch backlog, task polling, and source/sink throughput.

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.streaming.continuous.epochBacklogQueueSize` | `10000` | Maximum number of epochs buffered in continuous processing |
| `spark.sql.streaming.continuous.executorPollIntervalMs` | `100` | Poll interval in milliseconds for continuous processing tasks |
| `spark.sql.streaming.checkpointLocation` | none | Default checkpoint directory for streaming queries |
| `spark.sql.streaming.stopTimeout` | `0` | Timeout for stopping a streaming query |
| `spark.sql.streaming.noDataMicroBatches.enabled` | `true` | Skips empty micro-batches in micro-batch mode |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles in each micro-batch |
| `spark.sql.streaming.stateStore.providerClass` | `HDFSBackedStateStoreProvider` | State store implementation for stateful micro-batch operations |
| `spark.sql.streaming.stateStore.maintenanceInterval` | `60s` | Interval for state store maintenance |
| `spark.sql.streaming.aggregation.stateFormatVersion` | `2` | State format version for streaming aggregations |

Trade-offs between the two modes:

| Choice | Benefit | Cost |
|---|---|---|
| Micro-batch | Full feature set, exactly-once, high throughput | Higher latency than continuous |
| Continuous | Very low latency | Limited operations, at-least-once, experimental |
| Micro-batch with small trigger interval | Lower latency | More overhead and smaller batches |
| Continuous with stateless operations | Simple and low latency | No aggregations, joins, or stateful processing |
| Micro-batch with watermarks | Bounded state and correct event-time processing | Delayed output until watermark passes |
| Continuous without state | No state management overhead | Cannot express most business logic |

#### Best Practices and When to Use

- Use micro-batch for nearly all production workloads. It supports the full SQL and DataFrame API, stateful operations, watermarks, and exactly-once semantics.
- Use continuous processing only when sub-second latency is a hard requirement and the workload is limited to stateless transformations.
- Verify that your source and sink are supported in continuous mode before committing to it. Kafka and rate sources with Kafka, console, or memory sinks are the primary options.
- For micro-batch, tune `spark.sql.shuffle.partitions` to match the micro-batch size rather than leaving the batch default of `200`.
- For micro-batch, choose a trigger interval that balances latency against overhead. `processingTime` gives predictable intervals; `availableNow` is useful for backfills.
- For continuous, monitor epoch backlog and task polling to avoid latency spikes.
- Always set a durable and unique `checkpointLocation` for both modes.
- Test failure recovery to confirm the delivery guarantee. Micro-batch can provide exactly-once; continuous provides at-least-once.

#### Common Pitfalls and Limitations

- Continuous processing is experimental. APIs and behavior may change between Spark releases.
- Continuous processing does not support aggregations, joins, `dropDuplicates`, watermarks, or any stateful operation.
- Continuous processing provides at-least-once semantics. Duplicates are possible after a failure.
- The file sink is not supported in continuous mode in Spark 3.x.
- SQL queries that require stateful operations cannot run in continuous mode.
- Micro-batch latency may not meet sub-second requirements even with a very small trigger interval because of scheduling and checkpointing overhead.
- Using continuous mode without checking source and sink compatibility causes analysis errors at query start.
- Changing the trigger type from micro-batch to continuous, or vice versa, requires a new checkpoint location.
- Continuous mode with a high input rate can overwhelm the sink if it cannot keep up, because there is no backpressure equivalent to micro-batch batching.

#### Summary

Micro-batch and continuous processing are the two execution modes of Structured Streaming. Micro-batch is the default, production-ready mode that processes data in small batches with full SQL support, stateful operations, watermarks, and exactly-once semantics when paired with a replayable source and idempotent sink. Continuous processing is an experimental mode that achieves millisecond-level latency for stateless transformations, but it provides only at-least-once fault tolerance and does not support aggregations, joins, or stateful operations. In interviews, emphasize that micro-batch is the correct choice for most workloads, while continuous processing is a specialized tool for low-latency, stateless pipelines with strict latency requirements.
