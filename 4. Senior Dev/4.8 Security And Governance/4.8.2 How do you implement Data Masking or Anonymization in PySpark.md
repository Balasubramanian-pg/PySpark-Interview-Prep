### 4.8.2 How do you implement Data Masking or Anonymization in PySpark

**Data masking** and **anonymization** are the primary techniques for protecting Personally Identifiable Information (PII) in Spark pipelines. Masking replaces sensitive values with realistic but altered substitutes, preserving the data's format and usability for testing, analytics, or non-production environments. Anonymization irreversibly removes or transforms PII so that the original values cannot be recovered. In PySpark, these can be implemented at three levels: **application-level** using built-in functions and UDFs, **engine-level** using governance platforms such as Unity Catalog or Apache Ranger, and **storage-level** through Delta Lake's column masking features. Understanding the trade-offs between these approaches is critical for building compliant, performant pipelines.

#### Data Classification: The Foundation

Before masking can be applied, PII must be identified and classified. A common approach in the Medallion Architecture is to treat PII differently at each layer:

| Layer | PII Treatment | Rationale |
|---|---|---|
| **Bronze** | Raw PII retained | Audit trail, recovery, reprocessing |
| **Silver** | PII hashed or masked | Enable joins without exposure |
| **Gold** | No raw PII | Business consumption by all authorized users |

Detection operates in layers: column name matching (e.g., `email`, `ssn`, `phone`), regex pattern matching for structured PII, and sampling with ML-based services such as Amazon Comprehend PII or Microsoft Presidio for free-text columns. On Databricks, Unity Catalog's Data Classification automatically scans tables and applies `class.*` system tags to detected sensitive columns.

#### Masking vs Anonymization: Choosing the Right Technique

The choice of technique depends on whether the data must remain joinable, reversible, or displayable. The following table summarizes the core strategies:

| Technique | Reversible | Joinable | Preserves Format | Best For |
|---|---|---|---|---|
| **Salted SHA-256 hashing** | No | Yes (deterministic) | No | Join keys, deduplication |
| **Tokenization** | Yes (via vault) | Yes (deterministic) | Optional | Payment data, reversible analytics |
| **Partial masking** | No | No | Partial | Display, logs, exports |
| **Redaction** | No | No | No | Logs, compliance exports |
| **Generalization** | No | No | No | Analytics (age groups, ZIP prefixes) |
| **Format-preserving encryption** | Yes | Yes | Yes | SSNs, card numbers in legacy systems |

#### Application-Level Implementation with PySpark

Application-level masking uses PySpark's built-in functions to transform PII within the DataFrame pipeline. This is the most portable approach, but it requires the developer to apply it consistently across all access paths.

**Hashing** is the recommended approach for join keys. Salted SHA-256 hashing is irreversible, deterministic (same input produces the same hash, enabling joins), and resistant to rainbow table attacks. The salt must be stored in a secrets manager, never in code.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import sha2, concat, lit, col, regexp_replace

spark = SparkSession.builder.appName("DataMaskingDemo").getOrCreate()

# Salt retrieved from a secrets manager (Azure Key Vault, AWS Secrets Manager)
SALT = spark.conf.get("spark.secret.pii_salt")

df = spark.createDataFrame(
    [(1, "alice@example.com", "555-123-4567"), (2, "bob@example.com", "555-987-6543")],
    ["id", "email", "phone"]
)

# Hash PII fields with the salt
df_hashed = (
    df.withColumn("email_hash", sha2(concat(col("email"), lit(SALT)), 256))
      .withColumn("phone_hash", sha2(concat(col("phone"), lit(SALT)), 256))
      .drop("email", "phone")
)
```

**Partial masking** is used for display purposes where the user needs to recognize the data without seeing the full value. PySpark's `regexp_replace` function implements these patterns efficiently.

```python
def mask_email(column):
    """Partial masking for emails: j***@e***.com"""
    return regexp_replace(column, r"^(.).*@(.).*\.(.*)$", r"$1***@$2***.$3")

def mask_phone(column):
    """Show last 4 digits only: ***-***-1234"""
    return regexp_replace(column, r"^\d{3}-\d{3}-(\d{4})$", r"***-***-$1")

masked_df = (
    df.withColumn("email_masked", mask_email(col("email")))
      .withColumn("phone_masked", mask_phone(col("phone")))
      .drop("email", "phone")
)
```

**Tokenization** replaces PII with a surrogate token and stores the mapping in a secure vault. It is reversible when authorized, making it suitable for payment data and scenarios where the original value may be needed operationally. Libraries such as OpenPII-Vault provide PySpark UDFs for tokenization with subject-level salts and key rotation support.

```python
from openpii_vault.spark_udf import tokenize_pii_udf

pii_config = {
    "email": "$.contact.email",
    "phone": "$.contact.phones[*]",
    "name": "$.user.name"
}

tokenized_df = raw_df.withColumn("data", tokenize_pii_udf("data", pii_config))
```

For free-text columns, ML-based redaction libraries such as Phileas or Microsoft Presidio detect and redact PII entities inline. The service and policy are built once per worker and reused for every row, so the cost is paid once per executor, not per record.

```python
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType
from phileas import Policy, FilterService

POLICY = {
    "identifiers": {
        "emailAddress": {"emailAddressFilterStrategies": [{"strategy": "REDACT", "redactionFormat": "[EMAIL]"}]},
        "ssn": {"ssnFilterStrategies": [{"strategy": "REDACT", "redactionFormat": "[SSN]"}]},
        "phoneNumber": {"phoneNumberFilterStrategies": [{"strategy": "REDACT", "redactionFormat": "[PHONE]"}]},
    }
}

_service = None
_policy = None

def redact(text):
    global _service, _policy
    if text is None:
        return None
    if _service is None:
        _service = FilterService()
        _policy = Policy.from_dict(POLICY)
    return _service.filter(_policy, "spark", "doc", text).filtered_text

redact_udf = udf(redact, StringType())
cleaned = df.withColumn("note_redacted", redact_udf(df["note"]))
```

#### Engine-Level Implementation with Unity Catalog

Engine-level masking is enforced during query execution, across every access path (SQL, PySpark, JDBC). The engine rewrites the query plan itself, replacing every reference to a masked column with the masking expression. This ensures joins, subqueries, and CTEs all see the masked value.

On Databricks, Unity Catalog supports column masks using SQL UDFs. A policy can conditionally show full values to one group and masked values to another:

```sql
-- Create a masking function that shows full email to data scientists
CREATE OR REPLACE FUNCTION mask_email(email STRING) RETURNS STRING
RETURN CASE
    WHEN is_account_group_member('data-scientists') THEN email
    ELSE concat(substr(email, 1, 3), '*****@*****')
END;

-- Apply the mask to the column
ALTER TABLE customers ALTER COLUMN email SET MASKING POLICY mask_email;
```

For attribute-based access control (ABAC), governed tags identify which columns to mask and what PII type they contain. The `pii` tag with values such as `ssn`, `address`, and `email` drives automated policy application:

```sql
-- Create governed tags
-- (via Catalog Explorer or account-level API)

-- Create a UDF to mask SSNs
CREATE OR REPLACE FUNCTION mask_ssn(ssn STRING) RETURNS STRING
RETURN CASE
    WHEN is_account_group_member('compliance') THEN ssn
    ELSE '***-**-' || right(ssn, 4)
END;

-- Create a column mask policy using MATCH COLUMNS
CREATE POLICY mask_ssn_policy
ON CATALOG production
FOR COLUMN MASK mask_ssn
TO `account users`
MATCH COLUMNS (has_tag('pii', 'ssn'));
```

Apache Ranger provides similar functionality for Spark SQL, enabling table/column-level authorization, row-level filtering, and data masking through the Ranger Spark plugin. The masking policy is defined on the Ranger admin server and enforced transparently when queries are submitted through Spark Thrift Server.

#### Row-Level Security

Row-level security filters rows based on the user's identity or group membership. The engine injects the filter predicate directly above the table scan, exactly as if the user had written the `WHERE` clause themselves.

```sql
-- Create a row filter function
CREATE OR REPLACE FUNCTION region_filter(region STRING) RETURNS BOOLEAN
RETURN CASE
    WHEN is_account_group_member('global_analysts') THEN TRUE
    WHEN is_account_group_member('us_analysts') THEN region = 'US'
    WHEN is_account_group_member('eu_analysts') THEN region = 'EU'
    ELSE FALSE
END;

-- Apply the row filter to the table
ALTER TABLE customers SET ROW FILTER region_filter ON (region);
```

#### Complete Self-Contained Example

The following example demonstrates a complete PII masking pipeline using PySpark built-in functions.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import sha2, concat, lit, col, regexp_replace, when

spark = (
    SparkSession.builder
    .appName("PIIDataMaskingPipeline")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

# Salt retrieved from secrets manager
SALT = spark.conf.get("spark.secret.pii_salt")

# Raw customer data (Bronze layer)
raw_data = [
    (1, "Alice Smith", "alice@example.com", "555-123-4567", "US"),
    (2, "Bob Jones", "bob@example.com", "555-987-6543", "EU"),
]
raw_df = spark.createDataFrame(raw_data, ["id", "full_name", "email", "phone", "region"])

# Silver layer: hash PII, retain non-PII
silver_df = (
    raw_df
    .withColumn("name_hash", sha2(concat(col("full_name"), lit(SALT)), 256))
    .withColumn("email_hash", sha2(concat(col("email"), lit(SALT)), 256))
    .withColumn("phone_hash", sha2(concat(col("phone"), lit(SALT)), 256))
    .withColumn("email_masked",
                regexp_replace(col("email"), r"^(.).*@(.).*\.(.*)$", r"$1***@$2***.$3"))
    .withColumn("phone_masked",
                regexp_replace(col("phone"), r"^\d{3}-\d{3}-(\d{4})$", r"***-***-$1"))
    .drop("full_name", "email", "phone")
)

silver_df.write.format("delta").mode("overwrite").save("/data/silver/customers")

# Tag the table and columns for governance
spark.sql("""
    ALTER TABLE delta.`/data/silver/customers`
    SET TAGS ('data_classification' = 'PII', 'retention_days' = '730')
""")

print("Silver layer with hashed and masked PII:")
spark.read.format("delta").load("/data/silver/customers").show(truncate=False)
spark.stop()
```

#### Performance Implications

The masking method has a direct impact on query performance.

| Method | Overhead | Optimizer Impact | Notes |
|---|---|---|---|
| Built-in PySpark functions (`sha2`, `regexp_replace`) | Low | None | Catalyst optimizes natively |
| Python UDFs | High | Blocks predicate pushdown and nested column pruning | Runs on every row on the hot path |
| Pandas UDFs | Moderate | Blocks some optimizations | Vectorized, but still a UDF |
| Engine-level masking (Unity Catalog, Ranger) | ~13.2% CPU overhead per application | Plan rewritten before optimizer runs | Acceptable given access control importance |
| Native Databricks `mask()` function | Low | Optimized natively | Built-in, no UDF overhead |

Key findings from benchmarking on a 10M row dataset show that CPU overhead of data-masking views is approximately 13.2% per application. Implementing masking via UDFs prevents query optimizations like predicate pushdown or nested column pruning. Built-in PySpark functions are significantly faster than UDFs because they are optimized by Spark's Catalyst engine.

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Application-level masking (PySpark) | Portable, no external dependency | Must be applied consistently; not enforced at query time |
| Engine-level masking (Unity Catalog, Ranger) | Enforced on all access paths; no data rewrite | Requires governance platform; ~13% CPU overhead |
| Hashing at Silver layer | Irreversible, enables joins | Not reversible; no display value |
| Tokenization with vault | Reversible when authorized | Vault infrastructure and latency |
| Partial masking | Recognizable but protected | Not joinable; limited analytics utility |
| Python UDF-based redaction | Handles free-text PII | High overhead; blocks optimizations |
| Format-preserving encryption | Legacy system compatibility | Requires key management infrastructure |

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.sql.udf.skip.dynamic.mask` | Empty | Comma-separated list of UDF names that skip data masking. |
| `spark.sql.udf.hash.dynamic.mask` | Empty | Comma-separated list of UDF names that hash data before masking. |
| `spark.sql.authorization.enabled` | `false` | Enables authorization checks for SQL data sources. |
| `spark.acls.enable` | `false` | Enables ACL checks for the Spark UI. |
| `spark.sql.extensions` | none | Registers governance extensions (e.g., Ranger, Unity Catalog). |
| `spark.sql.catalog.spark_catalog` | none | Sets the catalog implementation for governance platforms. |
| `spark.sql.execution.arrow.pyspark.enabled` | `false` | Enables Arrow for faster Pandas UDF execution. |
| `spark.sql.ansi.enabled` | `true` | Controls strict type casting behavior, affecting masking UDFs. |
| `delta.deletedFileRetentionDuration` | `7 days` | Retention for VACUUM; affects GDPR deletion timelines. |

#### Best Practices

- Classify and tag PII columns before they enter the Silver layer. Use Unity Catalog Data Classification, Apache Ranger, or automated scanning tools.
- Prefer **built-in PySpark functions** (`sha2`, `regexp_replace`, `mask`) over UDFs for masking operations to avoid blocking query optimizations.
- Hash PII with a **salted SHA-256** algorithm at the Silver layer. Store the salt in a secrets manager such as Azure Key Vault, AWS Secrets Manager, or HashiCorp Vault.
- Use **engine-level masking** (Unity Catalog, Ranger) for production environments where all access paths must be covered. Application-level masking alone can be bypassed by users with direct table access.
- Use **tokenization** for data that must remain reversible. Use **format-preserving encryption** for legacy systems that require the original format.
- Tag tables with `data_classification` and `retention_days` and enforce retention policies automatically.
- Test masking and access control policies in a staging environment before applying them to production.
- Monitor PII access and deletion operations with audit logs from Unity Catalog, Apache Ranger, or platform-native logging.
- For GDPR deletion, use Delta Lake `DELETE` followed by `VACUUM` with a retention that balances compliance against time-travel requirements.

#### Common Pitfalls and Limitations

- Applying masking only in a BI layer. Users with Spark notebook or JDBC access can bypass it. Enforce at the engine level.
- Storing the PII salt in code or version control. Always retrieve it from a secrets manager at runtime.
- Using Python UDFs for masking. They block predicate pushdown and nested column pruning, degrading query performance.
- Forgetting to drop original PII columns after hashing. The raw values remain accessible in the table.
- Using unsalted hashing. Rainbow table attacks can reverse common values such as email addresses.
- Not testing masking performance. Engine-level masking adds approximately 13.2% CPU overhead per application.
- Direct file path access to tables protected by row or column-level security policies is blocked on platforms with FGAC. Pipelines must use catalog access.
- Certain PySpark functions are blocked by FGAC allow-lists and return access-denied errors. Test pipelines against the policy before deployment.
- Changing the masking function after it has been applied to tables can produce inconsistent results across queries. Version-control masking functions.

#### Summary

Implementing data masking and anonymization in PySpark requires choosing the right technique for each PII type and enforcing it at the appropriate level. Built-in PySpark functions such as `sha2` and `regexp_replace` provide fast, optimizer-friendly masking for application-level pipelines. Engine-level masking through Unity Catalog, Apache Ranger, or IOMETE ensures consistent enforcement across all access paths at a modest ~13% CPU overhead. Salted SHA-256 hashing is the recommended approach for joinable de-identification, while tokenization and format-preserving encryption support reversible use cases. In interviews, emphasize that masking must be enforced at the engine level to cover all access paths, that UDFs block query optimizations, and that the salt must be stored in a secrets manager.
