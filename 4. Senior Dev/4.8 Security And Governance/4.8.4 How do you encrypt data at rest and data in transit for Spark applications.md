### 4.8.4 How do you encrypt data at rest and data in transit for Spark applications

Encryption is the last line of defense when perimeter security, authentication, and access control fail. Spark applications move data across three planes: **in transit** between the driver, executors, and external services; **at rest** in storage systems such as HDFS, S3, or Delta Lake; and **locally** in shuffle files, cached blocks, and temporary spill files on executor disks. Native Spark provides configuration for encrypting in-transit communication and local temporary files, while encryption at rest is delegated to the storage layer. This answer covers the configuration parameters, the mechanisms, the performance implications, and the platform-specific details that senior engineers are expected to explain.

#### Data in Transit: TLS/SSL for External Communication

**Transport Layer Security (TLS)** and its predecessor **SSL** protect communication between Spark components and external clients. This includes the Spark UI, the History Server, the Thrift Server for JDBC/ODBC clients, and RPC channels between the driver and executors. TLS is disabled by default.

The configuration uses a key store (containing the server certificate and private key) and a trust store (containing trusted CA certificates). Spark supports per-namespace SSL configuration, allowing different settings for `ui`, `standalone`, `historyServer`, and other services.

| Parameter | Default | Description |
|---|---|---|
| `spark.ssl.enabled` | `false` | Enables SSL connections on all supported protocols. |
| `spark.ssl.protocol` | None | Required when `spark.ssl.enabled=true`. Specifies the TLS protocol version, e.g., `TLSv1.3`. |
| `spark.ssl.keyStore` | None | Path to the key store file containing the server certificate and private key. |
| `spark.ssl.keyStorePassword` | None | Password for the key store. |
| `spark.ssl.keyPassword` | None | Password for the private key in the key store. |
| `spark.ssl.keyStoreType` | `JKS` | Key store type. |
| `spark.ssl.trustStore` | None | Path to the trust store containing trusted CA certificates. |
| `spark.ssl.trustStorePassword` | None | Password for the trust store. |
| `spark.ssl.trustStoreType` | `JKS` | Trust store type. |
| `spark.ssl.enabledAlgorithms` | Empty | Comma-separated list of allowed cipher suites. |
| `spark.ssl.needClientAuth` | `false` | Requires client authentication (mutual TLS). |

Per-namespace SSL configuration uses prefixes such as `spark.ssl.ui.enabled`, `spark.ssl.standalone.enabled`, and `spark.ssl.historyServer.enabled`. This allows, for example, enabling TLS only for the Spark UI without affecting RPC communication.

```python
from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("TLSConfigurationDemo")
    # Enable SSL for all protocols
    .config("spark.ssl.enabled", "true")
    .config("spark.ssl.protocol", "TLSv1.3")
    # Key store
    .config("spark.ssl.keyStore", "/etc/security/ssl/spark.jks")
    .config("spark.ssl.keyStorePassword", "keystore_password")
    .config("spark.ssl.keyPassword", "key_password")
    # Trust store
    .config("spark.ssl.trustStore", "/etc/security/ssl/truststore.jks")
    .config("spark.ssl.trustStorePassword", "truststore_password")
    # Restrict to strong cipher suites
    .config("spark.ssl.enabledAlgorithms",
            "TLS_AES_128_GCM_SHA256,TLS_AES_256_GCM_SHA384")
    .getOrCreate()
)
```

#### Internal RPC Encryption

Communication between the driver and executors, and between executors during shuffle, uses Spark's internal RPC layer. This traffic is separate from external TLS and is controlled by two mechanisms: **authentication** with a shared secret, and **encryption** with AES.

| Parameter | Default | Description |
|---|---|---|
| `spark.authenticate` | `false` | Enables authentication for internal Spark RPC using a shared secret. |
| `spark.authenticate.secret` | None | Shared secret for authentication. Can also be set via `spark.authenticate.secret.file`. |
| `spark.network.crypto.enabled` | `false` | Enables AES-based encryption for internal RPC. Requires `spark.authenticate=true`. |
| `spark.network.crypto.keyLength` | `256` | Length in bits of the encryption key. |
| `spark.network.crypto.keyFactoryAlgorithm` | `PBKDF2WithHmacSHA1` | Algorithm used to derive the encryption key. |
| `spark.network.crypto.saslFallback` | `true` | Allows fallback to SASL authentication if crypto is unavailable. |
| `spark.network.crypto.cipher` | `AES/CTR/NoPadding` | Cipher for RPC encryption. |
| `spark.network.crypto.authEnabled` | `false` | Legacy setting; deprecated in favor of `spark.authenticate`. |

A man-in-the-middle vulnerability in Spark versions before 4.0.0, 3.5.2, and 3.4.4 used an insecure default network encryption cipher for RPC communication, allowing an attacker to modify encrypted traffic undetected. Upgrading to a patched version or explicitly configuring a strong cipher mitigates this.

```python
spark = (
    SparkSession.builder
    .appName("RPCEncryptionDemo")
    .config("spark.authenticate", "true")
    .config("spark.authenticate.secret", "shared_secret_value")
    .config("spark.network.crypto.enabled", "true")
    .config("spark.network.crypto.keyLength", "256")
    .config("spark.network.crypto.cipher", "AES/CTR/NoPadding")
    .config("spark.network.crypto.saslFallback", "false")  # fail if crypto unavailable
    .getOrCreate()
)
```

#### Local and Shuffle Data Encryption

Executors write intermediate data to local disk: shuffle files, cached RDD blocks, and temporary spill files. If an executor's disk is compromised or a node is decommissioned without wiping, this data is exposed. Spark provides **local I/O encryption** to protect these files.

| Parameter | Default | Description |
|---|---|---|
| `spark.io.encryption.enabled` | `false` | Enables encryption for local temporary files and shuffle data. |
| `spark.io.encryption.keySizeBits` | `128` | Key size in bits for local I/O encryption. |
| `spark.io.encryption.keygen.algorithm` | `HmacSHA1` | Algorithm for generating the local encryption key. |
| `spark.io.encryption.commons.config.*` | None | Legacy configuration for commons-crypto. |
| `spark.ssl.io.encryption.enabled` | `false` | Enables SSL-based I/O encryption. |

```python
spark = (
    SparkSession.builder
    .appName("LocalIOEncryptionDemo")
    .config("spark.io.encryption.enabled", "true")
    .config("spark.io.encryption.keySizeBits", "256")
    .config("spark.io.encryption.keygen.algorithm", "HmacSHA256")
    .getOrCreate()
)
```

#### Data at Rest: Storage Layer Encryption

Spark does not encrypt data at rest itself. It relies on the storage system to provide encryption. This is intentional: storage-layer encryption is transparent to Spark, requires no application changes, and is typically hardware-accelerated.

| Storage System | Encryption Mechanism | Configuration |
|---|---|---|
| **HDFS** | Transparent encryption with KMS | `hdfs-site.xml` encryption zones and key providers |
| **Amazon S3** | SSE-S3, SSE-KMS, SSE-C, or client-side | Bucket-level default encryption; `fs.s3a.server-side-encryption-algorithm` |
| **Azure Blob / ADLS** | Storage Service Encryption (SSE) with Microsoft-managed or customer-managed keys | Storage account settings; customer-managed keys in Azure Key Vault |
| **Google Cloud Storage** | Google-managed or customer-managed encryption keys (CMEK) | Bucket-level default KMS key |
| **Delta Lake** | Inherits storage-layer encryption; Parquet files are encrypted at rest by the storage system | Storage configuration; no Delta-specific setting |

For S3, the encryption algorithm is configured through the S3A filesystem:

```python
spark = (
    SparkSession.builder
    .appName("S3EncryptionDemo")
    # SSE-KMS with a customer-managed key
    .config("spark.hadoop.fs.s3a.server-side-encryption-algorithm", "SSE-KMS")
    .config("spark.hadoop.fs.s3a.server-side-encryption.key",
            "arn:aws:kms:us-east-1:123456789012:key/abc123")
    .getOrCreate()
)
```

For HDFS transparent encryption, the encryption zones and key providers are configured in `hdfs-site.xml`. Spark reads and writes encrypted data transparently; no Spark configuration is required.

#### Encryption and Performance Trade-offs

Encryption adds CPU overhead and, in some cases, latency. The impact depends on the mechanism and the workload.

| Encryption Layer | Overhead Source | Typical Impact |
|---|---|---|
| TLS/SSL for external communication | TLS handshake and symmetric encryption | Low; mostly at connection establishment |
| Internal RPC encryption | AES encryption/decryption per message | Moderate; proportional to shuffle volume |
| Local I/O encryption | AES for shuffle and spill files | Moderate; proportional to local disk I/O |
| Storage-layer encryption (S3 SSE-KMS) | KMS API calls and server-side encryption | Per-request KMS costs; S3 Bucket Keys reduce by up to 99% |
| HDFS transparent encryption | AES on DataNode | Low to moderate; hardware-accelerated on modern CPUs |

A key cost consideration for S3 SSE-KMS is the KMS `Decrypt` API call per object read. At scale, these costs accumulate. **S3 Bucket Keys** reduce KMS requests by up to 99% by using a bucket-level key to generate data keys locally, rather than calling KMS for every object.

| Choice | Benefit | Cost |
|---|---|---|
| TLS enabled | Protects external communication | Certificate management; slight handshake latency |
| RPC encryption enabled | Protects internal driver-executor traffic | CPU overhead for AES |
| Local I/O encryption enabled | Protects shuffle and spill files | CPU overhead for local disk I/O |
| S3 SSE-KMS with Bucket Keys | Strong at-rest encryption; 99% fewer KMS calls | Bucket-level configuration required |
| HDFS transparent encryption | Transparent to Spark; no app changes | KMS infrastructure; encryption zone planning |
| SSE-S3 | Simple, no KMS cost | Less control over key management |

#### Complete Self-Contained Example

The following example configures a Spark session with TLS, internal RPC encryption, local I/O encryption, and S3 SSE-KMS for a comprehensive security posture.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = (
    SparkSession.builder
    .appName("ComprehensiveEncryptionDemo")
    # External TLS
    .config("spark.ssl.enabled", "true")
    .config("spark.ssl.protocol", "TLSv1.3")
    .config("spark.ssl.keyStore", "/etc/security/ssl/spark.jks")
    .config("spark.ssl.keyStorePassword", "keystore_password")
    .config("spark.ssl.trustStore", "/etc/security/ssl/truststore.jks")
    .config("spark.ssl.trustStorePassword", "truststore_password")
    # Internal RPC authentication and encryption
    .config("spark.authenticate", "true")
    .config("spark.authenticate.secret", "shared_secret_value")
    .config("spark.network.crypto.enabled", "true")
    .config("spark.network.crypto.keyLength", "256")
    .config("spark.network.crypto.cipher", "AES/CTR/NoPadding")
    # Local I/O encryption
    .config("spark.io.encryption.enabled", "true")
    .config("spark.io.encryption.keySizeBits", "256")
    # S3 SSE-KMS
    .config("spark.hadoop.fs.s3a.server-side-encryption-algorithm", "SSE-KMS")
    .config("spark.hadoop.fs.s3a.server-side-encryption.key",
            "arn:aws:kms:us-east-1:123456789012:key/abc123")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# Run a simple aggregation to verify the configuration
df = spark.range(0, 100_000).withColumn("key", col("id") % 10)
result = df.groupBy("key").count()
result.show()

spark.stop()
```

#### SQL Equivalents

Encryption configuration is not expressed in SQL. SQL is used to manage access policies and to query encrypted data transparently.

```sql
-- Query encrypted data (decryption is transparent at the storage layer)
SELECT key, count(*) AS cnt
FROM encrypted_table
GROUP BY key
ORDER BY cnt DESC;

-- For Delta Lake tables, time travel works on encrypted data transparently
SELECT * FROM sales VERSION AS OF 5;

-- Inspect table properties (encryption is handled by the storage layer)
DESCRIBE DETAIL sales;
```

#### Best Practices

- Enable TLS for all external communication. Set `spark.ssl.protocol` to `TLSv1.3` or `TLSv1.2` and restrict cipher suites with `spark.ssl.enabledAlgorithms`.
- Enable internal RPC encryption with `spark.network.crypto.enabled=true` and `spark.authenticate=true`. Use a strong shared secret and store it in a secrets manager.
- Enable local I/O encryption with `spark.io.encryption.enabled=true` to protect shuffle and spill files on executor disks.
- Use storage-layer encryption for data at rest. For S3, prefer SSE-KMS with a customer-managed key and enable S3 Bucket Keys to reduce KMS API costs.
- For HDFS, configure transparent encryption zones with a KMS key provider. Spark requires no application changes.
- Store key store, trust store, and shared secrets in a secrets manager or a secure vault. Never commit them to version control.
- Rotate encryption keys and certificates according to organizational policy.
- Keep Spark versions up to date to mitigate known vulnerabilities such as the RPC cipher weakness in versions before 4.0.0, 3.5.2, and 3.4.4.
- Monitor encryption overhead in the Spark UI. If shuffle performance degrades after enabling local I/O encryption, consider whether the security benefit justifies the cost.
- Test encryption configuration in a staging environment before applying it to production.

#### Common Pitfalls and Limitations

- Leaving `spark.ssl.enabled=false` and `spark.authenticate=false` in production. The Spark UI and RPC traffic are unprotected.
- Enabling SSL without setting `spark.ssl.protocol`. Spark requires the protocol to be explicitly set when SSL is enabled.
- Using the default insecure RPC cipher in unpatched Spark versions. Upgrade or explicitly configure a strong cipher.
- Forgetting to enable `spark.authenticate=true` when enabling `spark.network.crypto.enabled=true`. RPC encryption requires authentication to be enabled.
- Storing key store passwords or shared secrets in code or version control. Always use a secrets manager.
- Assuming Spark encrypts data at rest. Spark relies on the storage layer for at-rest encryption. HDFS, S3, ADLS, and GCS must be configured separately.
- Ignoring KMS API costs when using SSE-KMS. Enable S3 Bucket Keys to reduce decrypt calls by up to 99%.
- Enabling local I/O encryption without testing performance. The CPU overhead can be significant for shuffle-heavy workloads.
- Using the same key for all applications. Use per-application or per-tenant keys where possible.
- Forgetting to rotate keys and certificates. Stale credentials increase the risk of compromise.

#### Summary

Encrypting Spark applications requires action across three planes: in transit, at rest, and locally. TLS protects external communication with key stores and trust stores. Internal RPC encryption with AES protects driver-executor and shuffle traffic. Local I/O encryption protects shuffle and spill files on executor disks. Data at rest is encrypted by the storage layer, not by Spark: HDFS transparent encryption, S3 SSE-KMS, Azure SSE, and GCS CMEK. The performance overhead of encryption is moderate but measurable, particularly for RPC and local I/O encryption. In interviews, emphasize that Spark delegates at-rest encryption to storage, that RPC encryption requires authentication to be enabled, and that S3 Bucket Keys dramatically reduce KMS API costs.
