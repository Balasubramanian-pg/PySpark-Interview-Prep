# 4.8.1 How do you handle PII data in Spark pipelines?

### 4.8.1 How do you handle PII data in Spark pipelines

Handling Personally Identifiable Information (PII) in Spark pipelines requires a defense-in-depth strategy that spans data classification, transformation at ingest, access control at query time, and verifiable deletion for compliance. PII includes direct identifiers such as names, SSNs, and emails; quasi-identifiers such as birthdates and ZIP codes that can identify individuals when combined; and sensitive attributes such as salary or health data. The core principle is **privacy by design**: de-identify at the source rather than retaining raw PII throughout the pipeline, and enforce controls at the engine level so that no access path—SQL, PySpark, JDBC, or batch job—can bypass them.

#### PII Treatment by Medallion Layer

The Medallion Architecture provides a natural framework for PII handling. Each layer has a different PII treatment policy based on its purpose.

| Layer | PII Treatment | Rationale |
|---|---|---|
| **Bronze** | Raw PII retained | Audit trail, recovery, reprocessing |
| **Silver** | PII hashed or masked | Enable joins and analytics without exposure |
| **Gold** | No raw PII | Business consumption by all authorized users |

The Bronze layer retains raw data for audit and replay. The Silver layer applies hashing or masking so that joins and aggregations can proceed without exposing raw values. The Gold layer contains only aggregated or fully de-identified data suitable for broad consumption.

Access control follows the same layered model. The Bronze layer is restricted to the data engineering team with read/write access for ingestion pipelines. The Silver layer is accessible to data engineers for transformations and to data analysts with read-only access to hashed PII. The Gold layer is readable by all authorized business users with no raw PII present.

#### Detection and Classification

Before masking can be applied, PII must be identified. Detection operates in layers, each covering a different signal.

- **Layer 1: Column name matching.** Columns named `email`, `ssn`, `phone`, `address`, `name`, and similar patterns are flagged automatically.
- **Layer 2: Regex pattern matching.** Regular expressions detect structured PII such as phone numbers, credit card numbers, SSNs, and email addresses inline in the Spark ingest job.
- **Layer 3: Sampling and ML-based detection.** For free-text columns flagged by layers 1 and 2, a sample of 1,000 rows per column is analyzed using services such as Amazon Comprehend PII to estimate the PII rate.

On Databricks, Unity Catalog's Data Classification automatically scans tables in the background and applies `class.*` system tags to detected sensitive columns such as `class.name`, `class.email_address`, and `class.us_ssn`. No custom tags are required for column-level detection.

#### Transformation Strategies: Masking, Hashing, and Tokenization

Once PII is identified, the appropriate transformation depends on whether the data must remain joinable, reversible, or displayable. The following table summarizes the core strategies.

| Strategy | Reversible | Joinable | Preserves Format | Best For |
|---|---|---|---|---|
| **Hashing (salted SHA-256)** | No | Yes (deterministic) | No | Join keys, deduplication |
| **Tokenization** | Yes (via vault) | Yes (deterministic) | Optional | Payment data, reversible analytics |
| **Masking (partial)** | No | No | Partial | Display, logs, exports |
| **Redaction** | No | No | No | Logs, compliance exports |
| **Generalization** | No | No | No | Analytics (age groups, ZIP prefixes) |
| **Format-preserving encryption** | Yes | Yes | Yes | SSNs, card numbers in legacy systems |

**Salted SHA-256 hashing** is the recommended approach for join keys. The salt is stored in a secrets manager such as Azure Key Vault or AWS Secrets Manager, never in code. Salted hashing is irreversible, deterministic (same input produces the same hash, enabling joins), and resistant to rainbow table attacks.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import sha2, concat, lit, col

spark = SparkSession.builder.appName("PIIHashingDemo").getOrCreate()

# Salt is retrieved from a secrets manager, never hardcoded
SALT = spark.conf.get("spark.secret.pii_salt")

df = spark.createDataFrame(
    [(1, "alice@example.com", "555-123-4567"), (2, "bob@example.com", "555-987-6543")],
    ["id", "email", "phone"]
)

# Hash PII fields with the salt
df_hashed = (
    df.withColumn("email_hash", sha2(concat(col("email"), lit(SALT)), 256))
      .withColumn("phone_hash", sha2(concat(col("phone"), lit(SALT)), 256))
      .drop("email", "phone")
)

df_hashed.show(truncate=False)
```

**Tokenization** replaces PII with a surrogate token and stores the mapping in a secure vault. It is reversible when authorized, making it suitable for payment data and scenarios where the original value may be needed for operational purposes. Libraries such as OpenPII-Vault provide PySpark UDFs for tokenization with subject-level salts and key rotation support.

```python
from openpii_vault.spark_udf import tokenize_pii_udf

pii_config = {
    "email": "$.contact.email",
    "phone": "$.contact.phones[*]",
    "name": "$.user.name"
}

tokenized_df = raw_df.withColumn("data", tokenize_pii_udf("data", pii_config))
```

**Partial masking** is used for display purposes where the user needs to recognize the data without seeing the full value. Common patterns include `j***@e***.com` for emails and `***-***-1234` for phone numbers.

```python
from pyspark.sql.functions import regexp_replace, col

def mask_email(column):
    """Partial masking for emails: j***@e***.com"""
    return regexp_replace(column, r"^(.).*@(.).*\.(.*)$", r"$1***@$2***.$3")

def mask_phone(column):
    """Show last 4 digits only: ***-***-1234"""
    return regexp_replace(column, r"^\d{3}-\d{3}-(\d{4})$", r"***-***-$1")

masked_df = (
    df.withColumn("email_masked", mask_email(col("email")))
      .withColumn("phone_masked", mask_phone(col("phone")))
)
```

**Format-preserving encryption (FPE)** encrypts data while maintaining its original format, so legacy systems and analytics tools can continue to use the data without modification. It is suitable for structured sensitive fields such as SSNs and card numbers.

#### Access Control: Row-Level and Column-Level Security

Transformation alone is insufficient if users can still access raw PII through some access path. Access control must be enforced at the query engine level, not just in a BI tool or semantic layer. The IOMETE platform, for example, rewrites the query plan during analysis so that every reference to a masked column is replaced with the masking expression, and row-filter predicates are injected above the table scan. This ensures that joins, subqueries, and CTEs all see the masked value, with no window where raw data exists in the result path.

**Column-level masking** applies a masking function to a column at read time, so the stored data is unchanged. Users with different roles see different values.

```sql
-- Apply a column mask using Unity Catalog
ALTER TABLE prod_catalog.silver.customers
ALTER COLUMN email SET MASK mask_email;

-- Grant access to the masked table
GRANT SELECT ON TABLE prod_catalog.silver.customers TO ROLE analyst;
```

**Row-level security** filters rows based on the user's identity or group membership. This is used when users should only see data belonging to their region, department, or customer segment.

```sql
-- Apply row-level security
ALTER TABLE prod_catalog.silver.customers
ADD CONSTRAINT valid_region CHECK (region IN ('US', 'EU'));
```

Apache Ranger provides a unified framework for configuring Spark access policies, data masking policies, and row-level filtering policies at the SQL level. Microsoft Fabric's OneLake security enforces row-level and column-level security policies defined once in OneLake consistently when users read lakehouse Delta tables from Spark notebooks and job definitions.

#### Data Retention and GDPR Deletion

GDPR and similar regulations require the ability to permanently delete personal data upon request—the "right to be forgotten." In a data lake with immutable Parquet files, logical deletion is insufficient because the underlying physical files may still exist. Delta Lake addresses this through two mechanisms.

- **DELETE** performs record-level logical deletion, marking affected files as deleted in the transaction log.
- **VACUUM** forces physical cleanup by permanently removing files no longer referenced by any active transaction. This is the critical step for achieving "physical forgetting".

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/gdpr/customers")

# Logical deletion of a user's records
delta_table.delete(condition="user_id = 'user123'")

# Physical deletion via VACUUM (requires disabling safety check for short retention)
spark.conf.set("spark.databricks.delta.retentionDurationCheck.enabled", "false")
delta_table.vacuum(0)
```

The default `delta.deletedFileRetentionDuration` is 7 days, which prevents accidental deletion and time-travel failures. For GDPR compliance, this retention may be shortened, but VACUUM is irreversible and removes time-travel ability to those versions.

Data classification tags drive automated retention enforcement. Tables and columns are tagged with `data_classification` and `retention_days`, and policies enforce deletion based on those tags.

```sql
ALTER TABLE prod_catalog.silver.customers
SET TAGS ('data_classification' = 'PII', 'retention_days' = '730');

ALTER TABLE prod_catalog.silver.customers
ALTER COLUMN email SET TAGS ('pii_type' = 'email');
```

#### Complete Self-Contained Example

The following example demonstrates a complete PII handling pipeline: hashing PII at the Silver layer, applying masking functions, and configuring retention tags.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import sha2, concat, lit, col, regexp_replace

spark = (
    SparkSession.builder
    .appName("PIIHandlingPipeline")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog",
            "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

# Salt retrieved from secrets manager
SALT = spark.conf.get("spark.secret.pii_salt")

# Raw customer data (Bronze layer)
raw_data = [
    (1, "Alice Smith", "alice@example.com", "555-123-4567", "US"),
    (2, "Bob Jones", "bob@example.com", "555-987-6543", "EU"),
    (3, "Charlie Brown", "charlie@example.com", "555-555-5555", "US"),
]
raw_df = spark.createDataFrame(
    raw_data, ["id", "full_name", "email", "phone", "region"]
)

# Silver layer: hash PII, retain non-PII
silver_df = (
    raw_df
    .withColumn("name_hash", sha2(concat(col("full_name"), lit(SALT)), 256))
    .withColumn("email_hash", sha2(concat(col("email"), lit(SALT)), 256))
    .withColumn("phone_hash", sha2(concat(col("phone"), lit(SALT)), 256))
    .withColumn("email_masked",
                regexp_replace(col("email"), r"^(.).*@(.).*\.(.*)$", r"$1***@$2***.$3"))
    .drop("full_name", "email", "phone")
)

silver_df.write.format("delta").mode("overwrite").save("/data/silver/customers")

# Register the masked view for analysts
spark.sql("CREATE OR REPLACE VIEW silver_masked AS SELECT * FROM delta.`/data/silver/customers`")

# Tag the table and columns for governance
spark.sql("""
    ALTER TABLE delta.`/data/silver/customers`
    SET TAGS ('data_classification' = 'PII', 'retention_days' = '730')
""")

print("Silver layer with hashed and masked PII:")
spark.read.format("delta").load("/data/silver/customers").show(truncate=False)

spark.stop()
```

#### SQL Equivalents

```sql
-- Create a view that applies masking for analysts
CREATE OR REPLACE VIEW masked_customers AS
SELECT
    id,
    mask_email(email) AS email,
    mask_phone(phone) AS phone,
    region
FROM customers;

-- Grant access to the masked view only
GRANT SELECT ON VIEW masked_customers TO ROLE analyst;

-- Apply column-level masking via Unity Catalog
ALTER TABLE customers ALTER COLUMN email SET MASK mask_email;

-- Apply retention tags
ALTER TABLE customers
SET TAGS ('data_classification' = 'PII', 'retention_days' = '730');

-- GDPR deletion
DELETE FROM customers WHERE user_id = 'user123';
VACUUM customers RETAIN 0 HOURS;
```

#### Relevant Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.databricks.delta.retentionDurationCheck.enabled` | `true` | Prevents VACUUM with retention below the safety threshold. |
| `delta.deletedFileRetentionDuration` | `7 days` | Default retention for VACUUM. |
| `delta.logRetentionDuration` | `30 days` | Retention for transaction log entries. |
| `spark.sql.authorization.enabled` | `false` | Enables authorization checks for SQL data sources. |
| `spark.acls.enable` | `false` | Enables ACL checks for the Spark UI. |
| `spark.databricks.delta.schema.autoMerge.enabled` | `false` | Enables automatic schema evolution; can affect tagging. |
| `spark.sql.ansi.enabled` | `true` | Controls strict type casting behavior, which affects masking UDFs. |
| `spark.sql.execution.arrow.pyspark.enabled` | `false` | Enables Arrow for faster Pandas UDF execution in masking operations. |

#### Trade-offs

| Strategy | Benefit | Cost |
|---|---|---|
| Hashing at Silver layer | Irreversible, enables joins | Not reversible; no display value |
| Tokenization with vault | Reversible when authorized | Vault infrastructure and latency |
| Runtime masking (engine-level) | No data rewrite; applies to all access paths | Slight query overhead; requires governance platform |
| Materialized masking (rewrite) | No runtime overhead | Storage duplication; drift risk |
| Short VACUUM retention | Faster GDPR compliance | Breaks time travel; risk of accidental deletion |
| Long VACUUM retention | Preserves time travel | Slower GDPR deletion; higher storage cost |
| Column-level tags | Automated enforcement | Requires governance platform and tag discipline |

#### Best Practices

- Classify and tag PII columns before they enter the Silver layer. Unity Catalog Data Classification and Apache Ranger provide automated tagging.
- Hash PII with a salted SHA-256 algorithm at the Silver layer. Store the salt in a secrets manager such as Azure Key Vault, AWS Secrets Manager, or HashiCorp Vault.
- Use tokenization for data that must remain reversible, such as payment data. Use format-preserving encryption for legacy systems that require the original format.
- Enforce masking and row-level security at the query engine level, not in a BI tool or semantic layer. This ensures every access path is covered.
- Restrict Bronze layer access to data engineers. Grant analysts read-only access to Silver with hashed or masked PII. Keep Gold free of raw PII.
- Tag tables with `data_classification` and `retention_days` and enforce retention policies automatically.
- For GDPR deletion, use Delta Lake `DELETE` followed by `VACUUM` with a retention that balances compliance against time-travel requirements.
- Monitor PII access and deletion operations with audit logs from Unity Catalog, Apache Ranger, or platform-native logging.
- Test masking and access control policies in a staging environment before applying them to production.

#### Common Pitfalls and Limitations

- Applying masking only in a BI layer. Users with Spark notebook or JDBC access can bypass it. Enforce at the engine level.
- Storing the PII salt in code or version control. Always retrieve it from a secrets manager at runtime.
- Using unsalted hashing. Rainbow table attacks can reverse common values such as email addresses.
- Forgetting to drop original PII columns after hashing. The raw values remain accessible in the table.
- Using VACUUM with retention shorter than the time-travel requirement. This permanently removes historical versions and breaks time travel.
- Not tagging PII columns. Without classification tags, automated masking and retention policies cannot identify sensitive data.
- Direct file path access to tables protected by row or column-level security policies is blocked on platforms with FGAC. Pipelines must use catalog access.
- Certain PySpark functions are blocked by FGAC allow-lists and return access-denied errors. Test pipelines against the policy before deployment.
- Spark job history logs may retain PII with no automatic purge. Configure log rotation and redaction.

#### Summary

Handling PII in Spark pipelines requires a layered approach: classify data, transform it at the Silver layer using salted hashing, tokenization, or masking, enforce access controls at the query engine level, and implement verifiable deletion through Delta Lake `DELETE` and `VACUUM`. The Medallion Architecture provides a natural framework, with raw PII retained only in Bronze and no raw PII in Gold. Salted SHA-256 hashing is the recommended approach for joinable de-identification, while tokenization and format-preserving encryption support reversible use cases. Row-level and column-level security must be enforced at the engine level to cover all access paths. In interviews, emphasize that masking in a BI tool is insufficient, that the salt must be stored in a secrets manager, and that GDPR deletion requires both logical `DELETE` and physical `VACUUM`.
