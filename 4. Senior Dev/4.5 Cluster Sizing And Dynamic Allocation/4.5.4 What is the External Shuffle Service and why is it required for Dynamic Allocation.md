# 4.5.4 What is the External Shuffle Service and why is it required for Dynamic Allocation?

### 4.5.4 What is the External Shuffle Service and why is it required for Dynamic Allocation

The **External Shuffle Service (ESS)** is a long-running auxiliary process that runs on each worker node and serves shuffle files independently of Spark executors. It is the classic mechanism that makes **dynamic allocation** safe. When dynamic allocation releases an idle executor, any shuffle data that executor wrote for downstream stages would normally be lost, causing `FetchFailedException` in the next stage. ESS decouples shuffle file storage from the executor lifecycle, so released executors can be removed without losing their shuffle output. This answer explains what ESS is, how it works on YARN, Kubernetes, and standalone mode, why it is required for dynamic allocation, and how shuffle tracking provides an alternative.

#### What is the External Shuffle Service

The External Shuffle Service is a service that runs outside the Spark executor JVM. It listens on a port (default **7337**) and serves shuffle blocks to executors that request them during the reduce phase of a shuffle.

- It runs as an auxiliary service inside the YARN NodeManager process on each worker node. On Kubernetes, it runs as a DaemonSet pod or as a sidecar container. On standalone mode, it runs as part of the worker process.
- It is independent of any single Spark application. One ESS instance serves shuffle files for all applications running on that node.
- It persists shuffle files on local disk, outside the executor's working directory. When an executor writes shuffle output, it registers the file locations with the ESS on the same node.
- When a downstream task needs to fetch shuffle blocks, it connects to the ESS on the node where the map output was written, not to the executor that produced it.
- Because the ESS outlives individual executors, shuffle data remains available even after the executor that wrote it has been released or has failed.

The configuration `spark.shuffle.service.enabled` defaults to **false** in open-source Spark 3.x. When enabled, Spark executors register with the ESS and route shuffle fetches through it.

#### Why ESS is Required for Dynamic Allocation

Dynamic allocation releases executors when they are idle. Without ESS, releasing an executor deletes its shuffle files, because the shuffle service runs inside the executor JVM. The next stage that needs those files fails with `FetchFailedException`.

The official Spark configuration documentation states that the external shuffle service "preserves the shuffle files written by executors so the executors can be safely removed" and that it "must be enabled if `spark.dynamicAllocation.enabled` is true". Cloudera's documentation is equally direct: the external shuffle service "preserves shuffle files written by executors so that the executors can be deallocated without losing work. Must be enabled if dynamic allocation is enabled".

In practice, ESS solves three problems for dynamic allocation:

- **Shuffle data survival**: Shuffle blocks written by a released executor remain available for downstream stages.
- **Safe executor removal**: The driver can release executors without checking whether they hold shuffle data for active jobs, because the ESS retains it.
- **Failure resilience**: If an executor crashes, its shuffle output is still served by ESS, so downstream tasks do not need to recompute the map stage.

#### How ESS Works in the Shuffle Lifecycle

The shuffle lifecycle with ESS proceeds in four phases:

- **Map phase**: Each map task writes shuffle data to local disk. It registers the file location and block metadata with the ESS on the same node. The executor does not serve shuffle blocks directly.
- **Registration**: The ESS records which shuffle blocks belong to which application and executor. This registration is lightweight; the ESS does not copy or move the data.
- **Reduce phase**: Reduce tasks connect to the ESS on the node where map output was written and fetch the required blocks. The ESS reads the blocks from local disk and sends them over the network.
- **Cleanup**: When an application finishes, or when `spark.shuffle.service.removeShuffle` is enabled and an executor is deallocated, the ESS cleans up the shuffle blocks. Without `removeShuffle`, shuffle data from deallocated executors remains on disk until the application ends.

#### ESS on YARN, Kubernetes, and Standalone

The deployment model of ESS differs by cluster manager.

| Platform | ESS Deployment | Configuration |
|---|---|---|
| YARN | Runs as an auxiliary service inside the NodeManager process | Set `spark.shuffle.service.enabled=true` and configure `yarn.nodemanager.aux-services` to include `spark_shuffle` |
| Kubernetes | Runs as a DaemonSet pod on each node, or as a sidecar | Spark's Kubernetes scheduler backend uses `KubernetesExternalShuffleService` to register executors with the service |
| Standalone | Runs as part of the worker process | Set `spark.shuffle.service.enabled=true` in `spark-env.sh` |
| Mesos | Runs as a long-running service | Set `spark.shuffle.service.enabled=true` |

On YARN, the ESS is configured at the cluster level in `yarn-site.xml`. The service name must match the Spark configuration `spark.shuffle.service.name`, which defaults to `spark_shuffle`. On Kubernetes, dynamic allocation requires a shuffle service DaemonSet to be deployed by the cluster administrator. Spark 3.x also supports shuffle tracking as an alternative to ESS on Kubernetes, which avoids the DaemonSet requirement.

#### Shuffle Tracking: The Alternative to ESS

Since Spark 3.4, **shuffle tracking** is enabled by default when dynamic allocation is enabled and no external shuffle service is configured. Shuffle tracking is a driver-side mechanism that tracks which executors hold shuffle data for active jobs. Executors with active shuffle data are not released until the data is no longer needed.

| Aspect | External Shuffle Service | Shuffle Tracking |
|---|---|---|
| Mechanism | External process serves shuffle files | Driver tracks executors with shuffle data |
| Platform | YARN, standalone, Kubernetes (DaemonSet) | All platforms, including Kubernetes |
| Configuration | `spark.shuffle.service.enabled=true` | `spark.dynamicAllocation.shuffleTracking.enabled=true` (default in Spark 3.4+) |
| Executor release | Immediate when idle | Delayed until shuffle data is no longer needed |
| Failure resilience | Shuffle data survives executor failure | Shuffle data is lost if executor fails |
| Cluster setup | Requires ESS deployment on every node | No additional service required |
| Spark version | All versions | Spark 3.0+ for experimental, 3.4+ for default |

The Spark source code confirms that dynamic allocation requires one of three conditions: enabling the external shuffle service, enabling shuffle tracking, or enabling shuffle block decommissioning. For production YARN clusters, ESS remains the standard choice because it provides failure resilience and immediate executor release. For Kubernetes clusters where deploying ESS is inconvenient, shuffle tracking is the practical alternative.

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.shuffle.service.enabled` | `false` | Enables the external shuffle service. Must be enabled for dynamic allocation when shuffle tracking is not used. |
| `spark.shuffle.service.port` | `7337` | Port on which the external shuffle service listens for fetch requests. |
| `spark.shuffle.service.name` | `spark_shuffle` | Service name used to register with the YARN NodeManager. Must match the `yarn.nodemanager.aux-services` configuration. |
| `spark.shuffle.service.removeShuffle` | `false` (enabled by default in Spark 4.0) | Whether to use ESS to delete shuffle blocks for deallocated executors when the shuffle is no longer needed. Without this, shuffle data from deallocated executors remains on disk until the application ends. |
| `spark.shuffle.service.index.cache.size` | `100m` | Cache size for shuffle index entries in the ESS. |
| `spark.shuffle.maxChunksBeingTransferred` | `Long.MAX_VALUE` | Maximum number of chunks that can be transferred concurrently on the shuffle service. |
| `spark.shuffle.registration.timeout` | `5000` | Timeout in milliseconds for registering with the external shuffle service. |
| `spark.shuffle.registration.maxAttempts` | `3` | Number of retry attempts when registration with ESS fails. |
| `spark.dynamicAllocation.shuffleTracking.enabled` | `true` (Spark 3.4+) | Enables shuffle tracking as an alternative to ESS. |
| `spark.dynamicAllocation.shuffleTracking.timeout` | `infinity` | Timeout for keeping executors with shuffle data alive. |
| `spark.dynamicAllocation.enabled` | `false` | Enables dynamic executor scaling. |

#### Complete Python Example

The following self-contained example configures a Spark session with dynamic allocation and the external shuffle service enabled. It runs a shuffle-heavy aggregation to exercise the shuffle service.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, rand

spark = (
    SparkSession.builder
    .appName("ExternalShuffleServiceDemo")
    .config("spark.dynamicAllocation.enabled", "true")
    .config("spark.dynamicAllocation.minExecutors", "2")
    .config("spark.dynamicAllocation.maxExecutors", "20")
    .config("spark.dynamicAllocation.initialExecutors", "4")
    .config("spark.dynamicAllocation.executorIdleTimeout", "60s")
    .config("spark.dynamicAllocation.shuffleTracking.enabled", "false")  # Use ESS instead
    .config("spark.shuffle.service.enabled", "true")
    .config("spark.shuffle.service.port", "7337")
    .config("spark.shuffle.service.removeShuffle", "true")
    .config("spark.executor.cores", "5")
    .config("spark.executor.memory", "16g")
    .config("spark.executor.memoryOverhead", "2g")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# A shuffle-heavy aggregation that writes shuffle files through ESS
df = (
    spark.range(0, 20_000_000)
    .withColumn("key", (rand() * 500).cast("int"))
    .withColumn("value", rand())
)

result = df.groupBy("key").agg(count("*").alias("cnt"))
result.orderBy(col("cnt").desc()).show(5, truncate=False)

# Monitor the Spark UI to confirm that shuffle read/write metrics are recorded
# and that executors can be released without causing fetch failures.
spark.stop()
```

For a YARN cluster, the cluster administrator must configure `yarn-site.xml` to include the shuffle service as an auxiliary service:

```xml
<property>
  <name>yarn.nodemanager.aux-services</name>
  <value>spark_shuffle</value>
</property>
<property>
  <name>yarn.nodemanager.aux-services.spark_shuffle.class</name>
  <value>org.apache.spark.network.yarn.YarnShuffleService</value>
</property>
<property>
  <name>spark.shuffle.service.port</name>
  <value>7337</value>
</property>
```

#### Performance Implications and Trade-offs

ESS adds a network hop between the executor that wrote shuffle data and the executor that reads it. In a normal shuffle, the reader fetches directly from the writer executor. With ESS, the reader fetches from the ESS process on the writer's node. This adds minimal latency because the ESS is on the same node and reads from local disk. The benefit of safe executor removal far outweighs the overhead.

| Choice | Benefit | Cost |
|---|---|---|
| ESS enabled | Safe executor removal, shuffle data survives executor failure, immediate release of idle executors | Requires cluster-level service deployment, additional network hop |
| Shuffle tracking | No additional service needed, works on Kubernetes | Delayed executor release, shuffle data lost on executor failure |
| ESS with `removeShuffle=false` | Simpler configuration | Shuffle data from deallocated executors remains on disk until application ends |
| ESS with `removeShuffle=true` | Faster disk cleanup | Requires Spark 3.3+ and additional configuration |
| Dynamic allocation without ESS or tracking | Not possible; query fails at startup | N/A |

#### Best Practices and When to Use

- Enable the external shuffle service on YARN and standalone clusters. It is the standard mechanism for dynamic allocation and provides failure resilience.
- On Kubernetes, either deploy a shuffle service DaemonSet or rely on shuffle tracking. Since Spark 3.4, shuffle tracking is enabled by default when dynamic allocation is enabled and no ESS is configured.
- Set `spark.shuffle.service.removeShuffle=true` on long-running clusters to clean up shuffle data from deallocated executors promptly. In Spark 4.0, this is enabled by default.
- Configure `spark.shuffle.service.port` consistently across the cluster. The default is 7337. If you run multiple Spark versions on the same nodes, use different ports.
- Ensure the ESS service name matches between Spark and the YARN NodeManager configuration. The default is `spark_shuffle`.
- Monitor shuffle read/write metrics, fetch failures, and executor release events in the Spark UI. If fetch failures occur after executor release, verify that ESS is running on the nodes where shuffle data was written.
- For streaming workloads with strict SLAs, consider fixed executors or a higher `spark.dynamicAllocation.minExecutors` to avoid latency spikes when executors are released.

#### Common Pitfalls and Limitations

- Enabling dynamic allocation without ESS or shuffle tracking causes the query to fail at startup with a message stating that dynamic allocation requires the external shuffle service.
- The ESS must be deployed on every worker node. If a node lacks the ESS, shuffle fetches from executors on that node fail when the executor is released.
- The ESS port must be consistent. If the port is changed on one node but not others, shuffle fetches fail with connection errors.
- On YARN, the ESS is configured at the cluster level and requires a NodeManager restart to take effect.
- `spark.shuffle.service.removeShuffle` defaults to false in Spark 3.x. Without it, shuffle data from deallocated executors remains on disk until the application ends, consuming storage.
- Shuffle tracking does not protect against executor failure. If an executor with shuffle data fails, the shuffle data is lost and downstream tasks must recompute the map stage.
- ESS adds a small network hop for shuffle reads. In most cases this is negligible, but for very latency-sensitive workloads it may be measurable.
- On Kubernetes, deploying ESS as a DaemonSet requires cluster-admin privileges and careful node labeling.
- Dynamic allocation with ESS can still cause shuffle fetch failures if the ESS itself crashes or is restarted.

#### Summary

The External Shuffle Service is a long-running process that serves shuffle files independently of Spark executors. It is required for dynamic allocation because releasing an idle executor would otherwise delete its shuffle files, causing downstream fetch failures. ESS preserves shuffle data on local disk and serves it to reduce tasks even after the writer executor is gone. On YARN, ESS runs as a NodeManager auxiliary service. On Kubernetes, it runs as a DaemonSet or is replaced by shuffle tracking. Shuffle tracking is the default alternative in Spark 3.4+ when no ESS is configured, but it delays executor release and does not survive executor failure.
