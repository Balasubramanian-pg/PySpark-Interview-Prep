# 4.5.2 Why is assigning 1 core per executor bad? Why is assigning 15 cores per executor bad?

### 4.5.2 Why is assigning 1 core per executor bad Why is assigning 15 cores per executor bad

Executor core count controls how many tasks an executor can run concurrently and how much JVM and memory overhead is duplicated per executor. Two extremes are common mistakes: assigning **1 core per executor** and assigning **15 cores per executor**. The first wastes cluster resources on JVM overhead and creates excessive executor count, while the second causes garbage collection pressure, HDFS I/O bottlenecks, and poor per-core throughput. This answer explains why both configurations degrade performance and what a balanced configuration looks like.

#### Executor Core Basics

Each executor is a JVM process. It has a fixed heap, a fixed overhead, and a fixed number of cores. Cores determine task concurrency. Memory determines how much data can be cached, shuffled, and aggregated before spilling. The widely cited sweet spot for most workloads is **5 cores per executor**. This balances JVM overhead against per-core throughput and avoids the HDFS client bottleneck that appears when too many cores share a single executor.

#### Why 1 Core per Executor is Bad

A 1-core executor runs only one task at a time. To achieve parallelism, Spark must launch many executors. This creates several problems.

- **JVM overhead is duplicated per executor.** Each executor reserves memory for JVM internals, thread stacks, and metadata. With 1 core, that overhead is paid for every single task slot. A 5-core executor pays that overhead once for five concurrent tasks.
- **Memory overhead is duplicated.** `spark.executor.memoryOverhead` defaults to `max(384 MB, 10% of executor memory)`. A 1-core executor with 4 GB heap still reserves at least 384 MB overhead. Ten such executors reserve 3.84 GB just for overhead, which could have been one 5-core executor with far less total overhead.
- **HDFS I/O throughput is underutilized.** Each executor opens its own connections to HDFS or object storage. More executors mean more connections, more file handles, and more metadata requests. This does not improve throughput; it increases contention.
- **Intra-executor parallelism is lost.** Operations that benefit from shared memory within an executor, such as broadcast joins or cached partitions, cannot share state across executors. Each 1-core executor has its own cache and its own broadcast copy.
- **Scheduling overhead grows.** The driver must track more executors, more heartbeats, and more task assignments. This increases driver CPU and memory usage.
- **Shuffle behavior worsens.** Shuffle data is written per executor. With many small executors, shuffle files are fragmented across more locations, increasing fetch overhead and the chance of fetch failures.
- **Cluster manager pressure increases.** YARN, Kubernetes, and standalone schedulers must allocate and monitor many containers. This slows down allocation and increases the chance of allocation failures.

| Aspect | 1 Core per Executor | 5 Cores per Executor |
|---|---|---|
| JVM overhead per task slot | High (overhead repeated per core) | Low (overhead shared across 5 cores) |
| Memory overhead | Repeated per executor | Shared across 5 cores |
| HDFS connections | Many, fragmented | Fewer, consolidated |
| Broadcast and cache sharing | None across executors | Shared within executor |
| Driver scheduling load | High | Moderate |
| Shuffle file fragmentation | High | Lower |
| Resource utilization | Poor | Good |

#### Why 15 Cores per Executor is Bad

A 15-core executor runs 15 tasks concurrently in one JVM. This creates a different set of problems.

- **Garbage collection pressure increases.** With 15 threads allocating objects concurrently, the young generation fills faster and GC pauses become more frequent and longer. If the heap is large, full GC pauses can stall all 15 tasks simultaneously.
- **HDFS I/O bottleneck appears.** The HDFS client and object storage clients are not designed for 15 concurrent threads per JVM. Throughput per core drops significantly beyond about 5 cores. This is the classic reason for the 5-core rule of thumb.
- **Context switching and CPU contention.** Fifteen threads compete for CPU time and memory bandwidth. The operating system spends more time switching between threads and less time doing useful work.
- **Memory per core shrinks.** If the executor has 60 GB and 15 cores, each core has about 4 GB of heap available. A shuffle-heavy task may need more. This leads to spill, disk I/O, and slower performance.
- **Task stragglers block more work.** If one task in a 15-core executor is slow, the other 14 cores may finish and sit idle while the slow task completes. Smaller executors allow better work stealing and load balancing.
- **Failure blast radius is larger.** If a 15-core executor dies, 15 tasks must be recomputed. If a 5-core executor dies, only 5 tasks are lost.
- **Memory management is harder.** The unified memory model divides heap between execution and storage. With many cores, the execution side is under more pressure, and cached data may be evicted more aggressively.
- **Executor memory must be very large.** To give each core adequate memory, the executor heap must be large. Large heaps worsen GC. This creates a feedback loop: more cores require more memory, which increases GC, which slows down all cores.

| Aspect | 15 Cores per Executor | 5 Cores per Executor |
|---|---|---|
| GC pressure | High | Moderate |
| HDFS per-core throughput | Degraded beyond ~5 cores | Near optimal |
| Context switching | High | Low |
| Memory per core | Low if heap is fixed | Adequate |
| Straggler impact | Blocks 15 cores | Blocks 5 cores |
| Failure blast radius | 15 tasks recomputed | 5 tasks recomputed |
| Heap size required | Very large, worsening GC | Moderate, GC-friendly |

#### Performance Implications and Configuration

The core count interacts with memory, shuffle partitions, and dynamic allocation. A common mistake is to set `spark.executor.cores` without adjusting `spark.executor.memory` and `spark.executor.memoryOverhead`. The result is either OOM kills or excessive GC.

| Parameter | Default | Description |
|---|---|---|
| `spark.executor.cores` | 1 (YARN); all available (standalone) | Number of concurrent tasks per executor. |
| `spark.executor.memory` | 1g | JVM heap size per executor. |
| `spark.executor.memoryOverhead` | `max(384m, 0.1 × executor.memory)` | Off-heap memory for VM overhead, interned strings, and native libraries. |
| `spark.executor.memoryOverheadFactor` | `0.1` (JVM); `0.4` (K8s non-JVM) | Fraction used when overhead is not set directly. |
| `spark.executor.minMemoryOverhead` | `384m` | Minimum overhead. |
| `spark.memory.fraction` | `0.6` | Fraction of heap used for execution and storage. |
| `spark.memory.storageFraction` | `0.5` | Fraction of unified memory reserved for storage. |
| `spark.dynamicAllocation.enabled` | `false` | Enables runtime executor scaling. |
| `spark.dynamicAllocation.maxExecutors` | `Integer.MAX_VALUE` | Upper bound for executor count. |
| `spark.dynamicAllocation.minExecutors` | `0` | Lower bound for executor count. |
| `spark.dynamicAllocation.executorIdleTimeout` | `60s` | Idle time before executor release. |
| `spark.sql.shuffle.partitions` | `200` | Partitions used for shuffles. Should match executor parallelism. |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| 1 core per executor | Maximum task isolation | High JVM and overhead duplication, poor I/O, driver pressure |
| 5 cores per executor | Balanced GC, I/O, and parallelism | Requires tuning memory per executor |
| 15 cores per executor | Fewer executors, less communication overhead | High GC, HDFS bottleneck, large failure blast radius |
| Small executors with many cores | Lower GC per core | More executors, more overhead |
| Few large executors | Less overhead | GC and I/O bottlenecks |

#### Complete Python Example

The following self-contained example configures a balanced 5-core executor setup and runs a shuffle-heavy aggregation. It also prints the effective configuration.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, rand

spark = (
    SparkSession.builder
    .appName("ExecutorCoresDemo")
    .config("spark.executor.cores", "5")
    .config("spark.executor.memory", "20g")
    .config("spark.executor.memoryOverhead", "3g")
    .config("spark.executor.instances", "10")
    .config("spark.sql.shuffle.partitions", "200")
    .config("spark.dynamicAllocation.enabled", "true")
    .config("spark.dynamicAllocation.minExecutors", "2")
    .config("spark.dynamicAllocation.maxExecutors", "20")
    .config("spark.dynamicAllocation.shuffleTracking.enabled", "true")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# Create a synthetic dataset with a shuffle-heavy groupBy
df = (
    spark.range(0, 50_000_000)
    .withColumn("key", (rand() * 1000).cast("int"))
    .withColumn("value", rand())
)

result = df.groupBy("key").agg(count("*").alias("cnt"), count("value").alias("non_null"))
result.orderBy(col("cnt").desc()).show(5, truncate=False)

# Print the effective executor configuration from the Spark UI environment
# Access the Spark UI at http://<driver-host>:4040 to inspect executor cores and memory.
spark.stop()
```

#### SQL Equivalents

The core count does not change the SQL text, but it changes how the query executes. A shuffle-heavy join or aggregation is the workload most sensitive to executor cores. The following SQL query would benefit from a balanced core configuration.

```sql
-- A shuffle-heavy aggregation that benefits from 5-core executors
SELECT key, count(*) AS cnt
FROM large_table
GROUP BY key
ORDER BY cnt DESC
LIMIT 10;
```

The physical plan can be inspected to confirm shuffle partitions and exchange operators.

```sql
EXPLAIN FORMATTED
SELECT key, count(*) AS cnt
FROM large_table
GROUP BY key;
```

#### Best Practices and When to Use

- Use **5 cores per executor** as the default starting point for most batch and streaming workloads.
- Keep executor heap below **32 GB** to maintain GC overhead under 10%.
- Adjust `spark.executor.memory` so that each core has adequate heap. A common target is 3–5 GB per core for shuffle-heavy workloads.
- Set `spark.sql.shuffle.partitions` to a multiple of total executor cores. For 10 executors with 5 cores each, 200 partitions is a reasonable start.
- Enable dynamic allocation with a finite `spark.dynamicAllocation.maxExecutors` to prevent cluster monopolization.
- Use shuffle tracking on Kubernetes or External Shuffle Service on YARN when dynamic allocation is enabled.
- Monitor GC time, spill, and task duration in the Spark UI. If GC time exceeds 10% of task time, reduce heap or cores. If spill is high, increase memory.
- For workloads with very large shuffles, consider more executors with fewer cores rather than fewer executors with many cores.

#### Common Pitfalls and Limitations

- Setting 1 core per executor and expecting better isolation. The overhead duplication usually outweighs any isolation benefit.
- Setting 15 cores per executor and expecting linear scaling. Per-core throughput drops beyond about 5 cores due to GC and HDFS client limitations.
- Forgetting to increase `spark.executor.memoryOverhead` when increasing executor memory. This causes container kills.
- Using the same executor configuration for every workload. A configuration tuned for a large shuffle-heavy join may be wrong for a streaming job or a small interactive query.
- Ignoring `spark.sql.shuffle.partitions`. If it is left at 200 while the cluster has 500 cores, many cores sit idle.
- Enabling dynamic allocation without shuffle preservation causes `FetchFailedException` when idle executors holding shuffle data are released.
- Using very large executors makes failures more expensive because more tasks must be recomputed.
- Assuming more cores always means faster. Memory bandwidth, disk I/O, and GC are often the real bottlenecks.

#### Summary

Assigning 1 core per executor is bad because it duplicates JVM and memory overhead across many executors, fragments shuffle data, increases driver and cluster manager load, and provides no intra-executor sharing. Assigning 15 cores per executor is bad because it causes excessive garbage collection, hits the HDFS client bottleneck, increases context switching, reduces memory per core, and enlarges the failure blast radius. The balanced choice for most workloads is 5 cores per executor with 16–20 GB heap, adjusted based on Spark UI metrics.
