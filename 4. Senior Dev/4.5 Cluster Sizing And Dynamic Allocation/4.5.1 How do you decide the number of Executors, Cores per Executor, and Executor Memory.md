### 4.5.1 How do you decide the number of Executors, Cores per Executor, and Executor Memory

Deciding the number of executors, cores per executor, and executor memory is one of the most consequential tuning decisions in a Spark application. A configuration that is too small leads to underutilized clusters and long job durations. A configuration that is too large causes excessive garbage collection, container kills, and wasted resources. There is no universal answer: the optimal values depend on the cluster hardware, the workload type, the size and shape of the data, and the shuffle and caching behavior of the job. This answer provides a structured methodology, starting with the three variables and then walking through a step-by-step calculation, configuration parameters, trade-offs, and best practices.

#### The Three Variables

**Number of executors** determines the total parallelism of the application. More executors mean more tasks can run concurrently, but also more communication overhead and more memory consumed by the cluster manager. In dynamic allocation, the number of executors changes at runtime; otherwise, it is fixed by `spark.executor.instances` or `--num-executors`.

**Cores per executor** determines how many tasks a single executor can run concurrently. Each core runs one task at a time. A common starting point is **5 cores per executor**, because beyond that, HDFS I/O throughput and JVM garbage collection can degrade. The widely cited rule of thumb is that 5 cores per executor is optimal for write throughput and avoids the HDFS client bottleneck.

**Executor memory** determines how much heap each executor has for execution, caching, and shuffle data. The heap should generally be kept below **32 GB** to keep GC overhead below 10%. Memory beyond the heap is covered by `spark.executor.memoryOverhead`, which defaults to `max(384 MB, 10% of spark.executor.memory)` for JVM jobs and 40% for non-JVM jobs on Kubernetes.

#### Step-by-Step Methodology

A practical approach starts from the cluster hardware and works toward a configuration, then validates it with the Spark UI.

- **Step 1: Determine available resources per node.** For each worker node, identify the total cores and total memory. Reserve 1 core per node for the OS and cluster manager, and reserve 1 GB per node for system overhead. For example, a node with 16 cores and 64 GB RAM has 15 usable cores and 63 GB usable memory.
- **Step 2: Choose cores per executor.** Start with 5. If the cluster has more than 100 executors, increasing cores per executor to 8 or more can reduce communication overhead, but keep an eye on GC and HDFS throughput.
- **Step 3: Calculate executors per node.** Divide usable cores by cores per executor. For a node with 15 usable cores and 5 cores per executor, that is 3 executors per node. One node will also run the ApplicationMaster, which consumes one core, so that node has 2 executors instead of 3.
- **Step 4: Calculate memory per executor.** Divide usable memory per node by executors per node, then subtract the memory overhead. For a node with 63 GB usable memory and 3 executors per node, that is 21 GB per executor. Subtract roughly 10% for overhead, giving approximately **19 GB** per executor. Alternatively, start with **30 GB per executor** and distribute the available machine cores, then adjust based on GC metrics.
- **Step 5: Calculate total executors.** Multiply executors per node by the number of worker nodes. If there are 6 worker nodes with 3 executors each, minus the ApplicationMaster on one node, the total is 17 executors.
- **Step 6: Validate and adjust.** Run the job and inspect the Spark UI. Look for spill, GC time, task duration skew, and executor memory utilization. Increase memory if spill is high, increase cores if parallelism is low, and increase executors if tasks are queued.

#### Worked Example

Consider a cluster with six worker nodes, each with 16 cores and 64 GB of memory. The goal is a configuration with 5 cores per executor.

- Usable cores per node: 16 − 1 = 15.
- Executors per node: 15 ÷ 5 = 3.
- Usable memory per node: 64 − 1 = 63 GB.
- Memory per executor before overhead: 63 ÷ 3 = 21 GB.
- Memory overhead: roughly 10% of 21 GB, or about 2 GB.
- Final executor memory: 21 − 2 = **19 GB**.
- Total executors: 6 nodes × 3 executors = 18, minus 1 for the ApplicationMaster on one node = **17 executors**.

This yields `--num-executors 17 --executor-cores 5 --executor-memory 19G`. This configuration fits within the NodeManager capacities, avoids the HDFS I/O bottleneck of 15-core executors, and leaves room for the ApplicationMaster.

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.executor.instances` | Not set | Fixed number of executors when dynamic allocation is disabled. |
| `spark.executor.cores` | 1 (YARN); all available (standalone) | Number of concurrent tasks per executor. |
| `spark.executor.memory` | 1g | JVM heap size per executor. |
| `spark.executor.memoryOverhead` | `max(384m, 0.1 × executor.memory)` | Off-heap memory for VM overhead, interned strings, and native libraries. |
| `spark.executor.memoryOverheadFactor` | `0.1` (JVM); `0.4` (K8s non-JVM) | Fraction of executor memory allocated as overhead when overhead is not set directly. |
| `spark.executor.minMemoryOverhead` | `384m` | Minimum overhead when the factor yields a smaller value. |
| `spark.dynamicAllocation.enabled` | `false` | Enables runtime executor scaling. |
| `spark.dynamicAllocation.minExecutors` | `0` | Lower bound for executor count under dynamic allocation. |
| `spark.dynamicAllocation.maxExecutors` | `infinity` | Upper bound for executor count. Set a finite value in shared clusters. |
| `spark.dynamicAllocation.initialExecutors` | `1` (or `spark.executor.instances` if higher) | Initial executor count at startup. |
| `spark.dynamicAllocation.executorIdleTimeout` | `60s` | Idle time before an executor is released. |
| `spark.dynamicAllocation.executorAllocationRatio` | `1.0` | Fraction of maximum parallelism to target. Lower values reduce resource usage. |
| `spark.memory.fraction` | `0.6` | Fraction of heap used for execution and storage. |
| `spark.memory.storageFraction` | `0.5` | Fraction of unified memory reserved for storage (cache). |
| `spark.memory.offHeap.enabled` | `false` | Enables off-heap memory for certain operations. |
| `spark.memory.offHeap.size` | `0` | Absolute amount of off-heap memory. |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Large executors (more cores/memory) | Fewer executors, less communication overhead | Higher GC pressure, slower per-core throughput, risk of JVM inefficiency beyond 16 cores and 128 GB |
| Small executors | Lower GC pressure, better per-core throughput | More executors, more scheduling overhead, more open connections |
| 5 cores per executor | Balanced HDFS I/O and GC | May underutilize nodes with many cores |
| Fixed executors | Predictable latency, no allocation delay | Idle resources when workload drops |
| Dynamic allocation | Better cluster utilization, cost savings | Executor request latency, shuffle preservation complexity |
| Heap below 32 GB | GC overhead below 10% | May require more executors to fit large data |
| High `executorAllocationRatio` | Maximum parallelism | May waste resources on small tasks |
| Low `executorAllocationRatio` | Lower resource usage | Potential under-parallelization and longer job duration |

#### Complete Python Example

The following self-contained example configures a Spark session with explicit executor sizing and dynamic allocation, then runs an aggregation to exercise the cluster.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count

spark = (
    SparkSession.builder
    .appName("ExecutorSizingDemo")
    .config("spark.executor.memory", "19g")
    .config("spark.executor.memoryOverhead", "2g")
    .config("spark.executor.cores", "5")
    .config("spark.executor.instances", "17")
    .config("spark.dynamicAllocation.enabled", "true")
    .config("spark.dynamicAllocation.minExecutors", "4")
    .config("spark.dynamicAllocation.maxExecutors", "50")
    .config("spark.dynamicAllocation.initialExecutors", "8")
    .config("spark.dynamicAllocation.executorIdleTimeout", "60s")
    .config("spark.dynamicAllocation.schedulerBacklogTimeout", "1s")
    .config("spark.dynamicAllocation.shuffleTracking.enabled", "true")
    .config("spark.memory.fraction", "0.6")
    .config("spark.memory.storageFraction", "0.5")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# A simple aggregation to exercise the cluster
df = spark.range(0, 20_000_000).withColumn("group", col("id") % 200)
result = df.groupBy("group").agg(count("*").alias("cnt"))
result.orderBy(col("cnt").desc()).show(5, truncate=False)

spark.stop()
```

#### SQL Equivalents

Executor sizing is not configured through SQL. These are Spark runtime configuration parameters set at session creation or via `spark-submit`. SQL is used for the workload itself.

```sql
-- After creating a temporary view from a DataFrame
CREATE OR REPLACE TEMPORARY VIEW numbers AS
SELECT id, id % 200 AS group_id FROM range(20000000);

SELECT group_id, count(*) AS cnt
FROM numbers
GROUP BY group_id
ORDER BY cnt DESC
LIMIT 5;
```

#### Best Practices and When to Use

- Start with **5 cores and 16–19 GB per executor** for medium workloads, then adjust based on Spark UI metrics.
- Keep executor heap below **32 GB** to maintain GC overhead under 10%.
- Reserve **1 core per node** for the OS and cluster manager, and **1 GB per node** for system overhead.
- Enable dynamic allocation for variable workloads, but set a finite `spark.dynamicAllocation.maxExecutors` to prevent a single job from monopolizing a shared cluster.
- Use shuffle tracking on Kubernetes; use External Shuffle Service on YARN and standalone clusters.
- Monitor executor utilization, GC time, shuffle spill, and task duration in the Spark UI before and after sizing changes.
- For streaming workloads with strict SLAs, consider fixed executors or a higher `spark.dynamicAllocation.minExecutors` to avoid latency spikes.
- Benchmark with a representative workload before committing to a production configuration.

#### Common Pitfalls and Limitations

- Enabling dynamic allocation without shuffle preservation causes `FetchFailedException` when idle executors with shuffle data are released.
- Very large executors (more than 5–6 cores) often perform worse due to GC and context switching.
- Executor memory overhead is often underestimated. PySpark jobs need more overhead than Scala jobs because of the Python worker process.
- `spark.executor.memoryOverhead` is not part of the JVM heap. Setting only `spark.executor.memory` without accounting for overhead causes container kills.
- Setting `maxExecutors` to infinity allows a single job to monopolize a shared cluster.
- Dynamic allocation can interfere with streaming workloads if executors holding state are released.
- `spark.dynamicAllocation.executorAllocationRatio` below 1.0 reduces resource usage but can increase job latency.
- Changing executor configuration mid-job is not possible. Stop and restart the application.
- The optimal configuration is workload-specific. A configuration that works for a batch aggregation may fail for a shuffle-heavy join.

#### Summary

Deciding the number of executors, cores per executor, and executor memory requires balancing parallelism against GC overhead, and memory against shuffle and caching demands. A practical methodology starts from cluster hardware, reserves resources for the OS and ApplicationMaster, chooses 5 cores per executor as a baseline, calculates memory per executor after subtracting overhead, and validates the configuration with Spark UI metrics. Dynamic allocation adds flexibility but requires shuffle preservation. There is no universal configuration; the right values depend on data size, workload type, and cluster shape. In interviews, the strongest answers propose a concrete starting configuration, explain the reasoning behind each value, and describe how to iterate based on observed metrics.
