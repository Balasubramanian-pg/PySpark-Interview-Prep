# 4.5.5 What are the pros and cons of running Spark on Kubernetes vs YARN?

### 4.5.5 What are the pros and cons of running Spark on Kubernetes vs YARN

**YARN** and **Kubernetes** are the two most common cluster managers for Spark in production. YARN is the battle-tested scheduler of the Hadoop ecosystem, purpose-built for data workloads with mature multi-tenancy, queue management, and native HDFS locality awareness. Kubernetes is the container orchestration standard of the cloud-native world, offering superior resource isolation, elastic scaling, and a unified platform for both data and microservices workloads. The choice between them is not about which is "better" in the abstract; it depends on existing infrastructure, team expertise, workload characteristics, and the broader platform strategy. This answer provides a structured comparison of the pros and cons of each, along with the operational and performance considerations that senior engineers are expected to articulate.

#### Head-to-Head Comparison

| Dimension | YARN | Kubernetes |
|---|---|---|
| Maturity | Battle-tested for 10+ years, purpose-built for data workloads | Mature for containers, Spark integration GA since Spark 3.1 |
| Multi-tenancy | Rich queue-based model (Capacity/Fair Scheduler), capacity guarantees, preemption | No native job queues; requires Volcano or YuniKorn for fair scheduling and gang scheduling |
| Gang scheduling | Native via ApplicationMaster resource negotiation | Not native; Pods scheduled individually, risking deadlock if not all can be placed |
| Data locality | Native HDFS locality awareness | Requires manual node affinity, taints, or topology spread constraints |
| External Shuffle Service | Runs as NodeManager auxiliary service, well-integrated | Requires DaemonSet or Sidecar deployment, or reliance on shuffle tracking |
| Elasticity | Supports dynamic allocation but auto-scaling the cluster itself is painful | Native cluster autoscaling, spot instances, and node pools |
| Isolation | Container-level isolation, but dependencies are coupled to Hadoop nodes | Strong Pod-level isolation with container images and namespaces |
| Dependency management | Application dependencies tied to Hadoop node environment | Docker images package all dependencies; consistent across environments |
| Version control | Upgrading Spark or libraries affects the shared Hadoop cluster | Per-application image versions; no cluster-wide upgrades required |
| Ecosystem integration | Deep integration with Hive, HDFS, HBase, MapReduce | Integrates with cloud-native ecosystem (monitoring, CI/CD, service mesh) |
| Operational complexity | Complex configuration (`yarn-site.xml`, queues, NodeManager tuning) | Complex in different ways (RBAC, networking, storage, shuffle service) |
| Cloud portability | Tightly coupled to Hadoop; harder to run on managed cloud services | Runs identically on any Kubernetes cluster (EKS, GKE, AKS, on-prem) |
| Cost efficiency | Fixed cluster capacity; idle resources are wasted | Elastic scaling and spot instances reduce cost for variable workloads |
| Data locality for short jobs | Does not consider locality for short-running applications | Same limitation; locality requires manual configuration |
| Executor startup latency | Faster container allocation via NodeManager | Slower: executor Pod creation is sequential in some Spark versions (about 15-16 pods/second) |

#### Pros and Cons of YARN

YARN remains the lowest-risk choice for organizations with an existing stable Hadoop cluster and batch-oriented workloads.

**Pros:**

- **Purpose-built for Spark and MapReduce.** YARN understands the resource model of data workloads: vcores, memory, containers, and ApplicationMaster negotiation. It was designed for exactly this use case.
- **Mature multi-tenancy.** The Capacity Scheduler and Fair Scheduler provide hierarchical queues, capacity guarantees, and preemption. Different teams can share a cluster with enforced resource boundaries and priority-based resource reclamation.
- **Native HDFS locality.** YARN is aware of HDFS block locations and can schedule tasks on nodes that hold the data, reducing network I/O for large scans and joins.
- **External Shuffle Service is first-class.** ESS runs as a NodeManager auxiliary service. Dynamic allocation works reliably without additional infrastructure.
- **Deep Hadoop ecosystem integration.** Hive, HBase, HDFS, and MapReduce share the same resource pool. Existing operational tooling and expertise apply directly.
- **Fewer moving parts for existing Hadoop shops.** If the cluster already runs YARN for Hive and MapReduce, adding Spark is incremental rather than a platform migration.

**Cons:**

- **Heavy stack.** Running YARN requires the full Hadoop stack: ResourceManager, NodeManager, HDFS, and their configurations. This is a significant operational burden, especially in cloud environments.
- **Poor isolation between jobs and dependencies.** All applications on a node share the same Hadoop environment. Conflicting library versions or Spark versions require separate clusters or complex workarounds. YARN's job isolation shortcomings often force the creation of dedicated clusters per workload type.
- **Painful auto-scaling.** Scaling the YARN cluster itself requires adding or removing NodeManagers, which is not as fluid as Kubernetes node autoscaling.
- **Data locality ignored for short jobs.** For short-running applications, YARN does not optimize for data locality, incurring shuffle overhead and slower performance.
- **Cloud-hostile.** YARN is tightly coupled to HDFS and Hadoop. Running it on managed cloud services is possible but awkward compared to Kubernetes.
- **Slow adaptation.** YARN evolves slowly compared to Kubernetes. New features like GPU scheduling, gang scheduling improvements, and container-native workflows arrive later or not at all.

#### Pros and Cons of Kubernetes

Kubernetes is the direction for cloud-native platforms, particularly when Spark workloads coexist with microservices or when elastic scaling and cost efficiency are priorities.

**Pros:**

- **Strong isolation and dependency control.** Each Spark application runs in its own container image with all dependencies packaged. There is no risk of library conflicts with other workloads. This is a major operational advantage over YARN.
- **Elastic cluster autoscaling.** Kubernetes node autoscaling and spot instance support allow the cluster to shrink and grow with demand. This is the primary cost-efficiency driver for variable workloads.
- **Unified platform.** Data workloads run alongside microservices, CI/CD, and other containerized applications on the same infrastructure. This reduces the number of platforms to operate and simplifies networking, monitoring, and security.
- **Cloud portability.** A Spark-on-Kubernetes configuration runs identically on EKS, GKE, AKS, and on-premises clusters. There is no HDFS dependency; storage is abstracted through S3, GCS, ADLS, or persistent volumes.
- **Declarative configuration and GitOps.** Pod templates, resource quotas, and namespace isolation integrate with existing Kubernetes tooling for deployment, monitoring, and policy enforcement.
- **Fine-grained resource control.** Requests and limits per Pod, namespace-level ResourceQuota, and PriorityClass provide precise control over resource allocation.

**Cons:**

- **No native gang scheduling.** Kubernetes schedules Pods individually. If a Spark job requests N executors and the cluster can only fit N-1, the job waits indefinitely while the pending Pods occupy resources, creating a deadlock. Volcano and YuniKorn are commonly deployed to provide PodGroup-based gang scheduling.
- **No native job queues or fair sharing.** Kubernetes has no equivalent to YARN's Capacity or Fair Scheduler. Multi-tenant fair sharing requires supplementary schedulers or careful namespace and ResourceQuota design.
- **Shuffle service complexity.** Kubernetes does not provide a built-in External Shuffle Service. Deploying ESS requires a DaemonSet or Sidecar, which adds operational complexity. Shuffle tracking is the default alternative in Spark 3.4+, but it delays executor release and does not survive executor failure.
- **Slower executor allocation.** Executor Pod creation can be sequential in some Spark versions. A JIRA issue reports about 15-16 pods per second, meaning 280 executors take approximately 17.5 seconds to allocate. This is a bottleneck for jobs that need many executors quickly.
- **Data locality requires manual configuration.** Kubernetes has no native awareness of HDFS block locations. Locality must be configured through node affinity, topology spread constraints, or by colocating with storage.
- **Jar download bottleneck.** When jars are large and many executors are requested, concurrent jar downloads from the driver can saturate the network and cause executor timeouts and loss.
- **Operational learning curve.** Teams without Kubernetes experience face a significant learning curve: RBAC, networking, storage classes, pod security, and resource tuning.

#### Dynamic Allocation and Shuffle Handling

Dynamic allocation is supported on both platforms, but the shuffle preservation mechanism differs significantly.

- **On YARN**, the External Shuffle Service runs as a NodeManager auxiliary service. It is the standard, well-integrated mechanism. Dynamic allocation works reliably with ESS, and shuffle data survives executor release and even executor failure.
- **On Kubernetes**, there is no built-in ESS. Options include deploying ESS as a DaemonSet, using shuffle tracking (`spark.dynamicAllocation.shuffleTracking.enabled=true`, default in Spark 3.4+ when no ESS is configured), or enabling node decommissioning with shuffle block migration. Shuffle tracking avoids the DaemonSet requirement but delays executor release and does not protect against executor failure.

| Aspect | YARN | Kubernetes |
|---|---|---|
| Shuffle preservation | External Shuffle Service (NodeManager auxiliary) | Shuffle tracking (default), or ESS DaemonSet |
| Executor release | Immediate when idle | Delayed with shuffle tracking; immediate with ESS |
| Failure resilience | Shuffle data survives executor failure with ESS | Shuffle data lost on executor failure with shuffle tracking |
| Setup complexity | Low; ESS is part of the Hadoop cluster | Moderate to high; requires DaemonSet or rely on tracking |

#### Performance Implications

With proper configuration, Spark on Kubernetes achieves comparable or superior performance to YARN. However, several factors can degrade performance if not addressed.

- **Executor allocation latency.** Kubernetes allocates executor Pods sequentially in some Spark versions, which slows down jobs that need many executors quickly.
- **Jar distribution.** Large jars and many executors can cause network saturation during download, leading to executor loss and re-provisioning loops.
- **Shuffle disk pressure.** Shuffle spill paths must be configured to use disk-backed storage. Using `spark.kubernetes.local.dirs.tmpfs=true` routes shuffle spill to memory, causing OOM kills under heavy shuffle.
- **Resource misconfiguration.** Setting executor memory without accounting for Kubernetes Pod memory limits and overhead leads to OOM kills. The overhead factor defaults to 0.4 for non-JVM workloads on Kubernetes, compared to 0.1 for JVM workloads.

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.master` | local[*] | `yarn` for YARN; `k8s://https://<host>:<port>` for Kubernetes. |
| `spark.submit.deployMode` | client | `cluster` or `client`. On Kubernetes, `cluster` is common. |
| `spark.kubernetes.container.image` | none | Docker image for driver and executor Pods. Required on Kubernetes. |
| `spark.kubernetes.namespace` | default | Kubernetes namespace for driver and executor Pods. |
| `spark.kubernetes.authenticate.driver.serviceAccountName` | default | Service account used by the driver Pod to create executor Pods. |
| `spark.kubernetes.executor.request.cores` | none | CPU request for executor Pods. |
| `spark.kubernetes.executor.limit.cores` | none | CPU limit for executor Pods. |
| `spark.kubernetes.driver.podTemplateFile` | none | Path to a Pod template for the driver. |
| `spark.kubernetes.executor.podTemplateFile` | none | Path to a Pod template for executors. |
| `spark.shuffle.service.enabled` | false | Enables External Shuffle Service. Required for dynamic allocation on YARN without shuffle tracking. |
| `spark.dynamicAllocation.shuffleTracking.enabled` | true (Spark 3.4+) | Enables shuffle tracking as an alternative to ESS. |
| `spark.dynamicAllocation.enabled` | false | Enables dynamic executor scaling. |
| `spark.executor.memoryOverheadFactor` | 0.1 (JVM); 0.4 (K8s non-JVM) | Fraction of executor memory allocated as overhead. Higher on Kubernetes for non-JVM workloads. |
| `spark.kubernetes.allocation.batch.size` | 5 (Spark 3.x); 20 (Spark 4.2) | Number of executor Pods to request in each allocation batch. |
| `spark.decommission.enabled` | false | Enables graceful decommissioning of executors on Kubernetes. |
| `spark.storage.decommission.shuffleBlocks.enabled` | false | Migrates shuffle blocks during node decommissioning. |
| `spark.kubernetes.local.dirs.tmpfs` | false | Use tmpfs for local directories. Set to false for shuffle-heavy workloads to avoid OOM. |

#### Best Practices and When to Use

- **Choose YARN** if you have an existing stable Hadoop cluster, batch-oriented Spark workloads, a team with Hadoop operations experience, and a need for mature multi-tenancy with queues and preemption. YARN remains the lowest-risk choice for traditional data platforms.
- **Choose Kubernetes** if you are building a cloud-native platform, need elastic scaling and cost efficiency, require strong isolation between workloads, or want Spark to coexist with microservices on the same infrastructure. Kubernetes is the direction for new platforms, but it requires investment in supplementary schedulers and shuffle handling.
- On Kubernetes, deploy **Volcano** or **YuniKorn** to provide gang scheduling, queues, and fair sharing. Native Kubernetes scheduling is insufficient for large-scale data workloads.
- Configure **shuffle tracking** or deploy an **ESS DaemonSet** for dynamic allocation on Kubernetes. Since Spark 3.4, shuffle tracking is the default when no ESS is configured.
- Use **Pod templates** to inject security contexts, node affinity, tolerations, and sidecar containers without modifying Spark code.
- Set `spark.kubernetes.local.dirs.tmpfs=false` for shuffle-heavy workloads to avoid memory-backed shuffle spill and OOM kills.
- Monitor executor allocation latency, shuffle fetch failures, and Pod OOM kills in both the Spark UI and the Kubernetes event log.
- For YARN, use **Capacity Scheduler queues** to isolate teams and **Node Labels** to schedule GPU or large-memory workloads on specific node types.

#### Common Pitfalls and Limitations

- **Kubernetes gang scheduling deadlock.** Without Volcano or YuniKorn, a Spark job may wait indefinitely if not all executor Pods can be placed simultaneously, while the pending Pods block resources.
- **Shuffle data loss on Kubernetes.** Using shuffle tracking without ESS means shuffle data is lost if an executor fails. Downstream stages must recompute the map stage.
- **Jar download storms.** Large jars and many executors can saturate the driver network, causing executor timeouts and re-provisioning loops.
- **Executor allocation latency.** Sequential Pod allocation slows down jobs that need many executors quickly. Increasing `spark.kubernetes.allocation.batch.size` helps but does not fully solve the problem.
- **YARN dependency coupling.** All applications on a YARN node share the same Hadoop environment. Conflicting library versions require separate clusters or complex classpath isolation.
- **YARN auto-scaling is painful.** Scaling the YARN cluster itself requires adding or removing NodeManagers, which is not as fluid as Kubernetes node autoscaling.
- **Data locality on Kubernetes.** Without manual configuration, Spark on Kubernetes may read data over the network instead of from local HDFS replicas, increasing I/O costs.
- **OOM kills from misconfigured overhead.** On Kubernetes, the memory overhead factor for non-JVM workloads is 0.4. Setting executor memory without accounting for this causes Pod OOM kills.
- **Cloud storage latency.** Kubernetes clusters typically use S3, GCS, or ADLS instead of HDFS. Object storage has higher per-request latency, which can affect shuffle and read performance.
- **Security configuration.** Both platforms require explicit security configuration. Neither enables authentication by default in open-source Spark.

#### Summary

YARN and Kubernetes each have distinct strengths for running Spark. YARN is the mature, purpose-built scheduler for data workloads, offering native HDFS locality, rich multi-tenancy with queues, and a well-integrated External Shuffle Service. It is the lowest-risk choice for existing Hadoop shops with batch-oriented workloads. Kubernetes offers stronger isolation through container images, elastic autoscaling, cloud portability, and a unified platform for data and microservices. However, it lacks native gang scheduling and job queues, requiring Volcano or YuniKorn, and shuffle preservation requires either a DaemonSet ESS or shuffle tracking. In interviews, the strongest answers avoid declaring a universal winner; they map the choice to the organization's existing infrastructure, workload characteristics, team expertise, and platform strategy, and they demonstrate awareness of concrete operational differences such as shuffle handling, executor allocation latency, and multi-tenancy models.
