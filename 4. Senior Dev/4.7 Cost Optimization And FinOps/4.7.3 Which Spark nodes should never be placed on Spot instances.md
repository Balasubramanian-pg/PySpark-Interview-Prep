### 4.7.3 Which Spark nodes should never be placed on Spot instances

**Spot instances** (AWS, Azure) and **Preemptible VMs** (GCP) offer discounts of up to 90% compared to on-demand pricing, but they can be reclaimed by the cloud provider with as little as 30 seconds of notice. While Spark's fault tolerance makes many workloads suitable for spot, certain nodes are critical to job orchestration, state management, or shuffle data availability. Placing these nodes on spot instances risks catastrophic job failure, data loss, or cascading service disruption. This answer identifies the Spark node roles that should never be placed on spot instances, explains the reasoning, and provides configuration guidance for a safe hybrid architecture.

#### Node Roles in a Spark Application

A Spark application comprises several node roles, each with different failure characteristics. The impact of losing a node depends on its role.

| Node Role | Function | Loss Impact | Spot Safe? |
|---|---|---|---|
| Driver | Orchestrates the job, schedules tasks, maintains job state | Entire application fails; no automatic recovery | Never |
| ApplicationMaster (YARN) | Negotiates resources, manages job lifecycle | Entire application fails | Never |
| Master (standalone) | Manages worker registration and resource allocation | Cluster becomes unavailable | Never |
| External Shuffle Service | Serves shuffle blocks to reduce tasks | Shuffle fetch failures for all apps on that node | Never |
| HDFS NameNode | Stores HDFS metadata | HDFS becomes unavailable | Never |
| HDFS DataNode (with local replicas) | Stores HDFS data blocks | Data loss, re-replication, potential corruption | Never |
| Stateful streaming executors | Hold in-memory state for Structured Streaming | State recovery from checkpoint, latency spike | Avoid for strict SLAs |
| Batch executors | Process tasks, write shuffle output | Tasks rescheduled; shuffle recomputation | Yes, with decommissioning |

#### The Driver: The Most Critical Node

The **driver** is the process that runs the `main()` function of a Spark application. It builds the DAG, schedules tasks, tracks job progress, and maintains the SparkContext. If the driver is lost, the entire application fails. Spark does not provide automatic driver recovery in client mode, and in cluster mode, the ApplicationMaster may restart the driver, but this is not guaranteed and can cause duplicate output.

- Losing the driver means losing all in-memory job state, including the DAG, stage progress, and task scheduling information.
- Recovering from a driver failure requires restarting the entire application from the beginning, re-reading all input data and recomputing all transformations.
- For streaming workloads, driver failure terminates the query. Recovery depends on checkpointing, but the interruption causes latency and potential duplicate processing.

The driver must always run on an on-demand instance. The cost difference between on-demand and spot for a single driver node is negligible compared to the risk of losing the entire job. AWS EMR, Cloudera, and Databricks all recommend keeping the driver on on-demand. On Kubernetes, this is implemented by scheduling the driver pod on an on-demand node pool using node selectors or taints and tolerations.

#### ApplicationMaster and Standalone Master

In YARN, the **ApplicationMaster** is the process that negotiates resources with the ResourceManager and manages the lifecycle of the Spark application. It is functionally similar to the driver in cluster mode. If the ApplicationMaster is lost, the application fails or must be restarted. YARN does not automatically restart the ApplicationMaster for Spark applications in a way that preserves job state.

In standalone mode, the **Master** process manages worker registration and resource allocation. If the Master is lost, the entire cluster becomes unavailable, and no new applications can start. Existing applications may continue running temporarily, but the cluster cannot recover without restarting the Master.

Both ApplicationMaster and standalone Master must run on on-demand instances. They are singleton processes with no fault tolerance, and their failure has cluster-wide or application-wide impact.

#### External Shuffle Service

The **External Shuffle Service (ESS)** is a long-running auxiliary process that serves shuffle files independently of Spark executors. It runs on each worker node and serves shuffle blocks for all applications running on that node. If an ESS node is reclaimed, several problems occur:

- All shuffle data stored on that node becomes unavailable to downstream tasks.
- Reduce tasks that attempt to fetch shuffle blocks from that node fail with `FetchFailedException`.
- Other applications running on the same node also lose their shuffle data, causing cascading failures across multiple jobs.

ESS is designed to outlive individual executors, but it is not designed to survive node loss. If the node itself is reclaimed, ESS goes down with it. Therefore, nodes running ESS should be on on-demand instances. On Kubernetes, where ESS is deployed as a DaemonSet, this means either deploying ESS only on on-demand node pools or using shuffle tracking instead of ESS for spot node pools.

#### HDFS NameNode and DataNodes

If Spark reads from or writes to HDFS, the **NameNode** and **DataNodes** are part of the storage layer. Losing a NameNode makes HDFS unavailable, which causes all Spark jobs that depend on HDFS to fail. Losing a DataNode with local replicas can cause data loss and trigger re-replication, which consumes network and disk resources. In clusters where HDFS data nodes also run Spark executors, placing those nodes on spot instances is dangerous because preemption can cause both data loss and job failure.

The general rule is that any node holding primary data replicas or metadata should not be preemptible. This includes HDFS NameNode, JournalNode, and DataNode roles, as well as any other persistent storage service colocated on the node.

#### Stateful Streaming Executors

Structured Streaming stateful operations such as aggregations, `dropDuplicates`, and stream-stream joins maintain state in the state store, which is checkpointed to durable storage. However, executors also hold in-memory state during processing. If an executor is preempted, the in-memory state is lost and must be recovered from the checkpoint. This recovery process takes time and can cause latency spikes.

For streaming workloads with strict SLA requirements, stateful executors should run on on-demand instances to avoid interruption. For fault-tolerant streaming pipelines where occasional latency spikes are acceptable, spot instances can be used with checkpointing and decommissioning enabled. The decision depends on the business tolerance for latency and the cost of recomputation.

#### Hybrid Architecture: The Recommended Pattern

The recommended pattern is a **hybrid cluster** with on-demand instances for critical nodes and spot instances for fault-tolerant executors. This balances cost savings against reliability.

| Node Type | Instance Type | Rationale |
|---|---|---|
| Driver | On-demand | Driver failure kills the job |
| ApplicationMaster | On-demand | Manages job lifecycle |
| Standalone Master | On-demand | Cluster-wide singleton |
| External Shuffle Service | On-demand | Serves shuffle data for all apps |
| HDFS NameNode | On-demand | HDFS metadata availability |
| HDFS DataNode | On-demand | Data durability |
| Batch executors | Spot | Fault-tolerant, rescheduled on failure |
| Stateful streaming executors | On-demand (for strict SLAs) or Spot (with checkpointing) | Latency sensitivity vs. cost |

On AWS EMR, this is implemented using **instance fleets** with separate instance groups for the master (on-demand) and core/task nodes (spot). On GCP Dataproc, **primary workers** run on on-demand and **secondary workers** run on preemptible VMs. On Kubernetes, node selectors and taints direct the driver to on-demand node pools and executors to spot node pools.

#### Complete Python Example

The following self-contained example configures a Spark session with executor decommissioning enabled for spot instance resilience. The driver placement is controlled at the cluster level, not in Spark configuration, so the code focuses on executor-side settings.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, rand

spark = (
    SparkSession.builder
    .appName("HybridSpotOnDemandDemo")
    # Executor decommissioning for spot instance resilience
    .config("spark.decommission.enabled", "true")
    .config("spark.storage.decommission.enabled", "true")
    .config("spark.storage.decommission.rddBlocks.enabled", "true")
    .config("spark.storage.decommission.shuffleBlocks.enabled", "true")
    .config("spark.storage.decommission.maxReplicationFailuresPerBlock", "3")
    .config("spark.storage.decommission.shuffleBlocks.maxThreads", "8")
    .config("spark.blacklist.decommissioning.enabled", "true")
    # Executor sizing
    .config("spark.executor.cores", "5")
    .config("spark.executor.memory", "16g")
    .config("spark.executor.memoryOverhead", "2g")
    # Dynamic allocation with shuffle tracking
    .config("spark.dynamicAllocation.enabled", "true")
    .config("spark.dynamicAllocation.minExecutors", "2")
    .config("spark.dynamicAllocation.maxExecutors", "20")
    .config("spark.dynamicAllocation.shuffleTracking.enabled", "true")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# A shuffle-heavy aggregation that exercises executor shuffle writes
df = (
    spark.range(0, 20_000_000)
    .withColumn("key", (rand() * 500).cast("int"))
    .withColumn("value", rand())
)

result = df.groupBy("key").agg(count("*").alias("cnt"))
result.orderBy(col("cnt").desc()).show(5, truncate=False)

spark.stop()
```

The driver placement is configured externally. For AWS EMR, an instance fleet JSON specifies `ON_DEMAND` for the master instance group and `SPOT` for task instance groups. For Kubernetes, a pod template with `nodeSelector: { "lifecycle": "on-demand" }` is applied to the driver pod.

#### Configuration Parameters

| Parameter | Default | Description |
|---|---|---|
| `spark.decommission.enabled` | `false` | Enables graceful executor decommissioning. |
| `spark.storage.decommission.enabled` | `false` | Enables block manager decommissioning. |
| `spark.storage.decommission.rddBlocks.enabled` | `false` | Transfers cached RDD blocks during decommissioning. |
| `spark.storage.decommission.shuffleBlocks.enabled` | `false` | Transfers shuffle blocks during decommissioning. Requires a migratable shuffle resolver. |
| `spark.storage.decommission.maxReplicationFailuresPerBlock` | `3` | Maximum failures tolerated when migrating shuffle blocks. |
| `spark.storage.decommission.shuffleBlocks.maxThreads` | `8` | Maximum threads for shuffle block migration. |
| `spark.blacklist.decommissioning.enabled` | `true` | Prevents new tasks from being scheduled on decommissioning nodes. |
| `spark.dynamicAllocation.shuffleTracking.enabled` | `true` (Spark 3.4+) | Preserves shuffle data without External Shuffle Service. |
| `spark.dynamicAllocation.minExecutors` | `0` | Lower bound for executor count. |
| `spark.dynamicAllocation.maxExecutors` | `Integer.MAX_VALUE` | Upper bound for executor count. Set a finite value. |
| `spark.dynamicAllocation.executorIdleTimeout` | `60s` | Idle time before executor release. |

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Driver on on-demand | Eliminates risk of total job failure | Higher cost for one node |
| ApplicationMaster on on-demand | Job lifecycle stability | Higher cost for one container |
| ESS on on-demand | Shuffle data availability for all apps | Higher cost for all ESS nodes |
| Executors on spot | Up to 90% savings on compute | Task retries and shuffle recomputation on preemption |
| Decommissioning enabled | Shuffle data migrated before termination | Additional configuration and migration overhead |
| Stateful streaming on on-demand | Avoids latency spikes from state recovery | Higher cost for stateful nodes |

#### Best Practices

- Always run the **driver** on an on-demand instance. The cost of one on-demand node is trivial compared to the cost of a failed job.
- Run the **ApplicationMaster** and **standalone Master** on on-demand instances.
- Deploy the **External Shuffle Service** on on-demand nodes, or use shuffle tracking for spot node pools.
- Keep **HDFS NameNode** and **DataNode** roles on on-demand instances to preserve data durability.
- For stateful streaming with strict SLAs, run executors on on-demand. For fault-tolerant streaming, spot with checkpointing and decommissioning is acceptable.
- Enable **executor decommissioning** with shuffle block migration for all spot executor pools.
- Use **instance fleets** or **node pools** to separate on-demand and spot resources by role.
- Monitor spot interruption rates and adjust instance types to reduce preemption frequency.

#### Common Pitfalls and Limitations

- Placing the driver on a spot instance. Driver loss fails the entire job, and recovery requires a full restart.
- Disabling decommissioning while using spot executors. Shuffle data is lost on preemption, forcing full map-stage recomputation.
- Running the External Shuffle Service on spot nodes without a fallback. Losing an ESS node breaks shuffle fetch for all applications on that node.
- Colocating HDFS DataNodes with spot executors. Preemption can cause data loss and trigger expensive re-replication.
- Assuming all executors are equally safe on spot. Stateful streaming executors holding in-memory state are more sensitive to interruption than stateless batch executors.
- Setting the decommissioning timeout longer than the spot termination notice. The executor is killed before migration completes.
- Forgetting that GCP preemptible VMs have a maximum lifespan of 24 hours, regardless of capacity pressure.
- Using spot instances for streaming workloads with strict latency SLAs. State recovery causes unacceptable delays.

#### Summary

The driver, ApplicationMaster, standalone Master, External Shuffle Service, HDFS NameNode, and HDFS DataNode roles should never be placed on spot instances. These nodes are singletons, hold critical metadata, or serve shuffle data for multiple applications, and their loss causes job failure, data loss, or cascading service disruption. Executors for batch workloads are safe on spot when decommissioning is enabled. Stateful streaming executors are safe only when checkpointing is in place and latency spikes are acceptable. The recommended architecture is a hybrid cluster with on-demand instances for critical roles and spot instances for fault-tolerant executors. In interviews, emphasize the driver-versus-executor distinction, the role of the External Shuffle Service, and the decommissioning mechanism that makes spot executors production-safe.
