### 4.7.5 What are some common ways to reduce cloud storage API costs

Cloud storage API costs are a hidden but significant component of Spark and Lakehouse spending. Every `LIST`, `GET`, `PUT`, `HEAD`, and `KMS Decrypt` operation is billed separately from storage capacity, and at scale these request charges can rival or exceed the cost of the data itself. A single Spark job writing to 5,000,000 partitions made approximately 19 S3 requests per partition, resulting in roughly $450 per day in API costs alone. The strategies that reduce these costs fall into four categories: Delta Lake and table format optimizations, Spark write path tuning, streaming and checkpointing optimization, and encryption cost reduction.

#### Delta Lake and Table Format Optimizations

Delta Lake's transaction log is the single most effective tool for eliminating redundant storage API calls, because it replaces expensive `LIST` operations with direct, sequential path reads. The following Delta-specific techniques compound the savings.

**File compaction with OPTIMIZE.** Small files are the primary driver of API cost inflation. Each file requires at minimum one `GET` to read and contributes to metadata overhead. Delta Lake's `OPTIMIZE` command compacts small Parquet files into larger, right-sized files (typically targeting 1 GB). This reduces the number of files and, consequently, the number of API requests required to read or write the table. Delta Lake optimization reduces storage costs by 40–60% through data compaction and efficient compression.

```sql
-- Compact small files into larger files
OPTIMIZE sales;

-- Compact with Z-Ordering on frequently filtered columns
OPTIMIZE sales ZORDER BY (region, order_date);

-- Scope OPTIMIZE to recent partitions to avoid full rewrites
OPTIMIZE sales WHERE order_date >= current_date() - INTERVAL 7 DAYS ZORDER BY (region);
```

```python
from delta.tables import DeltaTable

delta_table = DeltaTable.forPath(spark, "/data/sales")
delta_table.optimize().executeCompaction()
delta_table.optimize().executeZOrderBy("region", "order_date")
```

**Disable S3 bucket versioning for Delta tables.** Delta Lake manages versioning through its transaction log and writes immutable data files. S3 native object versioning retains noncurrent versions of every overwritten or deleted object, which directly conflicts with Delta Lake's versioning model. When `VACUUM` removes obsolete files, S3 retains them as noncurrent versions instead of deleting them, causing storage to grow indefinitely and slowing down API responses. Databricks recommends disabling S3 bucket versioning for Delta tables. If versioning must be retained for compliance, apply a lifecycle policy that expires noncurrent versions after a short period, such as seven days, and retains no more than three versions.

```bash
# Disable S3 bucket versioning
aws s3api put-bucket-versioning \
  --bucket your-bucket \
  --versioning-configuration Status=Suspended
```

```json
{
  "Rules": [
    {
      "ID": "LimitNumberOfVersions",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 7,
        "NewerNoncurrentVersions": 3
      }
    }
  ]
}
```

**Auto-optimize features.** Enable automatic compaction and optimized writes to prevent small files from accumulating in the first place. These features bin-pack data before or shortly after writing, reducing the number of files and the API calls needed to manage them.

```python
# Table-level auto-optimize properties
spark.sql("""
    ALTER TABLE sales SET TBLPROPERTIES (
        'delta.autoOptimize.optimizeWrite' = 'true',
        'delta.autoOptimize.autoCompact' = 'true'
    )
""")
```

**Storage classes and lifecycle policies.** Move infrequently accessed data to cheaper storage tiers such as S3 Infrequent Access (S3-IA) or Glacier. A lifecycle policy that transitions files older than 30 days to S3-IA reduces storage cost without affecting API access patterns for recent data.

#### Spark Write Path Optimizations

The write path generates API calls for file creation, directory markers, commit metadata, and cleanup. These techniques reduce write-side API volume.

**Use S3A committers instead of the default committer.** The default Hadoop `FileOutputCommitter` performs expensive rename and delete operations that translate to multiple S3 API calls. Switching to an S3A committer reduces the number of `PUT`, `COPY`, `POST`, and `LIST` requests. Hadoop 3.3.6+ includes optimizations that further reduce nominal safety checks. The EMRFS S3-optimized committer is another alternative that is optimized for writing Parquet, ORC, and text-based formats to S3.

```python
spark = (
    SparkSession.builder
    .appName("S3ACommitterOptimization")
    .config("spark.hadoop.fs.s3a.committer.name", "directory")
    .config("spark.hadoop.fs.s3a.committer.magic.enabled", "true")
    .getOrCreate()
)
```

**Reduce directory marker retention.** Directory markers are zero-byte objects that simulate directories in object stores. They require `DELETE` calls during cleanup. Setting `spark.hadoop.fs.s3a.directory.marker.retention` to `keep` avoids deleting directory markers, reducing `DELETE` API calls.

```python
spark.conf.set("spark.hadoop.fs.s3a.directory.marker.retention", "keep")
```

**Control file count at write time.** Before writing, use `coalesce()` or `repartition()` to control the number of output files. Writing 5,000,000 partitions to S3 generated approximately 19 requests per partition. Reducing the file count directly reduces the API call volume. However, avoid coalescing to a single partition for large datasets, as this causes data skew and memory pressure.

```python
# Reduce the number of output files before writing
df.coalesce(10).write.mode("overwrite").parquet("s3a://bucket/path/")
```

**Optimize file size.** Aim for Parquet files of approximately 128 MB to 1 GB. Files that are too small generate excessive API calls; files that are too large reduce parallelism. The AWS Glue documentation recommends keeping input and output file sizes within a moderate range, such as 128 MB.

#### Streaming and Checkpointing Optimizations

Structured Streaming and Glue streaming jobs generate API calls through checkpointing, file listing, and micro-batch writes. The following techniques reduce this overhead.

**Increase the micro-batch interval.** A 15-second trigger interval creates frequent checkpoint files and repeated `LIST` operations. Increasing the interval to 60 or 120 seconds significantly reduces S3 request volume without compromising reliability. Fast processing with sub-second intervals repeats listing operations and causes unintended costs.

```python
query = (
    stream_df.writeStream
    .foreachBatch(process_batch)
    .trigger(processingTime="60 seconds")
    .option("checkpointLocation", "s3a://bucket/checkpoints/my_job")
    .start()
)
```

**Use a dedicated checkpoint location with lifecycle rules.** Place checkpoints in a separate S3 prefix or bucket with a lifecycle policy that expires objects after a short retention period, such as 7 days or 1 day if safe. This reduces object listing size and avoids long `ListBucket` calls during job recovery.

**Minimize task-level checkpoint files.** Stateful operations such as `mapGroupsWithState` and `foreachBatch` can produce many task-level checkpoint files. Reducing the parallelism of the stream with `repartition(1)` limits the number of files written per checkpoint. However, this trades off parallelism and should be used only when the state is small.

**Use Delta Lake for streaming sinks.** Delta Lake's transaction log replaces directory listing with direct path reads. This eliminates the `LIST` API calls that file-based sinks generate on every micro-batch.

#### Encryption and KMS Cost Reduction

When S3 data is encrypted with AWS KMS, every object read triggers a `kms:Decrypt` API call. At scale, these costs accumulate quickly. Three techniques reduce KMS decrypt costs without changing the encryption strategy.

**Enable S3 Bucket Keys.** S3 Bucket Keys are the most effective way to reduce KMS Decrypt API calls. They reduce the number of KMS requests by up to 99% by using a bucket-level key to generate data keys locally, rather than calling KMS for every object. This is a bucket-level setting and requires no code changes.

**Aggregate small files.** Consolidating small files into larger blocks reduces the number of objects that need to be decrypted. Each file access triggers a separate `kms:Decrypt` call, so fewer files means fewer decrypt calls.

**Use Glue Data Catalog partition indexes.** Partition indexes reduce the number of partitions that Spark must scan, which in turn reduces the number of S3 objects read and KMS decrypt calls. This is particularly effective for tables with many partitions.

#### Reduce LIST Operations

`LIST` operations are among the most expensive S3 API calls because they return up to 1,000 objects per call. A job that lists a directory with 137,000 files requires 137 `LIST` calls; without proper handling, a full directory scan can balloon to 87,000 API calls.

**Use Delta Lake to eliminate listing.** Delta Lake's transaction log records the exact files that belong to each table version. Readers consult the log instead of listing the directory, replacing expensive `LIST` calls with direct path reads. This is the single most effective way to eliminate listing costs for lakehouse tables.

**Use SQS-based file discovery for streaming file sources.** Spark's file source lists the input directory on every micro-batch to discover new files. Amazon SQS can notify Spark of new files without listing the entire prefix. Spark can leverage SQS notifications to find new files written to an S3 bucket by reading from an SQS queue instead of listing files every micro-batch.

**Partition data to limit listing scope.** Partitioning by date or region means that a query for one day's data only lists that partition's directory, not the entire table. This reduces the number of `LIST` calls proportionally to the partition granularity.

#### Comparison of Cost Reduction Strategies

| Strategy | Primary API Impact | Effort | Typical Savings |
|---|---|---|---|
| Delta Lake OPTIMIZE | Reduces GET and LIST | Low | 40–60% storage cost |
| Disable S3 versioning | Eliminates noncurrent version storage | Low | Prevents exponential growth |
| S3A committer | Reduces PUT, COPY, LIST | Medium | 2 PUT + 1 LIST + 1 GET per task |
| Directory marker retention=keep | Reduces DELETE | Low | Eliminates marker cleanup calls |
| Increase streaming trigger interval | Reduces PUT and LIST | Low | Proportional to interval increase |
| Dedicated checkpoint + lifecycle | Reduces LIST during recovery | Low | Depends on retention |
| S3 Bucket Keys | Reduces KMS Decrypt | Low | Up to 99% of KMS calls |
| Data aggregation | Reduces GET and KMS Decrypt | Medium | Proportional to file count reduction |
| Delta transaction log | Eliminates LIST for reads | None (built-in) | Replaces all listing for table reads |
| SQS file discovery | Eliminates LIST for streaming | Medium | Replaces full-prefix listing |
| Partition pruning | Reduces LIST and GET | Medium | Proportional to partition selectivity |

#### Best Practices

- Enable `OPTIMIZE` and `autoCompact` on Delta tables that receive frequent small writes.
- Disable S3 bucket versioning for Delta Lake buckets. If versioning is required, set a lifecycle policy that expires noncurrent versions after 7 days and retains no more than three versions.
- Use S3A committers instead of the default committer for all Spark writes to S3.
- Set `spark.hadoop.fs.s3a.directory.marker.retention=keep` to avoid unnecessary `DELETE` calls.
- Increase streaming micro-batch intervals to 60 seconds or more where latency permits.
- Place checkpoints in a dedicated prefix with a short lifecycle expiration policy.
- Enable S3 Bucket Keys to reduce KMS decrypt costs by up to 99%.
- Aggregate small files before reading encrypted data to reduce KMS decrypt calls.
- Use Delta Lake's transaction log to avoid `LIST` operations on table reads.
- Monitor API call volume and costs using CloudTrail, CloudWatch, or the platform's billing system tables.

#### Common Pitfalls and Limitations

- Enabling S3 bucket versioning on Delta Lake tables causes storage to grow exponentially and slows API responses. `VACUUM` has little effect on versioned objects.
- Leaving the default committer in place generates 19 or more API calls per partition written, as seen in the $450/day example.
- Using a 15-second streaming trigger interval creates excessive checkpoint files and repeated listing operations.
- Writing millions of tiny partitions to S3 generates disproportionate API costs relative to the data volume.
- Ignoring KMS decrypt costs when encryption is mandatory. S3 Bucket Keys are a no-cost configuration change that dramatically reduces these calls.
- Coalescing to a single partition to reduce file count causes data skew and memory pressure for large datasets.
- Forgetting to scope `OPTIMIZE` with a `WHERE` clause rewrites the entire table on every run, consuming compute and I/O unnecessarily.
- Using `VACUUM` with a retention shorter than the time travel requirement breaks historical queries.

#### Summary

Reducing cloud storage API costs requires action across four areas: table format, write path, streaming, and encryption. Delta Lake's `OPTIMIZE` and transaction log eliminate small files and `LIST` operations. Disabling S3 bucket versioning prevents exponential storage growth. S3A committers and directory marker retention reduce write-side API calls. Longer streaming intervals and dedicated checkpoint locations reduce checkpoint overhead. S3 Bucket Keys cut KMS decrypt costs by up to 99%. In interviews, emphasize that API costs are often invisible until the bill arrives, and that the highest-ROI changes are configuration-level: disable versioning, enable Delta optimizations, switch to S3A committers, and enable S3 Bucket Keys.
