# 4.7.1 How do you identify zombie or idle Spark clusters in the cloud?

### 4.7.1 How do you identify zombie or idle Spark clusters in the cloud

A **zombie Spark cluster** is a compute resource that is running but serving no useful workload. It may have been left running after a job completed, may be attached to an interactive session that no one is using, or may be a driver process that has lost its executors but has not terminated. An **idle cluster** is similar but may still be intentionally running between jobs. Both waste cloud spend: a single idle cluster running overnight or over a weekend can generate significant unexpected charges, and a cluster whose most recent job finished days ago is a clear deletion candidate. Identifying these resources requires platform-specific metrics, Spark-level indicators, and automated detection patterns. This answer covers the detection methods across Databricks, AWS EMR, Azure HDInsight, and GCP Dataproc, plus programmatic approaches using Spark's REST API and status tracker.

#### Definition and Cost Impact

The distinction between a healthy idle cluster and a zombie cluster matters because the remediation differs. A healthy idle cluster may be intentionally kept warm for interactive use; a zombie cluster is one that should have been terminated but was not.

| State | Description | Typical Cause | Remediation |
|---|---|---|---|
| Healthy idle | Cluster is up but no jobs running, with an active auto-termination policy | User is between queries; job just finished | Leave it; auto-termination will handle it |
| Zombie | Cluster has been idle for an extended period with no auto-termination or with the policy disabled | Interactive session abandoned; job failed silently; driver stuck | Terminate manually or via automation |
| Ghost job | A job appears in the Spark UI but has no visible Job IDs or has been running for an abnormal duration | Process timed out or was force-cancelled, leaving a stale entry | Cancel the job; investigate the driver |

A single idle cluster running overnight or over a weekend can generate significant unexpected charges, and these costs compound when multiple teams share workspaces without visibility into resource usage patterns. FinOps practitioners classify zombie infrastructure as "the most blatant form of waste: resources that are running but serving zero business value".

#### Platform-Specific Detection Methods

Each cloud platform provides native tooling for identifying idle Spark clusters. The detection mechanism and the specific metric names differ.

##### Databricks

Databricks exposes cluster activity through **system tables** and the **compute metrics UI**. The `system.billing.usage` table records DBU consumption and cluster metadata, and `system.compute` tables record cluster events and node metrics. You can query these tables to identify clusters with high idle time relative to their total uptime.

```sql
-- Identify clusters with high idle time relative to total running time
SELECT
  u.workspace_id,
  u.cluster_id,
  u.cluster_name,
  SUM(u.usage_quantity) AS total_dbus,
  COUNT(DISTINCT u.usage_date) AS active_days,
  MAX(u.usage_date) AS last_active_date
FROM system.billing.usage u
WHERE u.usage_date >= current_date() - INTERVAL 30 DAYS
  AND u.sku_name LIKE '%ALL_PURPOSE%'
GROUP BY u.workspace_id, u.cluster_id, u.cluster_name
HAVING MAX(u.usage_date) < current_date() - INTERVAL 3 DAYS
ORDER BY total_dbus DESC;
```

A cluster whose `last_active_date` is several days old but is still running is a zombie candidate. The Databricks compute metrics UI shows **CPU utilization**, which reveals whether the cluster is working hard or sitting idle, and **Spark metrics** such as active tasks, failed tasks, and shuffle read/write. A cluster with near-zero CPU utilization and no active tasks over a sustained period is idle.

**Auto-termination** is the primary prevention mechanism. Auto-termination shuts down idle clusters after a specified period of inactivity. A cluster is considered inactive only when all commands—including Spark jobs, notebooks, and driver-specific application code—have stopped. Driver-specific code such as connecting to a REST API or polling a database can keep a cluster marked as non-idle even when no Spark jobs are running.

##### AWS EMR

Amazon EMR provides the **`IsIdle`** CloudWatch metric, which tracks whether a cluster is live but not currently running tasks. You can set an alarm to fire when the cluster has been idle for a given period, such as 30 minutes. EMR also emits **`AutoTerminationIsClusterIdle`**, which indicates whether the cluster is in use. A value of 1 means the cluster is idle, and EMR checks for continuous idleness before terminating based on the auto-termination policy's `IdleTimeout` value.

The `IsIdle` metric checks the value every five minutes; a value of 1 indicates that the cluster was idle at the time of the check, not necessarily for the entire five-minute interval. EMR determines idleness based on YARN application activity, HDFS utilization, active notebooks, and cluster UIs such as the Spark History Server.

An idle cluster is one with no active YARN applications, no active Spark tasks, and no active notebook kernels. A critical edge case is an active Python3 kernel: running a Python3 kernel does not submit a Spark job on the cluster, but it can keep the cluster from being considered idle.

##### Azure HDInsight

Azure HDInsight **bills hourly per node** across the entire VM fleet and offers **no stop operation**. Clusters cannot be stopped, so idle ones bill their full fleet continuously. This makes idle HDInsight clusters one of the costlier analytics leaks.

HDInsight provides **Autoscale**, which automatically increases or decreases the number of worker nodes based on cluster metrics and scaling policies. Autoscale monitors metrics such as CPU utilization, memory usage, and pending YARN memory to decide whether to scale in or out. You can monitor the HDInsight cluster using **Apache Ambari** or **Azure Monitor** to identify clusters that are not being utilized. The guidance is direct: delete clusters that are not in use.

##### GCP Dataproc

Google Cloud Dataproc clusters can be listed via the `list_clusters` API, which returns cluster status including state (`ACTIVE`, `RUNNING`, `STOPPED`, etc.). A cluster in `RUNNING` state whose most recent job finished days ago is a deletion candidate. Tools such as ZopNight discover clusters across 30+ regions via Cloud Asset Inventory, count active jobs on each cluster, and flag clusters sitting idle between Spark or Hadoop runs for deletion or ephemeral rebuilds.

#### Spark-Level Indicators of Idleness

Regardless of the cloud platform, the Spark UI and Spark's programmatic APIs provide direct evidence of idle or zombie state.

- **Executors tab**: The number of **Idled** cores represents cores that are available but unused while the Spark application is running. A high idle-core count over a sustained period indicates the cluster is over-provisioned or the application is stuck.
- **Stages tab**: A stage that has been running for an abnormally long time with no task progress or with all tasks in a pending state suggests a zombie job.
- **Jobs tab**: A job entry with no visible Job IDs indicates a zombie state. This typically happens when a process times out or is force-cancelled, leaving a "ghost" entry behind in the Spark UI.
- **Driver logs**: Repeated `Removing executor ... because it has been idle` messages or `Executor ... is idle` messages from the `ExecutorAllocationManager` indicate that executors are being released due to idleness. Persistent idleness with no new executor requests suggests the application is stuck.
- **Streaming queries**: As of Spark 3.4, when a streaming query is idle for more than `spark.sql.streaming.noDataProgressEventInterval` (default 10 seconds), an idle event is emitted. A streaming query that has been idle for hours without processing new data may be a zombie if it is no longer needed.

#### Programmatic Detection with the Spark REST API and Status Tracker

For automated monitoring, Spark provides a REST API and a status tracker that allow you to detect idle or zombie state without manual inspection of the UI.

The Spark status tracker exposes job and stage information. The following complete example demonstrates how to inspect job and executor state programmatically.

```python
import time
from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("IdleDetectionDemo")
    .master("local[2]")
    .getOrCreate()
)
sc = spark.sparkContext
sc.setLogLevel("WARN")

# Run a small job to populate the tracker
rdd = sc.parallelize(range(100_000), 4).map(lambda x: (x % 10, x))
rdd.reduceByKey(lambda a, b: a + b).count()

tracker = sc.statusTracker()

# Inspect all jobs and stages
for job_id in tracker.getJobIdsForGroup(None):
    job = tracker.getJobInfo(job_id)
    if job is None:
        continue
    print(f"Job {job_id}: status={job.status}, activeStages={job.numActiveStages}")
    for stage_id in job.stageIds:
        stage = tracker.getStageInfo(stage_id)
        if stage is None:
            continue
        print(
            f"  Stage {stage_id}: status={stage.status}, "
            f"activeTasks={stage.numActiveTasks}, "
            f"completedTasks={stage.numCompletedTasks}, "
            f"failedTasks={stage.numFailedTasks}"
        )

# Inspect executors
for ex in tracker.getExecutorInfos():
    print(
        f"Executor {ex.executorId}: host={ex.host}, "
        f"cores={ex.totalCores}, active={ex.isActive}, "
        f"maxMemory={ex.maxMemory}"
    )

# A cluster is idle if all executors report no active tasks and no
# pending stages exist over a sustained period.
spark.stop()
```

The Spark REST API at `http://<driver-host>:4040/api/v1/applications` exposes similar information as JSON. You can query `/api/v1/applications/{appId}/executors` to list executors and their `totalTasks`, `activeTasks`, and `rddBlocks`. An executor with zero active tasks over multiple polling intervals indicates idleness.

The following example polls the REST API to detect an idle application.

```python
import requests
import time

DRIVER_HOST = "localhost"
PORT = 4040
APP_ID = "local-1234567890"

def get_executors():
    url = f"http://{DRIVER_HOST}:{PORT}/api/v1/applications/{APP_ID}/executors"
    return requests.get(url).json()

def is_idle(executors, threshold=3):
    """Return True if every executor has zero active tasks."""
    return all(ex.get("activeTasks", 0) == 0 for ex in executors)

idle_count = 0
while idle_count < 3:
    executors = get_executors()
    if is_idle(executors):
        idle_count += 1
        print(f"Idle check {idle_count}/3: no active tasks")
    else:
        idle_count = 0
        print("Active tasks detected; resetting idle counter")
    time.sleep(30)

print("Application has been idle for 3 consecutive checks. Candidate for termination.")
```

#### Detection Method Comparison

| Method | Platform | Detection Signal | Automation Potential |
|---|---|---|---|
| System tables (`system.billing.usage`) | Databricks | DBU consumption, last active date | High; SQL queries and alerts |
| Compute metrics UI | Databricks | CPU utilization, active tasks, shuffle | Medium; manual inspection |
| Auto-termination status | Databricks | Cluster inactivity (all commands) | High; automatic termination |
| `IsIdle` CloudWatch metric | AWS EMR | Cluster live but no tasks running | High; CloudWatch alarms |
| `AutoTerminationIsClusterIdle` | AWS EMR | Continuous idleness check | High; automatic termination |
| Autoscale metrics | Azure HDInsight | CPU, memory, pending YARN memory | Medium; manual or policy-based |
| Ambari / Azure Monitor | Azure HDInsight | Cluster utilization | Medium; manual inspection |
| `list_clusters` API | GCP Dataproc | Cluster state, last job time | High; API-driven |
| Spark UI Executors tab | All | Idled cores, active tasks | Medium; manual inspection |
| Spark REST API | All | Executor active tasks | High; polling and alerting |
| Spark status tracker | All | Job and stage status | High; programmatic |

#### Configuration Parameters for Idle Prevention

| Parameter | Default | Description |
|---|---|---|
| `spark.dynamicAllocation.executorIdleTimeout` | `60s` | Idle time before an executor is released. Shorter values reduce cost but may cause churn. |
| `spark.dynamicAllocation.cachedExecutorIdleTimeout` | `infinity` | Idle timeout for executors holding cached data. Set a finite value to release cached executors. |
| `spark.dynamicAllocation.shuffleTracking.timeout` | `infinity` | Timeout for keeping executors with shuffle data alive. |
| `spark.sql.streaming.noDataProgressEventInterval` | `10s` | Interval after which an idle streaming query emits an event. |
| `spark.dynamicAllocation.schedulerBacklogTimeout` | `1s` | Backlog duration before requesting new executors. |
| `spark.dynamicAllocation.executorAllocationRatio` | `1.0` | Fraction of maximum parallelism to target. Lower values reduce resource usage. |

Cloud platform auto-termination settings are configured outside Spark. On Databricks, the `autotermination_minutes` cluster setting controls how long an idle cluster stays alive. On EMR, the `IdleTimeout` in the auto-termination policy controls the same behavior. On HDInsight, the `timetolive` property on on-demand clusters specifies how long the cluster stays alive after an activity run completes if there are no other active jobs.

#### Best Practices

- Enable auto-termination on all interactive clusters. A single idle cluster running overnight can generate significant charges.
- Set auto-termination to a short interval for development and exploratory clusters (e.g., 30 minutes) and a longer interval for production clusters that serve interactive queries.
- Monitor CPU utilization, active tasks, and idled cores in the compute metrics UI or Spark UI on a regular cadence.
- Use system tables or CloudWatch alarms to automate detection of clusters with high idle time relative to total uptime.
- Tag all compute resources with owner and cost-center metadata so that idle resources can be attributed to a team.
- Set `spark.dynamicAllocation.executorIdleTimeout` to a reasonable value (60–120 seconds) to release idle executors within a running application.
- For streaming workloads, monitor idle events and verify that the query is still needed. A streaming query that has been idle for hours may be a zombie.
- Use the Spark REST API or status tracker to build automated idle-detection scripts that poll for zero active tasks over consecutive intervals.
- Review the Spark UI for ghost jobs with no visible Job IDs. These indicate a zombie driver state and should be investigated.

#### Common Pitfalls and Limitations

- Driver-specific application code, such as connecting to a REST API or polling a database, can keep a cluster marked as non-idle even when no Spark jobs are running.
- An active Python3 notebook kernel does not submit a Spark job but can keep an EMR cluster from being considered idle, preventing auto-termination.
- `IsIdle` is checked every five minutes; a value of 1 indicates idleness at the check time, not necessarily for the entire interval.
- Auto-termination is disabled by default on some platforms. A cluster with no auto-termination policy can run indefinitely.
- Cached data prevents executor release by default (`cachedExecutorIdleTimeout=infinity`). A cluster holding cached data may appear idle but will not release executors.
- Shuffle tracking with `timeout=infinity` keeps executors alive indefinitely if shuffle data is not cleaned up.
- Azure HDInsight does not support stopping clusters. Idle HDInsight clusters bill their full fleet continuously until deleted.
- Zombie jobs in the Spark UI with no visible Job IDs indicate a driver that has lost track of its work. Terminating the driver is often the only remediation.
- Without tagging, cost attribution for idle resources is impossible.

#### Summary

Identifying zombie or idle Spark clusters requires a combination of platform-native metrics and Spark-level indicators. On Databricks, query `system.billing.usage` for clusters with high idle time and use auto-termination. On AWS EMR, use the `IsIdle` and `AutoTerminationIsClusterIdle` CloudWatch metrics. On Azure HDInsight, monitor with Ambari or Azure Monitor and delete unused clusters because they cannot be stopped. On GCP Dataproc, use the `list_clusters` API to find clusters in `RUNNING` state with no recent jobs. At the Spark level, the Executors tab's Idled cores, ghost jobs with no Job IDs, and the REST API's executor active-task counts provide direct evidence of idleness. In interviews, emphasize that zombie cluster detection is a FinOps practice, not just an operational one, and that auto-termination, tagging, and automated polling are the highest-ROI controls.
