### 4.7.2 When should you use Spot or Preemptible instances for Spark nodes

**Spot instances** (AWS, Azure) and **Preemptible VMs** (GCP) are discounted compute resources that cloud providers can reclaim at short notice. They offer savings of up to 90% compared to on-demand pricing, making them a powerful cost optimization lever for Spark workloads. The trade-off is that the provider can terminate the instance with minimal notice—typically a 30-second shutdown signal on GCP and a two-minute warning on AWS—which can disrupt running jobs. The decision to use spot instances for Spark nodes is therefore a risk assessment: is the workload tolerant of sudden node loss, and is the cost saving worth the operational complexity? This answer covers when spot instances are appropriate, when they are not, how to configure them safely, and the platform-specific considerations that senior engineers must articulate.

#### What Are Spot and Preemptible Instances

Spot instances and Preemptible VMs are spare cloud capacity sold at a discount. The provider retains the right to reclaim them when demand for on-demand capacity increases. The key characteristics are:

- **Deep discounts**: Up to 90% off on-demand pricing on AWS, approximately 70–80% on GCP. Alibaba Cloud reports about 30% lower cost for Spark executor spot instances on its platform.
- **Short lifespan**: GCP preemptible VMs have a maximum lifespan of 24 hours, after which they are terminated even without capacity pressure.
- **Interruption notice**: Providers give a brief window before termination—typically 30 seconds on GCP and up to two minutes on AWS—allowing graceful shutdown if the application supports it.
- **Reclaim risk**: The probability of interruption varies by instance type, region, and time. AWS provides a Spot Instance Advisor to evaluate average discounts and interruption frequency.

#### When to Use Spot Instances

Spot instances are best suited for **fault-tolerant workloads that can withstand the sudden interruption of an underlying node**. The following workload types are good candidates:

- **Distributed batch processing**: Spark and Ray are designed to handle node failures. If a worker node is reclaimed, the framework reschedules the affected tasks on remaining nodes without failing the entire job.
- **Non-urgent ETL pipelines**: Analytics jobs that can be re-run or checkpointed, and that do not have strict SLA requirements, benefit from substantial cost savings.
- **Development and testing**: Cost-conscious environments for experiments or CI tasks where occasional failures are acceptable and jobs are short-lived.
- **Fault-tolerant jobs using external storage**: Workloads that read from and write to durable external storage such as S3, GCS, or BigQuery. Data persists outside the worker's local disk, so preemption does not cause data loss.

A useful rule of thumb: ask how tolerant the workload is to sudden instance loss. If an interruption could result in losing hours of unsaved work, do not use spot instances. If the workload can recover automatically or the cost of interruption is acceptable, spot instances are appropriate.

#### When Not to Use Spot Instances

Spot instances are inappropriate when interruption directly impacts business operations or data integrity.

- **Mission-critical production pipelines with strict SLAs**: If a job must complete within a guaranteed time window, spot interruptions can cause SLA violations. Cloudera recommends using spot instances only for workloads without strict SLA requirements.
- **Real-time and low-latency systems**: Streaming workloads with strict latency requirements are poor candidates because preemption can cause unacceptable downtime and state loss.
- **Spark drivers**: Losing the driver abruptly fails the entire Spark application. The driver must run on an on-demand instance. Domino explicitly recommends keeping head nodes on on-demand instances. AWS EMR and Cloudera make the same recommendation: run drivers on on-demand, executors on spot.
- **HDFS data nodes with local replicas**: Preempting data nodes can cause data loss or trigger long re-replication processes. If the cluster relies on local disk for primary data replicas, those nodes should not be preemptible.
- **Long-running jobs exceeding the protection window**: Some platforms provide a protection period—Alibaba Cloud offers a 1-hour window during which spot resources are not preempted—but after that, the probability of preemption increases with usage duration. Jobs expected to run longer than the protection window should use on-demand instances.

#### Workload-to-Strategy Mapping

| Workload Type | Recommended Strategy | Reason |
|---|---|---|
| Development and testing | Spot for all jobs | Low cost; occasional failures acceptable |
| Cost-sensitive batch ETL | Spot for executors; on-demand for driver | Executor failure is recoverable; driver failure kills the job |
| Mixed workloads | Separate resource groups by job duration | Short jobs on spot; long jobs on demand |
| Mission-critical production | On-demand only | Failures directly impact business operations |
| Real-time streaming | On-demand only | Interruptions cause unacceptable downtime and state loss |
| Long-running jobs (>1 hour) | On-demand only | High preemption probability after protection window |

The default and recommended pattern is **hybrid**: on-demand for the driver and spot for executors. This reduces the impact of losing a spot instance because executor failure recovery is more efficient than recovery from a driver failure. If a worker node is reclaimed, the cluster framework simply reschedules tasks on remaining nodes without failing the entire job.

#### Handling Interruptions Gracefully

Spark's built-in fault tolerance reschedules missing tasks when an executor is lost. However, abrupt executor termination can lose shuffle data and cached RDD blocks, forcing downstream stages to recompute the map stage. Spark 3.x provides **executor decommissioning**, which allows a terminating executor to migrate its shuffle data and cached blocks to peer executors before shutdown.

The mechanism works as follows: when `spark.decommission.enabled` is true, Spark attempts a graceful shutdown. `spark.storage.decommission.enabled` enables migration of stored data, with separate flags for RDD blocks and shuffle blocks. The executor transfers its blocks to peer executors within a timeout, then terminates.

| Parameter | Default | Description |
|---|---|---|
| `spark.decommission.enabled` | `false` | Enables graceful executor decommissioning. |
| `spark.storage.decommission.enabled` | `false` | Enables block manager decommissioning. |
| `spark.storage.decommission.rddBlocks.enabled` | `false` | Transfers cached RDD blocks during decommissioning. |
| `spark.storage.decommission.shuffleBlocks.enabled` | `false` | Transfers shuffle blocks during decommissioning. Requires a migratable shuffle resolver such as sort-based shuffle. |
| `spark.storage.decommission.maxReplicationFailuresPerBlock` | `3` | Maximum failures tolerated when migrating shuffle blocks. |
| `spark.storage.decommission.shuffleBlocks.maxThreads` | `8` | Maximum threads for shuffle block migration. |
| `spark.decommissioning.timeout.threshold` | `20s` | EMR-specific: if a host decommissions within this time, EMR clears host state immediately rather than waiting for the full decommissioning timeout. |
| `spark.blacklist.decommissioning.enabled` | `true` | Blacklists decommissioning nodes so no new tasks are scheduled on them. |

The decommissioning timeout must be shorter than the cloud provider's spot termination notice. AWS EMR recommends keeping `terminationGracePeriodSeconds` on Kubernetes less than the spot instance timeout with about 5 seconds of buffer.

#### Complete Python Example

The following self-contained example configures a Spark session with decommissioning enabled for spot instance resilience and runs a shuffle-heavy aggregation.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count, rand

spark = (
    SparkSession.builder
    .appName("SpotInstanceDecommissionDemo")
    .config("spark.decommission.enabled", "true")
    .config("spark.storage.decommission.enabled", "true")
    .config("spark.storage.decommission.rddBlocks.enabled", "true")
    .config("spark.storage.decommission.shuffleBlocks.enabled", "true")
    .config("spark.storage.decommission.maxReplicationFailuresPerBlock", "3")
    .config("spark.storage.decommission.shuffleBlocks.maxThreads", "8")
    .config("spark.blacklist.decommissioning.enabled", "true")
    .config("spark.executor.cores", "5")
    .config("spark.executor.memory", "16g")
    .config("spark.executor.memoryOverhead", "2g")
    .config("spark.dynamicAllocation.enabled", "true")
    .config("spark.dynamicAllocation.minExecutors", "2")
    .config("spark.dynamicAllocation.maxExecutors", "20")
    .config("spark.dynamicAllocation.shuffleTracking.enabled", "true")
    .getOrCreate()
)

spark.sparkContext.setLogLevel("WARN")

# A shuffle-heavy aggregation that writes shuffle data to executors
df = (
    spark.range(0, 20_000_000)
    .withColumn("key", (rand() * 500).cast("int"))
    .withColumn("value", rand())
)

result = df.groupBy("key").agg(count("*").alias("cnt"))
result.orderBy(col("cnt").desc()).show(5, truncate=False)

spark.stop()
```

#### Platform-Specific Configuration

**AWS EMR**: EMR supports **instance fleets** that mix on-demand and spot instances. You can define separate instance groups for the driver (on-demand) and executors (spot). EMR also replenishes spot capacity from other pools when instances are interrupted, and the overall job continues processing due to Spark's fault-tolerant nature. EMR on EKS supports **pod templates** that schedule the driver on on-demand instances and executors on spot instances using node selectors.

**GCP Dataproc**: Dataproc distinguishes between **primary workers** (on-demand) and **secondary workers** (preemptible). Secondary workers are processing-only and do not store HDFS data, making them safe to preempt. The default secondary worker type is the standard preemptible VM, but you can specify spot VMs or a mix of spot and non-preemptible secondary workers.

**Cloudera Data Engineering**: The default setting uses on-demand instances for drivers and spot instances for executors. You can configure virtual clusters to use on-demand only, spot only, or the hybrid default.

#### Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Spot for executors only | Up to 90% savings on executor compute; driver failure avoided | Executor reclamation causes task retry and shuffle recomputation |
| Spot for all nodes | Maximum savings | Driver loss fails the entire application |
| Decommissioning enabled | Shuffle data migrated before termination; less recomputation | Requires additional configuration and migration overhead |
| Long protection window | Lower interruption probability | Not available on all platforms |
| Mixed on-demand/spot fleet | Balance between cost and reliability | More complex cluster configuration |

#### Best Practices

- Always run the **driver on an on-demand instance**. Losing the driver fails the entire Spark application, and the cost difference is negligible compared to the risk.
- Enable **executor decommissioning** with shuffle block migration on Spark 3.x for spot workloads. This allows executors to transfer shuffle data before termination, reducing recomputation.
- Use **instance fleets** with multiple spot pools and instance types to improve capacity availability and reduce the chance of simultaneous reclamation.
- Set `spark.blacklist.decommissioning.enabled=true` to prevent new tasks from being scheduled on nodes that are being decommissioned.
- For Dataproc, use **secondary workers** for preemptible capacity. They are processing-only and do not store HDFS data, so preemption does not risk data loss.
- Test the decommissioning timeout against the provider's termination notice. Keep the decommissioning timeout shorter than the spot termination window with a small buffer.
- Monitor **spot interruption rates** using the AWS Spot Instance Advisor or equivalent platform tools. Choose instance types with lower interruption frequency for more stable workloads.
- Use **checkpointing and idempotent job design** so that interrupted work can resume without duplicating output.

#### Common Pitfalls and Limitations

- Running the Spark driver on a spot instance. If the driver is reclaimed, the entire job fails and must restart from scratch.
- Not enabling decommissioning. Without it, shuffle data on terminated executors is lost, and downstream stages must recompute the entire map stage.
- Setting the decommissioning timeout longer than the spot termination notice. The executor is killed before migration completes, causing data loss anyway.
- Using spot instances for HDFS data nodes with local replicas. Preemption of a data node risks data loss and triggers re-replication.
- Assuming spot instances always work. On Alibaba Cloud, spot instances support only large and 2xlarge executor specifications and only Spark jobs.
- Forgetting that GCP preemptible VMs have a maximum lifespan of 24 hours, after which they are terminated regardless of capacity pressure.
- Using spot instances for streaming workloads with strict SLA requirements. State loss and interruption cause unacceptable downtime.
- Enabling spot instances without a fallback strategy. If spot capacity is unavailable, the job may wait indefinitely or fail to launch.

#### Summary

Spot and preemptible instances are appropriate for **fault-tolerant Spark workloads without strict SLAs**, particularly batch ETL, development, and testing. The default and recommended pattern is on-demand for the driver and spot for executors, because executor failure is recoverable while driver failure is not. Spark 3.x executor decommissioning migrates shuffle data before termination, reducing the cost of recomputation. On AWS EMR, use instance fleets and pod templates; on GCP Dataproc, use secondary workers; on Cloudera, the hybrid default is already configured. In interviews, emphasize the workload tolerance assessment, the driver-versus-executor distinction, the decommissioning mechanism, and the platform-specific safeguards that make spot instances production-safe.
